## 수정 요청

**R1 · 빠른 연속 이동에서 이전 화면 번호를 씀 (필수)** 실패 2건의 원인은 같습니다. 테스트가 `다음`을 누른 직후 기다리지 않고 `이전`을 누르면, 두 번째 클릭이 아직 다시 그려지지 않은 화면의 `state.index`로 계산됩니다. 로그상 S4-5b → `다음` → S4-6 → `이전` → **S4-5a**(S4-5b를 건너뜀), S4-5 → S4-5a → **S4-4**(그래서 I7 체크박스가 없음). 사람이 버튼을 빠르게 두 번 눌러도 같은 일이 생길 수 있으므로 앱에서 고쳐 주세요: 이동 대상은 클릭 시점의 **최신 위치**(예: 매 렌더에서 갱신하는 ref, 또는 현재 주소에서 다시 읽은 화면 ID) 기준으로 계산합니다. 상·하 이전/다음 버튼과 ←/→/PageUp/PageDown 모두. 공용 `B32Story.tsx`에서 고치면 v0.4 모드에도 적용되므로, v0.4 Playwright가 그대로 통과하는지 Claude가 확인하겠습니다(수정 이유를 QA 기록에 적어 주세요). 테스트는 각 이동 뒤 `data-screen`을 기다리는 단언을 넣고, 별도로 “기다리지 않는 연속 클릭 `다음`→`이전`이 원래 화면으로 돌아온다” 회귀 테스트를 추가해 주세요.

**R2 · 360px 인트로 로드맵이 너무 김 (필수)** [360-intro-roadmap.png](screens/360-intro-roadmap.png)의 전체 높이가 약 4,400px이고 `강의 시작하기`가 그 아래에 있습니다. 좁은 화면에서 학습자가 강의를 시작하려면 로드맵 전체를 지나야 합니다. **<1000px에서만** 카드를 줄여 주세요: 보이는 것은 `Scene n · 관점` · 카드 제목 · 학습 질문 · `화면 k개` · `이 Scene 시작`, 그리고 하나의 `자세히` 펼침 안에 도달 목표 · 핵심 개념 · 화면 목록. 정보는 그대로 DOM에 있어야 합니다(테스트가 원고 질문·목표·개념을 확인하는 방식은 펼친 뒤 확인으로 바꿔도 됨). 360에서 로드맵 높이가 대략 1,800px 이하가 되는지 측정해 QA 기록에 적어 주세요. ≥1000px 배치는 지금 그대로 좋습니다.

**R3 · I5 `git-cases`의 ④ 실패 칸이 초록색 (수정)** “네 사례 나란히”에서 ①–③(성공)은 주황, ④(실패)는 초록 계열로 보입니다. 초록은 흔히 성공으로 읽혀 학습 의도와 반대입니다. 성공 세 칸은 같은 중립 톤, 실패 칸은 기존 발표 변수 중 경고·오류에 해당하는 톤(없으면 테두리 굵기·점선 등)과 칸 제목의 `✕ 실패`(성공 칸은 `✓ 성공 · returncode 0`) 글자로 구분해 주세요. 색만으로 구분하지 않는 규칙도 함께 지킵니다. v0.4 I5 `git`·`http`·`program`의 색은 바꾸지 않습니다.

**R4 · 레일의 `펼치기` 글자가 두 줄로 끊김 (수정)** 1280×720에서 56px 레일 맨 위 버튼이 “펼치 / 기”로 나뉩니다. 아이콘(예: `☰` 또는 `»`) + `aria-label="학습 인덱스 펼치기"`처럼 한 줄에 들어가는 표시로 바꿔 주세요(터치 영역 44px 유지).

**R5 · 좁은 화면 위치 띠 (선택)** 360·390에서 현재 칸(`4 Python과 외부 AI 화면 7 / 9`)이 혼자 한 줄을 차지해 띠가 세 줄이 됩니다. <900px에서는 현재 칸도 `4 · 화면 7/9`처럼 번호 중심으로 줄이고 관점 이름은 바로 아래 요약 글에만 두는 것을 제안합니다. 설계 §3.3 범위 안의 조정이며 Codex 판단에 맡깁니다.
