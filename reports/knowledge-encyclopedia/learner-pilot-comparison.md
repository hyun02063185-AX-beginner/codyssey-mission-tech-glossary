## variable — 변수

`Programming` · 난이도 **mid** · AI 판정 읽기 **FRICTION** / 이해 **HARD**

**문제** — 정의의 뼈대가 미설명 영문(binding)이다. 정의가 정의를 요구한다.

### CURRENT — 지금 학습자가 보는 순서

```
[한 줄 설명]  ←  바뀜
  Variable은 프로그램이 값을 가리키고 다시 사용할 수 있도록 이름을 붙인 binding입니다.

[쉽게 설명하면]
  값을 담거나 가리키는 데 쓰는 이름표입니다. 이름으로 값을 읽고, 언어 규칙이 허용하면 다른 값을 연결할 수 있습니다.

[정확한 설명]  ←  바뀜
  변수는 단순한 상자라는 비유만으로 충분하지 않습니다. 언어는 이름과 값 또는 object reference의 연결, lifetime, scope, 재할당 규칙을 각기 다르게 정의합니다.

[이 미션에서는 왜 필요한가]
  M01의 화면 상태와 입력값, M02의 객체 속성·함수 지역값을 구분해 읽을 때 기본이 되는 개념입니다.

[코드 예]
  let visitor = 'Ada';
  visitor = 'Lin';

[주의할 점 / 경계 조건]
  변수 이름이 같아도 scope가 다르면 다른 binding일 수 있습니다. 값 복사와 object reference 공유도 구분해야 합니다.

[흔한 오해]
  모든 변수는 메모리에 값을 직접 복사해 넣는다는 설명은 reference를 쓰는 언어에서는 불완전합니다.

[동료평가 질문]
  같은 이름의 변수가 함수 안과 밖에 있을 때, 어느 값을 읽는지 어떻게 판단할까요?

```

### PROPOSED — 바뀌는 절만

```
[한 줄 설명]
  값에 이름을 붙여 두고, 그 이름으로 다시 꺼내 쓰는 것입니다.

[정확한 설명]
  변수는 단순한 상자라는 비유만으로 충분하지 않습니다. 언어는 이름과 값의 연결을 binding 이라 부르고, 값을 직접 담는지 값이 있는 자리를 가리키는지(object reference), 그 연결이 언제까지 살아 있고(lifetime) 어디서 보이는지(scope), 다시 연결할 수 있는지를 각기 다르게 정합니다.

```

### CHANGE

- 첫 문장에서 정의어(binding)를 빼고 정확한 설명으로 이동
- 명사구 → 문장
- 첫 화면 새 개념 1개 → 0개

### RISK — 이 제안이 잃을 수 있는 것

"꺼내 쓴다" 가 값 복사를 연상시킨다. 참조를 쓰는 언어에서는 현재 첫 문장의 "가리키고" 가 더 정확했고, 주의할 점 절이 이를 다루지만 첫 화면에서는 그 단서가 약해진다.

### WHY

binding 을 L1 에서 빼고 L4 로 내렸다. 표본에서 가장 쉬운 개념인데 Comprehension HARD 가 나온 원인이 이 한 낱말이었다.

## mysql — MySQL

`Data/DB` · 난이도 **basic** · AI 판정 읽기 **FRICTION** / 이해 **PASS**

**문제** — 한 줄 설명과 쉽게 설명하면이 같은 말인데 먼저 읽히는 쪽이 더 어렵다.

### CURRENT — 지금 학습자가 보는 순서

```
[한 줄 설명]  ←  바뀜
  널리 쓰이는 open-source relational database 관리 시스템.

[쉽게 설명하면]  ←  바뀜
  널리 쓰이는 서버형 데이터베이스입니다. 웹 서비스에서 오래 쓰여 자료와 사례가 많습니다.

[정확한 설명]
  저장 엔진을 고를 수 있고 기본 엔진이 트랜잭션과 외래 키를 지원한다. 기본 설정에서 문자열 비교가 대소문자를 구분하지 않으며, 문자 집합과 정렬 규칙 설정에 따라 한글과 이모지 저장 가능 여부가 달라진다.

[이 미션에서는 왜 필요한가]
  이 회차의 선택지 중 하나입니다. 설치와 계정 설정이 필요해 실습 초반에는 파일 기반보다 번거롭지만, 여러 사람이 같은 데이터베이스에 접속해 함께 보는 상황을 만들 수 있습니다.

[코드 예]
  CREATE DATABASE app
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;
  -- utf8 은 3바이트까지만 담는다. 이모지가 잘린다
  -- utf8mb4 를 써야 한다

  -- _ci 는 대소문자를 구분하지 않는다는 뜻
  SELECT * FROM member WHERE email = 'KIM@EX.COM';   -- kim@ex.com 도 나온다

[주의할 점 / 경계 조건]
  문자 집합을 확인하지 않으면 이모지나 일부 한자가 저장에서 잘립니다. 4바이트 문자를 지원하는 설정을 써야 합니다.

[흔한 오해]
  문자열 비교가 대소문자를 구분한다고 생각하기 쉽지만, 기본 설정에서는 구분하지 않습니다. 다른 데이터베이스에서 옮겨 오면 중복 검사 결과가 달라집니다.

[동료평가 질문]
  문자 집합 설정을 확인해야 하는 이유를, 저장이 잘리는 예로 설명할 수 있나요?

```

### PROPOSED — 바뀌는 절만

```
[한 줄 설명]
  여러 사람이 네트워크로 함께 접속해 쓰는 데이터베이스입니다.

[쉽게 설명하면]
  웹 서비스에서 오래 쓰여 자료와 사례가 많습니다. 파일 하나로 끝나는 방식과 달리 서버를 따로 띄워야 합니다.

```

### CHANGE

- 첫 문장을 쉬운 설명 쪽 문장으로 교체
- 영문 2개 → 0개
- 한 줄 설명과 쉽게 설명하면의 중복 제거

### RISK — 이 제안이 잃을 수 있는 것

open-source 라는 사실이 첫 화면에서 사라진다. 라이선스·비용을 따지는 상황에서는 그것이 선택 근거가 된다. 또 "여러 사람이 접속" 은 SQLite 에 네트워크 계층을 얹어도 가능하므로 완전한 구분은 아니다.

### WHY

첫 문장 역전의 순수 사례다. L1 을 가장 쉬운 문장으로 올리고, 중복을 없애면서 L2 에 '무엇과 다른가' 를 넣었다.

## commit — 커밋

`SWE/Git` · 난이도 **mid** · AI 판정 읽기 **FRICTION** / 이해 **PASS**

**문제** — 한 줄 설명이 Git 내부 어휘로 쓰여 있다(영문 6개).

### CURRENT — 지금 학습자가 보는 순서

```
[한 줄 설명]  ←  바뀜
  staging area의 snapshot과 부모 history를 기록하는 Git object.

[쉽게 설명하면]
  그 순간의 파일 상태를 통째로 찍어 기록에 남기는 일입니다. 변경한 것 중 골라 둔 것만 담깁니다.

[정확한 설명]
  스테이지에 올린 내용으로 그 시점의 전체 상태를 만들고, 부모 커밋·작성자·시각·메시지와 함께 저장한다. 저장되는 것은 변경분이 아니라 그 시점의 상태이며, 부모를 가리키기 때문에 이력이 사슬로 이어진다.

[이 미션에서는 왜 필요한가]
  이 회차에서 작업 단위를 남기는 방법입니다. 한 번에 몰아서 하면 나중에 무엇 때문에 무엇이 바뀌었는지 알 수 없고, 되돌릴 때도 필요한 부분만 골라내기 어려워집니다.

[코드 예]
  git add src/auth.py            # 담을 것을 고른다
  git commit -m "로그인 실패 메시지 통일"

  git cat-file -p HEAD
  # tree a1b2c3...          ← 그 시점의 전체 파일 상태
  # parent d4e5f6...        ← 바로 앞 커밋
  # author 김현래 <...> 1758499200 +0900
  #
  # 로그인 실패 메시지 통일

  # 변경분이 아니라 상태를 저장한다.
  # 안 바뀐 파일은 앞 커밋의 것을 그대로 가리킨다

[주의할 점 / 경계 조건]
  history를 바꾸는 명령은 이미 공유된 commit에 영향을 줄 수 있습니다. 실행 전 branch, remote, collaborator와의 합의를 확인해야 합니다.

[흔한 오해]
  변경된 내용만 저장된다고 생각하기 쉽지만, 그 시점의 전체 상태가 저장됩니다. 같은 파일은 중복 저장하지 않아 용량이 크게 늘지는 않습니다.

[동료평가 질문]
  한 커밋에 담을 변경의 범위를 어떻게 정하는지, 자기 기록을 예로 설명할 수 있나요?

```

### PROPOSED — 바뀌는 절만

```
[한 줄 설명]
  그 순간의 파일 상태를 통째로 찍어 기록에 남기는 일입니다.

```

### CHANGE

- 첫 문장을 쉬운 설명 쪽 문장으로 교체
- 영문 6개 → 0개
- Git 내부 어휘(staging area·snapshot·Git object)를 L2 이후로 이동

### RISK — 이 제안이 잃을 수 있는 것

"부모 history" 가 첫 문장에서 빠진다. 커밋이 사슬로 이어진다는 점은 M10(커밋 그래프)의 핵심인데 첫 화면에서 그 단서가 사라진다.

### WHY

이미 문서 안에 있던 더 나은 문장(쉽게 설명하면)을 L1 으로 올렸다. staging area·snapshot·Git object 는 L2 이후에 이미 설명돼 있다.

## process — process

`OS/System` · 난이도 **hard** · AI 판정 읽기 **FRICTION** / 이해 **FRICTION**

**문제** — '프로그램 파일과 다르다' 가 이 term 의 핵심인데 주의할 점 한 줄로만 있다. 코드 예는 ps 의 예제다.

### CURRENT — 지금 학습자가 보는 순서

```
[한 줄 설명]  ←  바뀜
  Process는 운영체제가 실행 중인 프로그램에 할당한 독립 실행 단위와 자원 경계입니다.

[쉽게 설명하면]  ←  바뀜
  프로그램 파일을 실제로 실행하면 운영체제가 그 실행을 위한 작업 공간과 번호를 마련하는데, 그 실행 단위가 process입니다.

[정확한 설명]
  Process는 자체 address space, resource, execution context를 가질 수 있습니다. 같은 프로그램을 두 번 실행하면 보통 별도 process가 되며, process 간 데이터 공유에는 명시적 통신 방식이 필요합니다.

[이 미션에서는 왜 필요한가]
  Linux·server·container 환경에서 어떤 프로그램이 실제로 실행 중인지, log나 resource 사용량을 어느 단위로 관찰하는지 이해하는 기반입니다.

[코드 예]  ←  바뀜
  ps -ef
  # 실행 중인 process 목록을 관찰한다.

[주의할 점 / 경계 조건]
  Process와 program file은 다릅니다. process 하나가 여러 thread를 가질 수 있으며, container도 process와 완전히 같은 개념은 아닙니다.

[흔한 오해]
  실행 파일 하나는 언제나 process 하나만 만든다는 생각은 맞지 않습니다.

[동료평가 질문]
  두 process가 기본적으로 서로의 변수에 바로 접근하지 못하는 이유는 무엇인가요?

```

### PROPOSED — 바뀌는 절만

```
[한 줄 설명]
  프로그램 파일을 실제로 실행했을 때 생기는, 지금 돌아가고 있는 한 덩어리입니다.

[쉽게 설명하면]
  프로그램 파일은 요리법이고 process 는 지금 요리를 하고 있는 상태입니다. 같은 요리법으로 두 명이 동시에 요리하면 요리는 둘입니다.

[코드 예]
  # 같은 프로그램을 두 번 실행하면 process 는 둘이다
  python app.py &   # PID 4211
  python app.py &   # PID 4212  ← 파일은 하나, process 는 둘

```

### CHANGE

- 첫 문장에서 추상명사 2개(독립 실행 단위·자원 경계) 제거
- 비유 추가(요리법 / 요리하는 중)
- 코드 예를 ps 목록에서 이 term 의 대비로 교체

### RISK — 이 제안이 잃을 수 있는 것

요리 비유는 "자원 경계" 를 담지 못한다. 두 요리사가 같은 주방을 쓰는 것처럼 읽혀 프로세스 사이의 메모리가 분리돼 있다는 핵심을 오히려 흐릴 수 있다. 그 점에서는 현재 문장이 정확했다.

### WHY

비유를 넣고 코드가 그 대비를 직접 보이게 했다. 현재 코드 예 `ps -ef` 는 이 term 이 아니라 ps 의 예제다.

## tcp — TCP

`Network` · 난이도 **hard** · AI 판정 읽기 **HARD** / 이해 **HARD**

**문제** — 정확한 설명이 메커니즘 5개를 쉼표로 나열한다. 설명이 아니라 용어 목록이다. 코드 예는 ufw 의 예제다.

### CURRENT — 지금 학습자가 보는 순서

```
[한 줄 설명]  ←  바뀜
  TCP는 두 endpoint 사이에서 순서와 전달 신뢰성을 관리하는 connection-oriented transport protocol입니다.

[쉽게 설명하면]
  데이터 조각을 보낸 순서대로 받았는지 확인하고, 빠진 조각이 있으면 다시 보내도록 돕는 전달 규칙입니다.

[정확한 설명]
  TCP는 byte stream, sequence number, acknowledgement, retransmission, flow/congestion control 등의 메커니즘을 사용합니다. HTTP 같은 application protocol의 의미를 정하는 것이 아니라 그 아래 전송을 담당합니다.

[이 미션에서는 왜 필요한가]
  본과정 M07은 20022와 15034 포트에 대한 인바운드 규칙을 만들게 합니다. 규칙을 적을 때 프로토콜을 골라야 하고, 이 둘은 연결을 맺고 순서대로 주고받는 방식이라 TCP로 지정합니다.

[코드 예]  ←  바뀜
  sudo ufw allow 20022/tcp    # SSH 포트를 옮긴 경우
  sudo ufw allow 15034/tcp    # 상태 점검 포트
  sudo ufw status numbered

[주의할 점 / 경계 조건]
  TCP가 application message 경계를 보존하지는 않습니다. 또한 HTTP/3처럼 TCP가 아닌 transport를 쓰는 HTTP도 있으므로 모든 HTTP가 TCP라는 표현은 정확하지 않습니다.

[흔한 오해]
  TCP와 HTTP는 같은 계층의 protocol이 아닙니다.

[동료평가 질문]
  TCP의 순서 보장이 application code에서 message 하나가 한 번에 읽힌다는 보장을 왜 대신하지 못하나요?

```

### PROPOSED — 바뀌는 절만

```
[한 줄 설명]
```

```
[이 미션에서는 왜 필요한가]
```

```
      def __init__(self, capacity=8):
          self.buckets = [[] for _ in range(capacity)]
          self.size = 0

          for i, (k, _) in enumerate(bucket):
              if k == key:
                  bucket[i] = (key, value)   # 같은 키면 덮어쓴다
                  return
          bucket.append((key, value))
          self.size += 1
```

```
  자바스크립트로 화면의 글자나 속성을 바꾸는 일입니다. HTML 파일을 고치는 것이 아니라, 브라우저가 이미 메모리에 올려 둔 문서 구조를 고칩니다.

[정확한 설명]  ←  바뀜
  DOM 변경 뒤 browser는 필요한 style, layout, paint 단계를 수행한다.

[이 미션에서는 왜 필요한가]
  이 회차의 목표 자체가 버튼을 눌렀을 때 화면이 바뀌게 만드는 것입니다. 바꾸는 방법이 여러 가지인데, innerHTML로 통째로 갈아 끼우면 그 안에 붙여 둔 이벤트와 입력 중이던 값이 함께 사라집니다.

[코드 예]
  const list = document.querySelector('#items');

  // 전체를 갈아 끼운다 — 안의 이벤트와 입력값이 사라진다
  list.innerHTML = items.map(i => `<li>${i}</li>`).join('');

  // 필요한 것만 붙인다
  const fragment = document.createDocumentFragment();
  for (const item of items) {
    const li = document.createElement('li');
    li.textContent = item;          // textContent 는 HTML 로 해석하지 않는다
    fragment.append(li);
  }
  list.append(fragment);            // 배치 계산이 한 번만 일어난다

[주의할 점 / 경계 조건]
  반복문 안에서 요소를 하나씩 추가하면 추가할 때마다 배치 계산이 일어날 수 있습니다. 여러 개를 넣을 때는 조각을 먼저 만들어 한 번에 붙이는 편이 낫습니다.

[흔한 오해]
  innerHTML 로 다시 그리면 깔끔하다고 생각하기 쉽지만, 그 안의 요소는 전부 새로 만들어진 것입니다. 이전 요소에 붙여 둔 이벤트 리스너와 사용자가 입력 중이던 값이 사라집니다.
```
