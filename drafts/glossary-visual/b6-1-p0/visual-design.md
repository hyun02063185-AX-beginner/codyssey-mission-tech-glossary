## 2. 그림 A — ERD (`erd-basics`)

- **핵심 질문:** ERD는 무엇을 그린 그림이고, 선과 숫자는 무엇을 의미할까?
- **핵심 메시지 한 줄:** 상자는 표, 선은 관계, 선 끝 기호는 "상대 쪽이 최소·최대 몇 개인가"다.
- **구성:** `student` — `enrollment` — `course` 상자 3개(대표 열만), 선 2개, 선 끝 기호 설명 상자, 읽는 법 ①②③.

| 표현 규칙 | 내용 |
| --- | --- |
| 표기법 | 까마귀 발(crow's foot). B6-1 원본 `docs/images/erd.mmd`의 `\|\|--o{`(반드시 하나 ↔ 0개 이상)와 미션 스토리 `erd-story`의 선 끝 모양을 그대로 따른다 |
| 기호 읽기 | 안쪽(상자에 가까운) 기호 = 최대, 바깥쪽 기호 = 최소. 막대 두 개 = 최소 1·최대 1. 동그라미 + 세 갈래 = 최소 0·최대 여럿 |
| 읽는 방향 | 한쪽 표에서 출발해 **반대쪽 끝**의 기호를 읽는다. ①②로 양방향을 한 번씩 읽어 보인다 |
| 숫자 `1`·`N` | 스토리·가이드와의 연속성을 위해 선 끝에 함께 둔다. 최소 개수는 기호(동그라미·막대)가 전한다 |
| 화살표 | 쓰지 않는다. 선은 관계이며 방향(흐름)이 아니라고 그림 안에 적었다 |
| 미션 연결 | ③ 문태양(수강 0건) = 동그라미(최소 0)가 허용하는 경우. JOIN 그림의 LEFT JOIN 행과 같은 학생이다 |

**의도적으로 넣지 않은 것:** `teacher`·`subject`·`score` 표, 학생·수업 N:M을 `enrollment`로 푸는 과정. 그림의 메시지를 "기호 읽기" 하나로 두기 위해서다. "ERD와 실제 표는 항상 같지 않다"는 기존 본문(정확한 설명·흔한 오해)이 이미 설명하므로 본문에 맡긴다.

## 3. 그림 B — PK·FK (`pk-fk-relationship`)

- **핵심 질문:** 한 테이블의 데이터는 다른 테이블의 데이터를 어떻게 정확히 가리킬까?
- **핵심 메시지 한 줄:** FK 칸에 담긴 값이 다른 표의 PK 값과 같아서 그 행을 가리킨다. 없는 값은 FK 제약이 막는다.
- **구성:** 왼쪽 자식 표 `enrollment(id, student_id)` 3행 · 오른쪽 부모 표 `student(id, name)` 2행 · FK 칸 → PK 칸 점선 화살표 3개 · 거부되는 행(교육용 예시) · PK/FK 설명 2줄.

| 표현 규칙 | 내용 |
| --- | --- |
| 화살표 | **FK 값 → PK 값** 방향의 점선. "가리킴(실행 순서 아님)"을 그림 안에 적었다. 가이드 V03의 "점선 = 번호로 가리키는 관계"와 같은 뜻이다 |
| 배치 | 자식 표를 왼쪽에 둔다. FK 열(자식의 오른쪽 열)과 PK 열(부모의 왼쪽 열)이 마주 보게 해 화살표가 짧고 교차하지 않는다 |
| 1:N | 김민준(1)을 두 행이 가리킨다는 이름표로 1:N을 보여 준다 |
| 무결성 | `student_id 99` 행을 짧은 점선 빨강 테두리로 그리고, 화살표가 닿지 못한 채 `✕`. "student에 99번이 없으므로 FK 제약이 입력을 거부한다" |
| 일반화 경계 | 그림 안: "값을 복사해 오는 기능이 아니다 · 보통 PK, 경우에 따라 UNIQUE 키를 가리킨다". NULL 허용·삭제 동작·SQLite 기본값은 본문으로 넘긴다(제안 문서) |
| 생략 | `enrollment.course_id` 등 열 생략을 부제에 적었다. `course_id`도 FK라는 사실은 ERD 그림에서 보인다 |

`primary-key`·`foreign-key` 두 용어가 이 그림 하나를 함께 쓴다. PK 설명 줄(행 하나를 구별, 중복·빈 값 불가)과 FK 설명 줄을 모두 그림에 넣은 이유다.

## 4. 그림 C — JOIN (`join-inner-left`)

- **핵심 질문:** INNER JOIN과 LEFT JOIN은 같은 데이터에서도 왜 다른 결과를 만들까?
- **핵심 메시지 한 줄:** 짝이 없는 왼쪽 행은 INNER에서 빠지고 LEFT에서는 NULL과 함께 남는다.
- **구성:** 연결 조건 `student.id = enrollment.student_id` · 왼쪽 표 `student` 3행(짝 수 2·2·0) · 오른쪽 표 `enrollment` 4행 · INNER 결과 4행 · LEFT 결과 5행 · 결과 행 수 메모.

| 표현 규칙 | 내용 |
| --- | --- |
| 짝 없는 행 | 문태양(15). 왼쪽 표에서 "0건" 칸 강조 → INNER 아래 취소선 + `✕ 짝이 없는 행은 빠진다` → LEFT 마지막 행 점선 초록 테두리 + `✓` |
| 1:N 확장 | 김민준·이서연은 짝이 2건이라 결과에 2행씩 나온다. 결과 표 옆 괄호 `]`와 설명. 기존 V06·`join-compare`에는 없던 요소다 |
| 행 수 | "왼쪽 3행 → INNER 4행 · LEFT 5행: 결과 행 수는 원본과 다를 수 있다" |
| NULL | 빨강을 쓰지 않고 굵은 글자로만 표시한다. NULL은 오류가 아니라 "값 없음"이다 |
| 영구 결합 아님 | "JOIN은 조회 결과만 만든다. student·enrollment 표는 그대로다" |
| 넣지 않은 것 | `ON`과 `WHERE`의 차이(기존 `left-join` 본문 코드 예가 다룬다), PK·FK 제약(조건만 맞으면 제약 없이도 JOIN된다 — 그림은 제약을 언급하지 않는다), 결과 순서(`ORDER BY` 없으면 보장되지 않음 — 본문 제안에 기록) |

검증: 학생 1·2·15로 거른 SQLite 실행 결과와 그림의 INNER 4행·LEFT 5행이 일치한다. 전체 15명 기준으로는 INNER 26행·LEFT 27행(스토리 `join-compare` 각주와 일치).

## 5. 모바일 재배치

현재 렌더러는 모든 용어 그림을 520px로 고정하고 700px 이하에서 가로 스크롤을 쓴다. 실제 앱에 넣어 390px에서 캡처해 보니(`preview/qa/*-current-renderer-390.png`), JOIN 그림은 **LEFT JOIN 결과 열 전체가 화면 밖**에 있어 비교라는 핵심이 첫 화면에서 보이지 않는다.

그래서 폭 320의 모바일판을 따로 만들었다.

| 그림 | 모바일 재배치 |
| --- | --- |
| ERD | 상자 3개를 세로로 쌓고(student → enrollment → course) 선 끝 기호를 위아래 방향으로 돌렸다. 설명 문장은 두 줄로 나눴다 |
| PK·FK | 두 표를 나란히 유지하되 열을 좁히고 `PK`·`FK` 이름표를 열 이름 아래 줄로 내렸다(가이드 V03과 같은 방식). 설명은 세로로 이어진다 |
| JOIN | 왼쪽 표 → 오른쪽 표 → INNER → LEFT 순서로 세로로 쌓았다 |

모바일판을 쓰려면 렌더러가 700px 이하에서 모바일 SVG를 `width:100%`(최대 520px)로 그려야 한다. 이번 단계에서는 코드를 바꾸지 않았다. Codex 통합 항목으로 [`review.md`](review.md#5-codex-웹-통합-시-필요한-작업)에 적었다.

**표기 차이 정리**

- 스토리는 PK를 파랑, FK를 초록으로 칠한다(다크 Presentation 팔레트). 가이드와 새 그림은 PK를 짙은 초록, FK를 갈색으로 칠한다. 두 체계 모두 `PK`·`FK` 글자 이름표가 있어 의미가 바뀌지는 않는다.
- 가이드 V02는 ERD 관계를 "부모 → 자식" 화살표로 읽게 하고, V03은 점선 화살표를 "FK → PK"로 쓴다. 같은 가이드 안에서 화살표 방향의 뜻이 다르다. 새 그림은 ERD에 화살표를 쓰지 않고, PK/FK 그림에서만 FK → PK 방향을 쓴다.
- 이 차이는 기존 승인 원본의 문제로 기록만 한다(수정 금지 범위).
