## 2. `erd` — ERD

**현재 부족한 부분**

- ERD는 그 자체가 그림 표기법인데 본문에는 문자 도식만 있다.
- 문자 도식이 `○`(0개여도 된다)를 기호 설명에만 두고 도식에서는 쓰지 않는다. `1`과 `<`만으로는 최소 개수를 읽을 수 없다.
- B6-1 미션 스토리·원본 ERD는 까마귀 발(`‖`, `○<`)로 그리는데, 본문은 다른 문자 기호를 쓴다. 스토리에서 넘어온 학습자가 표기를 다시 배워야 한다.
- `member`–`comment`의 "작성자" 관계는 도식에서 양쪽 끝 기호가 빠져 있다.

**그림의 목적:** 상자·선·선 끝 기호를 읽는 법을 한 장으로 보여 주고, 기호가 최소·최대 개수를 뜻한다는 것을 B6-1 실제 ERD 일부로 확인시킨다.

**삽입 위치:** `## 정확한 설명` 본문 바로 아래(같은 절 안).

**대체텍스트:** `ERD 읽기: 상자는 표, 선은 관계, 선 끝 기호는 최소·최대 개수`

**캡션 제안:** `ERD 읽기 — 상자는 표, 선은 관계, 선 끝 기호는 최소·최대 개수 (B6-1 사례 일부)`

**그림 아래 설명 제안 (정확한 설명 절 끝에 추가):**

> 선 끝 기호는 안쪽이 최대, 바깥쪽이 최소 개수입니다. 한쪽 표에서 출발해 반대쪽 끝의 기호를 읽습니다. 그림에서 학생 1명은 수강 기록을 0건 이상 가지고, 수강 기록 1건은 학생 정확히 1명에 속합니다.

**기존 텍스트 도식과의 충돌:** 있음. 문자 도식의 `1`·`<`·`○`가 그림의 `‖`·`○<`와 다르다. 도식을 지우지 않고 같은 표기로 고치는 것을 제안한다. Chrome 오픈북은 `코드 예` 절을 글자로 보여 주므로(`extension/sidepanel.js`의 `codeExample`), 그림이 보이지 않는 곳에서도 같은 표기를 유지한다.

예시는 그림과 같은 **B6-1 `student`·`enrollment`·`course`** 로 바꾼다. 기존 `member`·`post`·`comment`는 최소·최대 개수를 확인할 원본 스키마가 없어 정확한 기호를 정할 수 없다(독립 검토 R2).

현재:

```text
member ──1────< post ──1────< comment
   │                              │
   └──────────1───────────────────┘
                (작성자)

기호
  1      한 개
  <      여러 개 (까마귀 발)
  ○      0 개여도 된다

그림에서 "여러 개" 쪽 끝에 외래 키를 둔다.
post.author_id,  comment.post_id,  comment.author_id
```

제안 (B6-1 사례):

```text
student ||────o< enrollment >o────|| course

선 끝 기호 (상자 쪽 = 최대, 바깥쪽 = 최소)
  ||          반드시 하나   (최소 1 · 최대 1)
  o<  >o      0개 이상 여럿 (최소 0 · 최대 여럿)
              세 갈래(< >)가 상자 쪽, 동그라미(o)가 바깥쪽

읽기: 한쪽 표에서 출발해 반대쪽 끝의 기호를 읽는다
  학생 1명 → 수강 기록 0건 이상     (enrollment 쪽 o<)
  수강 1건 → 학생 정확히 1명         (student 쪽 ||)
  수업 1개 → 수강 기록 0건 이상     (enrollment 쪽 >o)
  수강 1건 → 수업 정확히 1개         (course 쪽 ||)

여럿 쪽 표(enrollment)에 외래 키를 둔다.
enrollment.student_id,  enrollment.course_id
```

**기호 근거 (B6-1 `8b99440`):**

| 관계 끝 | 기호 | 원본 근거 | 데이터 확인 |
| --- | --- | --- | --- |
| `student` 쪽 (수강 1건 → 학생) | `\|\|` 최소 1 · 최대 1 | `erd.mmd` `STUDENT \|\|--o{ ENROLLMENT` · `enrollment.student_id INTEGER NOT NULL` + `FOREIGN KEY (student_id) REFERENCES student(id)` | — |
| `enrollment` 쪽 (학생 1명 → 수강) | `o<` 최소 0 · 최대 여럿 | 같은 줄의 `o{` · 학생에게 수강을 강제하는 제약 없음 | 문태양(15) 수강 0건, 다른 학생 1~2건 |
| `course` 쪽 (수강 1건 → 수업) | `\|\|` 최소 1 · 최대 1 | `erd.mmd` `COURSE \|\|--o{ ENROLLMENT` · `enrollment.course_id INTEGER NOT NULL` + `FOREIGN KEY (course_id) REFERENCES course(id)` | — |
| `enrollment` 쪽 (수업 1개 → 수강) | `>o` 최소 0 · 최대 여럿 | 같은 줄의 `o{` · 수업에 수강을 강제하는 제약 없음 | 수업 12번 수강 0건 |

`UNIQUE (student_id, course_id)`는 같은 학생·수업 쌍의 중복을 막을 뿐 위 개수를 바꾸지 않는다.

**새 ERD SVG와의 일치:** SVG(`erd-basics-*`)는 같은 세 표와 같은 네 끝 기호를 쓴다. 왼쪽 선은 `student ‖ … ○< enrollment`, 오른쪽 선은 `enrollment >○ … ‖ course`이며, 문자 도식의 `||`·`o<`·`>o`가 SVG의 막대 두 개·동그라미 + 세 갈래에 대응한다. 읽는 방향("반대쪽 끝을 읽는다")과 최소·최대 설명 문구도 SVG 범례와 같다. 문자 도식은 고정폭 글자로 그리므로, 그림의 "안쪽"을 "상자 쪽"이라고 풀어 썼다.

**바꾸면서 함께 정리되는 것:** 기존 도식의 `member`–`comment` "작성자" 관계에서 빠져 있던 양쪽 끝 기호 문제, 그리고 이전 초안에서 확인이 필요했던 `member` 쪽 `||`/`o|` 선택 문제는 예시를 B6-1로 바꾸면서 함께 사라진다. 본문의 다른 절(`이 미션에서는 왜 필요한가`의 "표를 네 개 이상")은 미션 요구 사항이라 그대로 둔다.

**이 미션에서는 왜 필요한가 — 한 문장 추가 제안:**

> B6-1 사례에서는 공부방 데이터베이스의 표 6개와 관계를 ERD로 그렸고, 가운데 수강(`enrollment`) 표가 학생과 수업의 여럿 대 여럿 관계를 잇습니다.

**기술적 보완:** 없음. 한 줄 설명의 영어 혼용("entity와 attribute, relationship")은 입문자에게 낯설지만 이번 범위(그림 보강) 밖이다. 별도 가독성 개정 후보로만 기록한다.

**관련 용어(선택):** 현재 `sql`·`table`뿐이다. `primary-key`·`foreign-key`·`one-to-many-relationship` 추가를 검토할 수 있다.

## 3. `foreign-key` — 외래 키

**현재 부족한 부분**

- "FK가 다른 표의 PK를 가리킨다"는 위치와 방향이 핵심인데 그림·도식이 없다.
- 한 줄 설명이 참조 대상을 "기본 키"로만 적는다. FK는 UNIQUE 키를 참조할 수도 있다.
- 예시가 `users`/`orders`라 B6-1 스토리·가이드(`student`/`enrollment`)와 연결이 약하다.
- NULL 허용, DBMS 설정에 따른 검사 여부가 없다. B6-1의 SQLite는 `PRAGMA foreign_keys = ON` 없이는 FK를 검사하지 않는다(B6-1 `01_schema.sql` 첫 줄).

**그림의 목적:** FK 칸의 값이 PK 칸의 같은 값을 가리켜 행을 찾는다는 것, 없는 값은 FK 제약이 막는다는 것을 실제 값으로 보여 준다.

**삽입 위치:** `## 쉽게 설명하면` 본문 바로 아래. 이 용어에서 그림은 비유 설명을 실제 값으로 이어 주는 역할이다.

**대체텍스트:** `PK와 FK: enrollment의 student_id 값이 student의 id 값을 가리킨다`

**캡션 제안:** `FK 값이 다른 표의 PK 값을 가리킨다 (B6-1 사례 일부, 거부 행은 교육용 예시)`

**그림 아래 설명 제안 (쉽게 설명하면 절 끝에 추가):**

> B6-1의 수강(`enrollment`) 표는 학생 이름을 다시 적지 않고 `student_id` 값만 담습니다. 이 값이 학생(`student`) 표의 `id`와 같아서 어느 학생의 수강인지 정확히 찾을 수 있습니다.

**한 줄 설명 수정 제안:**

- 현재: 외래 키는 한 테이블의 열이 다른 테이블의 기본 키를 참조하게 해 두 테이블의 관계를 지키는 규칙입니다.
- 제안: 외래 키는 한 테이블의 열이 다른 테이블의 기본 키(또는 UNIQUE 키)를 참조하게 해 두 테이블의 관계를 지키는 규칙입니다.

**`## 주의할 점 / 경계 조건` 신설 제안 (흔한 오해 앞):**

> - 외래 키 열이 NULL을 허용하면, 값이 비어 있는 행은 아무 행도 가리키지 않습니다. NULL을 막으려면 `NOT NULL`을 함께 씁니다.
> - SQLite는 `PRAGMA foreign_keys = ON;`을 실행해야 외래 키를 검사합니다. 켜지 않으면 없는 값도 들어갑니다.
> - 표 사이의 관계가 모두 외래 키 제약으로 만들어지는 것은 아닙니다. 제약이 없어도 같은 값으로 JOIN할 수는 있지만, 잘못된 값을 막아 주지는 않습니다.

**"본과정 M11" 표기:** `## 이 미션에서는 왜 필요한가`의 "본과정 M11"을 사이트 공식 표기 "B6-1"로 바꾸는 것을 제안한다. 같은 표기가 `content/terms/` 65개 파일에 있으므로, 이 세 용어만 바꿀지 전체를 별도 배치로 바꿀지 Owner 결정이 필요하다.

**기존 텍스트 도식과의 충돌:** 없음(도식 없음).

## 4. `join` — JOIN

**현재 부족한 부분**

- INNER와 LEFT의 차이는 "짝이 없는 행이 남는가"인데, 표 두 개를 나란히 보면 바로 보이는 이 차이가 문장과 SQL 코드로만 설명되어 있다.
- 짝이 여러 개인 행이 결과에 여러 번 나온다(1:N 확장)는 설명이 없다. 정확한 설명의 "기대보다 많은 행이 곱해져" 문장은 조건을 빠뜨린 경우만 말한다.

**그림의 목적:** 같은 데이터로 INNER 결과와 LEFT 결과를 나란히 비교해, 짝 없는 행의 운명과 결과 행 수의 변화를 한 번에 보여 준다.

**삽입 위치:** `## 정확한 설명` 본문 바로 아래.

**대체텍스트:** `INNER JOIN과 LEFT JOIN: 짝이 없는 왼쪽 행은 INNER에서 빠지고 LEFT에서 NULL과 함께 남는다`

**캡션 제안:** `같은 데이터에서 INNER JOIN과 LEFT JOIN의 결과 비교 (B6-1 사례 일부)`

**그림 아래 설명 제안 (정확한 설명 절 끝에 추가):**

> 짝이 여러 개인 행은 결과에 그 수만큼 나옵니다. 그래서 JOIN 결과의 행 수는 원래 표의 행 수와 다를 수 있습니다. B6-1에서 학생 15명을 수강 기록과 연결하면 INNER JOIN은 26행, LEFT JOIN은 수강 0건인 학생 1명이 더해져 27행입니다.

(26·27행은 B6-1 SQL을 SQLite로 실행해 확인한 값이며 미션 스토리 `join-compare` 각주와 같다.)

**"본과정 M11" 표기:** `foreign-key`와 같은 제안.

**기존 텍스트와의 충돌:** 없음. 코드 예(`orders`/`users`)와 그림(`student`/`enrollment`)의 예시가 다르지만, 같은 원리를 다른 데이터로 보여 주는 것이라 충돌은 아니다. 하나로 맞추려면 코드 예를 그림과 같은 표로 바꾸는 선택지가 있다(선택).

**기술적 보완(선택):** `ORDER BY`가 없으면 결과 행의 순서는 보장되지 않는다. 그림의 행 순서는 설명을 위한 정렬이다. 입문자 본문에 넣을지는 GPT 판단에 맡긴다.

## 5. 공유 용어 (설계만, 이번 배치 제외)

| 용어 | 공유 그림 | 삽입 위치 제안 | 캡션 제안 | 메모 |
| --- | --- | --- | --- | --- |
| `primary-key` | B `pk-fk-relationship` | `## 쉽게 설명하면` 아래 | `PK 값은 행 하나를 구별하고, 다른 표의 FK가 이 값을 가리킨다 (B6-1 사례 일부)` | 그림에 PK 설명 줄(중복·빈 값 불가)이 있다. 이 용어의 "본과정 M11" 표기도 같은 결정을 따른다 |
| `inner-join` | C `join-inner-left` | `## 정확한 설명` 아래 | `INNER JOIN은 짝이 맞는 행만 남긴다 — LEFT JOIN과 비교 (B6-1 사례 일부)` | 본문의 "조건을 빠뜨리면 곱이 된다"는 그림과 다른 주제라 그대로 둔다 |
| `left-join` | C `join-inner-left` | `## 정확한 설명` 아래 | `LEFT JOIN은 왼쪽 행을 모두 남기고 짝이 없으면 NULL을 채운다 (B6-1 사례 일부)` | 본문 코드 예의 `ON`/`WHERE` 차이가 그림을 보완한다. 관련 용어에 `join`·`inner-join` 추가 검토(현재 `sql`·`table`뿐) |

같은 SVG를 여러 용어 페이지에서 써도 페이지마다 한 번씩만 인라인되므로 id 충돌은 없다. 캡션은 등록 키가 경로 하나에 하나이므로, 용어별로 다른 캡션을 쓰려면 등록 방식을 Codex가 정해야 한다(예: 같은 SVG를 용어별 키로 두 번 등록).
