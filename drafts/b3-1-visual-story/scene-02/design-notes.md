# Scene 02 설계 노트 — 웹사이트 요청과 응답은 어떻게 흐를까?

> 미션 스토리맵 · B3-1 · AWS로 다시 이해하는 네트워크. 상태: **시안(Owner 시각 검토 전)**. 기준: Scene 01 `8da2e59`.

## 1. 기존 자료 재사용 판단

| 자료 | 판단 | 근거 |
| --- | --- | --- |
| Scene 01 SVG·생성기 | **배치·도형·스타일을 그대로 계승** | 지시서 §4 "Scene 01의 구역과 장비 배치가 달라지지 않아야 한다". Scene 02 생성기는 Scene 01 생성기를 불러 같은 장비 정의와 그리기 도구를 쓴다 |
| 보강 자료 그림 2 `02-visitor-request-response.svg` | **재제작**(일부 표현만 계승) | ① 방문자 흐름 안에 웹 서버의 DB 조회(6·7)가 섞여 있다. 지시서 §5 "DB 조회는 방문자 접속의 기본 경로와 구분"과 맞지 않는다. ② 경계 라우터와 방화벽을 한 상자로 그려 Scene 01과 배치가 다르다. ③ 요청·응답 번호 표식이 같은 색·같은 모양이다. 계승한 것: 응답 = 갈색 점선(`#7a4a00`), "DNS는 끝난 상태" 전제, HTTPS 443 예시, "처리 순서는 장비마다 다름" 단서 |

그림 2의 순서 표기(방화벽 → NAT → 경로표)는 처리 순서를 고정한 것처럼 읽힐 수 있다. 다만 같은 그림이 "순서는 장비마다 다르다"고 적고 있으므로 오류로 보지 않았다. 수정 의견은 [terminology-review.md](terminology-review.md) 5절에 있다.

## 2. 단계별 표시 방식 결정

지시서는 "요청 / 응답 / 복습" 세 상태를 예로 들었다. 이번에는 **장치당 SVG 1개에 요청과 응답을 다른 차선으로 함께 그리는 방식**을 택했다.

| 후보 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 상태별 SVG 3개 × 2장치 = 6개 | 상태마다 화면이 단순하다 | 장비 배치를 6벌 관리해야 한다. 웹 기능 없이는 넘겨 보기가 불편하다 | 보류 |
| SVG 1개에 요청·응답 함께 + 단계 번호 | 파일 2개로 유지보수가 쉽다. 요청(위 차선)과 응답(아래 차선)을 한 화면에서 비교할 수 있다(복습 상태) | 첫 화면의 선이 늘어난다 | **채택** |
| SVG 1개 + 웹에서 상태 전환 | 학습 효과가 가장 크다 | 웹 기능 선행 구현 금지 | 후속 제안 |

**나중에 단계별 강조를 쓸 수 있게 해 두었다.** 요청은 `data-flow="A1"~"A5"`, 응답은 `data-flow="R1"~"R5"`, 단계 표시는 `data-step="1"~"8"`, 흐림 부분은 `data-faded`로 묶었다. 웹 통합 때 CSS만으로 "요청만 / 응답만 / 함께" 상태를 만들 수 있다(구현하지 않음).

## 3. 시각 언어 — Scene 01과의 일관성

| 의미 | Scene 01 | Scene 02 |
| --- | --- | --- |
| 구역 | 색 면 + 번호 칩 1~5 | **같음.** 저장 구역·업무망은 흐리게(불투명도 0.35) |
| 회사 안·밖 | 회색 면 / 굵은 테두리 | 같음 |
| 실제 연결 | 회색 선 + 끝점 원 | 같음 |
| 요청 | 초록 실선, 동그라미 표식 A1~A5 | **같은 선·같은 위치** |
| 응답 | (그리지 않음) | **갈색 점선**, 네모 표식 R1~R5. 회색 선 아래 차선(노트북) / 왼쪽 차선(휴대전화). 기존 그림 2·3의 응답 약속을 따랐다 |
| 기능 | 이름표(경로 선택·NAT·허용·차단 판단·구역 사이 길 안내) | 같음 |
| 설명 단계 | — | **흰 원 + 검은 테두리 + 숫자 1~8**(새로 추가). 구역 번호(네모 칩), 요청 표식(초록 동그라미), 응답 표식(갈색 네모)과 모양·색이 모두 다르다 |

요청과 응답은 **색·선 모양·표식 모양·글자(A/R)** 네 가지로 구별된다. 색만으로 구분하지 않는다.

## 4. 정보 구조

| 장면 단계 | 그림에서 보이는 곳 | Scene 01과의 연결 |
| --- | --- | --- |
| 1 요청 시작 | 외부 방문자 + A1 | 구역 1 |
| 2 회사 경계 도착 | A2, 경계 라우터 | 굵은 테두리를 넘는 곳 |
| 3 경로 선택 | 경계 라우터 + "경로 선택" 카드(경로표 예), 방화벽의 "구역 사이 길 안내" | Scene 01 이름표 "경로 선택", "구역 사이 길 안내" |
| 4 허용 판단 | 방화벽 + 카드 | 이름표 "허용·차단 판단" |
| 5 주소 변환 | 방화벽 + NAT 카드(요청 도착 주소, 응답 출발 주소) | 이름표 "NAT", Scene 01 NAT 카드 |
| 6 웹 서버로 전달 | A4·A5, DMZ 스위치 | 구역 3 |
| 7 응답 만들기 | 공개 웹 서버 | 구역 3 |
| 8 방문자에게 돌아감 | R1~R5, 노트북용 단계 목록 / 휴대전화용 카드 8 | — |

- **4와 5에는 순서 화살표가 없다.** 방화벽 안에 "4·5의 처리 순서는 장비·정책마다 다름"을 적었다.
- **3은 장비 두 곳에 걸쳐 있다.** 경계 라우터와 방화벽의 길 안내다. 그래서 단계 표시를 라우터에만 달고, 카드에 "방화벽도 구역 사이 길 안내"를 적었다.
- 노트북용은 왼쪽 열에 **단계 목록**(1~8, 짧은 이름 + 한 줄)을 두었다. Scene 01의 범례 자리이며, 범례는 그림 아래로 옮겼다. 휴대전화용은 장비 왼쪽에 짧은 이름을 두고, 세부는 그림 아래 카드(3·4·5·8)에 적었다.

DNS(전제만 표시), TLS 종료 위치, 로드 밸런서·프록시, 웹 서버의 DB 조회(Scene 03 후보), 직원 게시, AWS 대응(B3-1 비교는 각주의 "HTTP 80" 한 줄만).

## 7. 편집 방법

`_tools/build.py`를 수정하고 `python3 -I _tools/build.py`로 생성한 뒤 `_tools/check.cjs`로 검사한다. Scene 01 생성기를 불러 쓰므로, **Scene 01의 장비 정의·스타일을 바꾸면 Scene 02도 다시 생성해야 한다.** 검사기가 Scene 01 SVG와 장비 위치를 비교하므로 어긋나면 FAIL이 난다.
