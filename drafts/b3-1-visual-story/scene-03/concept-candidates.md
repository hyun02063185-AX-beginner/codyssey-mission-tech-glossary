# 개념지도 후보 정리 — Scene 01~03 (Revision 1 · 정합성 패치)

> 개념지도는 만들지 않았다. 기존 지식지도·용어사전 데이터는 읽기만 했다. 이 문서는 Scene 04 첫 지도의 **내용 범위**만 준비한다.
>
> 관계 유형: 포함 · 선행(**학습상** 먼저) · 역할 · 흐름(**실제** 이동) · 대응(다른 체계의 비슷한 역할) · 연관. 여섯 유형 밖의 유형은 쓰지 않고, 필요한 뜻은 관계 설명에 적는다.
> 등급: **핵심** = 첫 지도에 우선 배치 · **보충** = 자세한 설명·사전으로 넘김 · **제외** = 넣지 않음.
>
> 1·2절의 표는 `_tools/check_concepts.py`가 읽어 모든 관계의 끝점이 노드 목록에 있는지, 유형이 여섯 가지 안에 있는지, 고립된 노드가 없는지 확인한다.

## 1. Scene 04 첫 지도 — 핵심 노드 14개(안)

목표는 "B3-1에서 방문자가 웹사이트를 열 수 있었던 이유를 AWS 자원의 역할로 설명하고, 일반 네트워크의 세 역할과 이어 보기"다.

정합성 패치에서 15개 → 14개로 줄였다. 'HTTP 요청·응답(HTTP 80)' 노드는 흐름 관계 C12의 설명과 ID로 옮겼다. 노드로 두면 어느 관계의 끝점도 되지 않아 고립된다.

| # | 노드 | 기존 용어사전 ID | 비고 |
| --- | --- | --- | --- |
| N1 | 외부 방문자 | — | 브라우저 |
| N2 | VPC | `virtual-private-cloud` | |
| N3 | Subnet | `subnet`, `public-subnet` | B3-1은 Public Subnet 하나 |
| N4 | Route Table | `route-table` | AWS 항목. 일반 경로표와 같은 노드로 쓰지 않는다 |
| N5 | IGW | `internet-gateway` | 인터넷 게이트웨이 |
| N6 | Public IPv4 | `public-ip` | 자동 할당 |

일반망 쪽은 장비(라우터·방화벽) 대신 **역할 노드 3개**로 둔다. 장비 ↔ AWS 자원이 일대일로 보이는 것을 막고, 03-A 비교선과 같은 단위로 맞추기 위해서다.

## 2. 핵심 관계 15개

| # | A | B | 유형 | 관계 설명 | 장면 | 근거 |
| --- | --- | --- | --- | --- | --- | --- |
| C1 | VPC | Subnet | 포함 | Subnet은 VPC 주소 범위 안의 IP 주소 범위다 | 03-A | AWS VPC 동작 방식 |
| C2 | Subnet | EC2 | 포함 | B3-1의 EC2는 Public Subnet 안에서 실행되었다 | 03-A·B | 배포 기록 |
| C3 | EC2 | ENI | 연관 | **연결(attach).** ENI는 VPC 안의 논리적 네트워크 구성요소로 EC2에 연결된다. B3-1은 기본(주) ENI만 썼고, 주 ENI는 분리할 수 없다. EC2 안에 들어 있는 부품이 아니므로 '포함'으로 두지 않는다 | 03-A·B | AWS ENI 문서 |
| C4 | EC2 | Nginx | 포함 | Nginx는 EC2 안에서 실행되는 웹 서버 프로그램이다 | 03-A·B | 배포 기록 |
| C5 | IGW | VPC | 연관 | **연결.** IGW를 VPC에 연결해야 VPC와 인터넷이 통신한다 | 03-A·B | AWS IGW 문서 |
| C6 | Route Table | Subnet | 연관 | **연결(association).** Route Table을 Subnet에 연결한다 | 03-A·B | AWS Route Table 문서, 배포 기록 |
| C7 | Route Table | IGW | 연관 | **경로 대상.** `0.0.0.0/0` 경로의 대상이 IGW다. 이 Route Table에 연결된 Subnet이 Public Subnet이다 | 03-B | AWS IGW 문서 |
| C8 | Security Group | ENI | 연관 | **적용.** SG는 ENI에 적용되는 상태 추적 허용 규칙이다 | 03-A·B | AWS SG 문서, ENI 문서(ENI 속성에 SG 포함) |
| C9 | ENI | Private IPv4 | 연관 | **할당.** ENI에는 Subnet 범위의 주 사설 IPv4가 있다. EC2는 이 사설 주소만 안다 | 03-B | AWS ENI 문서, IGW 문서 |
| C10 | IGW | Public IPv4 | 연관 | **변환 주체.** IGW는 Public IPv4로 오는 트래픽의 목적지를 Private IPv4로 바꿔 VPC로 전달한다. 나가는 트래픽은 출발 주소를 Public IPv4로 바꾼다 | 03-A·B | AWS IGW 문서 |
| C11 | Public IPv4 | Private IPv4 | 연관 | **IGW의 1:1 변환으로 짝지어진 주소 쌍.** 비슷한 역할의 '대응'이 아니라, 변환 주체(C10의 IGW)에 의해 맺어지는 관계다 | 03-A·B | AWS IGW 문서 |
| C12 | 외부 방문자 | Nginx | 흐름 | HTTP 80 요청이 인터넷 → IGW → ENI → Nginx로 간다(03-B W1~W4). 연결 가능 ID: `http-request-response`, `port-80-http` | 03-B | 배포 기록, AWS 문서 |
| C13 | 경로 선택 | Route Table | 대응 | 목적지에 따라 다음 대상을 정하는 역할이 비슷하다. Route Table은 장비가 아닌 규칙표다 | 03-A | AWS Route Table 문서 |
| C14 | 접근 통제 | Security Group | 대응 | 규칙에 맞는 연결만 허용하고 상태를 추적하는 역할이 비슷하다. 적용 위치가 다르다(구역 경계 / ENI) | 03-A | NIST §2.1.2, AWS SG 문서 |
| C15 | 주소 변환 | IGW | 대응 | 공인 ↔ 사설 주소 대응이라는 역할이 비슷하다. B3-1에서는 IGW가 IPv4 1:1 변환을 제공했다. NAT Gateway가 아니다 | 03-A | AWS IGW 문서 |

**관계 유형을 바꾼 것(Revision 1 대비).**
- C3 EC2–ENI: 포함 → **연관(연결·부착)**.
- 1차 C9 Public IPv4 ↔ Private IPv4: 대응 → **연관(IGW의 1:1 변환으로 짝지어진 주소 쌍)**. 이제 C11이며, 변환 주체를 C10(IGW–Public IPv4)으로 따로 이었다. ENI–Private IPv4(C9)를 더해 두 주소가 어디에 붙는지도 보인다.
- 1차 C10 IGW → '주소 변환' 역할: 일반망 역할 노드 '주소 변환'과 같은 노드에 이으면 IGW가 일반망 NAT의 한 종류처럼 보인다. 그래서 C15 대응 하나로 합쳤다.
- 1차 C14(끝점 'IGW의 1:1 변환' — 노드 아님): 끝점을 노드 N5 IGW로 바꿔 C15로 정리했다.

## 2-1. 학습 순서(지도 밖에서 관리)

다음은 개념과 개념의 관계가 아니라 **설명 문장이나 장면 순서**의 선후다. 지도에 선으로 넣지 않고, 발표·복습 순서 안내로 따로 둔다. 패킷이 이동하는 순서(C12)와 다른 축이다.

| # | 먼저 | 다음 | 쓰는 곳 |
| --- | --- | --- | --- |
| L1 | Scene 01 구조 → Scene 02 흐름 | Scene 03 대응 | 장면 순서 안내 |
| L2 | 공인 주소와 사설 주소의 구분 | IGW의 1:1 변환(C10·C11) | 03-B 설정 ④ 설명 전 |
| L3 | 경로 선택 ≠ 허용 판단(Scene 02) | Route Table과 Security Group이 모두 필요한 이유(C13·C14) | 03-A 주의 카드 3, 03-B 설정 ③·⑤ |

1차의 C15·C16(선행)은 끝점이 노드가 아닌 설명 문장이었다. 그래서 L2·L3으로 옮겼다.

| ENI — Public IPv4(할당) | 연관 | 03-B | AWS 문서상 Public IPv4도 주 ENI에 할당된다. 첫 지도에서는 C10·C11로 충분 |

| HTTPS ↔ 포트 443(일반망 예시) | 연관 | 02 | B3-1은 HTTP 80 |
| 스위치 — 같은 구역 안 연결, DMZ ⊃ 공개 웹 서버, 회사 네트워크 ⊃ 구역 | 역할·포함 | 01·02 | 일반망 구조 설명용 |

## 4. 제외

| 관계 | 이유 |
| --- | --- |
| 경계 라우터 ↔ IGW (직접 대응) | IGW를 라우터 장비로 오해하게 한다. 03-A에서도 선을 긋지 않았다 |
| DMZ ↔ Public Subnet (직접 대응) | 서로 다른 개념이다. 03-A에서도 선을 긋지 않았다 |
| 일반 NAT ↔ `nat-gateway` 자동 연결 | `nat-gateway`는 B3-1에 없는 AWS 서비스다 |
| 일반 경로표·라우터 ↔ `route-table` 자동 연결 | `route-table`은 AWS 항목이다. C13 대응으로만 잇는다 |
| 일반 웹 서버 ↔ `nginx` 자동 연결 | Nginx는 특정 프로그램이다 |
| 일반 방화벽 ↔ `firewalld` | Linux 도구이며 무관하다 |
| 스위치 ↔ AWS 대응 | B3-1 기록에 대응 설정이 없다 |
| 구역 4·5(DB·업무망) ↔ AWS 자원 | B3-1에서 구현하지 않았다 |
| 요청이 Route Table을 통과하는 흐름 | 사실이 아니다(B3-1 계획도의 표현) |
| DNS → 요청 | 이번 장면들에서 생략했다 |
| 방화벽 → NAT 처리 순서 | 장비마다 다르다 |
| 리전·가용 영역·EBS·IAM·키 페어 | 이번 미션 스토리맵의 네트워크 역할 밖이다(다른 장면 후보) |
| HTTP 80(B3-1) ↔ HTTPS 443(예시) | 개념 관계가 아니라 사례 구분이다 |
| 웹 서버 → DB 조회, 직원 게시 | B3-1에 없고 이번 장면들에서 그리지 않았다 |
