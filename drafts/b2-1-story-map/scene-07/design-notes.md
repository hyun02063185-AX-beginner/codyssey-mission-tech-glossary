## 1. 핵심 시각화 네 가지

| 그림 | 질문 | 구성 | 관계의 종류 |
| --- | --- | --- | --- |
| **A** Parameter와 Argument 연결 | 넣은 값은 어느 자리에 들어갈까? | 맨 위 정의 `def calculate_total(price, quantity):`(Parameter 초록 밑줄) · 경우 카드 4개: **위치 인자**(순서대로) / **키워드 인자**(이름으로, 선이 엇갈림) / **순서를 바꾼 위치 인자**(결과 3000은 같지만 `price=3`) / **기본값**(`quantity=1`, 연결 선 없음) · 카드마다 호출식(Argument 갈색 칩) → Parameter 칸(`price ← 1000`) + 실제 출력 '연결: …' · 아래: 기본값 없는 정의에서 Argument가 모자랄 때의 `TypeError` | **연결**(보라 점선, 화살촉·번호 없음 — 관계, 순서 아님) |
| **B** Type Hint 유무에 따른 코드 이해 | 힌트를 붙이면 무엇이 달라지고 무엇이 그대로일까? | 두 열: 힌트 없음 `calculate_total_no_hint` / 힌트 있음 `calculate_total`(힌트 조각 `: int`·`-> int` 파란 바탕) · 힌트 쪽에 '표시 · 무엇인가 · 실행 중 하는 일' 세 칸(Parameter Type Hint·반환 Type Hint = 검사·변환하지 않음, `return` 문 = 실행됨) · 두 열의 **실제 실행 결과가 같음**(`'100010001000'`까지) · 달라지는 것(읽는 사람·도구) · `__annotations__` 보관 출력 | 비교(나란히). **번호·실행 선 없음** — 힌트가 실행 동작을 바꾸는 것처럼 그리지 않는다 |
| **C** 입력값이 통과하는 단계 | `--limit 10`·`abc`·`-2`는 어디까지 가고 어디서 멈출까? | 열 4개: 명령줄 입력(문자열) → argparse `type=int`(변환) → 서비스 함수 호출(`limit: int` **표시만** — 파란 파선 칸) → 범위 검증 `if limit <= 0:` · 경우 3줄 · 각 줄 아래 'main()이 끝난 뒤 실제 출력 · 종료 코드' | **실행 순서**(번호·검은 실선, 경우마다 번호를 따로) · **변환** `'10'` → `10`(청록 선, 번호 없음) · 끝: 성공 = **return**(회색), `abc` = **전파되는 종료**(빨간 점선, `SystemExit(2)`), `-2` = **처리되는 예외**(빨간 긴 파선, `main()`의 `except`) · `abc`의 뒤 두 단계는 **실행되지 않음**(회색 점선 칸) |
| **D** Type Hint와 런타임 검증 비교 | 선언이 기대하는 것과 코드가 실제로 검사하는 것은 같을까? | 표: 넣은 값 6개(`1000`·`'1000'`·`-5`·`True`·`3.5`·`None`) × (선언 `amount: int` 기준 · 타입 표시만 있는 함수 결과 · 검증 코드가 있는 함수 결과) · 비교 카드 4개 `str \| None`·`list[str]`·`int \| str`·`-> None`(뜻 · '실행 중 자동 검사: 없음' · 실제 실행 결과 · 한 줄 정리) | 비교 표·카드. **번호 원 없음** |

그림의 코드 줄·연결·실행 결과·종료 코드·단계 상태는 `_tools/demo/`의 실제 소스와 실행 결과이며 `verify_demo.py`가 매번 다시 대조한다(그림 A 연결은 `inspect.signature().bind()`, 그림 C 단계는 `sys.settrace` 호출 추적).

**예제 선택.** Parameter·Type Hint는 지시서의 `calculate_total(price, quantity)`·`set_amount(amount)`·`greet(name)`를 그대로 썼다. 곱셈은 순서를 바꿔도 결과가 같아서 **'결과가 같아도 연결은 다르다'**(그림 A 셋째 카드)를 보이기에 오히려 알맞다고 판단해 남겼다. 함수 안에서 '연결: price=…, quantity=…'를 출력하게 해 실제 연결을 화면으로 확인한다. 그림 C는 `ledger` 대신 학습용 `argparse_vs_hint.py`(거래 12건 목록, 서비스 역할 함수 + `main()`)로 그리고, 같은 구조의 `ledger` 실행은 원고 9절에서 비교한다(일반 개념 먼저, 사례는 마지막).

**그림 D의 선언 판단 칸.** '맞음/다름'은 `isinstance(값, int)` 기준이다(`bool`은 `int`의 하위 클래스라 `True`도 '맞음'). '도구가 알려 줄 수 있음'은 **가능성**으로만 적었다. 이번 작업에서 타입 검사기를 실행하지 않았으므로 특정 검사기의 경고를 그림에 적지 않았다.

## 2. 시각 약속 (Scene 01~06 약속 유지 + 이번 추가)

| 표현 | 뜻 | 출처 |
| --- | --- | --- |
| 진한 실선 + 채운 검은 화살촉 + 검은 번호 원 | **실제 실행 순서**(그림 C에서만, 경우마다 번호를 따로) | Scene 01~06과 같음 |
| 회색 가는 실선 + 빈 화살촉 + 'return' 글자, 번호 없음 | return(값을 돌려줌) | Scene 03-A와 같음 |
| 빨간 **긴 파선** + 채운 빨간 화살촉 | **처리되는 예외**(`-2`의 `ValueError`를 `main()`이 받음) | Scene 06과 같음 |
| 빨간 **점선** + 채운 빨간 화살촉 | **전파되는 예외·종료**(`abc`: argparse의 `SystemExit(2)`를 아무도 받지 않음) | Scene 06과 같음 |
| 청록 실선 + 청록 화살촉, 번호 없음 + 글자 `int('10') → 10` | **변환**(`type=int`) | Scene 04와 같음 |
| 보라 점선, 화살촉·번호 없음 | **연결**(Argument → Parameter, 순서 아님) | Scene 05·06 관계 선과 같은 모양 — 범례 글자로 뜻 구분 |
| 초록 테두리 칸 + 초록 밑줄 이름 | **Parameter**(받는 자리) | Scene 03-A의 Parameter 색(초록 밑줄)을 이어받음, 칸 모양은 **이번에 추가** |
| 갈색 테두리 둥근 칩 + 갈색 값 | **Argument**(넣은 값) | Scene 03-A의 전달값 색(갈색), 칩 모양은 **이번에 추가** |
| 파란 글자 + 연한 파란 바탕 | 코드 속 **Type Hint 조각**(`: int`, `-> int`) | **이번에 추가** |
| 파란 **파선** 테두리 + '표시만' 글자 | 실행 중 **아무것도 검사하지 않고 지나가는** 자리(`limit: int`) | **이번에 추가** |
| 빨간 테두리 단계 상자 | 그 단계에서 **멈춤**(변환 실패·검증 실패) | **이번에 추가** |
| 회색 점선 테두리 + '실행되지 않음' 글자 | 앞에서 멈춰 **실행되지 않은 단계** | **이번에 추가** |
| 청록 테두리 칩 / 회색 테두리 칩 | 변환 뒤의 정수 / 변환 전의 문자열 | **이번에 추가** |

- 색만으로 구분하지 않는다: Parameter·Argument는 모양(각진 칸/둥근 칩)·밑줄·범례 글자, '표시만'·'실행되지 않음'·실패는 테두리 모양 + 글자, 두 예외는 선 모양(긴 파선/점선). 검사기가 Parameter 칸의 이름, '표시만'·'실행되지 않음' 글자, 두 예외 선의 모양 차이를 확인한다.
- **번호를 붙이지 않은 곳:** 그림 A·B·D 전체, return·변환·연결 선 주변 16px. 그림 A의 연결 선은 '값이 자리에 들어감'이라는 관계이고 실행 순서가 아니다.
- 그림 B에는 실행 선을 하나도 긋지 않았다. 힌트 유무에 따라 실행 경로가 갈리는 것처럼 보이지 않게 하려는 선택이다. 대신 결과 칸과 '두 함수의 실행 결과는 같다' 띠로 같음을 보인다.

## 3. 이전 장면·기존 체험과 다른 점

- Scene 03-A 그림 A는 `add_tax(1000)`의 `price ← 1000` 연결을 한 줄 글로만 보였다. 이번 그림 A는 **연결 선**으로 위치·키워드 인자의 차이(평행 / 엇갈림)를 모양으로 보인다.
- Scene 01 그림의 ③ `sys.argv` → ④ `parse_args()` 흐름을 이어받아, 그림 C는 그 **다음**(서비스 함수 호출과 범위 검증)까지 한 줄로 이었다. Scene 01은 `--limit five`의 변환 실패만 다뤘고, 이번에는 **변환은 되지만 업무 규칙에서 막히는 `-2`**를 더했다.
- B3-1 그림의 배치·장면 전개는 쓰지 않았다. 그리기 도구는 Scene 06 생성기를 불러 썼고(그 안의 05·04·03-B·03-A·02·01 포함), 일곱 생성기 파일은 바꾸지 않았다.
- **기존 학습 체험 `src/B21LearningStoryView.tsx`의 `TypeHintEpisode`(변경하지 않음):** `ledger/services.py`의 `list_transactions(self, limit)`과 `list_transactions(self, limit: int) -> list[Transaction]`을 '표시 전후 비교'로 나란히 놓고, 읽는 사람·IDE/Type Checker·Python 런타임 세 칸과 '이 코드의 실제 값 검증 `if limit <= 0: raise ValidationError(...)`'를 보인다. 내용이 정확하고(시나리오 v2 §7.2 평가 유지) 원고 **9절 사례 1 + 6절 세 주체 표**와 겹치므로 **9절의 상호작용으로 재사용할 수 있다.** 다만 ① `ledger` 하나만 다루고 일반 예제가 없으며, ② Parameter/Argument(그림 A)와 argparse `type=int` 변환(그림 C)의 층위가 없다. 재사용 시 그림 A~D(일반 예제)를 앞에 두고 이 체험은 사례 절에 둔다(Codex 단계).

## 4. 노트북용과 휴대전화용

| 범례 | 세 줄(선 4종 / 변환·연결 / 칸 4종) | 세로 목록 |
