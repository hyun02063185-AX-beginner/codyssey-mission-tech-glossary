# Scene 02 — 여러 파일로 나누는 이유

**공통 질문:** 프로그램을 여러 파일로 나누는 이유는 무엇일까?

**목표:** 네 역할과 모듈·패키지·import·시작/초기화 파일의 의미를 설명한다.

**사례:** 가상 todo의 역할 분리 설계 예시. 이전 v2의 실제 데모 파일 구조를 복제하지 않는다. 전체 4~5분 계획.

## 화면 A — 네 가지 역할 (약 2분)

**메시지:** 역할을 구분하면 기능을 바꿀 때 살펴볼 곳을 찾기 쉽다.

**그림:** 명령 해석 / 요청 처리 / 데이터 읽기·저장 / 결과 표시의 네 큰 블록. PC 2×2, 모바일 세로. 관계선·호출 번호·파일명 없음. 블록 번호는 오직 강사가 가리키는 설명 순서다.

**처음 던질 질문:** “파일 저장 방식을 바꿨을 뿐인데 목록을 보여 주는 화면까지 모두 고쳐야 한다면 어떨까요?”

**가리킬 순서:**

1. 명령 해석 — 어떤 기능과 조건을 요청했는지 알아보기. Scene 01의 argparse와 연결.
2. 요청 처리 — 목록·추가·수정 등 요청한 일을 처리하기.
3. 읽기·저장 — 파일에서 기록을 읽고 바뀐 내용을 남기기.
4. 결과 표시 — 사람이 읽을 수 있게 목록·메시지를 보여 주기.

**꼭 설명할 세 문장:**

- “명령을 이해하는 일, 요청을 처리하는 일, 데이터를 읽고 저장하는 일, 결과를 보여 주는 일은 역할이 다릅니다.”
- “역할을 구분하면 문제가 생기거나 기능을 바꿀 때 어디를 볼지 찾기 쉽습니다.”
- “이 네 역할은 설계 예시이며, Python이 파일 네 개를 의무로 요구하는 것은 아닙니다.”

**혼동:** 네 블록은 실제 함수 호출도나 import 의존도가 아니다. 역할 하나가 항상 파일 하나와 일치하지 않는다. ‘결과 표시’는 필수 Python 계층명이 아니라 이해를 돕는 역할 구분이다.

**확인 질문:** 저장 방식을 바꾸면 어느 역할을 먼저 볼까? / 역할 네 개면 파일도 꼭 네 개여야 할까?

**기대 답:** 읽기·저장 / 아니다.

**한 문장 정리:** 역할을 나누면 프로그램에서 바꿀 곳과 함께 쓰는 곳을 구분하기 쉽다.

**다음 화면 연결:** “이 역할들을 파일과 폴더에 담아 함께 사용하려면 어떤 이름을 알면 될까요?”

## 화면 B — 모듈과 패키지 (약 2~3분)

**메시지:** 모듈은 코드를 담은 단위, 패키지는 관련 모듈을 묶는 구조다.

**그림:** `todo/` 경계 안에 `cli.py`(명령), `actions.py`(요청), `storage.py`(읽기·저장), `display.py`(표시). 아래에 `__main__.py`(패키지 실행 진입점), `__init__.py`(일반 패키지 초기화) 카드를 둔다. ‘import: 다른 모듈의 이름·기능을 가져와 사용’ 표식을 패키지 아래 놓되, 특정 파일 간 import 선을 만들지 않는다.

**처음 던질 질문:** “각 파일이 맡은 일을 알게 됐다면, 이 파일들을 어떻게 묶고 함께 사용할까요?”

**가리킬 순서:**

1. `cli.py` 등 모듈 파일 — 이 예시에서는 Python 코드가 들어 있는 `.py` 파일.
2. `todo/` 바깥 경계 — 관련 모듈을 모은 패키지. 이 예시는 일반 패키지.
3. import 표식 — 다른 모듈의 이름·기능을 가져와 쓴다는 관계. 함수 호출 순서 설명은 하지 않는다.
4. `__main__.py` — Scene 01의 `python -m todo`로 패키지를 실행할 때 쓰는 진입점.
5. `__init__.py` — 일반 패키지 초기화 파일. 시작 파일과 목적이 다르며 내용이 비어 있을 수도 있다.

**꼭 설명할 세 문장:**

- “이 예시에서는 Python 코드가 들어 있는 파일 하나를 모듈이라고 보고, 관련 모듈을 패키지로 묶습니다.”
- “import는 다른 모듈의 이름이나 기능을 가져와 사용하게 해 줍니다.”
- “`__main__.py`는 패키지 실행의 진입점이고 `__init__.py`는 일반 패키지의 초기화 파일입니다.”

**혼동:** 모든 모듈이 `.py` 파일은 아니며, namespace package에는 `__init__.py`가 없을 수 있다. 모든 패키지가 실행 가능하거나 `__main__.py`를 가지는 것은 아니다. 파일 안의 초기화 실행 순서·객체의 `__init__()`·name guard 문법은 이 화면에서 가르치지 않는다.

**확인 질문:** 패키지 실행 진입점은 어느 파일인가? / 모든 패키지의 파일 구성이 이 예시와 같을까?

**기대 답:** `__main__.py` / 아니다. 구성은 설계와 패키지 종류에 따라 다르다.

**한 문장 정리:** 모듈은 코드를 나누고 패키지는 모듈을 묶으며 import로 함께 사용한다.

**다음 장면 연결:** “이제 요청 처리 역할 안에서 기록을 추가·조회·수정·삭제하는 목적을 살펴봅시다.”

## 선택형 심화와 공식 요구

HTML 펼침: 내장·확장 모듈, namespace package, import와 함수 호출의 구분. 기존 [Scene 02 원고](../../scene-02/script.md)·[설계 노트](../../scene-02/design-notes.md)에 상세 실행·import 지도가 있다. 기본 수업을 진행하는 데 필요하지 않다.

공식 목표의 클래스·모듈 구조화 요구는 유지한다. 클래스 문법이 필요한 교육생은 기존 [Scene 03-A](../../scene-03a/script.md)를 선수 자료로 참고한다. 이 강의의 이해 확인이나 선수 수강으로 실제 클래스 구조화 구현을 완료 처리하지 않는다.
