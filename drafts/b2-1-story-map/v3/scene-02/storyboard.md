# Scene 02 v3.2 — 역할을 나누고 파일로 묶기

2026-10-24 · **v3.2 교육 콘텐츠 원고** (디자인·화면 구현 전 단계) · 시작 `ad2b1fd13bd97cbaf939fbd49ab3aded9b357606`

**핵심 질문: 프로그램은 왜 역할을 나누고 여러 파일로 만들까?**

## 0. 장면 범위

| 항목 | 내용 |
| --- | --- |
| 학습 목표 | ① 부탁 하나를 처리하는 데에도 여러 종류의 일이 필요하다는 것을 말한다. ② 네 가지 역할(Model·Repository·Service·CLI)을 일상 말로 구분한다. ③ 역할을 나누면 바꿀 곳을 찾기 쉽다는 이유를 말한다. ④ 모듈·패키지·import가 무엇인지 말한다. ⑤ `python -m todo`가 todo 패키지의 `__main__.py`에서 시작한다는 것을 Scene 01과 연결한다. |
| 기본 예시 | **Scene 01의 가상 todo를 계속 사용**한다. 네 역할 구분은 실제 용돈 기입장(ledger) 구현의 역할 구분을 참고했다. 실제 ledger 파일은 개념 설명을 마친 뒤 **‘실제 사례’ 한 단계로만** 보여 준다. |
| 선수 조건 | Scene 01. 이전 미션의 함수·클래스 학습이 전제이지만 이 장면은 문법 없이 이해할 수 있게 구성했으며, 숙련 여부를 가정하지 않는다. |
| 기본 화면에 새로 나오는 용어 | Model, Repository, Service, (프로그램 부분으로서의) CLI, 모듈, 패키지, import, `__main__.py` — 많으므로 **한 단계에 하나씩**, 일상 설명을 먼저 말한 뒤 이름을 붙인다. |
| 다루지 않는 것 | 클래스·객체·self·`__init__()` 문법, 함수 호출 경로, import 의존도 분석, 파일 안의 코드, 교육생 코드 리뷰 |
| 예상 시간 | 설명 약 11~14분 + 학습자 질문·확인 약 4~6분 = **약 15~20분**. 시범 수업 전 **추정치**다. |

## 1. 강의용 그림 7개

한 그림에는 한 가지 개념만 담는다. **F2·F4·F7은 네 역할의 자리를 똑같이 유지**해 같은 구조가 파일로, 실제 사례로 이어진다는 것이 보이게 한다.

### 그림 F1 — 부탁 하나, 여러 종류의 일 (관계)

| 위치 | 표시 문구 |
| --- | --- |
| 가운데 | Scene 01의 부탁 `list --limit 5` (할 일 목록을 최대 5개 보여 줘) |
| 주변 말풍선 4개 | 할 일 기록이 어떤 모양인지 알아야 해 (내용, 완료 여부) · 저장해 둔 기록을 꺼내 와야 해 · 그중 5개를 골라야 해 · 고른 결과를 화면에 보여 줘야 해 |
| 그림 아래 작은 라벨 | 필요한 일들 — 순서표가 아닙니다 |

- 말풍선은 가운데를 둘러싸도록 배치하고 **번호·화살표를 넣지 않는다**.
- 말풍선 네 개의 위치는 F2의 네 역할 자리와 같게 둔다(왼쪽 위=기록의 모양 … ).

### 그림 F2 — 네 가지 역할 (구조) · **핵심 역할 구조도**

같은 크기의 2×2 상자. 각 상자에 **큰 글씨 일상 설명**, 작은 글씨 이름, todo 예시 한 줄.

| 자리 | 큰 글씨 | 작은 이름 | todo 예시 |
| --- | --- | --- | --- |
| 왼쪽 위 | 기록의 모양을 정하는 부분 | Model | 할 일 하나 = 내용 + 완료 여부 |
| 오른쪽 위 | 기록을 읽고 저장하는 부분 | Repository | 저장된 할 일을 꺼내 오고, 새 할 일을 저장 |
| 왼쪽 아래 | 요청한 일을 처리하는 부분 | Service | 목록에서 최대 5개 고르기 |
| 오른쪽 아래 | 명령을 받고 결과를 보여 주는 부분 | CLI | `list --limit 5`를 받고, 고른 결과를 화면에 보여 주기 |

- 상자 사이에 번호·화살표·연결선이 없다. 네 상자의 크기와 굵기를 같게 한다(중요도 차이 없음).
- 설명 중인 상자만 테두리·색으로 강조하고, 나머지는 흐리게 지우지 않는다.

### 그림 F3 — 바꾸고 싶을 때 먼저 볼 곳 (비교)

두 줄의 대응표. 오른쪽 칸에는 F2 상자를 작게 그린 아이콘을 쓰고 해당 역할만 강조한다.

| 바꾸고 싶은 것 | 먼저 볼 역할 |
| --- | --- |
| 할 일을 저장하는 파일 형식을 바꾸고 싶다 | 기록을 읽고 저장하는 부분 · Repository |
| 목록을 표 모양으로 보여 주고 싶다 | 명령을 받고 결과를 보여 주는 부분 · CLI |

- 제목: **바꾸고 싶은 것이 있을 때, 먼저 볼 곳**. ‘먼저’를 굵게 표시한다(‘거기만 고친다’가 아님).

### 그림 F4 — 역할을 파일로 나누면: 모듈과 패키지 (구조)

F2와 같은 2×2 자리에 파일 카드 네 장을 놓고, 바깥에 폴더 경계를 그린다.

| 자리 | 파일 카드 | 카드 아래 작은 역할 이름 |
| --- | --- | --- |
| 왼쪽 위 | `models.py` | Model |
| 오른쪽 위 | `repository.py` | Repository |
| 왼쪽 아래 | `services.py` | Service |
| 오른쪽 아래 | `cli.py` | CLI |
| 폴더 경계 | `todo/` | — |
| 상단 작은 라벨 | 가상 todo를 역할별로 나눈 예 | |

- 강조 상태 세 가지를 단계에 따라 바꾼다: ① 파일 카드 네 장 등장 ② **파일 카드 한 장**만 강조 + 라벨 ‘모듈’ ③ **폴더 경계**만 강조 + 라벨 ‘패키지’.
- `__init__.py`는 이 그림에 넣지 않는다(선택 심화). `__main__.py` 카드는 F6 단계에서만 나타난다.

### 그림 F5 — import: 다른 모듈의 기능을 가져다 쓰기 (관계)

F4 위에 선 **한 개**만 더한다.

| 위치 | 표시 문구 |
| --- | --- |
| `cli.py` → `services.py` 선 | **import** — cli.py가 services.py의 기능을 가져다 씀 |
| 선 아래 작은 라벨 | 가져다 쓰는 관계 · 실행 순서가 아닙니다 |

- 다른 파일 사이의 선은 그리지 않는다. 의존 관계 전체를 보여 주는 그림이 아니다.

### 그림 F6 — `python -m todo`는 어디서 시작할까 (흐름)

| 상자 | 표시 문구 |
| --- | --- |
| ① 명령 | `python -m todo list --limit 5` (Scene 01과 같은 명령) |
| ② Python | todo 패키지를 찾음 |
| ③ 시작 파일 | `todo/__main__.py` — 패키지를 실행할 때의 시작 파일 |
| ④ 이어서 | CLI 부분이 `list --limit 5`를 받음 |

- 실제로 일어나는 흐름이므로 ①→②→③→④ 화살표를 쓴다.
- F4의 폴더 그림 옆에 `__main__.py` 카드를 이때 처음 추가해 위치를 보여 준다.

### 그림 F7 — 실제 사례: 용돈 기입장 ledger (구조)

| 위치 | 표시 문구 |
| --- | --- |
| 상단 라벨 | 실제 사례 · 용돈 기입장 ledger (참고 커밋 `d14e812`) |
| 폴더 경계 | `ledger/` |
| 같은 2×2 자리 | `models.py` · `repository.py` · `services.py` · `cli.py` |
| 아래 한 줄 | `__main__.py` — 실행: `python -m ledger list --limit 5` |
| 옆의 회색 묶음 | 이 프로젝트가 따로 둔 파일: `__init__.py`, `errors.py`, `validators.py`, `decorators.py` |

- 회색 묶음은 이름만 보여 주고 하나씩 설명하지 않는다. 핵심 문장은 ‘같은 네 역할, 그리고 필요한 파일은 더 둘 수 있다’이다.

## 2. 단계별 강의 진행

화면에는 **핵심 질문 + 그림 + 아래의 '화면 한 문장'**만 보인다. 단계 번호는 강의 진행 순서이며 프로그램의 실행 순서나 import 순서가 아니다.

| 단계 | 그림 · 가리킬 곳 | 화면 한 문장 |
| --- | --- | --- |
| 1 | F1 · 가운데 부탁 → 말풍선 네 개 | 부탁 하나를 처리할 때에도 프로그램은 여러 종류의 일을 해야 합니다. |
| 2 | F2 · 네 상자 전체 | 이 일들은 네 가지 역할로 나누어 볼 수 있습니다. |
| 3 | F2 · Model | 기록 하나가 어떤 항목으로 이루어지는지, 곧 기록의 모양을 정하는 부분을 Model이라고 합니다. |
| 4 | F2 · Repository | 기록을 파일에서 읽어 오고 저장하는 부분을 Repository라고 합니다. |
| 5 | F2 · Service | ‘최대 5개 고르기’처럼 요청한 일을 처리하는 부분을 Service라고 합니다. |
| 6 | F2 · CLI | 명령을 받아 알아듣고 결과를 보여 주는 부분을 CLI라고 합니다. Scene 01의 argparse는 이 부분에서 쓰입니다. |
| 7 | F3 · 첫 줄 → 둘째 줄 | 역할을 나누어 두면 무언가를 바꿀 때 어디부터 살펴볼지 찾기 쉽습니다. |
| 8 | F4 · 파일 카드 네 장 | 역할에 따라 코드를 여러 파일로 나눌 수 있습니다. |
| 9 | F4 · 파일 카드 한 장 | Python 코드를 담은 파일 하나를 모듈이라고 부릅니다. |
| 10 | F4 · 폴더 경계 | 관련 있는 모듈을 하나의 이름으로 묶은 것을 패키지라고 부릅니다. 여기서는 todo가 패키지입니다. |
| 11 | F5 · cli.py → services.py 선 | import를 쓰면 한 모듈에서 다른 모듈의 기능을 가져와 함께 쓸 수 있습니다. |
| 12 | F6 · ① → ② → ③ → ④ | python -m todo처럼 패키지를 실행하면, Python은 그 패키지의 `__main__.py`에서 시작합니다. |
| 13 | F7 · 같은 2×2 자리 → 회색 묶음 | 실제 용돈 기입장 프로그램도 같은 네 역할로 파일을 나누었고, 필요한 파일을 더 두기도 합니다. |
| 마무리 | 이해 확인 → 한 문장 정리 | (아래 3절) |

### 강사 설명 대본

**단계 1 — F1**
> “앞 장면에서 todo에게 ‘목록을 다섯 개 보여 줘’라고 부탁했죠. 이 부탁 하나를 들어주려면 프로그램은 무엇을 해야 할까요?” (학습자 답을 듣고 말풍선을 하나씩 가리키며) “할 일 기록이 어떤 모양인지 알아야 하고, 저장해 둔 기록을 꺼내 와야 하고, 다섯 개를 골라야 하고, 결과를 화면에 보여 줘야 합니다. 부탁은 하나인데 일은 여러 종류예요.”

**단계 2 — F2 전체**
> “이 네 가지 일은 성격이 서로 다릅니다. 그래서 프로그램을 만들 때 이것을 네 가지 역할로 나누어 생각하곤 해요. 하나씩 이름을 붙여 보겠습니다. 이 그림은 순서가 아니라 ‘누가 무엇을 맡는가’를 나타냅니다.”

**단계 3 — Model**
> “할 일 하나는 ‘내용’과 ‘완료했는지’로 이루어져 있다고 정해 둡시다. 이렇게 기록이 어떤 항목으로 이루어지는지, 기록의 모양을 정하는 부분을 **Model**이라고 부릅니다.”

**단계 4 — Repository**
> “기록은 프로그램을 꺼도 남아 있어야 하니까 어딘가에 저장해야 합니다. 저장해 둔 기록을 읽어 오고 새 기록을 저장하는 일을 맡는 부분이 **Repository**예요. 우리말로 ‘저장소’라고도 합니다.”

**단계 5 — Service**
> “꺼내 온 기록 중에서 다섯 개를 고르는 것처럼, 사용자가 요청한 일을 실제로 처리하는 부분이 **Service**입니다.”

**단계 6 — CLI**
> “마지막은 명령을 받고 결과를 보여 주는 부분, **CLI**입니다. 앞 장면에서 CLI는 ‘글자로 부탁하는 방법’이었죠. 여기서는 그렇게 들어온 명령을 받아 알아듣고, 처리한 결과를 화면에 보여 주는 프로그램 안의 부분을 말합니다. 앞에서 본 argparse도 바로 이 부분에서 쓰여요.”

**단계 7 — F3**
> “왜 이렇게 나눌까요? 저장하는 파일 형식을 바꾸고 싶다면 어디부터 볼까요?” (답: Repository) “그럼 목록을 표 모양으로 보여 주고 싶다면요?” (답: CLI) “이렇게 역할이 나뉘어 있으면 무엇을 바꿀 때 어디부터 보면 될지 찾기 쉽습니다. ‘거기만 고치면 끝’이라는 뜻은 아니고, ‘어디서부터 시작할지’가 분명해진다는 뜻이에요.”

**단계 8 — F4 파일 네 장**
> “역할을 나눴다면, 코드도 역할에 따라 여러 파일에 나누어 담을 수 있습니다. 같은 자리에 파일 이름이 붙은 것을 보세요. 기록의 모양은 models.py, 읽고 저장하기는 repository.py, 이런 식입니다. 파일 이름은 만드는 사람이 정하는 것이지 꼭 이렇게 지어야 하는 규칙은 아닙니다.”

**단계 9 — F4 파일 한 장**
> “이렇게 Python 코드를 담은 파일 하나를 **모듈**이라고 부릅니다. models.py도 모듈, cli.py도 모듈이에요.”

**단계 10 — F4 폴더 경계**
> “관련 있는 모듈을 하나의 이름 아래에 묶은 것을 **패키지**라고 합니다. 여기서는 todo라는 폴더가 네 모듈을 묶고 있으니 todo가 패키지예요. 파일 하나가 모듈, 그 묶음이 패키지입니다.”

**단계 11 — F5**
> “파일을 나눴으니 서로 도와야겠죠. 예를 들어 cli.py가 목록을 고르는 일을 services.py에 맡기려면, services.py의 기능을 가져와야 합니다. 이때 쓰는 것이 **import**예요. import는 ‘다른 모듈의 기능을 가져다 쓰겠다’는 표시입니다. 이 선은 가져다 쓰는 관계이지 실행되는 순서가 아닙니다.”

**단계 12 — F6**
> “이제 앞 장면의 명령으로 돌아가 봅시다. python -m todo를 입력하면 Python은 todo 패키지를 찾고, 그 안의 **`__main__.py`** 라는 파일에서 시작합니다. 패키지를 실행할 때의 시작 파일이에요. 이 예시에서는 거기서 CLI 부분으로 일을 넘기고, CLI 부분이 list --limit 5를 받아 알아듣습니다.”

**단계 13 — F7**
> “이건 가상의 예였는데, 실제 프로그램도 그럴까요? 용돈 기입장 프로그램 ledger를 보면 같은 자리에 models.py, repository.py, services.py, cli.py가 있고, `__main__.py`도 있어서 python -m ledger로 실행합니다. 그런데 옆을 보면 errors.py, validators.py처럼 다른 파일도 있죠. 실제 프로젝트는 같은 네 역할을 기준으로 하면서도, 필요한 파일을 더 두기도 합니다.”

## 4. 강사 노트 — 정확성 경계

### 설계 선택과 Python 규칙의 구분

학습자가 “꼭 이렇게 해야 하나요?”라고 물을 때 이 표로 답한다.

| 구분 | 내용 |
| --- | --- |
| **설계 선택** (프로젝트마다 다름) | 역할을 네 가지로 나누기, 역할 이름(Model·Repository·Service·CLI), 파일 이름(`models.py` 등), 역할 하나를 파일 하나에 담기 |
| **Python 규칙** | `.py` 파일은 모듈로 import할 수 있다, 모듈을 패키지로 묶을 수 있다, import로 다른 모듈의 이름·기능을 가져온다, `python -m 패키지`는 그 패키지의 `__main__.py`를 실행한다 |

- 역할과 파일은 일대일 규칙이 아니다. 작은 프로그램은 파일 하나에 모두 둘 수도 있고, 한 역할을 여러 파일로 나눌 수도 있다.
- ‘먼저 볼 곳’은 ‘거기만 고치면 된다’가 아니다. 실제 ledger에서도 CSV 가져오기·내보내기 처리는 `services.py`에 있다. 파일 형식과 관련된 변경이 Repository 밖에도 걸칠 수 있다는 예로 쓸 수 있다.
- F1·F2에는 순서를 넣지 않았다. 실제로는 CLI가 명령을 받아 Service에 넘기는 처리 흐름이 있지만, 이 장면에서는 흐름을 추적하지 않는다.
- **CLI의 두 뜻:** Scene 01의 CLI는 ‘글자로 부탁하는 조작 방식’, Scene 02의 CLI는 ‘그렇게 들어온 명령을 받고 결과를 보여 주는 프로그램의 부분’이다. 단계 6에서 반드시 짚는다.
- **Model과 클래스:** 실제 ledger의 Model은 클래스로 구현되어 있다. 이 장면에서는 클래스 문법을 다루지 않는다. 공식 미션의 ‘클래스·모듈 구조화’ 요구는 교육생의 실제 구현과 검증으로 별도 확인하며, 이 장면을 들은 것을 구현 완료로 보지 않는다.
- **모듈의 범위:** ‘코드 파일 하나 = 모듈’은 입문용 설명이다. argparse 같은 표준 라이브러리 모듈, 파일이 아닌 내장·확장 모듈도 있다.
- **패키지와 `__init__.py`:** 일반 패키지에는 `__init__.py`가 있지만 namespace package처럼 없는 경우도 있다. 모든 패키지가 `__main__.py`를 가져 실행 가능한 것은 아니다.
- **import와 호출:** import는 가져오는 것이고, 가져온 기능을 실제로 실행(호출)하는 것과 구분된다. F5의 선은 실행 순서가 아니다.
- **todo와 ledger의 구분:** 단계 1~12는 가상 todo, 단계 13만 실제 ledger다. F7 상단 라벨로 전환을 명시하고, 다른 단계에서 ledger 파일을 섞지 않는다.

## 5. 선택형 심화 목록

1. **`__init__.py`** — 일반 패키지의 초기화 파일. 패키지를 import할 때 먼저 실행된다. ledger의 것은 설명 한 줄뿐이다. namespace package는 강사 노트 수준으로만.
2. **import의 두 형태** — `import 모듈`과 `from 모듈 import 이름`
3. **표준 라이브러리 모듈** — argparse, json, csv도 모듈이다. 내가 만든 모듈과 같은 방식으로 import한다.
4. **보조 진입점** — ledger의 `main.py`처럼 `python main.py`로도 실행할 수 있게 하는 방식과 `python -m ledger`의 차이
5. **역할 사이 의존 방향** — 설계 문서의 의도와 실제 import가 다를 수 있다. 의존도 분석은 기본 강의에서 다루지 않는다.
6. **다른 구조 사례** — 파일 하나짜리 프로그램, 역할을 하위 폴더로 나누는 프로그램
7. **기존 자료** — [기존 Scene 02 원고](../../scene-02/script.md), [선수·심화 03-A](../../scene-03a/script.md)(클래스·객체 복습)
