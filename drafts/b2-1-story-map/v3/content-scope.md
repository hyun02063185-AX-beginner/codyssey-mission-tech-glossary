## 정확성 경계와 근거

- **실제 사례:** `m03-pocket-money-ledger` `d14e812ca1e1caaa88fd23fae7029d95d560c2d9`의 `ledger/` 9개 모듈과 패키지 밖 `main.py`를 정적 확인했다. `models.py`=기록 구조, `repository.py`=JSONL 파일 읽기·저장, `services.py`=업무 처리(CSV 가져오기·내보내기 포함), `cli.py`=argparse 규칙·입출력·결과 형식화, `__main__.py`=`python -m ledger` 진입점. `list --limit`(정수)가 실제로 정의되어 있다. 학습자 자료에는 코드 줄이나 함수 내부를 넣지 않는다.
- **설계 선택과 Python 규칙을 구분한다.** 네 역할·역할 이름·파일 이름·역할과 파일의 대응은 이 사례의 설계 선택이다. 모듈 import, 패키지, `python -m 패키지`→`__main__.py` 실행은 Python 규칙이다. 앞의 것을 Python 필수 규칙처럼 설명하지 않는다.
- **‘먼저 볼 곳’은 ‘거기만 고친다’가 아니다.** 실제 ledger에서도 CSV 처리는 `services.py`에 있어 형식 관련 변경이 Repository 밖에 걸칠 수 있다.
- **해석 주체:** Python은 `-m todo`까지 처리하고 그 뒤의 글자를 프로그램에 넘긴다. argparse는 프로그램이 정한 규칙으로 해석을 돕고 데이터를 처리하지 않는다. argparse는 모든 CLI의 필수 도구가 아니다. `python` 실행 파일을 찾는 것은 셸이다(강사 노트).
- **모듈·패키지 단순화:** ‘코드 파일 하나 = 모듈’은 입문 모델이다. 내장·확장 모듈, `__init__.py`가 없는 namespace package, `__main__.py`가 없는 패키지가 있다는 사실은 강사 노트에 보존한다.
- **CLI의 두 뜻:** Scene 01의 조작 방식과 Scene 02의 프로그램 부분을 구분해 설명한다.
- **가상과 실제:** todo는 가상 예시, ledger는 실제 사례다. 실행 결과를 지어내지 않는다.
- Generator·JSONL의 메모리 효과, Type Hint의 런타임 비강제, Decorator의 처리 범위를 단순화로 왜곡하지 않는다.
- 공식 목표 대응은 기존 v2에서 추적한 상태를 유지한다. 공식 원문·최신 평가 기준은 새로 대조하지 않았다.
