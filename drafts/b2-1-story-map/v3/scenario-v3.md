## 1. 교육 목표와 진행 방식

**목표:** Python 입문자가 CLI 프로그램의 주요 개념이 **무엇이고, 왜 필요하며, 어떤 관계로 사용되는지** 자신의 말로 설명하도록 돕는다. 함수 내부가 아니라 **프로그램의 큰 역할과 모듈 구조**를 중심으로 한다.

**진행 방식:** 강사 주도 대면 설명. 강사는 큰 구조도·순서도를 가리키며 말로 설명하고, 화면에는 핵심 질문·그림·현재 개념 한 문장만 둔다. 세부 기준은 [screen-guidelines.md](screen-guidelines.md).

**선수 조건:** 터미널에서 명령을 입력해 본 경험. 이전 미션에서 함수와 클래스를 학습했다는 것을 전제로 하지만, **실제 숙련 여부를 가정하지 않으며 그 학습을 공식 미션 완료로 취급하지 않는다.** 이 강의의 기본 설명은 함수·클래스 문법 없이 이해할 수 있게 구성한다.

**필수 학습 목표로 삼지 않는 것:** 함수 호출 순서 추적, 함수 내부 코드 분석, 클래스·객체·self·`__init__()` 문법 재교육, 교육생 소스코드 리뷰, 코드 줄 번호 찾기, 특정 프로젝트 구현 구조를 유일한 정답으로 설명하기.

**예상 시간 (모두 시범 수업 전 추정):**

| 장면 | 설명 | 질문·확인 | 합계 |
| --- | --- | --- | --- |
| 01 | 7~9분 | 3~5분 | 약 10~14분 |
| 02 | 11~14분 | 4~6분 | 약 15~20분 |
| 03~08 | 장면당 6~10분 | 장면당 3~5분 | 장면당 약 9~15분 |
| **전체** | | | **약 80~125분** |

3~5분에 억지로 맞추지 않았다. 전체가 한 번의 강의로는 길 수 있으므로 나누어 진행할지는 Owner 결정 사항이다(§9).

자산의 역할 구분은 [학습 운영 정책 §3](../../../docs/mission-guides/learning-operation-policy.md)을 따른다. 스토리는 역할과 흐름, 개념지도는 관계, 용어사전은 정확한 정의와 확장, 학습가이드는 실행·검증을 맡는다. 서비스 사이 이동은 이번에도 **미구현**이다.

## 2. Scene 01 — 명령 한 줄로 일을 부탁하기

- **핵심 질문:** 명령 한 줄로 프로그램에 어떻게 일을 부탁할까?
- **예시:** 가상 todo의 `python -m todo list --limit 5`
- **흐름:** GUI·CLI 비교(F1) → 명령 네 부분: 실행 도구·실행할 대상·할 일·조건(F2) → 누가 읽나: Python은 `-m todo`, todo 프로그램은 `list --limit 5`(F3) → argparse는 글자를 규칙대로 알아듣게 도움, 실제 일은 하지 않음(F4) → 확인·적용(`--limit 3`)·정리
- **한 문장:** 명령 한 줄은 실행 도구·실행할 대상·할 일·조건으로 나뉘고, 앞부분은 Python이, 뒷부분은 프로그램이 argparse의 도움을 받아 알아듣습니다.
- 원고: [scene-01/storyboard.md](scene-01/storyboard.md)

## 3. Scene 02 — 역할을 나누고 파일로 묶기

- **핵심 질문:** 프로그램은 왜 역할을 나누고 여러 파일로 만들까?
- **예시:** Scene 01의 가상 todo를 끝까지 사용. 실제 용돈 기입장 ledger는 개념 설명 후 ‘실제 사례’ 한 단계로만.
- **흐름:** 부탁 하나 뒤의 여러 일(F1) → 네 역할 Model·Repository·Service·CLI(F2) → 바꿀 때 먼저 볼 곳(F3) → 역할별 파일·모듈·패키지(F4) → import(F5) → `python -m todo`와 `__main__.py`(F6) → 실제 ledger 사례(F7) → 확인·정리
- **한 문장:** 프로그램의 일을 기록의 모양·읽고 저장하기·요청 처리·명령과 결과 보여 주기로 나누고, 역할별 코드를 모듈로, 관련 모듈을 패키지로 묶어 import로 함께 사용합니다.
- 원고: [scene-02/storyboard.md](scene-02/storyboard.md)

## 4. 예시 사용 원칙

- Scene 01·02의 기본 설명은 **가상 todo 하나**로 이어 간다. 같은 명령 `python -m todo list --limit 5`가 Scene 01에서는 ‘부탁의 모양’으로, Scene 02에서는 ‘그 부탁을 나누어 맡는 역할’과 ‘시작 파일’로 이어진다.
- 실제 ledger는 개념을 이해한 뒤 **실제 사례**로 제시한다. 화면에 ‘가상 예시’/‘실제 사례’ 라벨을 붙여 섞이지 않게 한다.
- 예시 전환은 장면 경계나 ‘실제 사례’ 단계에서 **한 번만** 하고, 한 장면 안에서 반복해 오가지 않는다.
- Scene 03~08의 기본 예시(가상 todo 유지 또는 용돈 기입장 개념 예시로 전환)는 Owner 결정 사항이다(§9). 요약·CSV·합계처럼 금액 기록이 자연스러운 개념이 많아, **Scene 03부터 용돈 기입장 개념 예시로 한 번 전환**하는 안을 권장한다.
- **v3.4 적용:** Scene 03·04는 권장안대로 **용돈 기입장 학습용 가상 기록**(4개, 합계 14,500원)을 쓴다. Scene 02 마지막의 실제 ledger 사례에서 한 번 전환하며, 화면에 ‘학습용 가상 기록’ 라벨을 붙인다. Scene 04의 실제 ledger 연결은 한 단계(`#4-11`)뿐이다. Owner 확인 대상이다.

### Scene 05 — 하나씩 처리하기: Generator와 yield

| 항목 | 기준 |
| --- | --- |
| 핵심 질문 | 많은 기록을 한꺼번에 모으지 않고, 필요할 때 하나씩 처리하려면 어떻게 할까? |
| 반드시 전달할 개념 | **Generator와 yield를 먼저 설명한다.** 모두 모아 처리하기와 필요할 때 하나씩 처리하기의 차이. Generator는 값을 하나씩 만들어 건네는 방식이다. yield는 값 하나를 건네고 잠시 멈췄다가, 다음 값을 요청받으면 이어서 진행한다. 실제 메모리 효과는 받은 값을 어떻게 쓰고 보관하느냐에 달려 있다. |
| 큰 그림 | **비교:** 모두 담은 바구니 vs 하나씩 지나가는 통로. **흐름(별도 그림):** 값 건넴 → 멈춤 → 다음 요청 → 이어서. 두 그림을 한 화면에 합치지 않는다. |
| 선택형 심화 | **Iterable·Iterator** 관계, `iter()`/`next()`, for 문이 값을 꺼내는 방식, 소진과 재생성, 파일 열림 수명, 메모리 측정. **기존 Scene 05 원고·데모·SVG와 개념지도 관계를 삭제하거나 수정하지 않고** 심화 자료로 보존한다. |
| 입문자 혼동 위험 | Generator를 쓰면 무조건 메모리가 절약된다고 오해 · yield를 return과 같다고 오해 · 다 쓴 Generator를 다시 처음부터 쓸 수 있다고 오해 · 결과를 모두 리스트로 모으면 다시 전부 보관한다는 점을 놓침 |
| 이전 장면과 연결 | Scene 04의 JSONL ‘한 줄에 기록 하나’ → 기록을 하나씩 처리하기. 실제 사례 단계에서 ledger의 저장소가 기록을 하나씩 읽어 건네는 데 Generator를 쓴다는 것을 보여 줄 수 있다. |
| 공식 목표 대응 | 목표 3. v2의 Owner 지정 입문 개념 ‘Iterable·Iterator·Generator의 관계’ 중 Iterable·Iterator가 심화로 이동했다(§9). |

### Scene 06 — 공통 처리 붙이기: Decorator

| 항목 | 기준 |
| --- | --- |
| 핵심 질문 | 여러 기능에 같은 부가 처리를 반복 없이 붙이려면 어떻게 할까? |
| 반드시 전달할 개념 | 로그 남기기·오류 처리·시간 측정처럼 여러 기능에 반복되는 공통 처리가 있다. Decorator는 원래 기능을 감싸 공통 처리를 붙이는 방법이다. 붙여 둔 처리만 할 뿐 만능 오류 해결 장치가 아니다. |
| 큰 그림 | **비교:** 붙이기 전(기능마다 같은 처리 반복) vs 붙인 후(공통 처리를 한 곳에). **구조:** 원래 기능 상자를 감싼 테두리, 테두리 앞뒤의 처리 표식. 오류 처리는 ‘정해 둔 오류만’이라는 경계를 따로 표시한다. |
| 선택형 심화 | wrapper, `@` 표기, 적용 시점, `functools.wraps`, 처리하지 않은 오류의 전달 |
| 입문자 혼동 위험 | 모든 오류가 자동으로 해결된다고 오해 · Decorator가 원래 기능의 내용을 바꾼다고 오해 · `@`를 주석으로 오해 |
| 이전 장면과 연결 | Scene 02의 역할 분리처럼, 공통 처리도 따로 모아 관리한다. |
| 공식 목표 대응 | 목표 4. ledger에는 **예외 처리 Decorator만** 있다. 로그·시간 측정은 일반 예시로만 설명하고 ledger에 구현됐다고 하지 않는다. |

### Scene 08 — 한눈에 연결하기: 핵심 개념지도

### Scene 03~08 공통 적용 기준

1. 장면마다 핵심 질문 하나. 그림 하나에 개념 하나. 그림의 종류(흐름·구조·비교·관계)를 명시하고, 실행 순서가 아닌 그림에는 번호·순서 화살표를 넣지 않는다.
2. 단계마다 화면 한 문장. 일상 설명을 먼저, 기술 용어를 뒤에 붙인다. 한 단계에 새 용어는 하나.
3. 확인 질문(기본·적용)과 한 문장 정리는 설명을 모두 마친 뒤. 흔한 오답과 강사 대응을 함께 작성한다.
4. 함수 내부 코드·호출 추적·줄 번호 없이 이해할 수 있어야 한다. 코드와 실행은 학습가이드·선택형 심화로 보낸다.
5. 예외·구현 한계는 사실 그대로 강사 노트나 심화로 옮긴다. 단순화한 문장이 사실을 왜곡하지 않는지 확인한다.
6. ‘설계 선택’과 ‘Python 규칙’을 구분해 말한다.
7. 가상 예시와 실제 사례를 라벨로 구분하고, 실제 사례는 저장소 기준 코드와 대조한다. 없는 구현을 있다고 하지 않는다.
8. 예상 시간은 질문·답 포함 추정으로 적고 시범 수업 전임을 밝힌다.
9. 공식 미션 요구를 축소하거나 완료된 것처럼 쓰지 않는다. 기존 자료는 삭제하지 않고 심화로 보존한다.

## 7. 수업 진입·복습·실습 연결

강의 시작 시 강사는 공식 미션의 구현 조건과 이 강의의 개념 이해 목표를 구분해 알린다. 01→02는 같은 todo 명령으로 이어지고, 02→03은 ‘Service가 처리하는 일의 종류’, 03→04는 ‘바꾼 기록을 남기기’, 04→05는 ‘한 줄씩 적힌 기록을 하나씩 처리하기’, 06→07은 ‘공통 처리와 값 확인’으로 이어진다. 08에서 전체 관계를 회수한다.

첫 실습 진입 활동은 **말로 설명하기**다. 자기 프로그램의 실행 명령을 네 부분으로 나누어 말해 보고, ‘저장 방식을 바꾼다면 어느 역할부터 볼까’를 고른다. 소스코드 제출·줄 번호 찾기·호출 추적은 기본 활동이 아니다. 실제 실행·구현은 기존 [학습가이드](../../../content/mission-guides/main-m03/scenario-v1.1.md)를 따른다.
