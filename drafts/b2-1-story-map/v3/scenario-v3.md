# B2-1 Story v3 — 개념 중심 대면 강의 시나리오

2026-10-23 · **Owner 검토용 초안** · 기준 `b7207cd90414fb50180026e17d8cd619ac14ce9f`

이번 범위는 8장면의 교육 설계와 Scene 01·02 독립 HTML 시안이다. 나머지 장면의 제작, React 통합, 공개 경로 변경은 후속 승인 대상이다. 기존 v2의 승인 상태·원고·그림·지도 후보를 변경하거나 대체하지 않는다.

## 교육 목표와 진행 방식

Python 입문자가 CLI 프로그램의 주요 개념이 **왜 필요하고, 어디에 쓰이며, 어떻게 연결되는지** 자신의 말로 설명하도록 돕는다. 강사 주도 대면 설명을 기본으로 하고 한 장면은 3~5분, 전체 핵심 설명은 약 24~40분을 계획한다. 실제 시간과 학습 효과는 시범 수업 전 미검증이다.

최소 선수 경험은 터미널에서 명령을 입력해 본 것이다. 함수·클래스 문법은 이 강의에서 복습하지 않는다. 클래스 구조화 요구가 나오면 선수 학습 자료로 연결하고 미션 구현·검증을 별도로 확인한다. 개념을 설명할 수 있는 것과 공식 미션을 완료한 것은 다르다.

스토리는 역할과 흐름을, 개념지도는 관계를, 용어사전은 정확한 정의와 확장을, 기존 학습가이드는 실행·검증을 맡는다. 이번 시안에는 서비스 간 이동을 구현하지 않는다. 강사는 수업에서 기존 자료를 별도 열어 사용법을 안내한다.

## 8개 장면 설계

모든 장면은 질문 하나, 핵심 그림 하나, 설명 최대 세 가지, 확인 질문 1~2개, 한 문장 정리, 선택 심화로 구성한다. 표의 화살표는 별도 표시가 없는 한 **교육 설명 순서**이며 Python 함수 호출 추적이 아니다.

### Scene 01 — CLI·명령어·옵션·argparse (4~5분)

- **질문:** 명령 한 줄은 누구에게 어떤 일을 부탁하는 말일까?
- **그림:** `python` / `-m todo` / `list` / `--limit 5` 네 블록. 이어 같은 명령의 프로그램 부분 → argparse → 해석한 요청을 보여 준다.
- **핵심 3개:** CLI는 문자, GUI는 버튼·메뉴로 요청한다. Python은 `-m todo`로 실행 대상을 고른다. 이 예시의 argparse는 프로그램이 정한 규칙으로 하위 명령과 옵션을 해석한다.
- **확인:** `--limit 5`의 옵션과 값은 무엇인가? `-m`도 todo의 argparse가 해석하는가? (아니요, Python의 옵션이다.)
- **한 문장:** 명령은 실행 도구·실행 대상·할 일·조건으로 나누어 읽을 수 있다.
- **선택 심화:** 짧은/긴 옵션, 도움말의 위치, argparse 규칙 코드와 입력 오류. [`storyboard.md`](scene-01/storyboard.md)

### Scene 02 — 모듈·패키지·큰 역할 구분 (4~5분)

- **질문:** 프로그램을 여러 파일로 나누는 이유는 무엇일까?
- **그림:** 명령 해석 / 요청 처리 / 읽기·저장 / 결과 표시의 네 역할 블록. 이어 관련 `.py` 파일을 감싼 패키지 경계를 보여 준다. 역할 그림은 호출·import 그래프가 아니다.
- **핵심 3개:** 역할을 구분하면 수정할 위치를 찾기 쉽다. 입문 예시의 모듈은 Python 코드 파일, 패키지는 관련 모듈의 묶음이다. import로 다른 모듈의 이름·기능을 사용하며 `__main__.py`와 `__init__.py`는 서로 다른 파일이다.
- **확인:** 저장 방식을 바꾸면 어느 역할을 먼저 볼까? 패키지 실행 진입점과 일반 패키지 초기화 파일은 각각 무엇인가?
- **한 문장:** 파일을 나누는 목적은 역할을 알아보고 함께 사용하기 쉽게 만드는 것이다.
- **선택 심화:** 내장·확장 모듈, namespace package, import와 호출의 차이. 클래스 문법은 별도 선수 학습. [`storyboard.md`](scene-02/storyboard.md)

### Scene 03 — CRUD·검색·요약 (3~4분)

- **질문:** 기록을 다루는 기본 동작은 어떻게 다를까?
- **그림:** 가운데 기록 묶음에 추가(Create)·조회(Read)·수정(Update)·삭제(Delete) 네 동작을 배치. 조회에서 검색(조건으로 고름)·요약(계산해 묶음) 카드를 연결한다. 이것은 동작의 분류이며 CRUD를 순서대로 실행한다는 뜻이 아니다.
- **핵심 3개:** CRUD는 데이터 처리의 기본 구분이다. 검색은 조건에 맞는 기록을 고르고 요약은 합계 같은 값을 계산한다. 조회·검색·요약은 원본 변경과 다르며 메모리 변경은 파일 반영과 구분한다.
- **확인:** 식비만 고르는 것은 검색인가 요약인가? 한 달 지출 합계는 원본을 지우는가?
- **한 문장:** 바꾸기·찾기·계산하기를 구분하면 기능의 목적이 보인다.
- **선택 심화:** ID와 위치, 안전한 수정·삭제, 기존 Scene 03-B 구현 추적. 기존 03-A 문법 강의는 v3 메인에서 제거한다.

### Scene 04 — 메모리·파일·JSON/JSONL/CSV (4~5분)

- **질문:** 프로그램을 종료해도 기록이 남으려면 무엇이 필요할까?
- **그림:** 실행 중 메모리 ↔ 읽기/저장 ↔ 파일. 파일 아래 JSON(문서 하나)·JSONL(줄마다 JSON 값)·CSV(행과 열) 형태를 나란히 보여 준다. 형식은 처리 단계가 아니다.
- **핵심 3개:** 메모리의 값과 저장된 파일은 다르다. 형식은 기록을 담는 규칙이며 JSONL의 각 줄은 JSON 값 하나다. CSV는 표 교환에 쓰기 좋지만 읽은 값의 형 변환·검증은 별도로 필요하다.
- **확인:** 메모리에서 수정한 값이 항상 파일에도 반영될까? JSONL이라는 이름만으로 메모리 사용량이 줄까?
- **한 문장:** 파일 저장은 기록을 남기는 일이고 형식은 남길 모양을 정하는 일이다.
- **선택 심화:** 경로·인코딩·덮어쓰기, CSV 인용·개행, 수정·삭제 재작성, 임시 파일 교체. JSONL은 자동 메모리 절약 기능이 아니다.

### Scene 05 — Iterable·Iterator·Generator·yield (4~5분)

- **질문:** 데이터를 필요할 때 하나씩 꺼낸다는 것은 무슨 뜻일까?
- **그림:** Iterable(반복해서 꺼낼 수 있는 대상) → Iterator(다음 값을 꺼내는 상태 있는 도구), Generator는 Iterator의 한 종류라는 포함 경계. 옆의 작은 `yield` 표식은 값 전달·일시정지·재개를 보여 준다.
- **핵심 3개:** Iterable에서 Iterator를 얻어 차례로 소비한다. Iterator는 현재 진행 상태를 가지며 소진될 수 있다. Generator 함수는 호출하면 Generator를 만들고, 소비 중 `yield`에서 값을 건네고 멈췄다가 재개한다.
- **확인:** Generator로 읽어도 모든 값을 리스트에 모으면 저장 공간이 필요할까? Iterator가 끝난 뒤 저절로 처음부터 다시 나올까?
- **한 문장:** Generator의 장점은 필요할 때 값을 만드는 방식이며 전체 메모리 효과는 소비 방식에 달려 있다.
- **선택 심화:** `iter`/`next`, 소진과 재생성, 파일 수명, 소비 방식 비교. 긴 코드와 측정 결과는 메인에서 제외한다.

### Scene 06 — Decorator와 공통 처리 (3~5분)

- **질문:** 여러 기능에 같은 부가 처리를 붙이려면 어떻게 할까?
- **그림:** 공통 처리 테두리 안에 원래 기능을 놓고 앞뒤에 로그·시간 측정 표식을 둔다. 예외 처리는 ‘지정한 오류만 처리’라는 별도 경계를 표시한다. wrapper를 쓰는 함수 Decorator의 개념 예시다.
- **핵심 3개:** 공통 처리를 모으면 반복을 줄일 수 있다. Decorator는 함수 등의 동작을 확장하거나 바꾸는 데 쓰이며 여기서는 감싸는 예를 본다. 어떤 로그를 남기고 어떤 예외를 처리할지는 구현한 범위로 제한된다.
- **확인:** Decorator가 붙으면 모든 오류가 해결될까? 로그 기록과 원래 기능은 같은 책임일까?
- **한 문장:** Decorator는 정해 둔 공통 처리를 붙이는 수단이며 만능 오류 해결 장치가 아니다.
- **선택 심화:** wrapper·적용 시점·`functools.wraps`·예외 전파. `ledger`는 예외 처리 사례만 있으며 로그·시간 측정 구현으로 소개하지 않는다.

### Scene 07 — Type Hint와 실제 값 검증 (3~4분)

- **질문:** 값의 형을 적어 두면 잘못된 입력도 막아 줄까?
- **그림:** ‘어떤 형을 기대하는가’ 안내판(Type Hint)과 ‘실제 값이 규칙에 맞는가’ 검사 문을 나란히 배치. 입력 변환은 검사와도 다른 작은 영역으로 둔다.
- **핵심 3개:** Type Hint는 기대하는 입력·출력 형을 사람과 도구에 알린다. Python은 일반적으로 힌트만으로 런타임 값을 강제 검사하지 않는다. 정수로 바꾸기와 양수인지 확인하기도 다른 일이다.
- **확인:** `int`라고 적으면 음수가 자동 거부될까? 숫자 문자열을 정수로 바꾼 뒤에도 양수 검사가 필요할까?
- **한 문장:** Type Hint는 기대를 표시하고 검증 코드는 실제 값이 규칙에 맞는지 판단한다.
- **선택 심화:** 정적 검사기, `type=int`, 기본값·None, 타입과 업무 규칙의 구분. 매개변수 문법 복습은 별도 선수 자료다.

### Scene 08 — 핵심 개념지도 (3~5분)

- **질문:** 지금 배운 개념은 한 프로그램 안에서 어떤 역할로 연결될까?
- **그림:** 실행·CLI / 모듈·패키지 / 데이터 동작 / 저장·형식 / 반복·Generator / Decorator / Type Hint·검증의 **7개 대표 영역**. 첫 화면은 관계선 없이 영역을 보여 주고 선택한 관계 하나만 종류·방향·범위와 함께 설명한다.
- **핵심 3개:** 지도는 실행 순서표가 아니라 개념의 관계를 보여 준다. 포함·종류·사용·역할 관계를 구분한다. 모르는 개념은 심화 자료·사전에서 확인하고 해당 장면으로 돌아온다.
- **확인:** 파일 형식과 Generator를 쓰는 방식은 같은가? 모듈 사이 연결이 함수 실행 순서와 항상 같은가?
- **한 문장:** 역할과 관계를 연결해 설명하면 세부 코드 없이 프로그램의 큰 구조를 말할 수 있다.
- **선택 심화:** 기존 [후보 지도](../scene-08/candidate-map.json)의 **45노드·24의미관계·10비교카드**, 기존 [탐색 시안](../scene-08/concept-map-preview.html)을 그대로 보존한다. v3 기본 영역은 교육용 새 묶음 제안이며 기존 후보의 7영역 이름/노드ID를 수정하지 않는다. `sceneRefs`와 03-A 자료도 역사적 참조로 유지한다. v3 재매핑·실제 왕복은 후속 검토 대상이다.

## 수업 진입·복습·실습 연결

시작 시 강사는 공식 미션 구현 조건과 이 강의의 개념 이해 목표를 구분해 알린다. 01→02로 진입하고, 03→04에서 ‘데이터 변경과 저장’, 04→05에서 ‘형식과 소비 방식’, 06→07에서 ‘처리와 표시’를 비교한다. 08에서는 CLI→모듈→저장 및 Generator→Iterator를 관계의 종류를 말하며 시연한다. 개념지도 전체를 한 번에 읽지 않는다.

첫 실습은 자기 프로그램 명령을 실행 도구·대상·기능·조건으로 말해 보고, 저장 방식을 바꿀 때 찾을 역할을 고르는 활동이다. 소스코드 제출·줄 번호 찾기·호출 추적은 기본 활동이 아니다. 실제 실행·구현은 기존 [학습가이드](../../../content/mission-guides/main-m03/scenario-v1.1.md)를 참고한다.
