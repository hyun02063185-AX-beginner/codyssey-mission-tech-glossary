## 1. 핵심 시각화 세 가지

| 그림 | 질문 | 구성 | 관계의 종류 |
| --- | --- | --- | --- |
| **A** 메모리에서 파일로 | 프로그램을 끝냈다가 다시 실행하면 데이터는 어디에 남아 있을까? | 저장 위치 범례 · '실행 1 / 실행 2' 띠 · 여섯 단계 머리글(실행 1 시작 → 메모리에 거래 추가 → 파일에 저장 → 프로그램 종료 → 실행 2 파일 읽기 → 거래 목록 복원) · **위 줄 = 저장하지 않는 프로그램**(`memory_only.py`), **아래 줄 = 파일에 저장하는 프로그램**(`file_crud.py`). 줄마다 **메모리 칸과 파일 칸을 따로** 두고, 각 칸에 그 단계 뒤의 거래(id)를 칩으로 · 두 번의 실제 실행 결과 | 데이터 상태 비교. **화살표 없음**(시간은 왼쪽 → 오른쪽 머리글로만) |
| **B** 세 가지 파일 형식 | 같은 거래 3건이 JSON·JSONL·CSV에서 어떤 구조가 될까? | 형식별 카드 3장(실제 파일 내용 + 줄 번호) · **같은 거래(id 2)를 세 형식에서 강조**(JSON 5줄 / JSONL 1줄 / CSV 1행) · 구조 설명 · 'Python으로 읽으면'(읽는 코드, 결과, amount의 종류) · 장점·주의 · '정해진 규칙 없음' 띠 | 같은 데이터의 구조 비교. 선 없음 |
| **C** JSONL 읽기·쓰기 | 파일의 한 줄과 메모리의 딕셔너리는 어떻게 오갈까? 수정·삭제는 파일에 어떻게 반영될까? | **C-1** dict → `json.dumps()` → 한 줄 문자열 → `f.write()`(`"a"`) → 파일 4행 / 파일 각 줄 → `json.loads()` → dict, 실제 결과 2줄(`Extra data`, 리스트에 모으면 4건) · **C-2** `update 2 2500`: 수정 전 파일 → ① `load_all()` → 메모리 리스트(② `update_amount()`로 id 2 값 변경) → ③ `save_all()`이 임시 파일에 → ④ `os.replace()` → 수정 후 파일 · CRUD × 파일 반영 표 · 다음 질문(10만 건) | C-1 = **변환**(청록 선, 번호 없음) / C-2 = **실제 처리 순서**(번호·검은 실선) |

그림의 모든 데이터 상태·파일 내용·읽은 결과·처리 순서·실행 결과는 `_tools/demo/`를 **임시 폴더**에서 실제로 실행하고 호출을 추적(`sys.setprofile`)해 얻었다. `verify_demo.py`가 매번 다시 대조한다.

**예제 선택.** 지시서의 예시 데이터(id 1 식비 8000, id 2 교통 2000, id 3 문구 3000)를 세 형식·그림 A·C 모두에 썼다. Scene 03-B의 4건(수입 포함)과 달리 필드를 `id`·`category`·`amount` 셋으로 줄여 한 줄 JSONL이 휴대전화 폭에 끊기지 않고 들어가게 했다(14단위에서 실측 323px). 새 거래는 C-1에서 id 4 식비 5000(`"a"`로 덧붙임), C-2에서 id 2의 금액 2000 → 2500.

**`file_crud.py`의 구조.** Scene 03-B의 메모리 CRUD 함수(`next_id`·`create`·`read_one`·`update_amount`·`delete`)를 그대로 두고, 앞뒤에 파일 함수(`load_all`·`append_one`·`save_all`)를 붙였다. 03-B와 04의 연결이 코드 모양으로 보이게 하려는 선택이다. 메모리 함수가 파일을 다루지 않는다는 것은 AST로 검사한다.

## 2. 시각 약속 (Scene 01~03-B 약속 유지 + 저장 위치·변환 표시 추가)

| 표현 | 뜻 | 출처 |
| --- | --- | --- |
| 진한 실선 + 채운 검은 화살촉 + 검은 번호 원 | **실제 처리 순서**(C-2, 호출 추적) | Scene 01~03-B와 같음 |
| 파란 **파선** 테두리 + '메모리' 글자 | 프로그램 **실행 중에만** 있는 값 | **이번에 추가** |
| 회색 점선 테두리 + '사라짐' | 실행이 끝나 회수된 메모리 | **이번에 추가** |
| 초록 **굵은 실선** 테두리 + '파일' 글자 | 프로그램 **밖에 남는** 파일 | **이번에 추가** |
| 회색 가는 테두리 + '—' + '파일 없음'류 설명 | 파일이 없음 / 저장하는 코드가 없음 | **이번에 추가** |
| 초록 실선 행 + `+` 글자 | 이 단계에서 새로 생긴 거래·줄 | 03-B 행 표시(추가) 재사용 |
| 갈색 테두리 + 이전 값 취소선 → 새 값 | 값이 바뀐 거래 | 03-B 행 표시(값 변경) 재사용 |
| 파란 굵은 테두리 + '파란 테두리 = 거래 id 2' 설명 | 세 형식에서 **같은 거래**가 있는 줄 | 03-B '읽음' 테두리 모양을 '같은 항목'으로 사용(그림 B에만) |
| **청록** 실선 + 채운 청록 화살촉 + 함수 이름, **번호 없음** | 데이터 **모양 바꾸기**(dict ↔ 한 줄 문자열 ↔ 파일 줄) | **이번에 추가** |

- 색만으로 구분하지 않는다: 메모리/파일은 색 + 테두리 모양(파선/굵은 실선) + 줄 이름표('메모리'·'파일') 또는 칸 안의 글자, 새 거래는 색 + `+` 글자, 값 변경은 색 + 취소선, 같은 거래 강조는 색 + 굵은 테두리 + 설명 글자. 검사기가 메모리 칸의 파선·파일 칸의 실선·새 거래의 `+`·값 변경 칩의 취소선을 확인한다.
- **번호를 붙이지 않은 곳:** 그림 A(실행 순서이지만 두 번의 다른 실행에 걸쳐 있어 호출 번호와 섞이지 않게 머리글로만), 그림 B, C-1(변환), CRUD 표, 다음 질문. 검사기가 이 영역 안에 번호 원이 없는지, 변환 선 16px 안에 번호 원이 없는지 확인한다.
- C-2의 ②는 메모리 안에서 일어나는 변경이라 선 없이 번호 원과 함수 이름만 두었다(①·③·④는 상태 사이를 잇는 선).

## 3. 이전 장면·B3-1과 다른 점

- 03-B 그림 A는 '동작 하나 = 카드 하나'였다. 04 그림 A는 **시간(열) × 저장 위치(줄) 격자**를 두 프로그램에 대해 반복해, 같은 단계에서 두 프로그램의 메모리·파일 칸을 위아래로 비교하게 했다.
- 03-B의 호출 흐름(가로 책임 띠 + `main()` 막대)은 쓰지 않았다. C-2는 **상태 상자 네 개를 ㄷ자로** 잇고, 처리 순서 번호를 상태 사이 선에 붙였다(휴대전화는 세로).
- 03-B·03-A의 return 선, import 선은 이 그림에 없다(범례에서도 뺐다).
- B3-1 네트워크 그림의 배치는 쓰지 않았다. 그리기 도구는 03-B 생성기를 불러 썼고(그 안의 03-A·02·01 도구 포함), 네 생성기 파일은 바꾸지 않았다.

## 4. 노트북용과 휴대전화용

| 항목 | 노트북용 `1280×4052` | 휴대전화용 `360×6490` |
| --- | --- | --- |
| 그림 A | 여섯 열 × (메모리·파일) 두 줄 × 프로그램 두 개, 칩에 '1 · 식비 · 8000' | **단계마다 카드 하나**, 그 안에 왼쪽 = 저장 안 함 / 오른쪽 = 저장함, 위 = 메모리 / 아래 = 파일. 칩 대신 `id 1·2 +3` 글자 |
| 실행 결과(그림 A) | 명령 → 출력 한 줄 | 명령 줄 + 출력. 긴 출력(딕셔너리)은 화면 줄을 나눔(`data-out`은 원래 한 줄) |
| 그림 B | 카드 3장 가로(JSON 330 · JSONL 520 · CSV 350px). 'Python으로 읽으면' 상자를 같은 높이에 맞춰 비교 | 카드 3장 세로. **JSONL은 줄 번호 없이 상자 폭 전체**(한 줄을 끊지 않기 위해) |
| C-1 | dict → str → 파일(가운데) → 읽은 결과(오른쪽) | 세로: dict → str → 파일(줄마다 'n행' 이름표) → 읽은 결과 상자 |
| C-2 | ㄷ자: 수정 전 → 메모리 → 임시 파일 → 수정 후 | 세로 한 줄, 처리 순서 선은 오른쪽 가장자리(상자 제목과 겹치지 않게) |
| 최소 글자 | 16단위 → 960px 칸 12.0px | 14단위 → 328px 칸 12.8px |
| 길이 | 1280px 화면(높이 약 900px)에서 약 4.5화면(A 약 1.2 · B 약 1.0 · C 약 1.3 · CRUD 표·다음 질문·각주 약 0.7) | 390px 화면(칸 358px, 높이 약 800px)에서 약 8.1화면(A 약 2.2 · B 약 2.0 · C 약 2.4 · CRUD 카드·다음 질문·각주 약 1.3) |

휴대전화용이 길다. 그림 A가 여섯 단계 × 두 프로그램을 모두 보여 줘야 '같은 단계에서의 차이'가 보이고, 그림 B가 세 형식의 실제 파일을 모두 담기 때문이다. 웹에서는 **그림 A/B/C 탭(I1)**으로 나누면 한 탭이 약 2~4화면이 된다(C 탭에 CRUD 표·다음 질문 포함).

### 5.2 상호작용 후보

| I4 | **한 줄씩 읽기** | **필요(Scene 05 준비).** `for line in f`가 한 번에 한 줄을 꺼내 `json.loads()`로 dict가 되는 과정 | '다음 줄' 버튼: C-1의 `data-line` k와 `data-read` k를 함께 강조, '지금 메모리에 있는 dict 1개' 표시. 마지막에 '리스트에 모으면 4건'(`data-out`)을 보여 줌. 자동 재생 없음. **Generator·`yield` 용어는 쓰지 않는다**(Scene 05 경계) |
| I5 | **파일 쓰기 모드 선택** | **유용.** `"w"`·`"a"`·`"r"`이 기존 파일에 하는 일을 비교 | 모드 3개를 고르면 `text_io.py`의 **실제 실행 결과**(덮어쓰기 뒤 `문구 3000`만 남음, 덧붙이기 뒤 3줄, 없는 파일 `"r"` → `FileNotFoundError`)만 보여 줌. 임의 입력·실제 파일 쓰기 없음 |
| I6 | **저장 전후 데이터 상태 비교** | **필요.** C-2의 수정 전/임시 파일/수정 후와 C-1의 4행 추가 전후 | '전·후' 토글. 값은 `data-format="c2-before"/"c2-after"`, C-1 1~3행/4행만 사용. ④ 앞에서는 '원본은 아직 그대로'를 표시 |
| I7 | 학습자 데이터 입력(직접 저장) | **보류.** 브라우저에서 실제 파일 쓰기는 학습 목표와 다르고 저장 위치 오해를 키움. 원고의 실습(직접 실행)으로 충분 | 구현하지 않음 |

**저장 오해 방지(필수).** 모든 상호작용은 **화면의 학습용 표시 상태만 바꾼다.** 파일·서버·브라우저 저장소에 기록하지 않으며 "학습용 표시 · 실제 파일에 저장되지 않음"을 늘 보인다. 버튼 이름에 '저장'·'불러오기'를 쓰지 않는다(예: '저장함 보기', '처음으로'). 웹 화면의 상태가 새로고침하면 처음으로 돌아가는 것은 그림 A 위 줄(메모리만)과 같은 현상이라는 점을 짧게 안내할 수 있다.

공통: 키보드 탐색, `aria-pressed`/`aria-live`, `prefers-reduced-motion` 존중, 강조는 색과 함께 굵은 테두리·글자로도 표시.
