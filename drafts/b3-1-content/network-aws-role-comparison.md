# 일반 네트워크 / AWS 네트워크 역할 비교

## 먼저 던지는 질문

사내망에서 하던 일(내부망 나누기, 길 안내, 외부 출입, 서버 방화벽)은 AWS에서 **어떤 부품이 나눠 맡을까요?**

## 한눈에 보기 — 구조도 [작업지시]

![AWS 네트워크 구조도](assets/aws-network-roles.svg)

그림에서 읽을 것은 세 가지입니다.

1. **포함 관계:** Internet Gateway는 VPC와 인터넷 **경계에** 걸쳐 있고, Public Subnet은 VPC 안, EC2는 Subnet 안에 있습니다.
2. **붙는 대상:** Route Table은 **Subnet에 연결**되고, Security Group은 Subnet이 아니라 **EC2의 네트워크 인터페이스**에 적용됩니다(그림에서는 점선이 EC2만 감쌉니다).
3. **두 갈래 접속:** HTTP(실선)는 누구나 접속하는 웹 요청이고, SSH(점선)는 관리자만 쓰는 별도 통로입니다. 같은 문(IGW)으로 들어오지만 **Security Group이 포트와 출처로 따로 판단**합니다.

## 역할 대응표 (구조도를 보완) [작업지시]

| 일반 네트워크에서 하던 일 | AWS의 부품 | 이 부품이 실제로 하는 일 | 일반 장비와 다른 점 |
|---|---|---|---|
| 내부 논리 네트워크 | **VPC** | 내가 정한 주소 범위(`10.0.0.0/16`)의 격리된 네트워크 | 물리 장비가 아니라 논리적 네트워크 |
| 주소 대역으로 나눈 구역 | **Subnet / Public Subnet** | VPC 범위의 일부(`10.0.1.0/24`)에 자원을 둠 | "Public"은 **이름이 아니라 연결된 Route Table**로 결정됨 |
| 목적지별 길 안내표 | **Route Table** | 목적지 범위별로 다음 경유지를 적은 규칙 목록. Subnet에 연결됨 | 패킷이 **통과하는 장비가 아님** |
| 인터넷 경계의 출입구 | **Internet Gateway** | VPC와 인터넷 사이의 통로. IPv4에서는 Public IPv4와 사설 IP를 1:1로 변환 | 방화벽이 아님. 있다고 아무나 들어오는 것은 아님 |
| 서버 접근 통제 | **Security Group** | 서버로 들어오고 나가는 통신을 포트·출처로 허용 | 경계의 전용 장비가 아니라 **서버(네트워크 인터페이스)마다 붙는** 상태 기반 규칙 |
| 웹 서버 | **EC2 + Nginx** | EC2가 컴퓨터, Nginx가 80번에서 응답하는 프로그램 | EC2는 컴퓨터이고 Nginx는 그 안의 프로그램 |

> **이 표의 한계 [작업지시]:** "≈ 대응"은 **역할을 이해하기 위한 단순화**입니다. 일반 네트워크 장비와 AWS 부품이 항상 1:1로 같지는 않습니다. 예를 들어 사내망 방화벽은 보통 경계의 한 장비가 맡지만, AWS Security Group은 서버마다 따로 붙습니다.

## 헷갈리기 쉬운 세 가지 [작업지시]

| 부품 | 한마디로 | 흔한 오해 | 실제 |
|---|---|---|---|
| Internet Gateway | 인터넷으로 통하는 **문** | 문이 있으면 인터넷이 된다 | 문 **앞까지 가는 길**(Route Table)이 있어야 합니다. |
| Route Table | 그 문으로 갈지 정하는 **길 안내표** | 문과 같은 것이다 | 표는 **규칙**이고, 문은 **통로**입니다. `0.0.0.0/0 → IGW` 줄이 없으면 문이 있어도 쓰이지 않습니다. |
| Security Group | EC2에 적용되는 **출입 통제** | Subnet 전체에 붙는다 | 적용 단위는 **EC2의 네트워크 인터페이스**입니다. |

## 브라우저 요청이 Nginx에 닿으려면 [작업지시]

네 가지가 **모두** 필요합니다. 하나라도 빠지면 증상은 보통 똑같이 "응답 없음"입니다.

| # | 조건 | 어디서 확인하나 | 빠지면 |
|---|---|---|---|
| 1 | EC2에 **Public IPv4**가 있다 | EC2 인스턴스 정보 | 인터넷에서 그 서버를 부를 주소가 없음 |
| 2 | Subnet에 연결된 Route Table에 **`0.0.0.0/0 → IGW`** 가 있다 | Route Table 경로와 서브넷 연결 | Public Subnet이 아니게 됨 |
| 3 | **Security Group이 80을 허용**한다 | Security Group 인바운드 규칙 | 요청이 EC2에 닿기 전에 막힘 |
| 4 | **Nginx가 80번에서 실행** 중이다 | EC2 안에서 확인 | 규칙은 열렸는데 응답할 프로그램이 없음 |

> **Public Subnet이라는 이름만으로 외부 접속이 완성되지 않습니다 [작업지시].** 이름이 `public-subnet`이어도 위 조건이 하나라도 빠지면 접속되지 않습니다.
>
> 서버 **안쪽의 방화벽**도 따로 있을 수 있습니다. AWS 쪽이 모두 열려도 서버 안에서 막으면 접속되지 않습니다. [AI 보충]

## SSH 관리 접속은 별개입니다 [작업지시]

| | 웹 접속 (HTTP) | 관리 접속 (SSH) |
|---|---|---|
| 누가 | 웹 사이트를 보는 **누구나** | **관리자(나)** 만 |
| 포트 | 80 | 22 |
| Security Group 출처 | `0.0.0.0/0` | **내 공인 IP/32** |
| 서버 안의 받는 쪽 | Nginx | sshd |
| 인증 | 없음(공개 웹페이지) | **Key Pair** (→ `ssh-key`) |

두 접속은 같은 문(Internet Gateway)과 같은 길(Route Table)을 쓰지만, **누구에게 열어 주는지가 다릅니다.** 그래서 같은 Security Group 안에서 포트마다 출처를 다르게 적습니다.

## Public IPv4는 서버 안에 보이지 않습니다 [AI 보충]

AWS Internet Gateway는 IPv4에서 **NAT(주소 변환)** 를 합니다. 서버 안에서 네트워크 설정을 보면 사설 IP(`10.0.1.x`)만 보이고, 밖에서 부르는 Public IPv4는 **Internet Gateway가 사설 IP와 1:1로 바꿔 줍니다.** 그림의 점선 상자가 이 관계를 나타냅니다.

## 구조도가 단순화한 점 [작업지시]

- Route Table을 Subnet 옆의 **연결된 규칙표**로 그렸습니다. 실제로는 VPC의 라우터가 이 표를 참조하며, 사용자의 패킷이 표를 "통과"하지는 않습니다.
- Security Group은 EC2를 감싸는 **점선**으로 그렸지만, 실제 적용 단위는 네트워크 인터페이스이고 하나의 EC2에 여러 개를 붙일 수도 있습니다.
- 인터넷 쪽 네트워크 ACL, NAT Gateway, Private Subnet, 로드 밸런서는 이 그림에서 **생략**했습니다.

2. Security Group을 "Subnet 전체에 걸린 방화벽"으로 그리면 어떤 점이 틀리나요?
3. SSH와 HTTP는 같은 Security Group을 쓰는데 왜 출처를 다르게 적나요?
4. 사내 방화벽 장비와 Security Group을 "같은 것"이라고 말하면 어디가 부정확한가요?
