## 0. 요약 판정

**판정: 수정 필요 (구조 유지, 내용 보강).** 4 Scene·8 슬라이드의 큰 흐름(활용 → 로컬 Git 수집 → 외부 API 요청·응답 → 검증과 사람 확인)은 입문자에게 맞는 순서이고, 기술적 사실도 실제 소스와 거의 정확히 일치한다. 하지만 **혼자 읽는 입문자 기준으로는 “API로 무엇을, 어디로, 어떻게 보내고 받는가”의 핵심 중 일부가 화면 어디에도 없다.** 특히 요청 주소(URL), 응답 JSON의 실제 모양, 상태 코드(성공·인증 실패), API 키가 필요한 이유, Python 데이터 ↔ JSON 텍스트 변환이 빠져 있다. 슬라이드 사이의 연결도 Scene 단위로는 이어지지만 화면 단위로는 S1-2→S2-1, S3-2→S4-1, 마지막 S4-2에서 끊긴다.

## 1. 1차 검토 — 처음 배우는 교육생 관점

슬라이드 화면과 P 해설만 순서대로 읽었다. 강사 스크립트·발표자 노트는 강의 후 혼자 보는 학습자가 펼칠 가능성이 낮다고 보고 판단에서 제외했다.

### A. 하나의 이야기로 이어지는가?

| 질문 | 판정 | 근거 |
| --- | --- | --- |
| 처음에 무엇을 배우는지 명확한가? | **부분 충족** | 제목·핵심 질문(“외부 AI 서비스의 기능을 내 Python 프로그램에서 사용하려면…”)은 명확하다. 그러나 강의 소개 화면의 학습 목표 4개가 “요청 본문의 작성 규칙과 Git 문맥, 인증 헤더, 전송 전 보안 검사, 응답 후 검증의 역할을 구별한다”처럼 **아직 배우지 않은 용어로 쓰여** 첫 화면에서 목표를 이해하기 어렵다. 원고 인트로의 “선수개념: 명령줄, diff, API와 JSON” 문단은 웹에 렌더링되지 않는다(`lessonFromStoryboard`가 제목·부제·질문·초안 안내·목표만 읽음). |
| 왜 Git의 변경 정보를 수집해야 하는가? | **충족** | S1-1 → S1-2가 “AI에 설명을 부탁하려면 어떤 정보가 필요할까?”라는 질문으로 자연스럽게 이어진다. |
| Python에서 다른 프로그램을 실행하는 이유가 자연스러운가? | **미흡** | S1-2에서는 **사람이** 터미널에 `git status`·`git diff`를 친다. S2-1은 곧바로 `python main.py commit`과 `argparse`로 시작한다. “사람이 치던 명령을 프로그램이 대신하려면 Python이 Git을 실행해야 한다”는 이유 문장이 없다. 또 `argparse`(사용자 → 프로그램 입력)와 `subprocess`(프로그램 → Git 실행)라는 **방향이 다른 두 개념**이 한 화면에 들어 있어, 입문자는 argparse가 Git 실행의 일부라고 오해하기 쉽다. |
| 수집한 정보를 외부 AI에 보내는 이유와 과정이 이해되는가? | **부분 충족** | S2-2 그림의 “있음 · 다음으로 → 보낼 데이터를 만든다(Scene 3)”가 좋은 연결이다. 하지만 S3-1이 “왜 보내기 전에 검사해야 하는가(내 컴퓨터 밖으로 나간 데이터는 되돌릴 수 없다)”를 말하지 않고 검사 규칙의 세부(6개 항목, 가림 vs 중단, 16,000자, `--unsafe`, 개인키 블록)를 먼저 보여 준다. S3-1에서 만든 글이 **다음 화면 요청의 `user` 메시지가 된다**는 사실은 S3-2 해설에만 있고 S3-1의 그림·해설에는 없다(원고 그림 제안에는 있으나 F6에 반영되지 않음). |
| AI 결과가 최종 업무에 활용되는 과정까지 연결되는가? | **충족** | S4-1(두 가지 초안) → S4-2(형식 검사와 사람 확인) → 사람이 커밋·PR을 직접 수행하는 흐름이 분명하다. |
| 마지막에 전체 흐름을 스스로 설명할 수 있는가? | **미흡** | S4-2가 F1 전체 그림으로 돌아오는 설계는 좋다. 그러나 S4-2 P 해설은 “사람의 확인”에만 집중하고, 처음 질문(“어떤 정보를 어떻게 주고받아야 할까?”)에 대한 **요약 답을 주지 않는다.** 학습자가 스스로 말해 볼 틀(예: “Python은 ○○를 ○○에 담아 ○○로 보내고…”)도 없다. |

**흐름이 끊기는 지점 (심각도 순)**

1. **S3-2 → S4-1**: S3-2 해설의 마지막 문장이 “모델 실행 위치는 미확인입니다”라는 기술적 단서로 끝난다. 다음 화면으로 넘어가는 이유가 사라진다. 그런데 S4-1은 사실 **`system` 메시지의 효과를 보여 주는 가장 좋은 사례**다. 실제로 `commit`과 `pr`은 같은 Git 문맥(`user`)에 작성 규칙(`system`)만 다르게 보냈다(`main.py` 41행, `demo-request.json` 주석). 이 연결이 화면에 드러나지 않는다.
2. **S1-2 → S2-1**: 사람이 치던 Git 명령 → 프로그램이 대신 실행, 이 전환 이유가 없다.
3. **S4-2 → (끝)**: 핵심 질문으로 돌아와 답하는 문장이 없다.
4. **강의 소개 → S1-1**: 학습 목표가 결과 용어로 쓰여 있어 S1-1의 출발 질문과 연결되지 않는다.

### B. 입문자가 이해할 수 있는가?

학습자 화면(제목·메시지·화면 설명·그림·P 해설)에 **정의 없이 등장하는 용어**를 미션 이해에 꼭 필요한지 기준으로 나눴다.

| 구분 | 용어 (첫 등장 화면) | 권고 |
| --- | --- | --- |
| **반드시 화면 안에서 설명** | API(S1-1, 한 문장 정의만 있음) · 로컬 저장소 vs GitHub(S1-2·S4-2) · subprocess(S2-1) · 종료 코드·stdout(S2-2, 해설에 있음) · **요청 주소/URL(어디에도 없음)** · HTTPS POST(S3-2) · 인증 헤더와 API 키(S3-2) · 환경변수(S3-2) · JSON 본문(S3-2) · `system`/`user`(S3-2, 있음) · 응답 JSON과 `choices[0].message.content`(S3-2) | 한 줄 정의 + “왜 필요한가”를 P 해설이나 그림 라벨에 넣는다. |
| **한 구절 풀이면 충분** | `argparse`(S2-1) · 셸 / “셸을 거치지 않는다”(S2-1 그림·해설) · 미추적 파일(S3-1) · 토큰(S3-1) · `--unsafe`(S3-1, argparse 옵션이라는 설명 없음) · 모델 ID(S3-2) · `urllib.request`(S3-2 학습 기술 라벨) · 원격·push(S4-2) · 후처리(S4-1) | 괄호 한 구절 수준. 예: “`--unsafe`(검사를 끄는 실행 옵션)” |
| **추가 학습으로 넘겨도 됨** | Bearer 방식의 세부 · `check=False`(F5) · `CompletedProcess`(F5) · 종료 코드 128의 의미 · 개인키 블록 · 정규표현식 패턴 · porcelain 형식 · `temperature`/`max_tokens` · `Content-Type` | 그림에서 빼거나 흐리게 하고 학습가이드 01·02·05장으로 넘긴다. F5의 “기본 check=False…” 상자는 입문 화면에서 주의를 분산한다. |

**이미 알고 있다고 가정하는 개념**: 명령줄 실행, Git 저장소·스테이징(`git add`), Python 리스트, JSON 형식, HTTP. 원고는 이를 선수개념으로 두었지만 학습자 화면에서는 안내하지 않는다.

**정의는 있지만 역할이 와닿지 않는 곳**

- S1-1 “API는 한 프로그램이 다른 서비스에 일을 부탁하고 결과를 받을 수 있는 창구”: 정의는 맞지만 **왜 내 컴퓨터에서 직접 하지 않고 외부에 부탁하는지**(AI 모델은 크고 외부 서버에서 실행된다, 서비스는 약속된 형식으로만 요청을 받는다)가 없다.
- S3-2 “API 키를 인증 헤더에”: **키가 왜 필요한지**(누가 요청했는지 확인, 사용량·비용 계산, 권한)와 **왜 환경변수에서 읽는지**(코드·Git 이력에 비밀값을 남기지 않으려고)가 없다. 학습가이드 02장 확인 문제 2번에는 있으나 슬라이드에서 이어지지 않는다.
- S3-2 “`choices[0].message.content`에서 초안 텍스트를 읽는다”: 응답 JSON의 모양을 한 번도 보여 주지 않아, 입문자는 이 경로를 “외워야 할 주문”으로 받아들이게 된다.

**구체 예시가 필요한데 추상적인 곳**: S3-2의 응답(실제 모양 없음), S3-1의 “문맥”(806자 글의 앞부분 몇 줄이 있으면 즉시 이해됨 — 근거 파일 `demo-context.txt`가 이미 있음).

**한 화면의 정보량**

| 화면 | 정보 밀도 | 메모 |
| --- | --- | --- |
| S1-1, S1-2, S4-1 | 적정 | 실제 사례가 이해를 돕는다. |
| S2-1 | 과다 | argparse + subprocess + 리스트 인수 + 셸 + 운영체제 + 6개 Git 명령 목록 + “commit은 초안 종류” |
| S2-2 | 다소 과다 | 객체 이름, 세 속성, 128, 두 분기, `check=False` |
| S3-1 | **과다** | 6개 문맥 항목 + 3단계 검사 + 2종 결과 + 16,000자 + `--unsafe` + 제외 목록. Scene 3의 두 화면 중 하나가 보안 세부에 쓰여 API 학습 시간이 사실상 한 화면이 된다. |
| S3-2 | 적정(누락 있음) | 정보량은 적당하나 핵심 요소가 빠져 있다(§3). |
| S4-2 | 적정 | |

### C. P 해설이 학습을 돕는가?

| 질문 | 판정 | 근거 |
| --- | --- | --- |
| 그림에서 무엇을 봐야 하는지 알려 주는가? | **충족** | 8개 모두 “그림의 오른쪽에서…”, “나가는 화살표는…”처럼 시선을 안내한다. |
| 왜 필요한지 설명하는가? | **부분 충족** | S1-2, S2-2는 이유가 있다. S2-1(왜 Python이 Git을 실행?), S3-1(왜 전송 전 검사?), S3-2(왜 키? 왜 JSON?)는 “무엇을 한다” 위주다. |
| 앞·뒤 화면을 연결하는가? | **미흡** | 뒤를 가리키는 문장은 S3-2(“앞 화면에서 검사한 Git 문맥”) 한 곳뿐이다. 다음 화면 예고 문장은 8개 중 0개다. |
| 그림만으로 어려운 부분을 보충하는가? | **부분 충족** | `M`, `+`, 128의 의미 보충은 좋다. 반대로 해설에 새 용어(`git diff --cached`, `--unsafe`, 16,000자)가 추가되어 그림보다 어려워지는 경우가 있다. |
| 읽은 후 그림을 다시 보면 이해가 깊어지는가? | **부분 충족 (UI 제약)** | 1280×720에서 S3-2 해설을 열면 하단 고정 패널이 그림의 **응답 상자와 돌아오는 화살표를 가린다**([캡처](../../reports/b32-story-v02/overlay-captures/1280-dark-api-open-viewport.png)). 해설이 “돌아오는 화살표는…”이라고 말하는 순간 그 화살표가 보이지 않는다. 닫았다 열어야 대조할 수 있다. |

## 2. 2차 검토 — 실제 소스 대조

| 항목 | 판정 | 소스 근거와 입문자 관점 메모 |
| --- | --- | --- |
| 로컬 Git vs GitHub | **정확 / 표현 보강** | `collect_changes(Path.cwd())`는 현재 폴더에서 `rev-parse`, `branch`, `status`×2, `diff`, `diff --cached`만 실행하고 네트워크를 쓰지 않는다. v0.1 화면 설명에 있던 “GitHub가 아니라 로컬 저장소”가 v0.2 화면 설명에서 빠졌다. S4-2의 “원격에 push하거나 PR을 등록”에서 GitHub가 처음 등장하므로 S1-2에서 대비를 한 번 해 두는 편이 좋다. |
| argparse의 역할 | **정확 / 범위 축소 표현** | `build_parser()`는 `command`(commit·pr) 외에 `--api-url`, `--model`, `--temperature`, `--max-tokens`, `--unsafe`도 읽는다. S3-1의 `--unsafe`가 argparse가 읽는 옵션이라는 연결이 화면에 없다. |
| subprocess의 역할 | **정확** | `_git()`은 리스트 인수, `capture_output=True`, `check=False`로 실행하고 `returncode`가 0이 아니면 `GitError`를 일으킨다. “셸을 거치지 않는다”는 맞지만(기본 `shell=False`) 입문자에게 의미가 전달되지 않는다. |
| Python이 API에 보내는 요청 데이터 | **정확 / 핵심 누락** | `generate()`는 `{"model", "messages":[system,user]}`(+선택 파라미터)를 보낸다. **API 주소는 `CODYSSEY_API_URL`/`--api-url`, 모델은 `CODYSSEY_MODEL`/`--model`에서 온다**(`main.py` 18·19행). 화면은 API 키만 환경변수라고 말해 주소·모델이 코드에 고정된 것처럼 보일 수 있고, **요청 주소 자체가 학습자 화면 어디에도 없다.** |
| API 키, 인증 헤더, JSON 본문 | **정확** | `Authorization: Bearer {key}`, `Content-Type: application/json`, 본문은 `json.dumps(...).encode("utf-8")`. 키가 본문에 없다는 점(F6 “제외”, v0.1 이해 확인)은 잘 다뤘다. |
| system / user | **정확 / 활용 부족** | `system = COMMIT_SYSTEM if command == "commit" else PR_SYSTEM`. 두 실행의 차이가 `system` 하나뿐이라는 사실을 S4-1에서 활용하지 않았다. |
| HTTP 요청·응답 방향 | **정확** | F1·F7 화살표 방향 일치. 다만 응답에는 **상태 코드**가 있고, 코드가 이를 분기한다(401·403 → “인증 또는 권한 오류”, 그 외 → “응답 오류”). 슬라이드에는 성공 응답만 있다. |
| 응답 추출 | **정확 / 예시 부재** | `json.load(response)` → `data["choices"][0]["message"]["content"]` → 비어 있으면 오류 → `strip()`. 응답 JSON 원본은 미확보지만, 구조를 보여 주는 **교육용 예시**는 근거 체계(교육용 예시 표기)로 충분히 표시할 수 있다. |
| 결과 검증 | **정확** | `validate_commit()`(8~72자, 금지 제목, `#`/`-`/`Title:` 시작 금지), `validate_pr()`(형식·길이·테스트 주장·불릿, How to Test 교체). 형식 검증에 실패해도 **AI 요청은 이미 1회 사용**되었고 자동 재요청은 없다. S4-2 해설만 읽으면 실패 시 요청이 없었다고 오해할 여지가 있다. |
| 자동 커밋·PR 없음 | **정확** | Git 쓰기 명령이 없다. F4 하단 띠, S2-1 해설, S4-2 해설에서 반복 확인된다. |

**기술적으로 맞지만 입문자가 오해하기 쉬운 표현**

1. **주어 “B3-2”**: “B3-2는 … 묶고”, “B3-2가 오류를 알리고 멈춘다”. B3-2는 미션 이름이자 강의 코드이자 프로그램이다. 처음 한 번 “B3-2 프로그램(`main.py`)”으로 정의하거나 “프로그램”으로 통일하는 것이 좋다.
2. **“모델 실행 위치 미확인”의 반복**(F1, F7, S3-2 해설 마지막 문장): 사실 표기로는 정확하지만, 입문자에게는 “무언가 문제가 있다”는 신호로 읽히고 핵심 메시지보다 늦게 남는다. 그림 각주 한 곳으로 줄이는 것을 권한다.
3. **F6 “검사를 통과한 것만”**: 실제로는 일부 값을 `[REDACTED]`로 **가린 글이 그대로 전송**된다. “가린 뒤 남은 글”이 정확하다.
4. **F5 “실제: 안 0 · 밖 128”, “저장소 밖 · 실제 값”**: 원고 v0.2는 이 예시에 “재현” 표시를 요구하지만 F5는 v0.2에서 다시 만들지 않아 “실제”로 남아 있다(`storyboard-v02.mjs`의 `REVISED`에 f5 없음). 2026-10-20 실제 API 실행과 혼동될 수 있다.
5. **S2-1 해설 “Python은 실행할 프로그램과 명령을 목록으로 건네며 셸을 거치지 않습니다”**: 맞지만 “셸”이 정의되지 않아 학습 효과가 없다. 입문 화면에서는 “Python이 Git 프로그램을 직접 실행한다”로 충분하다.

**S3-2 P 해설 수정 예시** (현재 5문장 → 6문장, 길이 비슷)

> 내 컴퓨터에는 AI 모델이 없으므로, Python은 외부 AI 서비스가 정해 둔 형식(API)대로 요청을 보내고 답을 받습니다. 그림의 나가는 화살표가 **요청**입니다. 요청에는 보낼 **주소**, 데이터를 담아 보내는 **POST 방식**, 누가 보내는지 증명하는 **API 키(인증 헤더)**, 그리고 보낼 내용인 **JSON 본문**이 들어갑니다. 본문의 `system`은 글을 어떻게 쓸지 정한 작성 규칙이고, `user`는 앞 화면에서 검사한 Git 문맥입니다. 돌아오는 화살표가 **응답**으로, 성공하면 JSON 글이 오고 Python은 그 안의 `choices[0].message.content`에서 초안을 꺼냅니다. 키가 틀리면 401 같은 오류 응답이 오고, B3-2 프로그램은 오류를 알리고 멈춥니다.

(키를 환경변수에 두는 이유, 모델 실행 위치는 그림 각주나 학습가이드 02장으로 넘긴다.)

| S3-2 → S4-1 | 같은 Git 문맥에 작성 규칙(`system`)만 바꾸면 돌아오는 글이 어떻게 달라질까요? |
| S4-1 → S4-2 | 형식에 맞는 초안이 나왔습니다. 형식이 맞으면 내용도 맞을까요? |
| S4-2 마무리 | 처음 질문에 답해 봅시다. Python은 API 주소로 API 키(헤더)와 작성 규칙·Git 문맥(JSON 본문)을 보내고, 응답 JSON에서 초안을 꺼내 형식을 검사한 뒤 사람에게 보여 줍니다. |

**종합 판단**: 8화면은 하나의 학습 이야기로 **충분히 발전할 수 있다.** Scene 순서를 바꿀 필요는 없다. 위 연결 문장과 §3의 Scene 3 보강, S4-2 마무리 문장이 들어가면 혼자 읽어도 “재료 → 수집 → 보내기 → 받기 → 확인”이 이어진다.

## 5. 개선 방향 비교

| | **A. 8슬라이드·P 해설만 개선** | **B. 8슬라이드 + 연속 읽기 자료** | **C. 슬라이드 안 스토리 탐색 기능** |
| --- | --- | --- | --- |
| 입문자 이해 | 개념 누락·연결 문장 문제를 대부분 해결 | 이야기로 읽는 경험이 가장 좋음 | 단계 관계 파악에는 좋으나 처음 이해에는 도움이 적음 |
| 자율학습 | P 패널이 화면당 따로 열리므로 이어 읽기는 여전히 끊김 | 한 페이지에서 그림과 글을 순서대로 읽음 | 흐름 탐색 화면은 현재 **개발 서버 전용**(`import.meta.env.DEV`)이고 슬라이드에서 진입 링크가 없음. 실행 순서(6단계)와 강의 순서(8화면)가 S1-2↔S2-1에서 뒤바뀌어 처음 배우는 사람에게 혼란 |
| 중복 위험 | 낮음 | **높음** — P 해설, 접힘 설명, 학습가이드 07장과 같은 내용을 또 씀 | 중간 — flowStages 설명이 P 해설과 겹침 |
| 비용 | 낮음 (원고 문장 + F7·F6 일부) | 중간 | 높음 (UI·반응형·QA) |

**권고: A를 먼저 하고, B는 “새 글”이 아니라 A의 결과를 이어 붙인 화면으로 만든다.**

- A 단계에서 P 해설을 **자율학습의 단일 기준 글**로 정하고, 각 해설에 연결 문장을 넣는다.
- B는 별도 원고를 쓰지 않고, 같은 `storyboard-v0.2.md`의 화면 해설 8개 + 그림을 한 페이지에 순서대로 렌더링하는 “이어 읽기” 보기로 만든다. 그러면 중복 원고가 생기지 않는다.
- v0.1 학습자 접힘 설명은 P 해설과 역할이 겹치므로, 접힘 영역에는 **이해 확인 질문만** 남기는 것을 권한다(Owner 결정 사항).
- C는 보류한다. 흐름 탐색은 강의 후 “실제 코드 위치를 찾는” 심화 도구로 가치가 있으나, 입문자의 첫 이해를 위한 수단은 아니다. 운영에 쓰려면 프로덕션 노출 여부부터 Owner가 결정해야 한다.
