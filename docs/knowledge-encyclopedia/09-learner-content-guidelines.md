# 09. 학습자 콘텐츠 기준

[08 Content Quality 기준](08-content-quality-criteria.md)은 설명이 **그 용어에 대한 것인지**를
물었다. 이 문서는 그다음을 묻는다 — **읽는 사람이 실제로 이해하는가.**

- 확정일: 2026-09-23 / 기준 커밋 `6971e71`
- 근거: [learner-readability-discovery](../../reports/knowledge-encyclopedia/learner-readability-discovery.md) 36개 표본 검토
- 상태: **가설이다.** 실제 학습자 검증 전까지 전면 적용하지 않는다

---

## 1. 대상 독자

> 컴퓨터와 일반적인 디지털 서비스 사용에는 익숙하지만, 프로그래밍·컴퓨터공학을
> 체계적으로 공부한 경험은 거의 없는 성인 학습자. Codyssey Mission 을 하면서
> 처음 기술 개념을 만나는 사람.

나이나 직업을 가정하지 않는다. 다음도 가정하지 않는다.

- 영어 기술 용어를 읽으면 뜻이 떠오른다
- `process`, `state`, `binding` 같은 낱말의 컴퓨터공학 용법을 안다
- 다른 용어 문서를 먼저 읽고 왔다

**학습자는 이 문서를 미션 중에, 막힌 상태에서, 처음 연다.** 첫 화면이 전부다.

---

## 2. 읽기 쉬움과 이해됨은 다르다

두 가지를 한 판정으로 묶지 않는다. 표본 36개에서 **읽기는 쉬운데 이해되지 않는 문서가
7개** 있었다. 반대는 1개였다.

| | 무엇을 묻나 | 잘 안 될 때의 모습 |
| --- | --- | --- |
| **Readability** | 문장이 읽히는가 | 긴 문장, 괄호 병기, 영문 밀집, 추상명사 연속 |
| **Comprehension** | 읽고 나서 아는가 | 정의가 모르는 낱말에 기대 있음, 비유만 있고 기술이 없음, 한 문장에 새 개념 4개 |

문장을 짧게 만드는 것으로 Comprehension 문제는 해결되지 않는다.

---

## 3. 첫 문장 규칙

표본에서 가장 크고 가장 고치기 쉬운 문제다.

> **`한 줄 설명` 은 화면에서 가장 먼저 읽히는 문장이다.
> 그러므로 그 문서에서 가장 쉬운 문장이어야 한다.**

현재는 반대다. 519개 중 **333개**에서 `한 줄 설명` 이 `쉽게 설명하면` 보다 영문 전문용어가
많다(평균 2.04 대 0.22, 9배).

```
지금    MySQL        널리 쓰이는 open-source relational database 관리 시스템.
        쉽게         널리 쓰이는 서버형 데이터베이스입니다.
        → 같은 말인데 먼저 읽히는 쪽이 더 어렵다

지금    변수          Variable은 프로그램이 값을 가리키고 다시 사용할 수 있도록 이름을 붙인 binding입니다.
        → 정의를 맡은 낱말(binding)이 미설명이다. 정의가 정의를 요구한다
```

규칙:

1. **정의를 학습자가 모르는 낱말로 하지 않는다.** 그 낱말이 정의의 뼈대라면 더욱 그렇다.
2. 영문 용어는 `정확한 설명` 이후로 내린다. `한 줄 설명` 에 남기려면 그 자리에서 풀어 준다.
3. 명사구로 끝내지 않는다. `…하는 entry file.` 이 아니라 `…가장 먼저 읽는 파일입니다.`

## 4. 설명 계층 — 순서는 고정, 형식은 자유

학습자가 밟는 **이해의 단계**는 공통이다. Markdown 절 구조를 통일하자는 말이 아니다.

| 단계 | 묻는 것 | 원칙 |
| --- | --- | --- |
| **L1 처음 이해** | 이게 한마디로 무엇인가 | 전공 지식을 전제하지 않는다. 1~3문장 |
| **L2 기본 개념** | 왜 필요하고 기본적으로 어떻게 되는가 | 여기서 핵심 기술 낱말을 **처음 소개한다** |
| **L3 구체적인 모습** | 실제로는 어떤 모습인가 | 코드·흐름·상황·비교 중 그 용어에 맞는 것 |
| **L4 기술 세부** | 더 정확히 알려면 무엇이 필요한가 | 초보 설명을 위해 정확성을 깎지 않는다 |

**L3 는 코드를 뜻하지 않는다.** `CORS` 는 코드 없이 동작 서술로 L3 를 채우고도 표본에서
가장 잘 읽히는 문서였다. `가용성` 같은 개념에 억지 코드를 붙이면 없는 것보다 나쁘다.

### 같은 단계, 다른 형식

```
변수        직관("이름표")      → 코드 두 줄   → 값·메모리   → scope·reference
CORS        문제 상황           → 출처         → 브라우저 제한 → 허용 방식
Process     프로그램과의 차이    → 실행         → OS 관리      → thread 와 비교
TCP         무엇이 보장되나      → 조각·순서    → 재전송       → 혼잡 제어
```

네 개 다 L1→L4 를 밟지만 안에 들어가는 것이 다르다. **template 으로 고정하지 않는다.**

## 5. 비유 정책

비유는 **허용하고 권장한다.** 단 반드시 돌아온다.

```
비유  →  "실제 기술에서는?"  →  정확한 개념
```

- **비유를 정의로 쓰지 않는다.** `deadlock` 의 "서로의 열쇠를 기다린다" 는 좋은 비유지만,
  정의는 "lock 을 잡은 채 다른 lock 을 기다리는 순환" 이다. 둘 다 있어야 한다.
- **비유가 설명 대상보다 어려우면 비유가 아니다.** `O(1)` 의 "한 번의 주소 계산처럼" 은
  해시맵을 이미 아는 사람에게만 통한다.
- **비유가 어긋나는 지점을 밝힌다.** 사물함 비유는 "서랍이 유한해서 겹칠 수 있다" 에서
  깨지는데, 그 지점이 바로 충돌 개념이 들어올 자리다.

## 6. 예시 정책

| 좋은 예시 | 나쁜 예시 |
| --- | --- |
| 그 용어에서만 의미가 있다 | 다른 용어에 그대로 붙여도 된다 |
| 개념의 핵심을 보여 준다 | 코드를 넣기 위한 코드 |
| 다른 기술을 새로 요구하지 않는다 | 설명보다 예제가 더 어렵다 |
| 실제로 겪는 상황이다 | 새 전문용어를 여럿 끌고 온다 |

표본에서 가장 나쁜 예시는 `TCP` 의 `ufw allow 20022/tcp` 였다. 방화벽 예제이지
TCP 가 무엇인지 보여 주지 않는다. **그 용어의 예제인지 옆 용어의 예제인지**를 먼저 묻는다.

## 7. 낱말 정책

첫 설명에 새 전문용어가 나오면 넷 중 하나로 정한다.

| 판정 | 뜻 | 기준 |
| --- | --- | --- |
| `KNOWN_FOUNDATION` | 설명 없이 써도 된다 | 대상 독자의 일상 낱말 (파일, 폴더, 주소, 브라우저) |
| `EXPLAIN_INLINE` | 그 자리에서 한 구절로 푼다 | 정의의 뼈대이고 짧게 풀린다 |
| `LINK_FIRST` | 선수 관계로 잇고 먼저 보게 한다 | 그 자체가 하나의 개념이다 |
| `AVOID_FOR_NOW` | 첫 설명에서 빼고 뒤로 내린다 | 지금 단계에서 필요 없다 |

**AI 가 임의로 "초심자도 알 것" 이라고 가정하지 않는다.** 판단 근거는 기존
prerequisite graph 다 — 선수 관계로 이어져 있으면 `LINK_FIRST` 가 성립하고,
이어져 있지 않은데 첫 화면에 나오면 `EXPLAIN_INLINE` 이나 `AVOID_FOR_NOW` 다.

`npm run content:readability` 가 첫 화면에서 **선수 관계 없이 등장하는 다른 용어**를
세어 준다. 전체 519개 중 87개가 걸린다.

## 8. 한 화면에 몇 개까지

`인지 부하` 는 점수가 아니라 확인 질문이다.

```
첫 화면에 처음 나오는 전문용어가 몇 개인가?
그중 이미 설명됐다고 볼 수 있는 것은?
한 문단이 핵심 하나를 가르치는가, 여럿을 동시에 가르치려 하는가?
```

표본에서 문제가 된 문서는 한 문장에 새 개념이 **넷 이상**이었다.

```
JWT      "JSON claims 를 header·payload·signature 형태로 표현해 전달하는 token format"
         → 한 문장에 claims · header · payload · signature · token format
TCP      "byte stream, sequence number, acknowledgement, retransmission, flow/congestion control"
         → 한 문장에 다섯
어텐션    "query·key·value 의 유사도를 점수화해 가중 합을 만든다"
         → 한 문장에 넷
```

숫자를 기준선으로 삼지 않는다. 다만 **셋을 넘으면 열어 본다.**

## 9. 문체

한 문서 안에서 존댓말과 평서체가 섞이면 읽는 리듬이 끊긴다. 현재 519개 중 **340개**가
섞여 있다(`쉽게 설명하면` 은 430개가 존댓말, `정확한 설명` 은 339개가 평서체).

이번 Cycle 에서는 **고치지 않는다.** 519개에 걸친 일괄 변경이고, 실제 학습자가
이것을 문제로 느끼는지 확인하기 전에 손댈 일이 아니다. 기록만 남긴다.

## 10. 하지 않는 것

- 이 기준을 근거로 **518개를 일괄 rewrite 하지 않는다.** 대표 Pilot 에 대한 Owner 판단이 먼저다
- 새 Markdown template 을 만들어 전체에 적용하지 않는다. 통일할 것은 이해 단계이지 절 구조가 아니다
- 자동 점수를 통과 기준으로 쓰지 않는다. 표본에서 자동 신호는 사람이 찾은 문제 21건 중
  **6건만** 잡았다
- 쉽게 쓰려고 틀리게 쓰지 않는다. L4 가 있는 이유다
