# Mission Learning Bridge — 운영 계약

> **상태: ACTIVE (계약 문서) · 구현: 없음**
> 이 문서는 "미션에서 배운 것이 사전에 어떻게 들어오는가"를 정한다.
> 절차를 정하는 문서이며, 이번 Cycle(Product Completion Audit)에서 **코드나 데이터로 구현하지 않았다.**
> 작성: 2026-09-24 · Product Completion Audit & V1 Closeout Planning

---

## 1. 이 문서가 정하는 것과 정하지 않는 것

**정한다**

- 미션 수행 과정에서 나온 학습 흔적이 사전에 닿기까지 거치는 단계
- 각 단계에서 무엇이 근거로 인정되고 무엇이 인정되지 않는가
- 사람이 멈춰 세우는 지점(Gate)이 어디인가
- 검토 결과로 나올 수 있는 판정의 목록

**정하지 않는다**

- 새 node 종류나 새 relation type. **이것은 ontology 확장이 아니다.**
  현재 node 5종(`term` · `foundation` · `academic` · `mission` · `field`)과
  relation 12종은 그대로다. 근거 수집 절차를 적은 것이지 그래프를 늘리는 것이 아니다
- canonical 선정 기준 자체. 그것은 [`docs/13`](../13_canonical_term_selection_growth_policy_v1.md)에 있고
  이 문서는 그 정책으로 넘기는 경로만 정한다
- 자동화. 이 절차에는 사람이 반드시 들어간다(§5)

---

## 2. 핵심 계약

```
Mission Learning Handoff  !=  automatic glossary update
```

미션에서 어떤 기술이 나왔다는 사실은 **사전을 고쳐야 한다는 결론이 아니다.**
그것은 **Learning Evidence Source** — 검토를 시작할 근거 후보일 뿐이다.

이 구분을 잃으면 사전은 다시 커진다. 그리고 커진 사전은
[FD-01](07-foundation-decisions.md)이 하지 않기로 한 "CS 백과사전"이 된다.

| | Mission Learning Handoff | Glossary Update |
| --- | --- | --- |
| 무엇인가 | 미션 수행에서 나온 학습 흔적의 전달 | 사전 콘텐츠·관계의 실제 변경 |
| 누가 만드는가 | 미션 쪽(학습자·튜터·미션 문서) | 사전 쪽 검토자 |
| 효력 | **없다.** 검토 대기열에 들어갈 뿐 | 있다 |
| 기본 결과 | `NO_CHANGE` 또는 `DEFER` | — |

## 3. 단계

```
[1] Handoff 수집        미션에서 학습 흔적이 전달된다
        ↓                (효력 없음 · 대기열에 쌓인다)
[2] 학습 근거 판정       §4 의 기준으로 근거인지 아닌지 가른다
        ↓                (근거가 아니면 여기서 끝. 기록만 남는다)
[3] ★ User Approval Gate  사람이 Candidate 로 올릴지 정한다   ← 반드시 사람
        ↓
[4] Candidate           검토 대상으로 등록된다
        ↓
[5] Glossary Review     §6 의 8가지 중 하나로 판정한다
        ↓
[6] 적용 / 보류 / 기각   판정에 따라 처리하고 근거를 함께 남긴다
```

**[3]을 건너뛸 수 없다.** AI 도, 스크립트도 Candidate 를 스스로 만들지 않는다.

## 4. 무엇이 학습 근거인가

Candidate 가 되려면 **실제로 학습이 일어났다는 증거**가 있어야 한다.

### 근거로 인정한다

- 학습자가 그 개념을 **모르는 상태에서 막혔고**, 알게 된 뒤에 미션을 진행했다는 기록
- 동료평가·리뷰에서 **그 개념을 설명하지 못해 논의가 멈춘** 기록
- 같은 미션에서 **여러 학습자가 반복해서 같은 지점에서 막혔다**는 관찰
- 미션 요구사항이 그 개념의 **판단**을 요구한다는 것 — 이름을 쓰는 것이 아니라
  두 선택지 중 하나를 고르고 이유를 대야 하는 경우
- 사전의 기존 설명이 그 미션 맥락에서 **틀렸거나 부족하다는** 구체적 지적

### 근거로 인정하지 않는다

| 인정하지 않는 것 | 왜 |
| --- | --- |
| **코드에 나왔다** | 나온 것과 배운 것은 다르다. 복사해 붙여도 코드에는 나온다 |
| **import / require 에 있다** | 의존성 목록은 학습 기록이 아니다 |
| **라이브러리·도구 이름** | 이름을 안다고 개념을 배운 것이 아니다. 제품명은 특히 그렇다 |
| **요구사항 문서에 단어가 있다** | 단어의 등장은 요구의 증거이지 학습의 증거가 아니다 |
| **AI 가 중요해 보인다고 판단했다** | 판단은 근거가 아니다. 관찰이 근거다 |
| **coverage 가 비어 있다** | 빈칸은 채워야 할 이유가 아니다. [§15 원칙](#8-기존-정책과의-관계) |
| **다른 사전에 있다** | 다른 사전의 범위는 이 사전의 범위가 아니다 |

경계가 애매하면 **근거가 아니다**. 근거를 넓게 잡는 쪽이 사전을 망가뜨린다.

## 5. User Approval Gate

Candidate 등록 **앞에** 사람이 선다.

- 올라오는 것: Handoff 원문 · §4 판정 결과 · 근거로 든 관찰 · 기존 사전에서 가장 가까운 term
- 사람이 하는 판단: **이것을 검토 대상으로 삼을 가치가 있는가**
- 사람이 하지 않는 판단: 어떤 결과로 갈 것인가 — 그건 [6] Glossary Review 의 몫이다

Gate 에서 거부해도 Handoff 기록은 지우지 않는다. 같은 것이 반복해 올라오면
그 반복 자체가 §4 의 "여러 학습자가 같은 지점에서 막혔다"는 근거가 된다.

## 6. Glossary Review 판정

Candidate 하나에 대해 **정확히 하나**를 고른다. 근거를 함께 적는다.

| 판정 | 뜻 | 고르는 때 | 결과물 |
| --- | --- | --- | --- |
| `EXISTING_TERM_ENRICHMENT` | 기존 term 의 설명을 보강한다 | 개념은 이미 사전에 있고 설명이 부족했다 | 해당 `content/terms/*.md` 의 절 보강 |
| `MISSION_CONNECTION` | 기존 term 을 그 미션에 잇는다 | 개념도 있고 설명도 되는데 그 미션과 연결되어 있지 않았다 | `mission_refs` 추가 (`source_status` 명시) |
| `ADVANTAGE_LIMITATION_ENRICHMENT` | 장점·한계·경계 조건을 보강한다 | 학습자가 막힌 지점이 "언제 쓰면 안 되는가"였다 | `주의할 점` · `흔한 오해` 절 보강 |
| `RELATED_TERM_CONNECTION` | 기존 term 사이의 관계를 잇는다 | 개념 둘 다 있는데 잇는 선이 없어 길을 못 찾았다 | 기존 relation 12종 중 하나로 edge 추가 |
| `MERGE_INTO_PARENT_CONCEPT` | 상위 개념에 흡수한다 | 별도 term 으로 세울 만큼 독립적이지 않다 | 상위 term 보강 + alias 추가 |
| `NEW_CANONICAL` | 새 canonical 을 만든다 | 위 어느 것으로도 표현되지 않는다 | [`docs/13`](../13_canonical_term_selection_growth_policy_v1.md) 절차로 넘긴다 |
| `DEFER` | 지금 판단하지 않는다 | 근거가 한 건뿐이거나 미션이 아직 안정되지 않았다 | 대기열에 남기고 보류 사유 기록 |
| `NO_CHANGE` | 사전을 고치지 않는다 | 근거를 봤지만 사전의 문제가 아니었다 | 판정과 사유만 기록 |

### 기본값은 `NEW_CANONICAL` 이 아니다

판정은 **위에서부터** 본다. 기존 term 을 보강하는 쪽이 새로 만드는 쪽보다 거의 항상 낫다.

- `NEW_CANONICAL` 은 **마지막 선택지**다. [FD-03](07-foundation-decisions.md)이 정한 대로
  이름이 다르다는 이유로 새 개념을 세우지 않는다
- `DEFER` 와 `NO_CHANGE` 는 실패가 아니다. **정상적인 결과**이고 가장 흔한 결과여야 한다
- 한 Candidate 에서 여러 판정이 필요해 보이면, 그건 Candidate 가 너무 크게 잡힌 것이다. 쪼갠다

## 7. Learner Feedback 과는 다른 것이다

둘 다 사람에게서 오지만 묻는 것이 다르다. 섞으면 둘 다 못 쓴다.

| | Mission Learning Bridge | Learner Feedback |
| --- | --- | --- |
| 출처 | 미션 수행 과정 | 사전 화면을 읽는 중 |
| 묻는 것 | **무엇을 배웠는가 / 어디서 막혔는가** | **이 문서가 읽히는가** |
| 대상 | 사전에 없거나 잇히지 않은 것 | 이미 있는 문서의 품질 |
| 결과 | §6 의 8가지 판정 | 해당 문서의 검토 후보 |
| 기록 | Handoff 대기열 | Feedback 유형별 집계 |

Learner Feedback 의 유형은 [`00-project-status.md`](00-project-status.md) 에 적혀 있다.

## 8. 기존 정책과의 관계

- **[FD-01] Scope** — Encyclopedia 는 수집이 아니라 연결이다. 이 Bridge 는 연결을 찾는 통로이고
  수집을 여는 문이 아니다
- **[FD-03] Foundation 경계** — 이름이 다르다고 개념을 만들지 않는다. §6 의 판정 순서가 이를 강제한다
- **[FD-05] Relation SSOT** — `RELATED_TERM_CONNECTION` 은 **기존 12종 안에서만** 쓴다.
  새 relation type 이 필요해 보이면 그건 Owner Gate 이지 이 절차가 아니다
- **[docs/13] canonical 성장 정책** — `NEW_CANONICAL` 은 이 절차를 끝내는 것이 아니라
  `docs/13` 의 절차를 **시작하는** 판정이다
- **[U14 · U15]** SRE 후보 5건과 Computer Architecture 후보 5건이 지금 대기 중인 이유가 바로 이것이다.
  미션이 그 개념을 요구한 근거가 없어 §4 를 통과하지 못했다. **coverage 를 채우려고 올리지 않는다**

## 9. 아직 구현하지 않은 것

이번 Cycle 은 Audit 이므로 다음은 **만들지 않았다.**

- Handoff 를 받는 입력 경로 (UI · 파일 형식 · API 어느 것도 없다)
- Candidate 대기열을 담을 데이터 파일
- 판정을 기록하는 registry
- 검토 상태를 보여 주는 화면

절차가 먼저 서야 도구가 맞게 만들어진다. 지금 도구를 만들면
§4 의 "근거가 아닌 것"들이 그대로 대기열에 쌓이는 도구가 된다.

**다음에 만들 때의 최소 요건**

1. Handoff 원문을 **가공하지 않고** 보관한다 — 나중에 판정을 되짚을 수 있어야 한다
2. 판정에 **근거를 함께** 적지 않으면 저장되지 않게 한다
3. `NO_CHANGE` 와 `DEFER` 가 기록으로 남는다 — 그것이 다음 판단의 재료다
4. 자동 승격 경로를 **넣지 않는다**

## 10. 실패 모드

이 절차가 망가지는 방식은 넷이다. 미리 적어 둔다.

1. **근거 기준이 느슨해진다** — "코드에 나왔다"가 슬그머니 근거가 되면 §4 표는 장식이 된다
2. **Gate 가 형식이 된다** — 올라오는 것을 전부 통과시키면 Gate 가 없는 것과 같다
3. **`NEW_CANONICAL` 이 기본이 된다** — 보강보다 신설이 쉬워 보이기 때문에 생긴다.
   판정 분포를 세어 보면 알 수 있다
4. **Learner Feedback 과 섞인다** — 읽기 어렵다는 말이 새 term 요청으로 둔갑한다
