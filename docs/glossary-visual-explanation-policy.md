# 용어사전 시각 설명 보강 정책

> **버전:** v0.1 · 2026-10-27
> **상태:** 정책 초안. GPT 독립 검토와 Owner 승인 대기. 이 문서의 후보 표는 제작 승인이 아니다.
> **적용:** 기술용어사전 용어 상세(`/terms/:termId`)에 들어가는 그림. 미션 스토리·개념지도·학습가이드의 그림은 각 미션 절차를 따르며, 이 문서는 그 그림을 용어사전에 가져올 때의 기준만 정한다.
> **함께 읽기:** [학습 운영 정책](mission-guides/learning-operation-policy.md) · [제작·검토·웹 통합 절차](mission-guides/workflow.md) · [용어 콘텐츠 작성 가이드](03_content_writing_guide.md) · [웹툰 콘텐츠 가이드](04_webtoon_content_guide.md)

## 1. 목적과 핵심 원칙

> 모든 용어에 그림을 넣는 것이 아니라, 시각적으로 설명했을 때 구조·흐름·차이의 이해가 분명하게 개선되는 용어를 선별한다.

- 그림은 정확한 정의와 설명을 **대체하지 않는다.** 정의·예외·코드는 텍스트에 남기고, 그림은 구조·흐름·관계를 보완한다.
- 그림은 원리를 설명하기 위한 것이다. 장식이나 용어명에 맞춘 일반 아이콘은 보강으로 보지 않는다.
- 후보는 **Owner의 실제 미션 수행과 학습 경험**에서 찾는다. 수집만 된 용어를 대량으로 그림 대상에 올리지 않는다.
- 이미 있는 그림의 재사용을 먼저 검토한다. 새로 그리는 것은 재사용이 맞지 않을 때다.
- 후보 선정은 제작 승인이 아니다. Owner가 승인한 용어만 별도 콘텐츠 개정 작업으로 진행한다.

## 2. 다른 학습 자산과의 관계

| 자산 | 그림이 맡는 역할 | 기준 문서 |
| --- | --- | --- |
| 미션 스토리 | 한 미션 안에서 무엇이 어떤 순서로 작동하는가 (강의·복습용, 미션 사례 중심) | [학습 운영 정책](mission-guides/learning-operation-policy.md) |
| 개념지도 | 미션 개념 사이의 관계 | 같은 문서 |
| **용어사전 시각 설명** | **한 용어의 구조·흐름·차이·범위** (미션 밖에서도 통하는 일반 설명) | **이 문서** |
| 학습가이드 | 코드·명령·실습·검증 과정 | [workflow](mission-guides/workflow.md) |
| 웹툰 | 개념이 쓰이는 상황을 유머로 풀어 첫 이해를 돕는 선택적 장치 | [웹툰 가이드](04_webtoon_content_guide.md) |

용어사전의 그림은 미션 사례를 그대로 옮기기보다 **그 용어를 이해하는 데 필요한 부분만** 남긴다. 미션 사례를 쓰면 사례임을 그림이나 캡션에 밝힌다.

## 4. 이미지 보강 유형

| 유형 | 설명 방식 | 예 |
| --- | --- | --- |
| 구조형 | 요소의 위치와 관계 | VPC, Subnet, DOM, ERD |
| 흐름형 | 단계와 동작 과정 | Packet, HTTP, 이벤트 처리 |
| 비교형 | 개념 간 공통점·차이점 | 공인 IP·사설 IP |
| 계층·범위형 | 포함 관계와 범위 | CIDR, Call Stack, Scope |

유형은 **내부 제작·검토용 관리 기준**이다. canonical의 `type`·`category`나 용어 분류 체계를 바꾸지 않으며 데이터에 저장하지 않는다. 한 그림이 두 유형에 걸치면 주된 유형 하나를 적는다.

## 5. 대상 선별 기준

다음 질문으로 후보를 판단한다.

1. 텍스트만으로 설명하면 이해하기 어려운가?
2. 구조·위치·범위·순서가 핵심인가?
3. 실제 미션 수행에서 혼동이나 질문이 있었는가?
4. 기존 스토리·개념지도·가이드에 활용 가능한 그림이 있는가?
5. 이미지로 설명했을 때 새로운 오해가 생길 가능성은 없는가?
6. 기존 텍스트·표보다 이미지가 더 효과적인가?

**보강 대상이 아닌 것:** 장식, 용어명에 맞춘 일반 아이콘, 이미 본문 그림이나 텍스트 도식으로 충분히 전달되는 용어, 그림이 실제 기술 구조를 과하게 단순화해 오해를 만들 용어.

**조사 판정** — 후보마다 하나를 고른다.

| 판정 | 뜻 |
| --- | --- |
| 이미 그림이 충분함 | 용어 상세나 바로 연결된 자료에 맞는 그림이 있다. 등록하지 않는다 |
| 기존 그림을 재사용할 수 있음 | 미션 스토리·가이드에 같은 개념을 정확히 그린 그림이 있다 |
| 그림이 있지만 설명 보완이 필요함 | 텍스트 도식·그림이 있으나 표기 불일치·가독성 등 문제가 있다 |
| 신규 이미지 제작이 유용함 | 재사용할 그림이 없고, 그림의 효과가 분명하다 |
| 지금은 이미지가 필요 없음 | 텍스트로 충분하거나, 판단 근거(미션 수행 경험)가 아직 없다 |

**우선순위**

| 순위 | 기준 |
| --- | --- |
| P0 | 질문 1·2에 해당하고, **미션 수행 중 실제 질문·혼동 기록이 있으며**, 용어 상세에 현재 그림이 없거나 문제가 있다. 재사용할 승인 그림이 있어 비용이 낮다 |
| P1 | 그림의 효과가 분명하고 재사용 자료가 있으나, 실제 혼동 기록이 저장소에서 확인되지 않거나 다른 P0과 같은 그림을 나눠 쓸 수 있다 |
| P2 | 효과는 있지만 현재 텍스트 도식으로 상당 부분 전달된다. 강의 피드백 후 다시 판단한다 |

## 6. 제작 원칙

- 하나의 용어에는 우선 **핵심 그림 1장**을 권장한다. 짝을 이루는 용어(예: PK·FK)는 같은 그림을 나눠 쓸 수 있다.
- 정확한 정의와 설명을 그림으로 대체하지 않는다.
- 미션 스토리·가이드의 그림을 재사용할 수 있으면 먼저 검토한다.
- 사전에서는 강의용 그림을 그대로 옮기기보다 해당 용어에 맞게 간결하게 줄일 수 있다.
- 그림은 원리 설명이 목적이며 장식이 목적이 아니다.
- SVG를 우선 검토한다. 실제 화면처럼 복잡한 장면은 PNG도 허용한다.
- PC와 모바일(360·390px) 가독성을 확인하고 대체텍스트를 준비한다. 가로로 긴 그림은 모바일용 세로 배치 또는 가로 스크롤 안내를 함께 준비한다.
- 색상만으로 개념을 구분하지 않는다. 이름표·선 모양·문구를 함께 쓴다.
- 비유·단순화·실제 기술 구조의 경계를 캡션이나 본문에 밝힌다 (예: "교육용 단순화 모델", "B6-1 사례").
- 소스, 저작권, 수정 가능성, 재사용 범위를 확인한다. 미션 저장소의 실제 자원 ID·공인 주소·개인 정보는 옮기지 않는다.
- 기존 승인 그림은 임의로 덮어쓰지 않는다. 간결화가 필요하면 **새 파일**로 만들고 원본을 보존한다.

## 7. 검수 체크리스트

| 항목 | 확인 |
| --- | --- |
| 기술 정확성 | 그림의 선·화살표가 흐름(순서)인지 관계(참조·포함)인지 구분되는가? 실제 동작과 다르게 읽히지 않는가? |
| 용어 정합성 | 본문 정의·텍스트 도식·미션 스토리의 표기(기호·이름)와 어긋나지 않는가? |
| 새 오해 | 단순화로 생긴 예외를 본문이나 캡션이 설명하는가? |
| 가독성 | 1280px과 360·390px에서 글자·선이 읽히는가? 가로 넘침이 없는가? |
| 접근성 | 대체텍스트가 그림의 핵심을 전달하는가? 색 없이도 구분되는가? 대비가 충분한가? |
| 테마 | 사이트 테마 전환 때 그림이 읽히는가? 교육 그림에 일괄 invert·필터를 쓰지 않았는가? ([미션 공통 UI 기준](mission-guides/mission-ui-standard.md)) |
| 출처 | 원본 파일·커밋, 재사용 범위, 미션 사례 표시가 기록되었는가? |

결과는 해당 개정 작업의 QA 기록에 `PASS / 수정 필요 / 미검증`으로 남긴다.

## 8. 미션 제작과의 연결

새 필수 미션을 실제로 수행하고 스토리를 기획할 때 다음을 추가한다.

1. Owner가 미션을 수행한다.
2. 미션에서 이해하기 어려웠던 용어를 기록한다 (학습 노트 등).
3. 스토리·개념지도 제작 중 이미지 보강 후보를 고른다.
4. 기존 용어 설명과 시각 자료를 조사한다 (§3의 위치 전체).
5. 필요성과 교육 효과를 §5 기준으로 평가한다.
6. Owner가 후보를 승인한다.
7. 승인된 용어만 별도 콘텐츠 개정 작업으로 진행한다.
8. GPT 독립 검토와 Owner 시각 검수를 거쳐 웹에 통합한다.

새 미션마다 이미지 제작을 의무로 하지 않는다. 후보가 없으면 보강 없이 미션 콘텐츠만 완성해도 된다.

## 9. 역할과 승인

| 역할 | 책임 |
| --- | --- |
| Claude Code | 후보 조사, 용어 원고와 시각 자료 제작, 출처·자체 QA 기록, 로컬 커밋 |
| GPT | 내용과 기술적 정확성의 독립 검토 |
| Codex | 승인된 자료의 웹 통합(그림 등록·화면 검증) |
| Owner | 제작 방향, 후보 승인, 시각 검수, 공개 승인, Push·병합 |

Owner 승인 없이 그림을 공개하지 않는다. 기존 [거버넌스 계약](knowledge-encyclopedia/06-agent-governance-model.md)의 Owner Gate와 [workflow](mission-guides/workflow.md)의 단계를 바꾸지 않는다.

## 10. 후보 관리 항목과 상태

별도 데이터 모델이나 서비스 기능을 만들지 않는다. 처음에는 §11의 표로 관리한다.

후보별 기록 항목: canonical 용어 ID · 용어명 · 관련 미션 · 이미지가 필요한 이유 · 유형 · 기존 이미지 존재 여부 · 재사용 가능 여부 · 우선순위 · 근거 및 사용자 피드백 · 상태.

| 상태 | 뜻 |
| --- | --- |
| 후보 | 조사·판정 완료, 승인 전 |
| 승인 | Owner가 제작을 승인함 |
| 제작 | 원고·그림 작업 중 |
| 검수 | GPT 검토·Owner 시각 검수 중 |
| 공개 | 웹 통합 후 `main`에 병합·배포됨 |
| 보류 | 지금은 진행하지 않음 (이유를 적는다) |

### 11.2 P0 — 당장 보강이 유용한 후보

세 후보 모두 B6-1 스토리보드에 **Owner의 B6-1 학습 노트 질문**이 출처로 기록되어 있다 (`content/mission-stories/main-m11/storyboard-v0.2.md`, `[노트 n장]` 표기). 저장소에서 실제 학습 질문이 확인되는 유일한 근거라 P0으로 둔다.

**1. `erd` ERD — 구조형**

- 필요 이유: ERD는 그 자체가 그림 표기법이다. 용어 본문은 문자 도식(`1`·`<`·`○`)으로 그리는데, `○`(0개 가능)를 기호 설명에만 두고 도식에는 쓰지 않는다. B6-1 스토리·가이드는 선과 `1`/`N` 이름표로 그린다. 학습자가 스토리에서 사전으로 넘어오면 표기가 달라진다.
- 기존 자료: 용어 본문 텍스트 도식 · 스토리 `erd-story-desktop.svg`/`-mobile.svg` · 가이드 `v02-data-modeling.svg`
- 재사용: 가능. 표 6개를 2~3개로 줄인 간결판을 새 파일로 만든다. 텍스트 도식과 표기를 맞출지 함께 판단한다.
- 근거: `[노트 1장]` "우리가 만든 데이터베이스는 어떤 모양이고, ERD는 무엇인가?"

**2. `foreign-key` 외래 키 — 구조형 (`primary-key`와 공유)**

- 필요 이유: "FK가 다른 표의 PK를 가리킨다"는 위치와 방향이 핵심인데, 두 용어 본문에 그림·도식이 없다. 본문 예시는 `users`/`orders`로 B6-1 사례(`student`/`enrollment`)와 다르다.
- 기존 자료: 가이드 `v03-keys-relations.svg`(부모·자식 표와 가리키는 번호) · 스토리 `split-story` `keys` 상태
- 재사용: 가능. 가이드 V03이 용어 설명에 가장 가깝다.
- 근거: `[노트 5장]` "PK와 FK는 무엇이고 왜 쓰는가? 엑셀과는 무엇이 다른가?"

**3. `join` JOIN — 비교형 (`left-join`·`inner-join`과 공유)**

- 필요 이유: INNER와 LEFT의 차이는 "짝이 없는 행이 남는가"이며, 표 두 개를 나란히 볼 때 바로 보인다. 현재 `join` 본문은 SQL 코드와 문장뿐이다.
- 기존 자료: 가이드 `v06-sql-joins.svg` · 스토리 `join-compare-desktop.svg`/`-mobile.svg` (같은 B6-1 데이터 사용)
- 재사용: 가능. B6-1 실제 데이터(학생 이름)를 쓰므로 "B6-1 사례" 표시를 하거나 일반 예시로 바꾼다.
- 근거: `[노트 4장]` "JOIN은 왜 필요하고, INNER JOIN과 LEFT JOIN은 무엇이 다른가?" · 스토리 S04-2 "AI 초안 INNER JOIN에서 수강 0건 학생이 빠짐" 사례

### 11.4 P2와 보류

- **#10 `responsive-web-design` (P2):** 가이드 `v03-responsive-layout.svg`가 "같은 HTML, 폭마다 다른 배치"를 잘 보여 준다. 다만 본문 설명만으로도 이해가 크게 어렵지 않아 강의 피드백 후 판단한다.
- **#11 `packet` (P2):** 본문 텍스트 도식이 스토리 V2와 같은 겹 구조를 이미 보여 준다. 모바일(360px)에서 고정폭 도식이 넘치는지 확인한 뒤, 문제가 있을 때만 그림으로 바꾼다.
- **#12 `cidr` (보류):** 본문에 `cidr-range.svg`가 이미 있고 가이드 2장에도 있다. 다시 만들지 않는다.
- **#13 `subnet` (보류):** 본문 텍스트 도식(구역별 주소 범위·AWS 예약 주소)과 개념 연결 `network-aws-role-comparison`의 구조도로 충분하다. 강의에서 혼동이 보고되면 다시 본다.
- **#14 `browser-rendering` (보류):** 본문 텍스트 도식이 단계 흐름을 이미 보여 준다. B1-1 `f6-browser`는 세 파일의 역할 관계 그림이라 이 용어의 단계(layout·paint·합성)와 맞지 않는다. 다만 `정확한 설명` 절이 한 문장으로 짧아, 그림보다 **텍스트 보완**이 먼저다(별도 개정 후보).
- **#15 `call-stack` · `scope` (보류):** 작업 지시의 예시 영역이었으나, 네 미션의 스토리·가이드가 다루지 않는다(`call-stack`은 B1-1·B5-2, `scope`는 예비 M02·B1-1에 `related`로만 연결). 판단 근거가 될 미션 수행 경험이 없으므로 관련 미션을 Owner가 수행한 뒤 다시 본다.

### 11.5 조사 중 발견한 텍스트 개정 후보 (그림과 별개)

다음은 그림이 아니라 용어 본문의 문제다. 이번 작업에서 고치지 않으며, 필요하면 별도 개정 작업으로 제안한다.

- `erd`: 텍스트 도식에서 `○` 기호를 정의만 하고 쓰지 않는다. 스토리와 표기 방식이 다르다.
- `primary-key`·`foreign-key`·`join`: 미션 맥락 절이 "본과정 M11"로 적혀 있고 예시가 B6-1 사례와 다르다. B6-1 스토리와 왕복할 때 연결이 약하다.
- `browser-rendering`: `정확한 설명` 절이 한 문장이다.
