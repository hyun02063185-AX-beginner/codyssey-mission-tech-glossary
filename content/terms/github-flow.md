# GitHub Flow

## 한 줄 설명

짧은 feature branch와 pull request로 main에 자주 병합하는 협업 흐름.

## 쉽게 설명하면

중심 줄기 하나와 짧은 작업 줄기들로 일하는 방식입니다. 작업 줄기는 검토를 거쳐 곧바로 중심에 합칩니다.

## 정확한 설명

중심 브랜치는 항상 배포 가능한 상태로 두고, 변경은 짧은 브랜치에서 만들어 검토 요청을 거쳐 합친다. 별도의 개발용 브랜치나 릴리스 브랜치를 두지 않아 규칙이 단순하며, 그래서 합치는 주기가 짧다는 전제 위에서만 작동한다.

## 이 미션에서는 왜 필요한가

이 회차의 협업 흐름입니다. 규칙이 적어 처음 협업하는 팀에 맞는데, 그만큼 "짧게 작업하고 자주 합친다"는 전제가 지켜지지 않으면 이점이 사라집니다.

## 코드 예

```text
1. main 에서 브랜치를 판다        feature/login
2. 커밋하고 원격에 올린다
3. Pull Request 를 연다
4. 동료가 검토하고 승인한다
5. main 에 합친다
6. 브랜치를 지운다

main 은 항상 동작하는 상태로 둔다.
2~5 가 며칠씩 걸리기 시작하면 이 흐름의 이점이 사라진다.
```

## 주의할 점 / 경계 조건

여러 버전을 동시에 유지해야 하는 제품에는 맞지 않습니다. 그런 경우에는 릴리스 브랜치를 따로 두는 방식이 필요합니다.

## 관련 용어

- `git`
- `commit`

## 흔한 오해

흐름을 정했으니 알아서 지켜질 것 같지만, 규칙은 설정으로 강제해야 지켜집니다. 사람의 기억에 맡기면 급할 때 건너뛰게 됩니다.

## 동료평가 질문

이 흐름이 잘 작동하기 위한 전제를 하나 들고, 지켜지지 않으면 무엇이 문제가 되는지 설명할 수 있나요?
