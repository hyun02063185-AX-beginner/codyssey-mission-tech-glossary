# Browser Rendering

## 한 줄 설명

브라우저가 HTML과 CSS로 구조와 스타일을 계산하고, 화면에 보일 픽셀을 만드는 과정입니다.

## 쉽게 설명하면

HTML은 제목·버튼 같은 화면의 구조를, CSS는 그 모양과 배치를 정합니다. 브라우저는 이 정보를 읽어 크기와 위치를 계산하고 색·글자·그림을 그립니다. JavaScript는 버튼을 누를 때 메뉴를 여는 것처럼 화면 내용을 바꾸는 데 사용될 수 있습니다.

![HTML에서 만든 DOM과 CSS에서 만든 CSSOM을 바탕으로 스타일 계산, Layout(크기와 위치), Paint(색·글자·그림), Compositing(레이어 합성)을 거쳐 화면을 표시합니다. CSS 변경에 따라 필요한 단계는 달라질 수 있습니다.](assets/browser-rendering.svg)

## 정확한 설명

- **DOM**: 브라우저가 HTML을 읽어 만든 문서의 트리 구조입니다. JavaScript는 DOM의 요소·텍스트·속성을 바꿀 수 있습니다.
- **CSSOM**: CSS 규칙을 브라우저가 다룰 수 있도록 표현한 구조입니다. 화면에 그릴 대상과 스타일을 연결한 Render Tree와 같은 개념은 아닙니다.
- **스타일 계산**: DOM 요소에 어떤 CSS 규칙이 적용되는지 판단하고 상속과 우선순위 등을 반영해 사용할 스타일 값을 계산합니다. 이를 바탕으로 화면 배치에 필요한 구조를 준비하며, `display: none`인 요소처럼 배치에 참여하지 않는 경우도 있습니다.
- **Layout(배치)**: 화면에 배치할 상자의 크기와 위치를 계산합니다. 한 요소의 크기 변화가 주변 배치에 영향을 주면 영향을 받는 범위도 다시 계산할 수 있습니다.
- **Paint(그리기)**: 배치 결과와 스타일을 바탕으로 글자·색·테두리·그림 등을 어떻게 그릴지 정합니다. 실제 표시할 픽셀로 만드는 작업(래스터화)도 이어집니다.
- **Compositing(합성)**: 준비된 레이어의 그리기 결과를 위치와 겹치는 순서 등에 맞게 합쳐 화면을 구성합니다. 이미 그려 둔 결과를 재사용할 수 있으면 Layout이나 Paint 일부를 생략할 수 있습니다.

위 순서는 교육용 기본 흐름입니다. 브라우저마다 내부 구현과 최적화가 다르며, 매 프레임마다 모든 단계가 반드시 실행되는 것은 아닙니다.

## 이 미션에서는 왜 필요한가

B1-1 홈페이지 미션에서 CSS로 글자 크기나 메뉴 색을 바꾸면, 브라우저는 변경의 영향을 계산해 화면에 반영합니다. JavaScript로 메뉴의 클래스나 텍스트를 바꾸는 DOM 변경도 필요한 렌더링 작업으로 이어질 수 있습니다. 무엇을 바꿨는지와 영향 범위를 알면 화면 반응이 느린 이유를 찾아볼 수 있습니다.

## 코드 예

```js
const menu = document.querySelector('.menu'); // 해당 요소가 있는 페이지의 예
menu.style.width = '240px';
menu.style.backgroundColor = 'navy';
menu.style.transform = 'translateX(8px)';
// DOM의 스타일은 바뀌지만 실제 화면 반영은 브라우저의 렌더링 시점에 이뤄집니다.
```

| 변경 사례 | 일반적인 영향 |
| --- | --- |
| `width`, `font-size` | 크기·배치가 달라지면 Layout 및 후속 단계가 필요할 수 있음 |
| `color`, `background-color` | 주로 Paint 및 후속 단계 |
| `transform`, `opacity` | 이미 그린 레이어를 재사용할 조건이 맞으면 주로 Compositing |

이 표는 각 변경을 따로 볼 때의 경향입니다. 위 코드처럼 함께 바꾸면 필요한 작업이 합쳐질 수 있으며, 속성 이름만으로 실행 단계나 비용을 확정할 수는 없습니다.

## 주의할 점 / 경계 조건

DOM을 바꿔도 보이지 않는 요소의 변경처럼 Layout이 필요하지 않은 경우가 있습니다. 실제 계산 범위는 다른 요소와의 관계, 화면 상태, 브라우저 최적화에 따라 달라집니다.

`transform`과 `opacity`도 레이어 준비나 새 그리기가 필요할 수 있습니다. 레이어가 많으면 메모리 비용도 늘어나므로 합성 위주라는 이유만으로 모든 상황에서 가장 빠르다고 보장할 수 없습니다. 성능 문제는 개발자 도구에서 실제 작업을 측정하며 확인합니다.

## 흔한 오해

DOM 변경이 곧 즉시 화면 표시라는 뜻은 아닙니다. DOM 자체는 코드 실행 중 바뀌지만, 브라우저는 보통 변경을 모아 렌더링 기회에 화면을 갱신합니다. 긴 JavaScript 작업은 그 기회를 늦출 수 있습니다. 크기 정보를 읽는 코드가 계산을 앞당기는 경우도 있지만, 그 자체가 즉시 화면 표시를 보장하지는 않습니다.

모든 변경에서 Layout이 발생하는 것도, 합성만 수행하면 언제나 부드러운 것도 아닙니다. 필요한 단계와 각 단계의 작업량을 함께 봐야 합니다.
