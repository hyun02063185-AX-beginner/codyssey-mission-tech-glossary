# Commit History

## 한 줄 설명

repository에 쌓인 commit graph와 변경 기록.

## 쉽게 설명하면

저장소에 쌓인 커밋들의 기록입니다. 언제 누가 무엇을 왜 바꿨는지가 여기 남습니다.

## 정확한 설명

커밋이 부모를 가리키며 이어진 구조다. 각 커밋은 그 시점의 전체 상태와 부모, 작성자, 메시지를 담으며, 이력을 다시 쓰면 새 커밋이 만들어지고 해시가 바뀐다. 따라서 공유된 뒤의 이력 재작성은 다른 사람의 기록과 어긋난다.

## 이 미션에서는 왜 필요한가

이 회차에서 협업의 증거가 되는 기록입니다. 각자 무엇을 했는지가 여기 남으므로 평가의 대상이 되는데, 이력을 다시 쓰면 해시가 달라져 이미 가져간 사람과 어긋나므로 언제 정리해도 되는지 판단이 필요합니다.

## 코드 예

```bash
git log --oneline --graph --all -15

# 누가 얼마나 했는지
git shortlog -sn

# 특정 파일의 이력
git log --follow -p src/app.py

# 해시가 바뀌는지 직접 확인
git log --oneline -1          # 해시를 적어 둔다
git commit --amend -m "고침"
git log --oneline -1          # 다른 해시다 — 같은 커밋이 아니다
```

## 주의할 점 / 경계 조건

공유한 뒤에 이력을 다시 쓰면 다른 사람의 기록과 어긋납니다. 정리는 공유 전에 합니다.

## 관련 용어

- `git`
- `commit`

## 흔한 오해

커밋 메시지를 고치면 그 커밋이 수정된다고 생각하기 쉽지만, 새 커밋이 만들어지고 해시가 달라집니다. 원래 것은 참조가 없어진 채로 남습니다.

## 동료평가 질문

이력을 정리해도 되는 시점과 그러면 안 되는 시점을 구분해 설명할 수 있나요?
