# Subnet

## 한 줄 설명

서브넷은 네트워크를 구역으로 나누고 구역마다 정한 IP 주소 범위입니다.

## 쉽게 설명하면

회사 건물을 층별로 나누고 층마다 방 번호 범위를 정해 두는 것과 비슷합니다. 주소만 보고 어느 구역인지 알 수 있고, 구역마다 다른 길 안내와 출입 규칙을 붙이기 쉬워집니다. 비유는 여기까지입니다.

## 정확한 설명

서브넷(subnetwork)은 IP 주소 범위로 정한 네트워크의 한 구역이며, 범위는 CIDR(`10.0.1.0/24`)로 적는다. 다른 서브넷으로 가는 패킷은 경로 규칙(라우터·Route Table)을 따라간다. 서브넷으로 나누는 것만으로 통신이 막히지는 않는다. 어디로 보낼지는 경로 규칙이, 통과를 허용할지는 방화벽·Security Group 같은 허용 규칙이 따로 정한다. AWS의 Subnet은 VPC 주소 범위 안에서 만들고, 하나의 가용 영역에 속하며, Subnet마다 Route Table이 하나 연결된다. 각 Subnet의 앞 4개와 마지막 1개 주소는 AWS가 예약해 쓰므로 실제로 쓸 수 있는 개수는 계산보다 적다.

## 동작 원리

AWS에서는 Subnet을 만들 때 VPC 범위 안에서 더 좁은 범위를 지정합니다. 그 안에 만든 자원은 이 범위의 주소를 받고, Subnet에 연결된 Route Table이 그 자원에서 나가는 트래픽의 다음 대상을 정합니다.

## 이 미션에서는 왜 필요한가

B3-1(M05)은 VPC `10.0.0.0/16` 안에 Subnet `10.0.1.0/24` 하나를 만들고 EC2를 두었습니다. 이 Subnet은 인터넷 게이트웨이로 가는 경로가 있는 Route Table에 연결되어 Public Subnet이 되었습니다. 미션 스토리의 일반 기업망 예시처럼 공개 서버·업무망·자료 저장을 구역별로 나누는 설계도 있지만, B3-1에는 구역이 하나뿐이고 데이터베이스용 구역도 만들지 않았습니다.

## 코드 예

```text
일반 기업망 예시 (미션 스토리 Scene 01 · 설명용 사설 주소)
  DMZ          172.16.10.0/24
  자료 저장     10.20.30.0/24
  업무망        192.168.10.0/24
  ← 구역마다 주소 범위 하나. 허용 여부는 방화벽 규칙이 따로 정한다

B3-1 AWS (2026-10-14 배포 기록)
  VPC     10.0.0.0/16   (65,536개)
  Subnet  10.0.1.0/24   (256개)   Route Table: 0.0.0.0/0 → IGW

AWS가 각 Subnet에서 예약하는 주소 (/24 → 쓸 수 있는 것 251개)
  .0   네트워크 주소
  .1   VPC 라우터
  .2   DNS
  .3   예약
  .255 브로드캐스트 자리 (VPC는 브로드캐스트를 지원하지 않아 예약)
```

## 주의할 점 / 경계 조건

나누기는 주소 범위를 정하는 일이지 통신을 막거나 허용하는 일이 아닙니다. AWS의 같은 VPC 안 Subnet끼리는 기본 local 경로로 서로 닿을 수 있고, 막으려면 Security Group이나 Network ACL 같은 규칙이 필요합니다. AWS Subnet은 하나의 가용 영역에만 속하므로, 여러 영역에 서비스를 두려면 영역마다 따로 만들어야 합니다.

## 관련 용어

- `cidr`
- `ip-address`
- `private-ip`
- `virtual-private-cloud`
- `route-table`
- `public-subnet`

## 흔한 오해

서브넷을 나누면 서로 통신이 안 된다고 생각하기 쉽지만, 나누기는 주소 범위를 정하는 일이고 통신 허용은 별도 규칙이 정합니다. 또 /24로 나누면 254개를 쓸 수 있다고 생각하기 쉽지만, AWS는 5개를 예약해 251개입니다.

## 비슷한 개념과의 차이

VPC는 AWS 안의 가상 네트워크 전체 범위이고, Subnet은 그 안의 구역입니다. Public Subnet은 Subnet의 별도 종류가 아니라, 연결된 Route Table에 인터넷 게이트웨이로 가는 경로가 있다는 뜻입니다.
