# SSH 키

## 한 줄 설명

비밀번호 대신, 나만 가진 파일로 "나 맞아요"를 증명해서 서버에 로그인하는 방법입니다.

## 쉽게 설명하면

> **비유:** 서버에는 내 **인감 견본**(공개키)만 맡겨 두고, 나는 **도장**(개인키)을 갖고 있습니다. 서류에 도장을 찍어 보내면 서버가 견본과 대조해 본인인지 확인합니다. 도장 자체는 서버에 건네지 않습니다.

이 비유가 맞는 곳과 어긋나는 곳이 있습니다.

| | 비유 | 실제 SSH |
|---|---|---|
| 서버가 가진 것 | 인감 견본 | 공개키 |
| 내가 가진 것 | 도장 | 개인키 (파일) |
| 증명 방법 | 서류에 도장 찍기 | 개인키로 **서명**을 계산해서 보내기 |
| 어긋나는 점 | 도장 찍힌 서류는 다시 쓸 수 있음 | 서명은 **그 연결에서만 유효한 값**을 포함해 매번 새로 계산되므로 다른 연결에 재사용할 수 없음 |

## 정확한 설명

### 개인키를 보내지 않는데 어떻게 인증될까

![SSH 키 인증 흐름](assets/ssh-key-auth.svg)

1. 서버에는 **공개키**가 미리 등록되어 있습니다.
2. 클라이언트는 **개인키로 서명**을 만듭니다. 서명에는 이 연결에서만 쓰이는 세션 식별자, 사용자 이름 등이 들어갑니다.
3. 클라이언트는 **공개키와 서명**만 보냅니다. 개인키 파일은 어느 단계에서도 전송되지 않습니다.
4. 서버는 등록된 공개키로 서명을 **검증**합니다. 맞으면 "그 개인키를 가진 사람"으로 인정합니다.

공개키로 서명을 검증할 수는 있어도, 공개키만으로 서명을 만들 수는 없습니다. 그래서 공개키는 알려져도 괜찮고, 개인키는 지켜야 합니다.

> **헷갈리기 쉬운 점 — 암호화와 서명은 다릅니다.** "공개키로 암호화하고 개인키로 푼다"는 설명을 먼저 들으면 SSH 로그인도 그렇게 동작한다고 오해하기 쉽습니다. SSH 로그인에서 개인키가 하는 일은 **내용을 푸는 것이 아니라 서명을 만드는 것**이고, 공개키가 하는 일은 **그 서명이 맞는지 확인하는 것**입니다.

## EC2 Key Pair와 SSH 접속의 관계

EC2에서 Key Pair를 만들면 이 흐름이 그대로 이어집니다.

1. AWS가 키 쌍을 만들고 **공개키는 AWS가 보관**하며, **개인키 파일(`.pem`)은 만든 사람이 내려받습니다.** 개인키를 내려받을 기회는 만들 때 한 번뿐이라고 안내됩니다.
2. Linux EC2 인스턴스를 시작할 때 그 Key Pair를 지정하면, 첫 부팅 때 공개키가 로그인 허용 키 목록(`~/.ssh/authorized_keys`)에 등록됩니다.
3. 접속할 때 내려받은 개인키로 서명하고, 서버는 등록된 공개키로 검증합니다.

| | 내 PC에서 직접 만들 때 | EC2 콘솔에서 Key Pair를 만들 때 |
|---|---|---|
| 키 쌍을 만드는 곳 | 내 컴퓨터 (`ssh-keygen`) | AWS |
| 개인키 | 내 컴퓨터에 처음부터 있음 | 만들 때 **한 번** 내려받음 (`.pem`) |
| 공개키 | 서버에 내가 직접 등록 | AWS에 보관, 인스턴스에 등록됨 |
| 주의 | 개인키 파일 권한 | 내려받은 파일 분실 시 같은 개인키를 다시 받을 수 없음 |

## 서버를 믿는 키와 나를 증명하는 키는 다릅니다

SSH에서는 **두 방향의 확인**이 서로 다른 키로 일어납니다.

| | 호스트 인증 | 사용자 인증 |
|---|---|---|
| 확인하는 것 | **서버가 진짜인지** | **내가 그 사용자인지** |
| 증명하는 쪽 | 서버 | 나 (클라이언트) |
| 사용하는 키 | 서버의 **호스트 키** | 내 **개인키 / 공개키** |
| 기록되는 곳 | 내 컴퓨터의 `known_hosts` (서버의 **호스트 공개키**) | 서버에 등록된 공개키 목록 |
| 처음 접속할 때 | 호스트 공개키에서 계산한 지문을 보여 주고 확인을 요청 | 키가 등록돼 있으면 별도 입력 없이 진행 |
| 문제가 생기면 | 지문이 달라졌다는 **경고** | 접속 거부 (`Permission denied`) |

`known_hosts`에는 서버의 호스트 **공개키**가 저장됩니다. 화면에 보이는 지문은 그 공개키에서 계산한 짧은 확인값입니다.

> **지문 경고가 뜨면:** 서버를 다시 만들었거나 다른 서버로 바뀌었을 수 있습니다. 경고를 지우고 넘어가기 전에 이유부터 확인합니다.

## 코드 예

### 명령어가 실제로 하는 일

```bash
chmod 400 ./b3-1-demo-key.pem
ssh -i ./b3-1-demo-key.pem ec2-user@203.0.113.10
```

| 명령 | 의미 | 주의 |
|---|---|---|
| `chmod 400 ./b3-1-demo-key.pem` | 파일을 **소유자만 읽을 수 있게** 합니다. (`4` = 읽기, 소유자에게만) | SSH 클라이언트는 다른 사람이 읽을 수 있는 개인키 파일을 사용하지 않습니다. |
| `ssh -i ./b3-1-demo-key.pem` | 로그인에 쓸 **개인키 파일의 경로**를 알려 줍니다. | 파일 경로를 지정할 뿐입니다. **파일 내용이 서버로 전송되지 않습니다.** 서명을 만드는 데만 읽습니다. |
| `ec2-user@203.0.113.10` | 어느 서버에 어느 사용자로 들어갈지 | `ec2-user`는 Amazon Linux 예시이고 실제 기본 사용자 이름은 AMI마다 다릅니다. `203.0.113.10`은 문서용 예시 주소입니다. |

> 위 명령은 실행 가능한 **문서용 예시**입니다. `b3-1-demo-key.pem`과 `203.0.113.10`을 실제 키 파일 이름이나 서버 주소로 오해하지 않습니다. 실제 개인키 내용, 사용자 계정명, 서버 주소는 문서나 저장소에 기록하지 않습니다.

## 개인키를 GitHub에 올리거나 공유하면 안 되는 이유

개인키를 가진 사람은 **누구나 나로 로그인**할 수 있습니다. 서버는 서명이 맞는지만 확인하고, 서명한 사람이 누구인지는 알 수 없기 때문입니다.

- 공개 저장소에 한 번이라도 올라가면, 이후에 파일을 지워도 **커밋 기록·복제본·캐시**에 남을 수 있습니다.
- 올렸다면 "지웠으니 괜찮다"가 아니라 **그 Key Pair를 폐기하고 새로 만드는 것**이 안전한 대응입니다.
- `.gitignore`에 `*.pem`을 넣어 실수로 커밋되는 것을 막아 둡니다.

## 흔한 오해

| 오해 | 실제 |
|---|---|
| 서버에 개인키를 올려야 로그인된다 | 서버에는 **공개키**만 있고, 개인키는 내 컴퓨터를 떠나지 않습니다. |
| `ssh -i`가 키 파일을 서버로 보낸다 | 로컬 파일 경로를 알려 주는 옵션입니다. |
| 공개키로 암호화한 내용을 개인키로 푸는 방식이다 | 로그인에서는 **서명을 만들고 검증**합니다. |
| 서버의 지문 확인이 내 키를 확인하는 단계다 | 서버가 진짜인지 확인하는 **호스트 인증**이고, 내 키는 그다음 단계입니다. |
| 키를 쓰면 비밀번호보다 덜 안전하다 | 추측으로 뚫기 어려워 일반적으로 더 안전합니다. 단, 개인키 파일 관리가 보안의 전부가 됩니다. |

## 이 미션에서는 왜 필요한가

B3-1은 EC2에 접속해 Nginx를 확인하는 미션입니다. SSH 22번 포트는 인터넷에 열려 있는 관리용 문이라, **비밀번호 대신 Key Pair**로 로그인하고 **Security Group에서 내 공인 IP 하나(`/32`)만 허용**합니다. 개인키가 새면 포트 제한과 상관없이 같은 IP에서 누구나 들어올 수 있으므로, 둘 다 필요합니다.

## 동료평가 질문

1. 서버에 공개키만 있는데 어떻게 "내가 그 사람"인지 확인할 수 있나요?
2. 접속할 때 `.pem` 파일이 서버로 전송되나요? 왜 그렇게 생각하나요?
3. "지문이 바뀌었다"는 경고와 `Permission denied`는 각각 어떤 확인이 실패한 것인가요?
4. 개인키를 실수로 GitHub에 올렸다면 파일을 지우는 것으로 충분한가요?
