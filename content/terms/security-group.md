# Security Group

## 한 줄 설명

cloud resource의 inbound·outbound traffic을 제어하는 가상 방화벽 규칙.

## 쉽게 설명하면

EC2에 들어오고 나가는 통신을 포트와 출처별로 걸러 주는 가상 방화벽 규칙입니다.

## 정확한 설명

Security Group은 VPC나 Subnet 자체가 아니라 EC2의 네트워크 인터페이스에 적용하는 상태 기반 가상 방화벽이다. Inbound는 서버로 들어오는 통신, Outbound는 서버에서 나가는 통신이다. 허용된 Inbound 연결의 응답은 상태를 기억해 별도 Outbound 규칙 없이도 반환될 수 있다. 허용 규칙만 적을 수 있고 적지 않은 것은 모두 막힌다.

## 이 미션에서는 왜 필요한가

B3-1에서 배포한 EC2에 외부에서 접속할 수 있게 만드는 설정입니다. HTTP 80은 누구나 웹 페이지를 볼 수 있도록 `0.0.0.0/0`에 열고, 관리용 SSH 22는 현재 공인 IP 하나(`/32`)에만 엽니다. 웹 포트를 열지 않으면 서버가 정상 동작해도 밖에서 보이지 않고, 반대로 필요 이상으로 열면 열어 둔 만큼 노출됩니다.

## 코드 예

```text
인바운드 규칙 (들어오는 것만 적는다)

  유형    포트   출처              이유
  SSH     22     현재 공인 IP/32   관리 접속. 0.0.0.0/0 로 열지 않는다
  HTTP    80     0.0.0.0/0         누구나 접속해야 한다
  HTTPS   443    0.0.0.0/0         HTTPS를 쓸 때만 (B3-1은 설정하지 않음)

유형 HTTP·SSH 는 프로토콜 TCP + 포트 80·22 를 고르는 이름이다.
규칙은 출발지 · 프로토콜 · 포트를 보고, HTTP 내용은 검사하지 않는다.

아웃바운드는 기본값 그대로 둔다.
들어온 연결의 응답은 규칙 없이도 나간다.

접속이 안 될 때 확인 순서
  1. 여기 규칙   2. 서버 안 방화벽(OS 방화벽)   3. 서비스가 그 포트에서 떠 있는지
```

## 주의할 점 / 경계 조건

접속이 안 될 때 원인이 여기일 수도 서버 안의 방화벽일 수도 있습니다. 두 겹이 모두 열려야 통하므로 한쪽만 보고 판단하면 안 됩니다.

## 관련 용어

- `route-table`
- `socket-port`
- `cidr`
- `port-80-http`
- `port-22-ssh`
- `network-protocol`

## 흔한 오해

Security Group이 Subnet 전체에 붙는 방화벽이라고 생각하기 쉽지만, 실제 적용 단위는 EC2의 네트워크 인터페이스입니다. 또한 나가는 규칙을 매 연결마다 함께 열어야 한다고 생각하기 쉽지만, 허용된 Inbound 연결의 응답은 상태를 기억해 자동으로 나갑니다.

## 비슷한 개념과의 차이

Security Group은 출발지 IP·프로토콜·포트를 보고 통과를 허용하는 규칙이고, Route Table은 목적지 IP를 보고 다음 대상을 정하는 경로 규칙입니다. 허용 규칙이 있어도 경로가 없으면 통신되지 않고, 경로가 있어도 허용 규칙이 없으면 막힙니다. 일반 기업망의 경계 방화벽 장비와 허용 판단 역할은 비슷하지만, Security Group은 장비가 아니라 네트워크 인터페이스에 적용하는 규칙이라 위치가 다릅니다.
