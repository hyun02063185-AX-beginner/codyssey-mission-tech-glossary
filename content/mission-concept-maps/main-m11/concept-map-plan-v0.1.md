> 검토 기록: [review.md](review.md)

**지도의 질문:** 스토리에서 만난 데이터베이스 용어들은 서로 어떤 관계일까?

스토리는 "흩어진 데이터가 하나의 답이 되는 **과정**"을 순서대로 보여 준다. 이 지도는 그 과정에 나온 용어가 **무엇이 무엇을 담고, 구별하고, 가리키고, 요청하는지**만 보여 준다. 실행 순서나 SQL 문법은 그리지 않는다.

## 1. 핵심 개념 (11개)

| # | 개념 (화면 이름) | 영역 | 짧은 설명 (지도 상세 패널) | canonical 용어 ID | 연결 방식 |
| --- | --- | --- | --- | --- | --- |
| 1 | **데이터베이스** (관계형 데이터베이스) | 중심 | 규칙에 따라 정리해 둔 데이터의 모음이다. 관계형 데이터베이스는 데이터를 테이블로 나누어 담고 테이블끼리 잇는다. | `relational-database` | direct |
| 2 | **DBMS** | 중심 | 데이터베이스를 만들고, 읽고 쓰고, 규칙을 검사하는 프로그램이다. B6-1에서는 SQLite를 썼다. | — (단독 ID 없음) | none → 가이드 1장 · 관련 `sqlite` |
| 3 | **테이블** (Table) | 데이터 구조 | 같은 모양의 기록을 모아 담는 표다. 학생·수업처럼 주제마다 하나씩 만든다. | `table` | direct |
| 4 | **행** (Row) | 데이터 구조 | 테이블에 담긴 기록 한 건이다. 학생 테이블이라면 학생 한 명이 한 행이다. | — | extension → `table` |
| 5 | **열** (Column) | 데이터 구조 | 모든 행이 공통으로 가지는 정보의 종류다. 이름과 데이터 타입이 정해져 있다. | — | extension → `table` · 관련 `column-data-type` |
| 6 | **기본키** (PK) | 데이터 관계 | 테이블 안에서 각 행을 하나씩 구별하는 열(또는 열 묶음)이다. 값이 겹치거나 비어 있을 수 없다. | `primary-key` | direct |
| 7 | **외래키** (FK) | 데이터 관계 | 다른 테이블의 PK 값을 가리키는 열이다. 없는 값을 가리키지 못하도록 DBMS가 검사할 수 있다. | `foreign-key` | direct |
| 8 | **관계** (Relationship) | 데이터 관계 | 테이블과 테이블이 이어진 방식이다. "학생 1명 : 수강 기록 여러 건"처럼 몇 대 몇인지로 읽는다. | — | extension → `one-to-many-relationship` · 관련 `many-to-many` `cardinality` |
| 9 | **ERD** | 데이터 관계 | 테이블과 관계를 한 장에 그린 설계도다. 상자는 테이블, 선은 관계다. | `erd` | direct |
| 10 | **SQL** | 데이터 활용 | 데이터베이스에 원하는 일을 요청하는 언어다. 테이블을 만들고 데이터를 조회·추가·변경·삭제한다. | `sql` | direct |
| 11 | **JOIN** | 데이터 활용 | 여러 테이블의 행을 조건에 맞춰 이어 한 결과로 보여 주는 조회 방법이다. 테이블을 영구히 합치지 않는다. | `join` · 관련 `inner-join` `left-join` | direct |

- **canonical ID 7개는 모두 실제로 있다.** `glossary-master-v0.1.yaml`과 `src/data/generated/glossary.json` 양쪽에서 확인했고, 7개 모두 `main/M11` 출처와 상세 설명(`hasDetailedContent`)이 있다.
- **단독 ID가 없는 4개**(DBMS · 행 · 열 · 관계)는 ID를 새로 만들지 않았다. 연결 방식은 B2-1 후보 지도의 `glossary.mode` 어휘(`direct` · `extension` · `none`)를 그대로 쓴다.
  - `extension`: 더 넓은 항목으로 보낸다. 상세 패널에 "행·열은 *table* 항목 안에서 설명합니다" 같은 안내를 한 줄 붙인다.
  - `none`: 사전 링크 없음. DBMS는 [학습가이드 1장](../../mission-guides/main-m11/chapters/01-database-basics.md)으로 보내고, `sqlite`는 "B6-1이 쓴 DBMS"로만 소개한다.
- 관련 ID(`sqlite` `column-data-type` `one-to-many-relationship` `many-to-many` `cardinality` `inner-join` `left-join`)도 모두 있다. 노드가 아니라 상세 패널의 "더 알아보기" 링크로만 쓴다.

### 선정 이유

| 개념 | 왜 핵심에 넣었나 |
| --- | --- |
| 데이터베이스 · DBMS | 스토리 S03-1 · S04-1의 메시지("SQL은 요청하는 언어, DBMS는 실행하고 지키는 프로그램")가 둘의 구분이다. 지도의 출발점이 된다. **데이터베이스와 관계형 데이터베이스는 노드 하나로 합쳤다.** 학습가이드 1장도 둘을 같은 사전 항목으로 연결하고, 입문자에게 두 노드는 차이를 설명하기 어렵다. |
| 테이블 · 행 · 열 | S02-1 · S02-2의 "나누기"와 PK의 정의("행을 구별")를 설명하려면 행·열이 필요하다. 사전 항목은 없지만 지도에서 가장 기초가 되는 말이다. |
| PK · FK | 학습 목표 ② "표를 나누고 PK·FK로 잇는 이유". S02-3의 핵심이다. |
| 관계 | ERD의 "선"과 FK가 공통으로 가리키는 대상이다. 이 노드가 없으면 "ERD는 무엇을 그리나", "FK는 무엇을 남기나"를 선으로 보여 줄 수 없다. |
| ERD | 학습 목표 ①, Scene 01 전체, S04-3의 복귀 지점이다. |
| SQL · JOIN | 학습 목표 ③, Scene 03 전체. |

## 2. 관계 (12개)

관계 유형은 B2-1 지도의 다섯 가지 중 **두 가지만** 쓴다. 뜻도 B2-1과 같다.

| 유형 | 뜻 |
| --- | --- |
| **포함** | 한 개념이 다른 개념을 안에 담는다. |
| **역할** | 한 개념이 다른 개념에 대해 맡는 일(관리·구별·가리킴·그림·요청·잇기). |

B2-1의 "사용"은 쓰지 않는다. `SQL → DBMS`를 "사용"으로 두면 SQL이 DBMS를 쓰는 것처럼 읽혀 뜻이 뒤집힌다.

| ID | 출발 → 도착 | 유형 | 선 이름표 | 한 문장 설명 | 처음 화면 | 스토리 |
| --- | --- | --- | --- | --- | --- | --- |
| R01 | DBMS → 데이터베이스 | 역할 | 관리한다 | DBMS는 데이터베이스의 데이터를 읽고 쓰고, 정해진 규칙을 검사한다. | **핵심** | S03-1 · S04-1 |
| R02 | 데이터베이스 → 테이블 | 포함 | 테이블에 나누어 담는다 | 관계형 데이터베이스는 데이터를 주제별 테이블에 나누어 담는다. | **핵심** | S02-2 |
| R03 | 테이블 → 행 | 포함 | 기록 한 건 | 테이블은 여러 행으로 이루어지고, 행 하나가 기록 한 건이다. | 보충 | S02-1 |
| R04 | 테이블 → 열 | 포함 | 정보의 종류 | 테이블은 열로 어떤 정보를 담을지 정하고, 모든 행이 같은 열을 가진다. | 보충 | S02-1 |
| R05 | PK → 행 | 역할 | 행을 하나씩 구별한다 | PK 값이 같은 행은 한 테이블에 둘 수 없으므로, PK로 행 하나를 정확히 찾을 수 있다. | **핵심** | S02-3 |
| R06 | FK → PK | 역할 | 다른 테이블의 PK를 가리킨다 | FK 열의 값은 다른 테이블 PK 열의 값과 같아서, 그 행을 가리킨다. | **핵심** | S02-3 · S03-2 |
| R07 | FK → 관계 | 역할 | 관계를 데이터로 남긴다 | 테이블 사이의 관계는 FK 열의 값으로 저장된다. B6-1의 관계선 5개는 FK 선언 5개와 같다. | 보충 | S02-3 · S04-3 |
| R08 | ERD → 테이블 | 역할 | 상자로 그린다 | ERD는 테이블을 상자 하나로 그린다. | 보충 | S01-2 |
| R09 | ERD → 관계 | 역할 | 선으로 그린다 | ERD는 관계를 선으로 그리고, 선 끝 모양으로 몇 대 몇인지 나타낸다. | **핵심** | S01-1 · S01-2 |
| R10 | SQL → DBMS | 역할 | DBMS에 요청한다 | SQL은 DBMS에게 원하는 결과를 요청하는 언어이고, 실제로 찾고 실행하는 것은 DBMS다. | **핵심** | S03-1 · S04-1 |
| R11 | SQL → JOIN | 포함 | 조회에서 쓰는 방법 | JOIN은 SQL로 데이터를 조회할 때 쓰는 방법 중 하나다. | 보충 | S03-2 |
| R12 | JOIN → 행 | 역할 | 조건에 맞는 행끼리 잇는다 | JOIN은 여러 테이블의 행을 ON 조건이 맞는 것끼리 이어 결과 표를 만든다. | **핵심** | S03-2 · S03-3 |

- **핵심 7개 / 보충 5개.** 처음 화면은 핵심 선 7개만 진하게, 보충 선 5개는 흐리게 보인다. 노드를 선택하면 그 노드의 선이 모두 진해진다. (정책 §3 "모든 연결을 한 번에 강하게 보여주지 않는다")
- 핵심 선 7개만 읽어도 지도 전체의 뜻이 전해진다. **ERD는 관계를 그린다. 데이터베이스는 데이터를 테이블에 나누어 담는다. PK는 행을 구별하고, FK는 PK를 가리킨다. SQL은 DBMS에 요청하고, DBMS는 데이터베이스를 관리한다. JOIN은 행을 잇는다.** (이 문장들의 순서는 설명 순서일 뿐 실행 순서가 아니다)
- 일부러 **긋지 않은 선**은 3절에 따로 적었다.

## 3. 선을 긋지 않는 관계와 비교 (3개)

지도에서 선 대신 노드 상세 패널의 "헷갈리기 쉬운 점" 카드로 보여 준다.

| ID | 대상 | 설명 | 선을 긋지 않는 이유 |
| --- | --- | --- | --- |
| N01 | JOIN ↔ PK · FK | B6-1의 JOIN은 `FK = PK`를 조건으로 썼다. 하지만 **JOIN은 FK 선언이 없어도 ON 조건만 맞으면 된다.** FK는 그 값이 실제로 있는 행을 가리키도록 지켜 줄 뿐이다. | JOIN → FK 선을 그으면 "FK가 있어야 JOIN할 수 있다"로 읽힌다. 학습가이드 6장 "JOIN은 FK 선언이 없어도 됩니다"와 같은 입장이다. |
| C01 | PK ↔ FK | PK는 **자기 테이블의 행**을 구별한다. FK는 **다른 테이블의 PK**를 가리킨다. 같은 열 이름(`id`, `student_id`)이 붙어 있어도 하는 일이 다르다. | R06 하나로 둘의 관계는 이미 보인다. 차이는 선이 아니라 나란히 놓고 비교할 때 잘 보인다. |
| C02 | SQL ↔ DBMS | SQL은 **언어**, DBMS는 **프로그램**이다. SQLite는 SQL이 아니라 DBMS의 한 종류다. | R10이 관계를 이미 보여 준다. "이름이 비슷해서 헷갈리는 것"(학습가이드 1장)을 따로 짚는다. |

INNER JOIN과 LEFT JOIN의 차이는 노드로 만들지 않는다. JOIN 상세 패널의 "더 알아보기"에서 S03-3 화면과 `inner-join` · `left-join` 항목으로 보낸다.

## 4. 보충 학습으로 뺀 용어

핵심 지도에는 넣지 않는다. 노드 상세 패널의 "더 알아보기" 링크나 학습가이드로 보낸다.

| 용어 (ID) | 뺀 이유 | 어디로 보내나 |
| --- | --- | --- |
| SQLite (`sqlite`) | DBMS의 **한 사례**다. 노드로 두면 B6-1의 선택이 정답처럼 보인다. | DBMS 상세 패널 "B6-1 사례" · 가이드 1장 |
| 스키마 (`schema`) | 테이블·열·키를 묶어 부르는 말이라 지도 안의 개념과 겹친다. 입문 첫 화면에서는 테이블·열로 충분하다. | 테이블 상세 패널 · 가이드 2장 |
| 1:N · N:M · 카디널리티 · 연결 테이블 (`one-to-many-relationship` `many-to-many` `cardinality`) | "관계"를 읽는 세부 방법이다. 노드로 나누면 관계 영역만 5개가 넘는다. | 관계 상세 패널 · S01-3 · 가이드 3장 |
| 복합키 (`composite-key`) | PK의 한 형태. | PK 상세 패널 설명의 "(또는 열 묶음)" · 가이드 3장 |
| INNER JOIN · LEFT JOIN (`inner-join` `left-join`) | JOIN의 종류. 차이는 S03-3이 그림으로 더 잘 보여 준다. | JOIN 상세 패널 · S03-3 · 가이드 6장 |
| 제약조건 · 무결성 · 참조 무결성 (`data-integrity` `referential-integrity` `not-null` `unique-constraint`) | FK가 "가리키는 값이 있는지 검사"한다는 한 문장만 남기고 나머지는 실행·검증의 영역이다. | FK·DBMS 상세 패널 · 가이드 4장 |
| SELECT · 쿼리 실행 (`select` `query-execution`) | SQL 문법·내부 동작이다. | SQL 상세 패널 · 가이드 5장 |
| GROUP BY · 집계 · 서브쿼리 · INDEX · UPDATE · DELETE · CRUD | 스토리 S04-1의 "하는 일 칩"에만 나오는 활용 범위다. 노드로 두면 활용 영역이 지도를 덮는다. | 가이드 7~9장 |
| 정규화 (`normalization`) | B6-1이 깊게 다루지 않은 설계 이론이다(가이드 2장). | 가이드 2장 |
| ORM · JPA (`object-relational-mapping` `jpa`) | 다음 미션에서 만날 개념이다. | 가이드 10장 |

## 5. 스토리와의 연결

학습 왕복 경로: **스토리 화면 → 지도 노드·관계 → 용어사전 → 원래 화면.** 스토리 주소는 이미 쓰고 있는 `/missions/main-M11/story?scene=0N&screen=N` 형식이다.

| 스토리 화면 | 지도에서 열 곳 | 강사가 짚는 관계 |
| --- | --- | --- |
| S01-1 ERD 등장 | ERD 노드 | R09 ERD → 관계 |
| S01-2 읽는 법 | ERD 노드 | R08 · R09 (상자 = 테이블, 선 = 관계) |
| S01-3 주제는 달라도 | 관계 노드 | 관계 상세 패널의 1:N · N:M |
| S02-1 한 장의 표 | 테이블 노드 | R03 · R04 (행·열) |
| S02-2 나누기 | 데이터베이스 노드 | R02 |
| S02-3 키로 잇기 | FK 노드 | R05 · R06 · R07, 비교 C01 |
| S03-1 요청하기 | SQL 노드 | R10 · R01 |
| S03-2 JOIN = 키를 따라가기 | JOIN 노드 | R12, **N01(JOIN과 FK의 경계)** |
| S03-3 INNER와 LEFT | JOIN 노드 | JOIN 상세 패널의 INNER · LEFT |
| S04-1 SQL과 DBMS | DBMS 노드 | R10 · R01, 비교 C02 |
| S04-2 AI가 써 준 SQL 확인하기 | JOIN 노드 | R12 · R09 (ERD의 0개 가능 = LEFT JOIN 필요) |
| S04-3 처음의 ERD로 | 지도 전체 | 핵심 선 7개 |

- 상세 ERD(6개 표의 실제 열·관계)는 **스토리 안의 기존 상세 ERD 보기**에만 있다. 지도는 ERD를 다시 그리지 않고, ERD 노드 상세 패널에서 S01-1로 보낸다.
- 지도 → 스토리 복귀 링크는 현재 **미구현**이다. 구현 전에는 "미구현"으로 표시하고 작동하는 것처럼 보이지 않게 한다.

## 6. 강의 시연 순서 (1개)

대면 강의에서 S04-3 직후 또는 Scene 04 정리 단계에 지도를 열어 아래 순서로 노드를 선택한다. **복습 순서이며 실행 순서가 아니다.**

| 단계 | 노드 | 학습자에게 던질 질문 |
| --- | --- | --- |
| 1 | ERD | 내 ERD에서 상자 하나, 선 하나를 짚어 보세요. |
| 2 | 테이블 | 그 상자의 행 하나는 무엇을 기록한 한 건인가요? |
| 3 | PK | 그 행을 다른 행과 구별하는 열은 무엇인가요? |
| 4 | FK | 그 테이블에서 다른 테이블을 가리키는 열은 무엇인가요? |
| 5 | SQL | 이 구조에 무엇을 요청하고 싶나요? 실제로 실행하는 것은 누구인가요? |
| 6 | JOIN | 두 테이블을 어떤 조건으로 이을까요? FK가 없어도 이을 수 있을까요? |

## 7. 배치 시안

### PC (701px 이상) — 영역 4개를 열로

기존 B3-1 지도 엔진의 배치 함수(`layoutConceptMap`)는 **영역 하나를 세로 열 하나**로 놓고 카드를 자동 배치한다. 지시서의 "중앙 — DB·DBMS"를 이 엔진에서 살리려면 중심 영역이 구조와 활용 사이에 와야 한다.

```
  열 1 · 데이터 관계    열 2 · 데이터 구조    열 3 · 중심            열 4 · 데이터 활용
  ──────────────────   ──────────────────   ──────────────────   ──────────────────
  [ ERD ]              [ 테이블 ]            [ 데이터베이스 ]       [ SQL ]
  [ 관계 ]             [ 행 ]                [ DBMS ]             [ JOIN ]
  [ FK ]               [ 열 ]
  [ PK ]
  (스토리 Scene 01·02)  (Scene 02)            (Scene 03·04)        (Scene 03·04)

  같은 열 안      R09 ERD→관계 · R07 FK→관계 · R06 FK→PK │ R03 테이블→행 · R04 테이블→열
                 R01 DBMS→데이터베이스 │ R11 SQL→JOIN
  옆 열로        R08 ERD→테이블 · R05 PK→행 (열 1→2) │ R02 데이터베이스→테이블 (열 3→2)
                 R10 SQL→DBMS (열 4→3)
  열을 건너뜀    R12 JOIN→행 (열 4→2, 열 3 아래 통로로 지남) ← 유일한 긴 선
```

- **열 순서: 데이터 관계 | 데이터 구조 | 중심 | 데이터 활용.** 왼쪽부터 읽으면 스토리 순서(설계도 → 나누기 → 요청 → 답 찾기)와 같다.
- 위 시안의 노드·관계를 실제 `layoutConceptMap`에 넣어 확인했다(로컬 임시 스크립트, 저장소 밖). 지도 크기 **1536×502**, 열을 건너뛰는 긴 선은 **R12(JOIN → 행) 1개**다. 지시서 순서 그대로(중심 | 구조 | 관계 | 활용) 놓으면 긴 선이 **R10 · R12 2개**로 늘어 SQL과 DBMS가 지도 양 끝으로 멀어진다.
- 열 안의 위아래 순서: 관계 영역은 ERD · 관계 · FK · PK, 구조 영역은 테이블 · 행 · 열, 중심은 데이터베이스 · DBMS, 활용은 SQL · JOIN.
- 노드를 선택해도 카드 위치는 바뀌지 않는다. 강조만 바뀐다.

### 모바일 (700px 이하)

- 같은 지도 좌표를 그대로 쓴다(별도 모바일 배치 없음). 처음에는 전체 맞춤, 노드를 고르면 그 노드와 이웃을 읽기 크기로 맞춘다(B2-1 `focusNode` 동작).
- 상세 설명은 지도 아래 43dvh 하단 시트. 시트 맨 위에 짧은 설명 두 문장, 그 아래 관계 목록, 마지막에 "용어사전에서 보기 · 스토리 화면 보기 · 학습가이드" 링크.
