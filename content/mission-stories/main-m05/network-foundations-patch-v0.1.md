## 2. 보강할 핵심 메시지 (다섯 + 연결 하나)

화면당 한 문장. 모든 예시는 **IPv4**이며 그렇게 표시한다.

| # | 핵심 메시지 | 덧붙이는 한 문장 |
| --- | --- | --- |
| M1 | **IP 주소는 네트워크에서 기기를 찾아가기 위한 번호다.** | IPv4는 `203.0.113.10`처럼 0~255 숫자 4개로 쓴다. (정확히는 기기의 네트워크 인터페이스에 붙는다 → B3-1의 ENI) |
| M2 | **공인 IP는 인터넷 어디서나 찾아올 수 있고, 사설 IP는 회사망·VPC 안에서만 쓴다.** | 사설 주소는 다른 조직도 같은 번호를 쓰므로, 인터넷과 오갈 때는 변환 규칙(NAT, B3-1은 IGW)이 공인 주소와 짝지어 준다. |
| M3 | **서브넷은 네트워크를 구역으로 나누고 구역마다 준 주소 범위다.** | 나누면 주소만 보고 어느 구역인지 알 수 있고, 구역마다 다른 허용 규칙과 경로를 붙일 수 있다. |
| M4 | **데이터는 패킷에 담겨 이동하고, 패킷에는 출발지와 목적지 IP 주소가 적혀 있다.** | 포트 번호는 IP 주소가 아니라 그 안의 TCP 정보에 있다. 큰 데이터는 여러 패킷으로 나뉜다. |
| M5 | **IP는 주소로 목적지까지 보내고, TCP는 포트로 프로그램을 찾아 빠짐없이 순서대로 전하고, HTTP는 무엇을 요청하고 응답할지 정한다.** | 셋은 같은 일을 하는 프로토콜이 아니라, 한 통신에서 **역할을 나눠 겹쳐 쓰는** 약속이다. |
| M6 | **B3-1의 AWS 설정은 이 기초 정보를 각각 다룬다.** | 주소 범위 = VPC·Subnet, 공인↔사설 = IGW, 목적지로 다음 길 = Route Table, 출발지·프로토콜·포트로 허용 = Security Group, HTTP = Nginx. |

- **Scene 03-A에는 넣지 않는다.** 03-A는 일반망↔AWS 역할 비교(비교선 6·주의 카드 4)가 이미 꽉 차 있다. 공인 IP ↔ Public Subnet 주의는 실제 설정이 보이는 03-B 카드 C에 둔다.

  - A: "IP 주소가 없으면 무엇을 할 수 없을까요?" · "공인 IP와 사설 IP 중 인터넷에서 바로 찾아올 수 있는 것은 무엇이고, 왜 그럴까요?"

  - C: "Public Subnet 안의 EC2는 공인 IP만 가지고 있을까요?" · "Security Group 규칙의 'TCP 80'에서 TCP와 80은 각각 무엇일까요?"

## 4. 시각 자료 구성

새 SVG는 **2개(각 노트북·휴대전화판)**, 나머지 하나는 HTML 표다. 기존 Scene 그림과 같은 **밝은 배경·B3-1 의미 색**을 쓰고 `PresentationSurface`·Dark 테마를 적용하지 않는다(공통 UI 기준 v1.2).

### V1 — 주소와 구역 (카드 A)

```
 ① IP 주소 = 찾아갈 번호          ② 두 종류의 주소                       ③ 네트워크를 구역(서브넷)으로
 ┌───────────────────────┐   ┌─────────────┐  변환 규칙  ┌─────────────┐   ┌ 회사 네트워크 (Scene 01 예시) ┐
 │ 203 . 0 . 113 . 10    │   │ 공인 IP      │◀──(NAT)──▶│ 사설 IP      │   │ [DMZ]      172.16.10.0/24  │
 │ └─ 숫자 4개, 각 0~255 ┘│   │ 203.0.113.10 │            │ 172.16.10.10 │   │ [자료 저장] 10.20.30.0/24   │
 │ IPv4 · 문서용 예시 주소 │   │ 인터넷 어디서나│            │ 회사 안에서만  │   │ [업무망]    192.168.10.0/24 │
 └───────────────────────┘   └─────────────┘            │ 다른 회사도 씀 │   │ 구역마다 주소 범위 하나       │
                                                         └─────────────┘   │ 구역마다 다른 허용 규칙       │
                                                                           └────────────────────────────┘
 각주: 모든 주소는 IPv4 예시(203.0.113.x는 문서용, 나머지는 사설 대역). /24 = 앞 세 숫자가 같은 주소 256개.
       범위 표기(CIDR)는 학습가이드 2장. 실제 B3-1 구성이 아닙니다.
```

- 값은 **Scene 01·02와 똑같이** 쓴다(새 주소를 만들지 않는다).
- ③은 "큰 범위 하나를 잘라 나눈다"로 그리지 않는다. Scene 01의 세 구역은 서로 다른 사설 대역에서 골랐다. **하나의 범위 안에서 나누는 모습**(VPC `10.0.0.0/16` ⊃ Subnet `10.0.1.0/24`)은 가이드 2장 `cidr-range.svg`가 이미 그리므로 링크만 둔다.
- 휴대전화판: ①②③을 세로로 쌓는다.

### V2 — 패킷 한 개 들여다보기 (카드 B)

```
 패킷 한 개 (봉투 세 겹)                                         누가 무엇을 보나 (Scene 01·02 예시)
 ┌ IP 정보 ─ 주소로 목적지까지 ──────────────────────────────┐   경계 라우터   목적지 IP → 다음 길 선택
 │ 출발지 IP 198.51.100.25 (방문자)   목적지 IP 203.0.113.10   │   방화벽 규칙   출발지·목적지 IP + TCP·포트
 │ ┌ TCP 정보 ─ 포트로 프로그램 찾기 · 순서·빠진 조각 확인 ┐   │                → 허용 / 차단
 │ │ 출발지 포트 51514 (브라우저가 고른 번호)  목적지 포트 80 │ │   NAT          IP 주소를 바꿈 (이 예시: 목적지만)
 │ │ ┌ HTTP 내용 ─ 무엇을 요청하나 ─────┐                   │ │   웹 서버       HTTP 내용을 읽고 응답
 │ │ │ GET /   "홈페이지를 주세요"       │                   │ │
 │ │ └──────────────────────────────────┘                   │ │
 │ └──────────────────────────────────────────────────────┘ │
 └──────────────────────────────────────────────────────────┘
 각주: IPv4·HTTP 80 예시(B3-1 배포 기록과 같은 포트). Scene 02의 HTTPS 443은 같은 구조에서 HTTP 내용이 TLS로 암호화된다.
       큰 데이터는 여러 패킷으로 나뉜다. MAC 주소 등 장비 사이 정보는 생략했다.
```

- **주소와 포트를 다른 겹에 둔다.** 포트는 IP 정보 상자 밖, TCP 상자 안에만 쓴다.
- 오른쪽 열의 장비 이름은 Scene 01·02와 같다. "허용 / 차단"은 방화벽 줄에만 쓰고, 라우터 줄에는 쓰지 않는다.
- 출발지 `198.51.100.25`는 Scene 01·02에 없는 새 값이다. 문서용 대역(RFC 5737, 보강 README가 이미 언급)에서 고른다.
- 휴대전화판: 봉투 세 겹 → "누가 무엇을 보나" 표 순으로 세로 배치.

### V3 — 기초 개념이 B3-1에서 쓰인 곳 (카드 C · HTML 표, SVG 없음)

| 기초 정보 | B3-1에서 맡은 것 (2026-10-14 기록) | 03-B 번호 |
| --- | --- | --- |
| 주소 범위 (서브넷 · CIDR) | VPC `10.0.0.0/16` 안에 Subnet `10.0.1.0/24` 하나 | ③ |
| 공인 IP ↔ 사설 IP | 자동 할당 Public IPv4 ↔ ENI의 Private IPv4. IGW가 1:1로 바꾼다. EC2 운영체제는 사설 주소만 안다 | ② ④ |
| 목적지 IP → 다음 길 | Route Table `0.0.0.0/0 → IGW`. 응답이 VPC 밖으로 나갈 다음 대상을 정한다. 허용·차단은 하지 않는다 | ③ |
| 출발지 IP · 프로토콜 · 포트 → 허용 | Security Group inbound **TCP 80** from `0.0.0.0/0` (ENI에 적용). 길은 정하지 않는다 | ⑤ |
| HTTP | Nginx가 TCP 80에서 HTTP 요청에 응답 | ① ⑥ |

표 아래 주의 두 줄:
- **공인 IP ≠ Public Subnet.** Public Subnet은 IGW로 가는 경로가 있는 Route Table에 연결된 Subnet이다. 그 안의 EC2도 사설 IP를 가지며, 인터넷에서 찾아오려면 공인 IP가 따로 있어야 한다.
- 이 표는 **B3-1이 고른 한 가지 구성**이다. 다른 클라우드·회사망은 다른 장비·설정으로 같은 일을 할 수 있다.

## 5. 개념지도 변경 후보

### 원칙: 기존 세 보기는 건드리지 않고 "네트워크 기초" 보기를 하나 더한다

- 새 노드를 기존 영역(예: 공통)에 넣으면 지도 엔진이 열 높이·선 통로를 다시 계산해 **기존 좌표와 승인 화면 128개가 바뀐다**(공통 UI 기준: "좌표를 바꾸지 않는다").
- 엔진은 보기마다 `nodeDomains`·`relationScopes`로 노드·관계를 걸러 따로 배치한다. 그래서 새 도메인 `basics`와 새 보기 `basics`를 더하면 기존 보기는 영향이 없다.
- **확인:** 아래 후보를 현재 데이터에 더해 `layoutConceptMap`을 돌렸다(저장소 밖 임시 스크립트). `all`·`general`·`aws` 세 보기의 **노드 좌표·관계 경로·지도 크기가 변경 전과 완전히 같았다.** 기초 보기는 노드 12개(새 7 + 공통 5), 1158×604, 열을 건너뛰는 긴 선 1개(BA09).

### 새 노드 7개 (도메인 `basics`, 영역 2개)

| ID | 이름 | 영역 | 한 줄 요약 | 용어 연결 |
| --- | --- | --- | --- | --- |
| `bas:network` | 네트워크 | 기초 · 주소와 구역 | 데이터를 주고받도록 연결된 기기들의 묶음 | — (등록 보류) |
| `bas:subnet` | 서브넷 | 기초 · 주소와 구역 | 네트워크를 구역으로 나누고 구역마다 준 IP 주소 범위 | `subnet` (extension: 사전은 VPC 기준) |
| `bas:ip-address` | IP 주소 (IPv4) | 기초 · 주소와 구역 | 네트워크에서 기기(인터페이스)를 찾아가기 위한 번호 | **신규 `ip-address`** |
| `bas:packet` | 패킷 | 기초 · 패킷과 프로토콜 | 출발지·목적지 IP 주소가 적힌 데이터 조각 | **신규 `packet`** |
| `bas:ip` | IP (인터넷 프로토콜) | 기초 · 패킷과 프로토콜 | 주소를 보고 패킷을 목적지까지 보내는 약속 | **신규 `network-protocol`** (extension) |
| `bas:tcp` | TCP | 기초 · 패킷과 프로토콜 | 포트로 프로그램을 찾고 순서·누락을 관리하는 약속 | `tcp` |
| `bas:http` | HTTP | 기초 · 패킷과 프로토콜 | 웹 요청과 응답의 내용을 정하는 약속 | `http` · 관련 `port-80-http` |

기초 보기에는 기존 공통 노드 5개(방문자·인터넷·공인 IP·사설 IP·포트)가 함께 보인다. 각 새 노드 상세 패널에 **"B3-1에서 쓰인 곳"** 링크를 둔다(기존 URL 형식 `view=aws&node=…`로 다른 보기의 노드를 연다). 예: 서브넷 → `gen:zone-subnets`(일반망) · `aws:subnet`(AWS), IP → `aws:route-table`, TCP → `aws:security-group`, HTTP → `aws:nginx`.

| --- | --- | --- | --- | --- |

### 선 없는 비교 3개

| ID | 대상 | 보기 | 설명 |
| --- | --- | --- | --- |
| CB01 | 공인 IP ≠ Public Subnet | 전체·AWS | 주소의 종류와 Subnet의 경로 기준은 다른 개념이다. Public Subnet 안의 EC2도 사설 IP를 가진다 |
| CB02 | IP ≠ TCP ≠ HTTP | 기초 | 한 통신에서 역할을 나눠 겹쳐 쓴다. 같은 일을 하는 프로토콜 셋이 아니다 |

**기존 노드·관계·좌표는 바꾸지 않는다.** 유일한 기존 데이터 변경 후보는 `com:private-ip`의 `termIds`에 신규 `private-ip`를 넣는 것이며, 용어 등록 후 Owner 승인 시에만 한다(배치 영향 없음).

## 7. 구현 시 주의사항

### 기술 정확성

1. **IPv4 표시:** 그림 각주·카드에 "IPv4 예시"를 적는다. 공인 주소 예시는 문서용 대역(`203.0.113.0/24`, `198.51.100.0/24`)만 쓴다. B3-1의 실제 공인 주소는 표시하지 않는다.
2. **공인/사설 IP ≠ Public/Private Subnet:** 카드 C와 CB01로 분리한다. "Public Subnet에 있으니 공인 IP"라는 문장을 쓰지 않는다.
3. **주소와 포트 분리:** 포트는 언제나 TCP 겹 안에 둔다. "IP:포트"를 한 덩어리 주소처럼 부르지 않는다.
4. **IP·TCP·HTTP는 역할이 다르다:** "세 가지 프로토콜"로 나란히 나열만 하지 않고 겹쳐 쓰는 관계로 보인다. "모든 HTTP는 TCP" 같은 단정을 쓰지 않는다(BA10).
5. **라우팅 ≠ 허용:** 라우터·Route Table 줄에 "허용/차단"을 쓰지 않는다. Route Table은 03-B 각주처럼 "응답이 VPC 밖으로 나갈 다음 대상"으로 쓴다.
6. **사례와 일반:** V3 표와 카드 C에 "B3-1이 고른 한 가지 구성"을 적는다. Scene 01의 세 구역 주소를 "한 범위를 잘라 나눈 것"으로 그리지 않는다.
7. **기록 시점:** B3-1 값은 모두 "2026-10-14 배포 기록 기준 · 현재 AWS 상태가 아님".

### 웹·데이터 (Codex)

- 카드는 `StoryScene`에 선택 필드(예: `basics`)를 더해 렌더한다. 기존 5개 Scene의 `explanation`·`checks`·`map` 원문과 SVG 8개는 바꾸지 않는다.
- 지도 타입 `Domain`·`ViewId`에 `basics`를 더해야 한다(`src/missionConceptMap/conceptMapTypes.ts`).
- **`readMapState`의 대체 보기 주의:** 지금은 선택 노드가 현재 보기에 없으면 `all`로 바꾸는데, 기초 노드는 `all`에도 없다. 노드가 속한 보기를 찾아 바꾸도록 해야 한다. `changeView`도 같이 확인한다.
- 기초 보기에서 방문자·인터넷 노드는 연결선이 없다. 보기 정의에 노드 제외 목록을 두거나 그대로 둘지 Codex가 판단하고 Owner가 승인한다.
- 스토리 → 기초 보기 링크(`view=basics&node=bas:…`)는 기존 `conceptHref` 검증 경로를 그대로 쓴다. 임의 return URL을 받지 않는다.
- 새 SVG는 기존처럼 `_tools/build.py` 한 벌에서 노트북·휴대전화판을 만들고 `check.cjs`로 두 판의 요소 수·글자 범위를 비교한다.
