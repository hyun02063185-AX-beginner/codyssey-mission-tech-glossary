### 중복 조사 정정

- 공인 IP와 Public Subnet의 차이는 기존 지도·03-B뿐 아니라 **학습가이드 3장**에도 있다. 카드 C는 짧은 비교와 해당 가이드 링크로 연결한다.
- TCP·HTTP·포트는 기존 사전과 **네트워크 분야 지도 및 M05 overlay**에도 있다. 이전의 “M05 맥락이 없다”는 말은 일부 canonical mission_refs에 한정되며 본문·분야 지도 전체에 해당하지 않는다.
- CIDR 계산은 가이드 2장의 기존 그림을 사용한다. 새 계산 그림을 만들지 않는다.
- IP 주소·패킷·일반 프로토콜의 짧은 입문 설명은 카드에서 제공하되, 존재하지 않는 용어 ID의 링크는 만들지 않는다.

## 2. 핵심 메시지와 기술 경계

1. **네트워크와 주소:** 네트워크는 연결된 기기들이 데이터를 주고받는 체계다. IP 주소는 상대를 찾아갈 번호이며 정확히는 네트워크 인터페이스에 붙는다. IPv4 예시는 0~255 숫자 네 개다.
2. **공인·사설 주소:** 공인 IP는 인터넷 라우팅에 쓰고, 사설 IP는 내부 통신에 쓰며 공용 인터넷에서 직접 라우팅하지 않는다. 공인 IP가 있어도 경로·허용 규칙·응답하는 서비스가 함께 필요하다. 사설 주소는 다른 조직에서 재사용할 수 있고 사설 연결로 조직 간 통신도 가능하다.
3. **서브넷:** 구역마다 정한 IP 주소 범위다. 주소 배정과 경로·정책 관리에 도움이 되지만, 나누는 것만으로 통신이 차단되지는 않는다. 경로·방화벽·SG 등은 별도로 설정한다.
4. **패킷과 프로토콜:** 프로토콜은 형식·절차의 약속이다. IP 패킷의 출발지·목적지와 TCP의 포트를 구분한다. IP는 목적지로 전달하며 도착을 보장하지 않는다. TCP는 손실 재전송·순서 복원으로 신뢰성 있는 바이트 스트림을 제공하지만 연결 실패·암호화·웹 업무 성공을 보장하지 않는다. HTTP는 요청·응답의 의미를 정한다.
5. **NAT와 AWS:** NAT는 주소 변환이다. 포트 변환을 함께 할 수 있고 항상 1:1은 아니다. 이 B3-1 IPv4 인터넷 접속 사례는 IGW의 1:1 NAT를 썼으며 별도 NAT Gateway는 만들지 않았다. Public Subnet 여부는 IGW로 가는 직접 경로로 정하며, 공인 IP 유무와 다르다.

문서용 `203.0.113.10`·`198.51.100.25`는 **공인 주소 자리를 대신하는 예시**이며 실제 인터넷 접속 주소가 아니다. 실제 배포 공인 주소·작업자 주소·자원 ID를 복사하지 않는다.

## 4. 시각 자료 2개와 표 1개

### V1 · 찾아갈 번호, 주소의 종류, 구역의 범위

- ① IPv4의 숫자 네 개: `203 · 0 · 113 · 10`, 각 0~255. 정확한 인터페이스 설명과 문서용 예시 표시.
- ② 공인 IP / 사설 IP의 짧은 비교. 주소 종류와 실제 접속 조건을 분리한다.
- ③ 기존 Scene 01 회사망의 DMZ `172.16.10.0/24`, 자료 저장 `10.20.30.0/24`, 업무망 `192.168.10.0/24`. 서로 다른 사설 범위에서 고른 예시이며 단일 CIDR 분할 그림으로 포장하지 않는다. 서브넷 자체는 차단 규칙이 아님을 표시한다.

### V2 · 요청 데이터가 실린 IP 패킷의 단순화 예시

- 제목과 배지: **IPv4 / HTTP 80**. 기존 Scene 02는 **HTTPS / TCP 443**이라고 본문에서 구분한다. HTTPS에서는 HTTP 내용이 TLS로 보호된다. 모든 HTTP가 TCP를 쓴다고 일반화하지 않는다(HTTP/3 등).
- IP 겹: 출발지 `198.51.100.25`, 목적지 `203.0.113.10`.
- TCP 겹: 클라이언트 임시 포트 `51514`, 서버 포트 `80`. 포트를 IP 겹에 놓지 않는다.
- HTTP 겹: **요청 일부** `GET /`. HTTP 요청 하나가 항상 패킷 하나에 온전히 들어가는 것은 아니며, TCP 연결·확인용 패킷에는 HTTP 내용이 없을 수도 있다.
- 역할 목록: 라우터=목적지에 따른 경로, 방화벽 규칙=허용 판단, NAT=이 수신 요청의 목적지 주소 변환 및 응답의 출발지 역변환, 웹 서버=HTTP 해석·응답.
- TCP는 신뢰성 있는 전송을 제공하지만 암호화·애플리케이션 성공 보장이 아님을 짧게 표시한다.

### V3 · 기초 개념과 B3-1 AWS 구성 비교

HTML 표의 다섯 줄은 주소 범위(VPC·Subnet), 공인↔사설(IGW·ENI), 다음 경로(Route Table), 허용(SG inbound TCP 80 from `0.0.0.0/0`), HTTP(Nginx)다. 기존 03-B 번호 ①~⑥과 대조하고, `caption`, 행·열 머리글을 제공한다. Public Subnet 안의 EC2도 사설 주소를 가지며 IPv4 직접 인터넷 접속에는 공인 주소·경로·보안 규칙·서버 수신이 함께 필요하다.

### 실제 렌더링 방식과 테마

시각 자료 두 개는 별도 SVG 두 판 대신 **반응형 HTML/CSS 그림**으로 구현한다. 고정 SVG를 축소해 글자가 작아지거나 데스크톱·모바일 원문이 갈라지는 일을 막는다. PC는 V1 3열·V2 중첩 그림과 역할 목록 2열, 좁은 화면은 세로 배치다. 텍스트·주소·포트가 실제 CSS 글자 크기로 렌더되며 의미 있는 본문·코드·표는 최소 14px를 확인한다. 메타 라벨은 별도다.

이번 Owner 지시의 Dark 기본 테마를 강의 상태에 적용한다. 기존 `PresentationSurface`·`PresentationThemeSelector` 및 색 토큰을 재사용하고 Light·저장·사이트 테마와의 분리를 유지한다. **기존 구조도 SVG의 밝은 배경·의미 색·타이포·좌표는 그대로** 두며 필터를 쓰지 않는다. 개념지도와 강의 인트로에는 PresentationSurface를 적용하지 않는다. 이는 기존 B3-1이 PresentationSurface 없이 렌더되던 상태에서 의도된 UI 변경이며, 예전 테스트의 “B3-1에는 presentation-theme가 없다” 단언은 새 요구와 맞게 갱신한다. 공통 UI 규격 문서를 소급 변경하지 않는다.

## 5. 이번에 제외한 후속 후보

이전 §5의 기초 도메인·보기·노드 7개·관계 10개·비교 3개, §6의 신규 canonical 4개는 **구현 지시가 아닌 보류 후보**다. 신규 지도·용어 등록을 하지 않는다. 향후에는 아래 문제를 별도 설계로 해소해야 한다.

- 서브넷 용어의 복수 노드 소유권, 미구현 extension 링크 의미.
- domain/scope/prefix 검증, 방문자·인터넷 고립, 보충 포트 표시 정책.
- readMapState뿐 아니라 실제 selectNode/selectRelation·전역 검색의 보기 복구.
- 비교 카드 보기 범위, ‘역할 차이’와 ‘관계선 없음’ 의미 충돌.
- 기존 three-view 좌표·경로·보기 전환 결과 보존 검증.

후보 임시 좌표 실험은 커밋된 코드·데이터가 없어 재현하지 않았다. 이전 문서의 “기존 세 보기와 완전히 같다”는 실험 주장은 이번 구현의 증거로 사용하지 않는다. 검증기를 끄거나 의미 없는 관계를 추가하지 않는다.

기술 정확성은 위 근거와 Owner가 전달한 독립 검토로 대조했다. 구현 후의 실제 화면 승인·교육 효과·현재 AWS 상태는 Owner 검수 또는 후속 확인 대상이다. 자동 검사 결과만으로 독립 콘텐츠 재승인·배포 승인을 선언하지 않는다.
