### 3-1. 스토리 연속성 — 8개 해설이 네 가지 흐름을 갖는가

| 화면 | 지금까지 무엇을 알아냈나 | 이번에 이해할 것 | 그림에서 일어나는 일 | 왜 다음 단계가 필요한가 |
| --- | --- | --- | --- | --- |
| S1-1 | (출발) 강의의 핵심 질문 | API = 외부 서비스에 일을 부탁하는 창구, 왜 외부인가 | 왼쪽 직접 쓰기 vs 오른쪽 프로그램이 AI에 맡기기, 실제 제목 | “무엇이 바뀌었는지 알아야 한다. 어디에 있을까?” |
| S1-2 | 재료가 필요하다 | 재료 = 파일 이름 + 바뀐 줄, 내 컴퓨터에 있다 | `M`(수정 파일), `+`(추가된 줄) | “사람 대신 프로그램이 하려면 Python이 Git을 실행해야” |
| S2-1 | 사람이 Git 명령을 입력했다 | argparse(입력 읽기)와 subprocess(Git 실행)의 방향 | `commit` 읽기 → Git 실행 | “Git이 돌려준 결과를 보고 다음 일을 정해야” |
| S2-2 | Python이 Git을 실행했다 | 결과 세 가지, 종료 코드 먼저 | 저장소 밖 실패, 두 갈래 분기 | “변경이 있으면 이제 밖으로 나간다” |
| S3-1 | 변경을 읽었고 보낼 변경이 있다 | 나간 데이터는 되돌릴 수 없다 → 보내기 전 검사 | 넣는 것 / 넣지 않는 것 / 가리고 계속·멈춤 | “이 글이 요청의 `user`가 된다” |
| S3-2 | 보낼 글을 준비했다 | 요청 4요소, 키의 이유, 변환, 응답에서 값 꺼내기, 401/403 | 나가는 요청, 돌아오는 응답 | “작성 규칙만 바꾸면 결과가 어떻게 달라질까?” |
| S4-1 | 요청은 `system`+`user`를 보낸다 | 같은 `user`, 다른 `system` → 다른 모양 | 실제 두 출력, How to Test 교체 | “형식이 맞으면 내용도 맞을까?” |

**판정: PASS(자체).** 8개 모두 네 요소를 갖되, 같은 문형을 반복하지 않도록 시작 방식(질문 회수, 요약, 전환 이유, 결과 정의)과 끝 방식(질문, 예고, 이유)을 화면마다 달리했습니다. 해설 8개만 이어 읽었을 때 “재료 → 수집 → 판단 → 보낼 글 → 요청·응답 → 결과 비교 → 확인 → 답”으로 끊김 없이 읽히는지 확인했습니다.

| 이야기의 학습 목표에 필요한 기술 범위를 고른다. | 입문자가 Git과 Python의 전체 문법을 익히기 전에도 각 도구가 이 흐름에서 맡는 일을 구별한다. |
| 같은 사례를 학습 목표에 따라 다른 관점으로 구성할 수 있다. | 같은 변경 사례라도 Python 관점은 프로그램의 실행·데이터 변환, Git 관점은 변경 종류와 수집 범위에 각각 초점을 맞출 수 있다. |
| 학습 목표에 필요한 선수지식을 먼저 밝힌다. | 명령줄 실행과 Python 딕셔너리·리스트 경험을 기준으로, 학습자가 부족한 내용을 수업 전에 파악한다. |
| 그림, P 해설, 용어사전, 학습가이드에 서로 다른 역할을 둔다. | 그림으로 흐름과 경계를 찾고, P 해설로 개념과 이유를 설명하고, 용어사전으로 뜻을 확인하고, 학습가이드로 실행하고 검증한다. |

실제 수업에서 S3-2의 요청·응답 설명과 S4-2의 마무리 문항을 정답 공개 전에 확인한다. 특히 API 키와 JSON 본문의 자리, 같은 문맥에서 달라지는 작성 규칙, 프로그램의 형식 검사와 사람의 사실 확인을 자기 말로 구별하는지 관찰한다. 작은 휴대전화와 강의실 화면에서 그림과 해설을 오가는 데 어려움이 있는지도 기록한다.
