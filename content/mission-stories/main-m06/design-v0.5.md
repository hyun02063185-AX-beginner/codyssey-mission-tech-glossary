## 2. 학습 인덱스 정보 구조

학습 인덱스는 페이지 제목 목록이 아니라 **이 미션의 학습 구조를 설명하는 자료**입니다. 학습자가 언제든 다음 여섯 질문에 답할 수 있게 합니다: 무엇을 배우는가 · 어떤 순서인가 · 지금 어떤 관점인가 · 지금 개념은 전체의 어디인가 · 앞에서 배운 것은 어디서 다시 보는가 · 다음에는 무엇을 배우는가.

### 2.1 데이터 출처 — 원고 한 곳 (중복 하드코딩 금지)

| 인덱스 정보 | 출처 (storyboard-v0.5.md) |
| --- | --- |
| Scene 번호·학습 관점·카드 제목·대표 학습 질문·도달 목표 | 인트로의 Scene 표 1–5열 (v0.4와 같음) |
| 핵심 기술 개념 | Scene 표 **6열 `핵심 개념`** (신규, ` · `로 구분, Scene당 3–5개) |
| 슬라이드 수·상세 슬라이드 목록 | 파싱된 화면 배열 (`### S<n>-<m>` 제목). 수를 따로 적지 않음 |
| 화면별 제목·핵심 메시지 | 각 화면의 제목, `**핵심 메시지**` |
| 전체 학습 흐름 설명 | 인트로 `**학습 로드맵**` (신규 필드) |
| 현재 Scene·화면 | URL 상태(`scene`·`screen`)에서 계산. 저장하지 않음 |

웹 코드는 Scene 제목·화면 제목·화면 수·번호를 다시 적지 않습니다. 화면 위치(`6 / 9`, `22 / 33`)는 배열 순서에서 계산합니다(거버넌스의 “View에서 계산 가능하면 저장하지 않는다”).

핵심 개념은 키워드를 늘어놓지 않고 그 Scene의 화면이 실제로 가르치는 개념만 골랐습니다. 예: Scene 4의 5개 = REST API와 HTTPS(S4-1) · API 키와 환경변수(S4-2) · system·user 프롬프트와 요청 JSON(S4-3·S4-4) · temperature와 max_tokens(S4-5·S4-5a·S4-5b) · HTTP 상태 코드와 usage(S4-6·S4-7).

### 2.2 Scene 사이의 연결 — 실제 학습 순서

```
Scene 1 사용자 ── 전체 그림: 무엇을 만들고 어떻게 쓰나
   │
   ▼  README.md 메모 한 줄이 이동하는 길
Scene 2 Git ──▶ Scene 3 Python ──▶ Scene 4 Python과 외부 AI ──▶ Scene 5 결과 검증과 활용
 변경 기록         문자열·Git 문맥        요청 JSON·응답               검증된 초안
   │
   ▼
Scene 6 종합과 응용 ── 전체를 자기 말로 설명하고 다른 프로그램에 옮기기
```

Scene 2–5 사이의 화살표는 **데이터가 실제로 이동하는 시간 순서**입니다(I10 pipeline과 같은 흐름). Scene 1→2, 5→6은 “전체 그림 → 확대 → 다시 전체”라는 **학습 순서**이며 데이터 이동이 아닙니다. 로드맵은 두 종류의 연결을 다른 선 모양(실선 화살표 / 점선 구획)과 글자로 구분합니다(정책 §5-2 흐름과 관계 구분).

## 3. 학습 인덱스 UX

### 3.1 인트로 학습 로드맵 (A-3)

- 위치: `MissionStoryOverview`의 `entryActions` 자리(제목·핵심 질문·학습 목표 접힘 바로 아래, “강의 시작하기” 위). 공통 컴포넌트는 고치지 않습니다.
- 구성: `**학습 로드맵**` 문단 → §2.2 모양의 6단계 로드맵. Scene 2–5는 “메모 한 줄이 이동하는 길” 구획 안에 화살표로 잇고, 1과 6은 구획 밖 앞뒤에 둡니다.
- Scene 카드 하나: `Scene n · 관점` → 카드 제목 → 학습 질문 → 도달 목표(작게) → 핵심 개념 칩 → `화면 k개` → `이 Scene 시작` 링크 → `화면 목록` 펼침(각 화면 `ID · 제목` 링크).
- PC(≥1000px): Scene 1 / [2→3→4→5] / 6을 한 줄 또는 두 줄로. 좁은 화면(<1000px): 세로로 쌓고 화살표는 아래 방향.
- **중복 정리** v0.4의 `introOrientation` 안 “Scene별 학습 질문과 도달 목표” 목록(`dl`)은 같은 정보가 로드맵에 있으므로 v0.5에서는 그리지 않습니다(정보 손실 없음, 테스트로 6개 질문·목표가 로드맵에 있는지 확인). 학습 목표 5개·초안 안내·학습 안내·F1 개요 그림·실습으로 확인하기는 그대로 둡니다.
- **공통 Scene 카드는 유지** 미션 공통 UI 기준 v1.2는 `MissionStoryOverview`의 Scene 목차 카드를 모든 Story에 쓰도록 하고, 예외는 Owner 명시 승인을 요구합니다. 그래서 로드맵이 카드를 대신하지 않고, 카드는 기준대로 아래에 남깁니다(빠른 Scene 이동용). 카드를 없애고 로드맵으로 합치려면 기준 예외 승인이 필요하므로 이번 범위에서 하지 않고 최종 보고에 후보로 적습니다.

### 3.2 상시 학습 인덱스 패널 (A-4)

**여는 곳** 모든 스토리 화면의 상단 왼쪽(화면 ID 앞) `학습 인덱스` 버튼(`aria-expanded`, `aria-controls`). 인트로에는 패널 대신 로드맵이 있습니다.

**패널 내용 (위에서 아래로)**

1. 머리: `학습 인덱스` 제목 · `모두 펼치기`/`모두 접기` · `닫기`
2. 현재 위치 한 줄: `지금 Scene 4 · Python과 외부 AI · 화면 6 / 9 · 전체 22 / 33`
3. Scene 6개 구획. 구획 머리(버튼, `aria-expanded`): `Scene n · 관점` · 카드 제목 · `화면 k개` · 현재 Scene이면 `지금 여기` 표시
4. 펼친 구획: 학습 질문 → 도달 목표 → 핵심 개념 칩 → 화면 목록(`ID · 제목` 링크, 현재 화면은 `aria-current="page"`와 글자 `현재 화면`)
5. 끝: `강의 소개와 학습 로드맵` 링크

**펼침 규칙** 처음 열면 현재 Scene만 펼칩니다. 다른 화면으로 이동해 Scene이 바뀌면 새 Scene을 펼친 목록에 **더합니다**(학습자가 직접 펼친 구획을 접지 않음). 펼침 상태는 페이지를 새로 열면 초기화합니다(저장하지 않음).

**폭별 동작**

| 폭 | 방식 | 세부 |
| --- | --- | --- |
| ≥1000px | **고정형 왼쪽 열** | 폭 `clamp(260px, 22vw, 300px)`, 화면 높이 안에서 sticky·자체 스크롤. 열면 슬라이드 영역이 그만큼 좁아지고, 닫으면 v0.4와 같은 폭으로 돌아갑니다. 비모달: 슬라이드를 계속 조작할 수 있습니다. 화면을 골라도 패널은 열린 채로 남습니다(“펼쳐 둔 채 연속 학습”). |
| 1240–1439px **이고** P 패널이 열림 | **레일로 축소** | P가 오른쪽 열을 차지하는 폭이므로 인덱스를 폭 56px 레일(Scene 번호 1–6, 현재 Scene 강조, `펼치기` 버튼)로 줄여 본문이 지나치게 좁아지지 않게 합니다. 레일의 `펼치기`는 인덱스를 슬라이드 위에 겹쳐 엽니다(본문을 밀지 않음). P를 닫으면 원래 열로 돌아갑니다. ≥1440px에서는 두 패널을 모두 열 수 있습니다. |
| <1000px | **Drawer (모달 오버레이)** | 왼쪽에서 폭 `min(86vw, 360px)`. 뒤 배경을 흐리게 덮고 `role="dialog"` `aria-modal="true"`. 초점을 패널 안에 가둡니다. Esc·배경 누르기·닫기로 닫고 초점을 `학습 인덱스` 버튼으로 돌려줍니다. 화면을 고르면 이동하면서 닫고, 초점은 v0.4처럼 새 화면의 `h1`로 갑니다. 본문은 줄어들지 않습니다. |

**열림 기억** ≥1000px에서 학습자가 고정해 연 상태는 `localStorage`의 `b32-v05-learning-index`(`open`/`closed`)에 기억해 다음 화면·새로고침에서도 유지합니다. 기본값은 **닫힘**입니다. <1000px의 drawer는 기억하지 않고 늘 닫힌 채 시작합니다. 저장소를 쓸 수 없으면 기억 없이 동작합니다(테마 선택기와 같은 처리).

**초점과 키보드**

- 버튼으로 열면 초점이 패널 제목으로 가고, 닫으면 버튼으로 돌아옵니다(P 패널과 같은 규칙).
- 패널 안의 Tab 순서: 머리 버튼들 → Scene 구획 버튼 → (펼친 구획의) 화면 링크. Enter/Space로 펼침·이동.
- 슬라이드 이동 키(←/→/PageUp/PageDown)는 v0.4처럼 슬라이드 영역에서만 동작합니다. 인덱스 안에서 눌러도 슬라이드가 넘어가지 않습니다.
- Esc: 초점이 인덱스 안이면 인덱스를 닫습니다. 그 밖에서는 v0.4처럼 P 패널을 닫습니다. drawer가 열린 동안 `P` 단축키는 무시합니다(모달 뒤의 패널을 열지 않음).
- 현재 화면이 바뀌면, 패널이 열려 있을 때 현재 화면 링크가 **패널 스크롤 영역 안에서만** 보이도록 스크롤합니다(페이지 전체를 움직이지 않음).

**뒤로 가기** 인덱스를 열고 닫는 것은 브라우저 기록을 만들지 않습니다. 인덱스에서 화면을 고르는 것은 v0.4의 이전·다음과 같은 일반 이동(기록 추가)입니다. drawer가 열린 채 뒤로 가기를 누르면 이전 화면으로 이동하면서 drawer가 닫힙니다.

### 3.3 현재 위치 표시 (A-5)

인덱스를 닫아도 보이는 최소 정보입니다. v0.4의 “관점 띠”(Scene 칩 6개, `.b32-perspectives`) 자리를 **위치 띠**로 바꿉니다(같은 자리, 같은 높이 안에서, Scene 첫 화면으로 가는 링크 기능 유지).

- 6칸 띠: `1 사용자` · `2 Git` · `3 Python` · `4 Python과 외부 AI` · `5 결과 검증과 활용` · `6 종합과 응용`. 현재 칸만 `aria-current="step"` + 강조 + 그 칸 안에 `화면 6 / 9`. 칸 사이 화살표는 §2.2의 길(2–5 실선)을 따릅니다.
- 띠 아래 한 줄 글: `Scene 4 / 6 · Python과 외부 AI · 화면 6 / 9 · 전체 22 / 33` (화면 읽기 프로그램에도 같은 글).
- 상단 조작의 `22 / 33`은 그대로 둡니다.

## 4. I11 Temperature 인터랙티브 시뮬레이션 (S4-5a)

**학습 목표** temperature가 후보의 선택 확률 분포를 조절한다는 것을 이해하고, ① 낮으면 높은 후보에 모이는 이유 ② 높으면 낮은 후보가 뽑힐 가능성이 커지는 이유 ③ temperature ≠ 정확성 ④ 일관성이 중요한 커밋 메시지에 낮은 값이 합리적일 수 있는 이유를 설명한다.

**데이터** 원고 S4-5a `**도식 표**`의 후보·기준 확률(1.0 열)을 읽습니다. 앞 4행 = 상태 `sentence`(“오늘 날씨가 좋아서 공원에…” · 갔다 55 · 산책하러 나갔다 25 · 놀러 갔다 15 · 그림을 그리러 갔다 5), 뒤 4행 = 상태 `commit`(같은 README 변경의 커밋 제목 후보 50·30·15·5, 4번째는 “변경에 없는 내용”). 0.2·2.0 열은 웹 계산이 맞는지 확인하는 **테스트 기준값**입니다.

**계산**

```
weight_i = p_i ** (1 / T)          (T > 0)
prob_i   = weight_i / Σ weight
T = 0  → 식에 넣지 않음. 극한 처리: 기준 확률이 가장 높은 후보 100%, 나머지 0% (동률 없음)
```

- 슬라이더 0–2, 0.1 단위(B3-2 프로그램의 허용 범위와 같은 범위). 0에서는 `0 (극한)`으로 표시하고 “식에 0을 넣으면 0으로 나누게 됩니다 · 가장 높은 후보만 고르는 상태를 따로 보여 줍니다 · 실제 서비스의 0 처리는 공급자마다 다를 수 있음(미확인)” 안내를 보입니다.
- 표시: 소수 첫째 자리 %. 0 < 값 < 0.05%이면 `0.1% 미만`. 합계 줄 `합계 100.0%`(반올림 전 값의 합으로 계산).
- 검증: 모든 T에서 합계 1 ± 1e-9, T가 커질수록 가장 높은 후보의 확률은 줄고 가장 낮은 후보는 늘어남(단조), T=1이면 기준과 같음, 0.2·2.0 값이 원고 표와 같음.

**조작** 슬라이더(`aria-valuetext="temperature 0.2"`) · 현재 값 · 대표 값 버튼 `0.2` `1.0` `2.0` · `초기화`(1.0) · `0.2와 1.0 나란히 비교` 토글 · 상태 버튼 `문장 예시`/`커밋 제목 예시`(`aria-pressed`). 바뀐 확률 요약을 `aria-live="polite"`로 알립니다(예: “temperature 0.2 · 갔다 98.0% · 그림을 그리러 갔다 0.1% 미만”).

**막대** 후보마다 가로 막대(길이 = 확률) + 글자 % + 기준(1.0) 위치의 점선 표시 + 기준보다 늘었는지 줄었는지 `▲`/`▼`/`=` 글자. 색만으로 구분하지 않습니다. `prefers-reduced-motion`이면 막대 길이 변화 전환 효과를 끕니다.

**미션 연결 (`commit` 상태)** 맥락 줄 “같은 README 변경: README.md 끝에 메모 한 줄 추가”. 4번째 후보에 `변경에 없는 내용(추측)` 표시. 도식 아래 고정 문장 3개: “낮은 값: 가장 흔하고 일관된 표현이 거의 매번 나옵니다.” · “높은 값: 표현이 다양해지고, 변경에 없는 내용을 추측한 후보도 뽑힐 가능성이 커집니다.” · “낮은 값이 늘 정확한 것은 아닙니다. 가장 높은 후보가 틀렸다면 그 틀린 표현이 일관되게 나옵니다.”

**표시 의무** `교육용 시뮬레이션 · 실제 AI 출력·측정값이 아닙니다` · `실제 AI API 호출 없음` · `후보는 실제 모델의 토큰 후보가 아닌 단순화된 예시` · `temperature=0.2는 교육용 설정 예시 (미션 공식 값 아님)` · `코디세이 gpt-5-mini 지원 미확인`. 무작위로 뽑아 보는 기능은 실제 출력과 혼동될 수 있어 넣지 않습니다.

## 5. I12 Max Tokens 인터랙티브 시뮬레이션 (S4-5b)

**학습 목표** 토큰과 글자의 차이, 최대 생성 토큰 수와 실제 생성 수, 답변 완성과 한도 도달, Python 출력 검증, 실제 사용량·비용을 구분한다.

**데이터 (재현 기록을 읽기만 함)** `assets/evidence/max-tokens-v0.5-claude-2026-11-28.json`

- `draft`: 교육용 PR 초안(2026-11-25 Owner의 실제 PR 출력을 바탕으로, 기록되지 않은 How to Test 원문만 교육용으로 작성). Title · Why · What · How to Test.
- `unit_rule`: 교육용 단위 1 = 공백·줄바꿈으로 나눈 글 조각 1개(정규식 `\S+`). 완성 초안 = `total_units` 57.
- `results[n]` (n = 0…57): 초안을 앞에서 n조각까지만 남긴 글을 **실제 B3-2 코드**(`AIClient.generate()`의 응답 처리 → `validate_pr()`)에 넣은 결과. `result`(`pass`/`reject`), `stage`(`response`/`validate`), `message`(거부 문구), `output`(통과 시 후처리된 PR). `urlopen`을 가로채 요청은 밖으로 나가지 않았습니다(R12).
- 웹은 이 기록을 **그대로 표시**하고 검증기를 JavaScript로 다시 만들지 않습니다(I9와 같은 원칙). 웹의 조각 나누기는 같은 정규식을 쓰고, 조각 수가 57인지 테스트합니다.

**모델**

```
한도 L (교육용 단위, 슬라이더 1–80 · 프리셋 8 20 40 48 52 57 80)
추론 가정 R = 0 (끔) 또는 30 (켬, 보이지 않는 내부 추론에 쓴다고 가정)
추론 소비 r = min(L, R)                          (막대에 쓰는 값. 가정값 30은 안내 글에 남김)
보이는 글 n = min(57, max(0, L − R))
상태: L − R ≥ 57 → 답변 완성 (finish_reason 표시 stop · 교육용)
        L − R = 57이면 “답변 완성 · 한도와 같은 양”, L − R > 57이면 “한도 L 중 57만 만들었습니다”
      그 밖 → 생성 한도 도달 (finish_reason 표시 length · 교육용)
Python 처리 결과 = results[n]  (stage `response` = 응답 처리 단계에서 거부 · PR 형식 검사 전 / stage `validate` = 형식 검증)
```

확인 사례(B-0 협의): 추론 켬 한도 20·30 → 보이는 글 0·응답 처리에서 거부, 31 → 1·섹션 거부, 80 → 50·통과(끊김) / 추론 끔 57 → 완성·한도와 같은 양, 80 → 완성·57만.

**네 가지 상태 표시 (글자 + 기호, 색만으로 구분하지 않음)**

1. `생성 중` — `생성 시작`을 누르면 조각이 하나씩 붙습니다(조각당 약 40ms, `prefers-reduced-motion`이거나 n = 0이면 바로 끝 상태). 재생 중 카운터 `만든 단위 n / 한도 L`. 화면 읽기 프로그램에는 시작과 최종 상태만 요약해 알립니다(40ms 갱신은 시각적으로만).
2. `답변 완성` — 위 상태 규칙의 두 문구. L > 57의 문구에 “max_tokens는 목표가 아니라 상한입니다”를 붙입니다.
3. `생성 한도 도달` — 글 끝에 `⟂ 한도에서 끊김` 표시.
4. `Python 처리 결과` — 단계 이름을 함께 표시(`응답 처리` 또는 `형식 검증`). 거부: 실제 문구 + “종료 코드 1 · 다시 요청하지 않음 · 이 요청 1회와 사용량은 이미 생겼습니다”. 통과: 후처리된 PR 전문, 교체된 How to Test 줄 강조. **한도에 닿아 끊겼는데 통과한 경우(n = 49–56)** “검증 통과 ≠ 생성 완료 · 끊긴 문장이 후처리로 교체되어 보이지 않습니다” 안내.

처음 상태(`stream`)는 한도 20 · 추론 가정 끔의 **끝난 결과를 바로** 보여 줍니다(자동 재생 없음 — 강의 화면과 테스트가 안정적).

**추론 모델 가정 (토글)** 켜면 막대 하나를 `추론(보이지 않음) r | 보이는 글 n | 남은 한도`로 나눠 보여 줍니다(r = min(L, 30)). 한도 30 이하 → 보이는 글 0 → `results[0]` = 응답 처리 단계의 “AI API 응답에 텍스트가 없습니다.”(PR 형식 검사 전). 표시: `교육용 가정 · 추론 토큰의 양과 계산 방식은 공급자·모델마다 다름 · 코디세이 gpt-5-mini 미확인`.

**형식이 완성되어도 실패하는 경우** 결과 아래 고정 안내 두 줄과 S5-3 링크: “제목 81자 → 거부 (I9 P5)” · “확인되지 않은 테스트 통과 주장 → 거부 (I9 P4)”, 그리고 “검증을 통과해도 내용의 사실 여부는 사람이 판단 (S5-5)”. 판정 문구는 기존 R9 기록(I9 데이터)을 재사용합니다.

**토큰 표시의 정확성 (C-3)** 모든 숫자 옆에 `교육용 단위`를 붙이고 “실제 토크나이저의 토큰 수가 아닙니다”를 도식 머리에 둡니다. `max_tokens=500`은 “PR 초안에 충분한 한도를 가정한 교육용 예시값 · 이 도식의 단위와 1:1로 대응하지 않음”으로 표시합니다. 실제 사용량은 응답 `usage`(S4-7, 실제 기록 8·101·109)로 안내합니다.

**두 가지 제한 구분 (C-4)** 도식 오른쪽(좁은 화면은 아래)에 두 칸 고정 표: `Python이 결과를 검사하는 규칙`(커밋 제목 최대 72자 · PR 제목 최대 80자 · PR 필수 섹션과 불릿) / `외부 AI의 생성 한도`(요청 JSON의 `max_tokens`). 표 아래 주석: “커밋 제목 50자 이내는 프롬프트 권장이며 Python이 검사하지 않습니다(S5-2)”. 이어서 “서로 대신할 수 없습니다”. 문구는 원고 해설과 같게 씁니다.

**I5 `git-cases` (S3-5)** 네 사례 버튼(`① 변경 없음` `② 변경 있음` `③ stderr에 진행 정보` `④ 실패`, `aria-pressed`)과 `네 사례 나란히` 토글. 각 사례 칸: 실행 명령 · `returncode` · `stdout` · `stderr` · **Python의 판단**. 판단은 B3-2 `_git()` 기준(구현 · 소스): ① 0 → stdout `''`를 돌려줌 → 프로그램은 “변경 사항이 없습니다.”·요청 0(실제 기록) ② 0 → stdout을 돌려줌 → 다음 단계 ③ 0 → stderr는 보지 않고 stdout을 돌려줌(B3-2는 clone을 실행하지 않음 · 일반 Git 예) ④ 128 → stderr를 담아 `GitError` → 종료 1·요청 0. ①에 “stdout이 비었지만 성공”, ③에 “stderr에 글이 있지만 성공” 말풍선. 값은 원고 S3-5 실습 결과에서 읽고, 값 배지는 `재현 · Claude 2026-11-28 (R10)`, 판단 배지는 `구현 · 소스 be21c49`. v0.4의 `I5:git`(두 사례)는 v0.4 모드에서 그대로 씁니다.

## 7. Scene 4 흐름과 주소 호환 (작업 D)

**순서** S4-1 REST·HTTPS → S4-2 환경변수·API 키 → S4-3 프롬프트 → S4-4 요청 JSON → S4-5 세 파라미터의 역할·기존 JSON 조작 도식(I7 params, 그대로) → **S4-5a Temperature 원리** → **S4-5b Max Tokens 원리** → S4-6 HTTP 성공·오류 → S4-7 응답 추출·토큰 비용. 학습 질문이 “파라미터를 바꾸면 요청은?(S4-5) → 결과는 왜?(5a·5b) → 그 요청이 실패하면?(S4-6) → 성공하면 무엇을 꺼내나?(S4-7)”로 이어집니다. S4-5b의 “요청 1회·사용량은 이미 생김”이 S4-6의 요청 횟수와 S4-7의 usage로 자연스럽게 넘어갑니다.

**주소 결정 — 고정 ID와 표시 순서 분리** 새 화면에 `S4-5a`·`S4-5b`라는 고정 ID를 붙입니다. 기존 화면을 다시 번호 매기지 않습니다.

| 주소 | v0.4 의미 | v0.5 의미 |
| --- | --- | --- |
| `?scene=4&screen=6` | S4-6 HTTP 성공과 오류 | **같음** |
| `?scene=4&screen=7` | S4-7 응답·토큰 | **같음** |
| `?scene=4&screen=5a` / `5b` | (없음 → 복구 안내) | S4-5a / S4-5b |
| 그 밖 31개 화면 주소, `lab/NN?from=S4-6` 등 Lab 복귀, 용어사전 `?b32-story=scene=…&screen=…` | — | **모두 같음** |

- 이유: 다시 번호를 매기면 `screen=6`이 Temperature를 가리켜, 강의 자료·메모·Lab 07 복귀(`from=S4-6`)·용어사전 복귀 주소의 뜻이 바뀝니다. 영문 접미사는 “S4-5를 깊이 보는 보충 화면”이라는 원고 구조와도 맞습니다.
- 표시: 화면 ID는 원고 그대로(`S4-5a · Temperature …`), 위치는 배열 순서에서 계산(`Scene 4 화면 6 / 9`, `전체 22 / 33`). ID 숫자와 위치 숫자가 다를 수 있으므로 위치는 늘 `화면 n / N` 형식으로만 씁니다.
- 기존 주소 해석(`readStoryState`)은 `S${scene}-${screen}` 일치로 화면을 찾으므로 형식 변경이 필요 없습니다. 다만 `screen` 값이나 화면 ID에 숫자만 허용하는 검사(Lab `from`, 용어사전 복귀 `b32-story`, 테스트 정규식)가 있으면 v0.5 모드에서 `[0-9]+[a-z]?`를 허용해야 합니다. **영향 범위 확인은 Codex 설계 검토 항목**입니다(인수인계 §9).
- v0.4 모드(`b32-v04`)는 31화면·기존 동작 그대로입니다. 공개 route 경로·공개 빌드는 바꾸지 않으므로 Owner Gate 대상이 아닙니다.
