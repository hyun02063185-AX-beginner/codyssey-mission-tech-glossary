## 인트로와 강의 구성

**초안 안내** B3-2는 외부 AI API의 응답을 검토용 글로 출력합니다. 같은 Git 변경을 커밋 메시지나 PR 설명으로 작성해 보는 사례로, Python 프로그램이 외부 서비스를 호출하는 과정을 배웁니다.

**학습 목표**

1. Python에서 외부 AI API로 보내는 요청과, 응답에서 Python이 읽어 오는 내용을 설명한다.
2. Python이 로컬 Git을 실행해 변경 내용을 수집하고, 실패와 변경 없음을 구별하는 이유를 설명한다.
3. 요청 본문의 작성 규칙과 Git 문맥, 인증 헤더, 전송 전 보안 검사, 응답 후 검증의 역할을 구별한다.
4. 실제 diff와 초안을 대조해 어떤 내용을 사람이 확인하고 고쳐야 하는지 말한다.

대면 강의에서는 F1 전체 그림으로 **내 컴퓨터와 외부 AI API**의 경계부터 짚습니다. 선수개념은 명령줄에서 프로그램 실행, 변경 내용 비교(diff), API와 JSON의 역할입니다. Scene 1은 사례의 목적과 입력을 소개하고, Scene 2는 Python이 그 입력을 얻는 과정을 보여 줍니다. Scene 3에 가장 많은 시간을 배정해 요청이 나가는 방향과 응답이 돌아오는 방향을 각각 설명합니다. Scene 4에서는 실제 초안을 비교한 뒤 처음 질문으로 돌아옵니다.

## Scene 1 — 내 Python 프로그램에서 외부 AI 쓰기

### S1-1 · 내 Python 프로그램이 외부 AI에 맡길 일

**화면 설명** B3-2는 로컬 Git의 변경 내용을 외부 AI API에 보내 설명 초안을 받아 옵니다.

**그림 제안 · F2** 직접 쓸 때와 Python으로 초안을 받을 때의 비교를 유지합니다. 오른쪽의 Git과 AI 사이에서 **Python이 준비해 보내고 받아 오는 역할**을 드러냅니다. 끝의 사람 확인과 기존 실제 출력 제목은 유지합니다. 왼쪽의 “수정”은 교육용 예시로 표시합니다.

**화면 해설**

API는 한 프로그램이 다른 서비스에 일을 부탁하고 결과를 받을 수 있는 창구입니다. 그림의 오른쪽에서는 Python이 Git에서 얻은 변경 내용을 건네고 외부 AI의 답을 받아 옵니다. B3-2는 학습 문서에 실습 메모를 추가한 변경으로 설명 초안을 받았고, 그림의 오른쪽 제목은 그때의 실제 출력입니다. 초안은 사람이 읽고 고쳐 쓸 수 있는 검토용 글입니다.

**더 읽기** [02 Python과 AI API][g02] · [07 전체 실습][g07]

### S1-2 · AI에 설명을 부탁하려면 어떤 정보가 필요할까?

**화면 설명** `git status`에서 어떤 파일이 바뀌었는지, `git diff`에서 어떤 줄이 바뀌었는지 읽습니다.

**그림 제안 · F3** 파일 목록과 바뀐 줄이 서로 다른 정보를 준다는 점을 강조합니다. 메모와 빈 줄이 추가된 기존 터미널 출력을 그대로 사용하고 **연습 저장소에서 재현**이라고 표시합니다. 줄 위치 표기와 스테이징의 자세한 읽기는 기존 접힘 설명과 학습가이드로 이어 갑니다. [Git 재현 기록](assets/evidence/demo-git-output.txt)

**화면 해설**

AI가 무엇이 바뀌었는지 설명하려면 파일 이름과 바뀐 줄이 필요합니다. 그림은 공부하던 문서에 실습 메모를 추가한 변경을 연습 저장소에서 다시 만든 것으로, `git status`의 `M`은 수정된 파일을, `git diff`의 `+`는 추가된 줄을 보여 줍니다. B3-2의 Python은 현재 폴더의 로컬 저장소에서 이 정보를 읽어 요청에 쓸 재료로 삼습니다. `git add`로 골라 둔 변경은 `git diff --cached`로 따로 확인할 수 있습니다.

**더 읽기** [01 Git과 diff][g01]

## Scene 2 — Python이 로컬 Git에서 변경 읽기

### S2-1 · Python이 로컬 Git을 실행하는 방법

**화면 설명** `argparse`는 초안 종류를 읽고, `subprocess.run()`은 운영체제를 통해 Git을 실행합니다.

**그림 제안 · F4** 사용자 명령 입력 → Python의 초안 종류 해석 → 로컬 Git 호출 → 결과 반환을 유지합니다. Python이 Git에 넘기는 인수 목록의 축약 표시와 셸을 거치지 않는 구간을 기존 그림처럼 구분합니다. 실제 읽기 명령은 “저장소·브랜치 확인, 상태 두 번, diff 두 번”으로 묶어 보여 줍니다.

**화면 해설**

`python main.py commit`에서 `commit`은 만들 초안이 커밋 메시지라는 뜻입니다. 그림에서 Python의 `argparse`가 이 값을 읽으면, `subprocess.run()`이 운영체제를 통해 로컬 Git 프로그램을 실행합니다. 이 Git 호출에서 Python은 실행할 프로그램과 명령을 목록으로 건네며 셸을 거치지 않습니다. B3-2는 이렇게 변경 정보를 읽고 초안을 준비하며, 실제 커밋과 PR 등록은 사람이 별도로 합니다.

**더 읽기** [01 Git과 diff][g01] · [07 전체 실습][g07]

### S2-2 · Python은 Git 결과를 보고 어떻게 판단할까?

**화면 설명** Git 명령의 종료 코드로 성공을 확인하고, 수집한 상태에 변경이 있을 때 다음 단계로 진행합니다.

**그림 제안 · F5** 종료 코드 확인, Git 성공 시의 변경 확인, 외부 요청 준비의 순서가 드러나게 합니다. `stdout`이 비어 있을 수 있는 두 경우인 **Git 실패**와 **명령 성공 후 변경 없음**을 나란히 보여 줍니다. 예시의 종료 코드 128과 오류 메시지에는 **재현**을 표시합니다. [Git 실행 결과 재현](assets/evidence/subprocess-results.txt)

**화면 해설**

Git을 실행하고 나면 Python은 결과에 담긴 종료 코드(`returncode`), 표준 출력(`stdout`), 표준 오류 출력(`stderr`)을 읽을 수 있습니다. 그림의 저장소 밖 사례는 표준 출력이 비어 있어도 종료 코드 128로 실패를 구별할 수 있음을 보여 줍니다. B3-2는 Git 명령이 성공한 뒤 수집한 `git status` 결과에 내용이 있는지 확인합니다. Git 명령이 실패하거나 성공했지만 변경이 없으면 이 실행의 AI 요청 횟수는 0회입니다.

**더 읽기** [01 Git과 diff][g01] · [07 전체 실습][g07]

## Scene 3 — Python과 외부 AI API의 요청·응답

### S3-1 · 외부 AI에 보낼 Git 문맥 준비하기

**화면 설명** Python은 로컬 Git 결과를 문맥으로 묶고, 값 가리기와 전송 중단을 구별해 처리합니다.

**그림 제안 · F6** 여섯 항목을 기존 문맥 순서대로 보여 줍니다. 브랜치, 상태, 변경 파일명, 미추적 파일명, `git add`한 변경, 아직 `git add`하지 않은 변경 순입니다. 검사에서 **감지한 값은 가린 뒤 계속**, **위험 경로·불완전한 개인키 또는 한도 초과는 전송 중단**으로 결과를 구분합니다. 806자는 문맥 재현 값이며 S3-2의 `user` 메시지로 이어지는 값입니다. [Git 문맥 재현](assets/evidence/demo-context.txt)

**화면 해설**

외부 AI에 전달할 Git 문맥은 파일 이름과 변경 내용에 브랜치와 상태를 더해 만든 글입니다. 그림에서 B3-2는 `git add`한 변경과 아직 `git add`하지 않은 변경을 함께 묶고, Git이 추적하지 않는 새 파일은 이름만 담습니다. 기본 검사는 발견한 이메일·토큰 값을 가려 계속 진행하고, 비밀 파일로 보이는 경로나 불완전한 개인키 블록을 감지하면 전송을 중단합니다. 16,000자 한도는 `--unsafe`를 지정한 실행에도 적용됩니다. 패턴으로 찾을 수 있는 값에 한계가 있으므로, 전송 전에 보낼 내용을 직접 확인합니다.

**더 읽기** [05 검증과 보안][g05]

### S3-2 · Python과 외부 AI API가 주고받는 것

**화면 설명** Python은 HTTPS로 JSON 요청을 보내고, 돌아온 응답 JSON에서 초안 글을 꺼냅니다.

**그림 제안 · F7** 이 화면을 강의의 기술적 중심으로 둡니다. **내 컴퓨터의 Python**과 **외부 코디세이 AI API** 사이에 방향이 반대인 실선 화살표 두 개를 배치합니다. 모바일에서는 위아래로 배치해도 요청은 API 쪽, 응답은 Python 쪽을 가리킵니다.

| 표시 순서 | 그림에서 강조할 문구 | 그림에 담을 내용 |
| --- | --- | --- |
| ① Python → 외부 AI API | **요청 · HTTPS POST** | 인증 헤더 `Authorization`은 `Bearer ••••`로 표시. JSON 본문에 모델 ID와 `messages`를 표시. `system`은 작성 규칙, `user`는 S3-1에서 검사한 Git 문맥. |
| ② 외부 AI API → Python | **응답 · JSON** | Python이 `choices[0].message.content`에서 초안 텍스트를 읽음. 다음 목적지는 S4의 검증과 터미널 출력. |

요청 구조는 **재현**으로 표시합니다. `gpt-5-mini`를 표시하면 “2026-10-20 실제 실행 설정”을 함께 붙입니다. 실제 초안 문구를 예로 넣을 때는 응답 카드 아래에 “실제 터미널 출력 발췌 · 검증·후처리 후”로 따로 표시합니다. 원본 응답 JSON은 확보되지 않았습니다. 그림에서 외부 경계는 API에서 끝내고 “모델 실행 위치 미확인”을 덧붙입니다. [요청 재현](assets/evidence/demo-request.json) · [실제 출력](assets/evidence/real-output-2026-10-20.txt)

**화면 해설**

외부 AI API에 일을 부탁할 때, Python은 보낼 내용과 인증 정보를 요청에 담습니다. 그림의 나가는 화살표는 HTTPS POST 요청이며, B3-2는 환경변수에서 읽은 API 키를 인증 헤더에, 모델 ID와 메시지를 JSON 본문에 넣습니다. 두 메시지 중 `system`은 글을 어떻게 쓸지 정하는 작성 규칙이고, `user`는 앞 화면에서 검사한 Git 문맥입니다. 돌아오는 화살표는 응답 JSON으로, Python이 그 안의 `choices[0].message.content`에서 초안 텍스트를 읽습니다. 이 그림에서 확인할 수 있는 범위는 외부 API와의 통신까지이며, 모델 실행 위치는 미확인입니다.

## Scene 4 — AI 응답을 검증하고 업무에 쓰기

### S4-1 · 같은 변경에서 얻은 두 가지 초안

**화면 설명** 같은 변경을 커밋 메시지나 PR 설명으로 받아 볼 수 있습니다. 화면의 두 결과는 실제 터미널 출력입니다.

**그림 제안 · F8** 기존 두 출력과 실제 제목을 유지합니다. 커밋 제목과 선택 본문, PR의 제목·이유·변경 내용·확인 방법을 비교하고, **How to Test는 Python이 교체한 문구**라고 표시합니다. 날짜, 발췌 표시와 원문 연결을 유지합니다. [실제 출력 전문](assets/evidence/real-output-2026-10-20.txt)

**화면 해설**

같은 Git 변경 정보라도, 요청에 담은 작성 규칙에 따라 필요한 형태의 초안을 받을 수 있습니다. 그림은 학습 문서에 실습 메모를 추가하고 2026년 10월 20일에 실행한 두 명령의 실제 출력입니다. B3-2는 커밋 메시지를 제목과 선택 본문으로, PR 설명을 제목과 Why·What·How to Test로 받도록 요청합니다. PR의 How to Test는 검증 후 프로그램이 정해 둔 테스트 실행 권장 문구로 바뀌므로, 이 줄은 테스트를 이미 실행했다는 기록과 구별해야 합니다.

### S4-2 · AI가 만든 초안을 업무에 사용하기

**화면 설명** 형식 검사를 통과한 글을 사람이 실제 diff와 비교한 뒤, 필요한 곳에 사용합니다.

**그림 제안 · F1 `return`** 인트로의 구조도로 돌아옵니다. 외부 AI API에서 Python으로 돌아온 답 → 검증 후 터미널 출력 → 사람의 확인 순서가 드러나게 합니다. 사람의 확인은 터미널 출력 뒤에 이어지며 Python 바깥에 표시합니다. “파일 끝에”라는 실제 초안 표현은 당시 위치 기록이 없으므로 오류 사례로 단정하지 않습니다. [v0.1 검토 기록](review.md)

**화면 해설**

형식이 맞는 초안도 실제 변경과 내용이 일치하는지는 사람이 확인합니다. 그림에서 Python은 제목 길이나 PR의 필수 섹션과 불릿을 검사해 검토용 초안을 출력합니다. 사용자는 초안에 적힌 파일·변경 내용·수정 이유를 실제 diff와 작업 의도에 비춰 읽습니다. 확인하거나 고친 글로 커밋을 만들고 원격에 push하거나 PR을 등록하는 일은 사람이 별도로 수행합니다. 형식 검사에 실패하면 B3-2는 오류를 출력하고 그 실행을 끝냅니다.
