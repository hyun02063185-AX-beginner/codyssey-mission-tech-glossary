## 인트로와 강의 구성

**초안 안내** 이 미션에서 다루는 B3-2 프로그램(`main.py`)은 외부 AI API가 돌려준 글을 검토용 초안으로 터미널에 출력합니다. 같은 Git 변경을 커밋 메시지나 PR 설명 초안으로 받아 보는 사례를 따라가며, 내 Python 프로그램이 외부 서비스에 일을 부탁하고 답을 받는 과정을 배웁니다.

**학습 목표**

1. 내 Python 프로그램이 외부 AI 서비스에 무엇을, 어디로 보내고, 무엇을 받아 오는지 설명한다.
2. Python이 내 컴퓨터의 Git을 실행해 변경 내용을 읽고, Git 실패와 변경 없음을 구별하는 이유를 설명한다.
3. 요청에서 API 키와 보낼 내용이 서로 다른 자리에 들어가는 이유를 말한다.
4. AI가 만든 초안을 실제 변경과 비교해 사람이 확인하고 고칠 부분을 찾는다.

**학습 안내** 각 화면에서 **P** 또는 **설명 보기**를 누르면 해설이 열립니다. 해설을 순서대로 읽으면 처음 질문에 대한 답이 하나의 이야기로 이어집니다. 코드와 세부 규칙은 해설 아래의 학습가이드에서 확인합니다. 이 강의는 명령줄에서 프로그램을 실행해 본 경험과 Python 딕셔너리·리스트를 안다고 가정합니다. Git 저장소와 JSON은 이야기 속에서 처음부터 짚습니다.

## Scene 1 — 내 Python 프로그램에서 외부 AI 쓰기

### S1-1 · 내 Python 프로그램이 외부 AI에 맡길 일

**화면 설명** B3-2 프로그램은 내 컴퓨터의 Git 변경 내용을 외부 AI API에 보내 설명 초안을 받아 옵니다.

**그림 제안 · F2** 왼쪽의 “수정”은 교육용 예시입니다. 오른쪽 제목은 2026-11-25 실제 출력인 `README에 실습 메모 문장 추가`로 바꿉니다. 10-20 제목은 이전 실행 사례로 근거 파일에 보존합니다.

**실습으로 확인하기** 같은 변경으로 초안을 직접 받아, 이 그림 오른쪽 아래의 실제 제목과 내 초안을 비교해 보세요.

**화면 해설**

이 강의의 질문은 내 Python 프로그램이 외부 AI 서비스의 기능을 어떻게 빌려 쓰느냐입니다. 글을 써 주는 AI 모델은 내 컴퓨터가 아니라 외부 서비스에서 동작하므로, 내 프로그램은 그 서비스가 정해 둔 창구인 API를 통해 일을 부탁하고 결과를 받습니다. 그림의 왼쪽은 사람이 바뀐 내용을 직접 읽고 설명을 쓰는 방법이고, 오른쪽은 이 미션의 B3-2 프로그램(`main.py`)이 Git에서 얻은 변경 내용을 AI에 건네고 답을 받아 오는 방법입니다. 오른쪽 아래 제목은 README.md 끝에 실습 메모를 추가한 변경으로 실제로 받은 초안이며, 이 글을 쓸지 말지는 사람이 읽고 정합니다. 그런데 AI가 변경을 설명하려면 먼저 무엇이 바뀌었는지 알아야 합니다. 그 정보는 어디에 있을까요?

### S1-2 · AI에 설명을 부탁하려면 어떤 정보가 필요할까?

**화면 설명** 내 컴퓨터의 Git에서 `git status`로 바뀐 파일을, `git diff`로 바뀐 줄을 읽습니다.

**그림 제안 · F3** README.md 변경을 보여 줍니다. ` M README.md`는 add 이전 상태이며, diff는 `@@ -76,3 +76,5 @@`와 파일 끝에 추가한 두 줄(빈 줄, 실습 메모)을 표시합니다. `git diff --cached`의 전후 비교는 Lab 03 도식 01에서 봅니다. [Git 재현 기록 §7](assets/evidence/lab-v0.3-r1-repro-2026-11-25.txt)

**실습으로 확인하기** 왜 Python은 두 가지 diff를 모두 읽을까요? `git add` 전후로 세 명령을 비교해 보세요. 이 그림은 add **이전** 모습입니다.

**화면 해설**

AI에게 건넬 재료는 무엇이 바뀌었는지에 대한 정보이고, 그 정보는 인터넷의 GitHub가 아니라 내 컴퓨터의 Git 저장소에 있습니다. 그림은 같은 실습 메모 변경을 연습 저장소에서 다시 만든 터미널 화면입니다. 위쪽 `git status`의 `M`은 어떤 파일이 수정되었는지를, 아래쪽 `git diff`의 `+`는 그 파일에 어떤 줄이 추가되었는지를 보여 줍니다. 파일 이름과 바뀐 줄, 이 두 가지가 AI가 설명을 쓰는 데 필요한 재료입니다. 지금은 사람이 터미널에 명령을 입력했지만, 프로그램이 이 일을 대신하려면 Python이 Git을 직접 실행해야 합니다.

**더 읽기** [01 Git과 diff][g01]

**이해 확인** `git status`와 `git diff`는 각각 무엇을 알려 주나요? → *`git status`는 어떤 파일이 바뀌었는지, `git diff`는 어떤 줄이 바뀌었는지 알려 줍니다.*

## Scene 2 — Python이 로컬 Git에서 변경 읽기

### S2-1 · Python이 로컬 Git을 실행하는 방법

**화면 설명** `argparse`는 사용자가 입력한 초안 종류를 프로그램이 읽게 하고, `subprocess.run()`은 프로그램이 Git을 실행하게 합니다.

**그림 제안 · F4** v0.2 데스크톱 그림의 네 단계를 유지하되 방향이 다른 두 구간을 구별합니다. ① `argparse` 칸 위에 “사람 → 프로그램: 입력 읽기”, ② `subprocess.run()` 칸 위에 “프로그램 → Git: 실행”을 붙입니다. ② 칸의 “셸 없이 운영체제로 실행”은 그림에서 빼거나 흐리게 하고 학습가이드 01장과 v0.1 접힘 설명으로 넘깁니다. 하단의 “commit은 초안의 종류다 · git commit을 실행하지 않는다”와 “기록·전송 명령은 없다” 띠는 유지합니다. (F4는 이번 설계 범위 밖의 선택 수정입니다.)

**실습으로 확인하기** 이 그림의 ② 화살표를 내 Python 코드로 실행해 보세요. ①은 Lab 01의 도움말입니다.

**화면 해설**

앞 화면에서 사람이 입력한 Git 명령을 이제 Python 프로그램이 대신 실행합니다. 그림에는 방향이 서로 다른 두 도구가 나옵니다. 먼저 `argparse`는 사용자가 터미널에 입력한 `python main.py commit`을 프로그램이 읽는 도구로, 여기서 `commit`은 커밋 메시지 초안을 만들라는 뜻입니다. 이어서 `subprocess.run()`은 Python이 다른 프로그램을 실행하는 도구로, B3-2 프로그램은 이것으로 내 컴퓨터의 Git을 실행해 상태와 바뀐 줄을 읽어 옵니다. 이때 Git에서 정보를 읽기만 하므로, 이 명령을 실행해도 실제 커밋은 만들어지지 않습니다. Git을 실행했다면, 이제 Python은 Git이 돌려준 결과를 보고 다음에 무엇을 할지 정해야 합니다.

**더 읽기** [01 Git과 diff][g01] · [07 전체 실습][g07]

### S2-2 · Python은 Git 결과를 보고 어떻게 판단할까?

**화면 설명** Git 명령의 종료 코드로 성공을 확인하고, 수집한 상태에 변경이 있을 때만 다음 단계로 진행합니다.

**그림 제안 · F5** 종료 코드 → 변경 확인의 두 갈래를 유지합니다. stdout은 add 이전의 ` M README.md`로 보여 줍니다. [Git 실행 결과 재현 · Lab 04](assets/evidence/lab-v0.3-repro-2026-11-25.txt)

**실습으로 확인하기** 결과 세 칸의 값을 내 화면에서 직접 받아 보세요. 변경이 없을 때의 ② 갈래는 Lab 02에서 확인합니다.

**화면 해설**

Python이 Git을 실행하면 결과 세 가지를 돌려받습니다. 종료 코드(`returncode`)는 명령이 성공했는지를, 표준 출력(`stdout`)은 명령이 보여 준 내용을, 표준 오류 출력(`stderr`)은 오류 메시지 같은 내용을 담습니다. 그림의 저장소 밖 사례처럼 Git이 실패해도 표준 출력은 비어 있을 수 있으므로, 프로그램은 종료 코드가 0인지부터 확인하고 그다음에 변경이 있는지 봅니다. Git이 실패하면 오류를 알리고, 성공했지만 변경이 없으면 “변경 사항이 없습니다”를 출력하고 끝나며, 두 경우 모두 AI에는 아무것도 보내지 않습니다. 변경이 있을 때만 다음 단계로 가는데, 여기서부터는 이 정보가 내 컴퓨터 밖으로 나가게 됩니다.

**더 읽기** [01 Git과 diff][g01] · [07 전체 실습][g07]

## Scene 3 — Python과 외부 AI API의 요청·응답

### S3-1 · 외부 AI에 보낼 Git 문맥 준비하기

**화면 설명** 내 컴퓨터 밖으로 나간 데이터는 되돌릴 수 없으므로, Python은 보낼 글(Git 문맥)을 정하고 보내기 전에 검사합니다.

**그림 제안 · F6** README.md 사례에서 검사한 글(이번 실행 535자)이 다음 화면의 `user`로 이어집니다. add 전후 변경을 함께 읽는 부분, 가리고 계속하는 갈래, 전송을 멈추는 갈래를 표시합니다. [Git 문맥 원문](assets/evidence/context-readme-2026-11-25.txt)

**실습으로 확인하기** 보내기 전에, 내 컴퓨터 밖으로 나갈 글을 직접 출력해 오른쪽 글자 수와 비교해 보세요.

**화면 해설**

지금까지 Python은 내 컴퓨터의 Git에서 변경 내용을 읽었고, 보낼 변경이 있다는 것도 확인했습니다. 이제 이 정보를 외부 AI 서비스로 보낼 차례인데, 한 번 내 컴퓨터 밖으로 나간 데이터는 되돌릴 수 없습니다. 그래서 B3-2 프로그램은 무엇을 보낼지 먼저 정하고, 보내기 전에 검사합니다. 그림의 왼쪽은 보낼 글(Git 문맥)에 담기는 브랜치·상태·파일 이름·바뀐 줄이고, 그 아래는 새 파일의 내용이나 API 키처럼 이 글에 넣지 않는 것입니다. 가운데 검사는 이메일이나 토큰처럼 보이는 값을 가린 뒤 계속 진행하고, 비밀 파일로 보이는 경로처럼 위험한 경우에는 전송을 멈춥니다. 자동 검사가 모든 비밀을 찾아내지는 못하므로, 보내기 전에 `git diff`로 내용을 직접 확인하는 습관도 필요합니다. 이렇게 준비한 글이 다음 화면에서 요청의 `user` 메시지가 됩니다.

**더 읽기** [05 검증과 보안][g05]

### S3-2 · Python과 외부 AI API가 주고받는 것

**화면 설명** Python은 API 주소로 POST 요청을 보내고, 돌아온 응답 JSON에서 초안 글을 꺼냅니다.

**학습 기술** urllib.request(파이썬 기본 HTTP 도구) · AI API

**그림 제안 · F7** 요청의 주소·인증 헤더·JSON 본문을 구분하고 `user`를 앞 화면의 Git 문맥(이번 실행 535자)으로 연결합니다. 성공, 401·403과 그 밖의 오류(예: 400)를 구분합니다. 응답 상자는 교육용 예시이며 실제 최소 연결 테스트는 응답 경로만 확인하는 근거로 표시합니다. [Lab 06 요청 재현](lab-guide-v0.3-r1.md#lab-06) · [최소 연결 테스트 기록](assets/evidence/lab-v0.3-r1-owner-2026-11-25.txt)

**실습으로 확인하기** 요청 JSON을 보내지 않고 만들어 보고(Lab 06), 실제로 보내 보세요(Lab 07). 응답 경로는 Lab 08에서 실제 응답으로 확인합니다.

**화면 해설**

앞 화면에서 준비한 Git 문맥을 이제 외부 AI API로 보냅니다. 그림의 나가는 화살표가 요청인데, 요청에는 어디로 보낼지 정하는 주소(URL), 데이터를 담아 보내는 POST 방식, 요청을 인증하고 권한을 확인하는 자격 증명인 API 키, 그리고 보낼 내용인 JSON 본문이 들어갑니다. 서비스는 키를 기준으로 권한과 사용량을 관리합니다. Python은 환경변수에서 키를 읽어 요청 내용과 분리된 인증 헤더에 넣습니다. JSON 본문에는 모델 ID와 두 메시지가 들어가는데, `system`은 글을 어떻게 쓸지 정한 작성 규칙이고 `user`는 앞 화면에서 준비한 Git 문맥입니다. Python은 이 내용을 딕셔너리로 만든 뒤 JSON 글로 바꿔 보내고, 돌아온 JSON 글은 다시 Python 데이터로 읽습니다. 돌아오는 화살표가 응답으로, 성공하면 응답 JSON의 `choices[0].message.content`에서 초안 글을 꺼냅니다. 서비스가 401이나 403으로 요청을 거절하면 프로그램은 “인증 또는 권한 오류”를 알린 뒤 멈춥니다. 그 밖의 HTTP 오류(예: 400)는 “AI API 응답 오류”로 알리고 멈추며, 이때도 요청은 이미 한 번 보낸 것입니다. 그렇다면 같은 Git 문맥에 작성 규칙만 바꿔 보내면, 돌아오는 글은 어떻게 달라질까요?

**더 읽기** [02 Python과 AI API][g02]

**Scene 3 이해 확인** 작성 규칙·Git 문맥·API 키는 요청의 어느 자리에 들어가고, 돌아온 응답 JSON에서 Python은 어떤 값을 꺼내나요? → *작성 규칙은 JSON 본문의 `system`, Git 문맥은 `user`, API 키는 인증 헤더에 들어갑니다. 응답 JSON의 `choices[0].message.content`에서 초안 글을 꺼냅니다.*

## Scene 4 — AI 응답을 검증하고 업무에 쓰기

### S4-1 · 같은 변경에서 얻은 두 가지 초안

**화면 설명** 프로그램은 같은 Git 문맥에 커밋용 또는 PR용 작성 규칙을 적용할 수 있습니다. 그림의 두 결과는 같은 README.md 변경을 대상으로 한 실제 터미널 출력입니다.

**그림 제안 · F8** 2026-11-25 Owner의 두 실제 출력과 제목을 표시합니다. 공통 `user`와 서로 다른 `system` 규칙을 연결하고, **How to Test는 Python이 교체한 문구**로 표시합니다. [실제 출력 전문 · Lab 08](assets/evidence/lab-v0.3-owner-2026-11-25.txt)

**실습으로 확인하기** `pr` 초안을 받아 `commit` 초안과 비교하고, 위쪽 띠와 카드 머리를 다시 읽어 보세요.

**화면 해설**

앞 화면에서 요청은 작성 규칙(`system`)과 Git 문맥(`user`)을 함께 보낸다는 것을 보았습니다. 그림의 두 결과는 같은 실습 메모 변경으로 2026년 11월 25일에 `commit`과 `pr`을 한 번씩 실행해 받은 실제 터미널 출력입니다. B3-2 프로그램은 두 명령 모두 같은 방법으로 Git 문맥을 만들어 `user`에 담습니다. 준비한 문맥이 같다면 `user`는 같고, `system` 작성 규칙은 명령에 따라 달라집니다. 커밋 규칙은 한 줄 제목과 선택 본문을, PR 규칙은 제목과 Why·What·How to Test를 요구합니다. 실제 두 실행의 원본 요청은 남아 있지 않아 `user`가 글자 단위로 같았는지는 확인할 수 없습니다. 단, PR의 How to Test 줄은 AI가 쓴 문장이 아니라 프로그램이 정해 둔 테스트 실행 권장 문구로 바꾼 것이므로, 테스트를 실제로 실행했다는 기록으로 읽으면 안 됩니다. 이렇게 형식에 맞는 초안이 나왔습니다. 그렇다면 형식이 맞으면 내용도 맞을까요?

### S4-2 · AI가 만든 초안을 업무에 사용하기

**화면 설명** 프로그램이 형식을 검사해 출력한 초안을 사람이 실제 diff와 비교한 뒤, 필요한 곳에 사용합니다.

**그림 제안 · F1 `return`** 인트로의 구조도로 돌아옵니다. 답을 받은 Python의 형식 검사, 사람의 확인, 사람이 직접 사용하는 순서를 유지합니다. 11-25 초안의 ‘마지막에’·‘파일 끝에’는 diff(`@@ -76,3 +76,5 @@`, 뒤 문맥 없음)와 일치합니다. 사람의 확인 예는 [Lab 08](lab-guide-v0.3-r1.md#lab-08)에서 봅니다.

**실습으로 확인하기** 내 초안을 diff와 비교하고(Lab 08), 출력이 두 통로로 나뉘는 것을 확인한 뒤(Lab 09) 마무리 빈칸을 채워 보세요.

**화면 해설**

외부 AI의 답은 바로 사용되지 않고, 먼저 B3-2 프로그램의 형식 검사를 거칩니다. 그림의 ①처럼 프로그램은 커밋 제목의 길이, PR의 필수 섹션과 불릿, “테스트를 통과했다” 같은 확인할 수 없는 주장을 검사하고, 형식에 맞지 않으면 이미 한 번 보낸 요청의 답을 버린 채 다시 요청하지 않고 오류를 알린 뒤 끝냅니다. 하지만 형식이 맞아도 내용이 사실인지는 알 수 없으므로, ②처럼 사람이 초안에 적힌 파일·변경 내용·이유를 실제 diff와 작업 의도에 비춰 확인하고 고칩니다. 그 글로 커밋을 만들고 GitHub에 push하거나 PR을 등록하는 ③의 일도 사람이 직접 합니다. 이제 처음 질문에 답할 수 있습니다. 내 Python 프로그램은 내 컴퓨터의 Git에서 변경 내용을 읽어 보낼 글을 만들고 검사한 뒤, API 주소로 API 키(인증 헤더)와 작성 규칙·Git 문맥(JSON 본문)을 담아 요청을 보냅니다. 그리고 응답 JSON에서 꺼낸 초안의 형식을 검사해 사람에게 보여 주고, 마지막 판단은 사람이 합니다.

**마무리 · 스스로 설명하기** 빈칸을 채워 전체 흐름을 말해 봅니다. “Python은 내 컴퓨터의 ( ① )에서 변경 내용을 읽고, 밖으로 보내기 전에 ( ② )한다. 그다음 API ( ③ )로 ( ④ )를 인증 헤더에, 작성 규칙과 Git 문맥을 ( ⑤ )에 담아 요청한다. 응답 JSON에서 초안을 꺼내 ( ⑥ )을 검사하고, 내용은 ( ⑦ )이 확인한다.” → *① Git 저장소 ② 검사 ③ 주소 ④ API 키 ⑤ JSON 본문 ⑥ 형식 ⑦ 사람*
