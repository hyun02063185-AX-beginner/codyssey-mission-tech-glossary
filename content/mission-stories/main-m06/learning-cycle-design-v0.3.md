## 1. 왜 순환형인가 — 2026-11-25 Owner 학습 기록

Owner는 B3-2 프로그램을 macOS 교육장 PC에서 처음부터 다시 실행하며 다음을 관찰했습니다.

| 관찰 | 설계에 주는 의미 |
| --- | --- |
| 이론을 먼저 읽고 실습해도 한 번에 충분히 이해되지 않았다. | “설명 → 실습” 한 방향 순서만으로는 부족하다. |
| 실습을 먼저 하고 이론을 읽어도 한 번에 충분히 이해되지 않았다. | “실습 → 설명” 한 방향 순서도 부족하다. 순서를 바꾸는 것만으로는 해결되지 않는다. |
| 실습 결과를 관찰한 뒤 도식과 설명을 **다시** 보았을 때 개념과 경험이 연결되었다. | 연결이 일어나는 지점은 **자기 결과를 들고 도식으로 돌아올 때**다. 콘텐츠가 이 왕복을 쉽게 만들어야 한다. |
| 이 왕복을 반복할수록 미션 전체 기술 구조에 대한 이해가 깊어졌다. | 한 번의 왕복으로 끝나지 않는다. 같은 사례를 여러 번 다른 각도에서 다시 만나도록 설계한다. |
| `git status` · `git diff` · `git diff --cached`를 연속 실행했을 때 출력이 같아 보여 차이를 몰랐다. 구분선을 넣고 마지막 커밋·스테이징 영역·작업 폴더의 관계를 도식으로 보자 이해했다. | **관찰할 수 있게 만드는 장치**(구분선, 전후 비교)와 **관찰 결과를 정리하는 도식**이 함께 있어야 한다. |

이 관찰은 Owner 한 사람의 학습 기록입니다. 순환형 구조가 학습 효과를 높인다는 일반적 결론으로 쓰지 않으며, 효과는 §7의 기준으로 시범 수업에서 확인합니다.

## 2. 학습 순환

```text
        ┌─────────────── ① 개념 이해 ───────────────┐
        │      (미션 스토리 화면 · P 해설 · 용어사전)      │
        ▼                                             │
  ⑥ 추가 실습                                   ⑤ 개념 재이해
  (다음 Lab · 선택 실험)                         (같은 화면을 내 결과로 다시 읽기)
        │                                             ▲
        ▼                                             │
  ② 직접 실습 ──────▶ ③ 결과 관찰 ──────▶ ④ 결과 해설 · 도식화
  (Lab 명령 실행)      (예측과 비교, 관찰 목록)   (Lab 해설 · Lab 도식 · 스토리 그림)
```

**어느 지점에서든 시작할 수 있습니다.** 순서는 권장 흐름일 뿐 강제하지 않습니다.

| 단계 | 학습자가 하는 일 | 주로 쓰는 콘텐츠 | 다음으로 넘어가는 신호(강제 아님) |
| --- | --- | --- | --- |
| ① 개념 이해 | 화면의 질문과 그림을 보고 P 해설을 읽는다. 모르는 용어를 찾는다. | 미션 스토리, P 해설, 용어사전 | “직접 해 보면 어떻게 나올까?”가 궁금해진다. |
| ② 직접 실습 | Lab의 **실행 전 질문**에 먼저 답을 적고 명령을 실행한다. | Lab 명령 | 내 화면에 결과가 나왔다. |
| ③ 결과 관찰 | Lab의 **관찰 목록**으로 내 결과를 살펴본다. 아직 해설은 펼치지 않는다. | Lab 관찰 목록, 실습 상태 카드 | 예측과 같은 점·다른 점을 말할 수 있다. |
| ④ 결과 해설·도식화 | 해설과 도식을 펼쳐 내 결과와 하나씩 맞춰 본다. 결과가 다르면 분기 안내를 본다. | Lab 해설·도식, 분기 안내 | 내 결과의 각 줄이 무엇인지 가리킬 수 있다. |
| ⑤ 개념 재이해 | 연결된 스토리 화면으로 돌아가 같은 그림을 **내 결과를 떠올리며** 다시 읽는다. | 스토리 화면 · P 해설 · 개념지도(미구현) | 화면의 핵심 메시지를 내 결과로 설명할 수 있다. |
| ⑥ 추가 실습 | 이해 확인 질문에 답하고, 선택 실험이나 다음 Lab으로 간다. | Lab 이해 확인, 선택 실험 | 새 질문이 생긴다 → 다시 ① 또는 ② |

## 3. 설계 원칙

| # | 원칙 | 구체적 적용 |
| --- | --- | --- |
| C1 | **하나의 사례를 끝까지 쓴다** | 모든 핵심 Lab은 `README.md` 끝에 “실습 메모: AI가 작성한 초안은 사람이 검토한다.”를 추가한 같은 변경을 씁니다. 이 문장 하나가 작업 폴더 → diff → Git 문맥 → 요청 JSON → 초안으로 모습을 바꾸며 이동하는 것을 학습자가 직접 따라갑니다. ([데이터의 여행](lab-guide-v0.3.md#데이터의-여행)) |
| C2 | **관찰이 해설보다 먼저 온다** | 각 Lab은 실행 전 질문 → 명령 → 관찰 목록 → (펼치기) 실행 기록·해설 순서입니다. 실행 기록과 해설은 접혀 있어 학습자가 자기 결과를 먼저 봅니다. |
| C3 | **비교할 수 있게 출력한다** | 여러 명령의 출력은 항상 `===== 이름 =====` 구분선과 함께 실행합니다(Lab 03의 Owner 기록이 근거). 상태가 바뀌는 실습은 전후를 나란히 비교하는 표·도식을 줍니다. |
| C4 | **도식은 결과를 되돌아보는 도구다** | Lab 도식과 스토리 그림은 같은 이름·색을 씁니다(Git 금색, Python 파랑, 외부 AI API 점선, 결과 초록, 프로그램 고정 문구 주황). 학습자가 Lab 도식에서 본 상자를 스토리 그림에서 다시 찾을 수 있어야 합니다. ([명칭·색 규칙](lab-story-mapping-v0.3.md#5-데이터와-도식의-일관성)) |
| C5 | **실행 조건과 학습 순서를 분리한다** | “Git 문맥을 만들려면 변경이 있어야 한다” 같은 **기술적 선행 조건**은 각 Lab의 시작 조건과 [실습 상태 카드](lab-guide-v0.3.md#실습-상태-카드)로 안내합니다. 어떤 이론을 먼저 읽을지는 강제하지 않습니다. 상태 카드의 명령 한 줄로 어떤 Lab에서든 시작 상태를 맞출 수 있습니다. |
| C6 | **근거를 섞지 않는다** | 모든 실행 결과에 [근거 표시](#5-근거-표시-v03) 하나를 붙입니다. Owner 실제 기록, Claude 재현, 소스 기반 예상, 교육용 예시를 한 상자 안에서 섞지 않습니다. |
| C7 | **API 호출은 꼭 필요한 곳에서만** | Lab 01–06은 API 키 없이, 비용 없이 할 수 있습니다. API를 부르는 곳은 Lab 07·08(최소 2회)뿐이고, Lab 09는 추가 호출 없는 경로를 함께 줍니다. 오류 재현을 요구하지 않습니다. |
| C8 | **종합 강의로 넓히지 않는다** | 각 Lab에는 “이 Lab에서 다루지 않는 것”을 적습니다. Git·Python·HTTP 전반은 용어사전과 B3-2 학습가이드로 넘기고, Lab은 중심 질문에 필요한 만큼만 다룹니다. |
| C9 | **AI와 사람의 일을 끝까지 구분한다** | 초안 생성 ≠ 커밋·PR 실행, 권장 테스트 명령 ≠ 테스트 수행, 자동 마스킹 ≠ 완전한 보호. 실습 중에도 실제 커밋·PR·push는 하지 않습니다. |

## 6. 학습자 유형별 진입 경로

세 경로 모두 같은 콘텐츠를 다른 순서로 지납니다. 화면 ID는 v0.2 r1 그대로입니다.

### 6-1. 설명 중심 학습자 — 미션 스토리 → 관련 실습 → 결과 관찰 → 도식·설명 다시 보기

```text
인트로(F1) → S1-1 → S1-2 ──▶ Lab 03 ──▶ 관찰 ──▶ Lab 03 도식 ──▶ S1-2 다시(F3)
                         └─(시작 조건)─ Lab 01 · 02
S2-1 → S2-2 ──▶ Lab 04 ──▶ 관찰 ──▶ S2-2 다시(F5: 0 · 128을 내 결과로)
S3-1 ──▶ Lab 05 ──▶ S3-1 다시(F6: 806자 그림 옆에 내 535자)
S3-2 ──▶ Lab 06 ──▶ (선택) Lab 07 ──▶ S3-2 다시(F7: 요청 상자의 user = 내 문맥)
S4-1 ──▶ Lab 08 ──▶ S4-1 다시(F8) ──▶ S4-2 ──▶ Lab 09 ──▶ S4-2 마무리 빈칸 채우기
```

강의 직후 대면 수업의 “안내된 첫 실습”이 이 경로의 앞부분(Lab 01–03)입니다.

### 6-2. 실습 중심 학습자 — Lab → 결과 관찰 → 관련 스토리 → 개념 이해 → 다음 실습

```text
Lab 01 → Lab 02 ──▶ S2-2(왜 요청 0회인가) ──▶ Lab 03 ──▶ S1-2 · S3-1 ──▶ Lab 04 ──▶ S2-1 · S2-2
──▶ Lab 05 ──▶ S3-1 ──▶ Lab 06 ──▶ S3-2 ──▶ Lab 07 · 08 ──▶ S3-2 · S4-1 ──▶ Lab 09 ──▶ S4-2
```

각 Lab 끝의 **“이 결과를 설명하는 화면”** 연결이 이 경로를 이끕니다. 실습 중심 학습자도 Lab 05 전에는 변경이 있어야 하고, Lab 07 전에는 키가 필요합니다(실행 조건). 반면 S3-1을 먼저 읽어야 Lab 05를 할 수 있는 것은 아닙니다(학습 순서는 자유).

### 6-3. 미션 완료 학습자 — 내 실행 결과 → 관련 개념 찾기 → 부분 실습 → 전체 구조 이해

이미 B3-2를 실행해 본 학습자는 자기 터미널에 남은 출력에서 출발합니다. [결과로 찾아보기](lab-guide-v0.3.md#결과로-찾아보기) 색인이 출력의 한 줄(예: `M  README.md`, `AI API 요청 횟수: 1`, `오류: AI API 응답 오류 (HTTP 400).`)에서 해당 Lab·화면·용어로 바로 보냅니다.

```text
내 출력의 한 줄 ──▶ 결과로 찾아보기 ──▶ 해당 Lab의 해설·도식만 펼쳐 보기
      ──▶ (필요하면) 그 Lab만 부분 실습 ──▶ 연결 화면 ──▶ S4-2 마무리 빈칸으로 전체 구조 확인
```

## 7. 학습 효과 검증 기준

명령어를 외웠는지나 Lab을 몇 개 끝냈는지로 판단하지 않습니다. 학습자가 **자기 말로, 자기 실행 결과를 근거로** 설명할 수 있는지를 봅니다.

| # | 질문 | 주로 연결된 Lab · 화면 | 설명에 들어가야 할 요소 |
| --- | --- | --- | --- |
| Q1 | 왜 Git 변경 정보를 두 종류의 diff로 수집하는가? | Lab 03 · S1-2 · S3-1 | `git diff`는 작업 폴더↔스테이징 영역, `--cached`는 스테이징 영역↔마지막 커밋을 비교 / 변경이 어디에 있을지 프로그램은 모름 / 둘 다 있어야 빠짐없이 모음(예: `MM`) |
| Q2 | Python은 Git의 실행 결과를 어떻게 받는가? | Lab 04 · S2-1 · S2-2 | `subprocess.run()` / Git이 종료 상태를 정하고 운영체제가 전달, Python은 `returncode`로 받음 / `stdout`·`stderr`는 글로 받음(`capture_output`, `text`) |
| Q3 | Git 문맥은 API 요청에서 어디에 들어가는가? | Lab 05 · Lab 06 · S3-1 · S3-2 | `messages`의 `user` 메시지 `content` / 검사를 마친 글 그대로 |
| Q4 | `system`과 `user` 메시지의 역할은 어떻게 다른가? | Lab 06 · Lab 08 · S3-2 · S4-1 | `system` = 작성 규칙(명령마다 다름) / `user` = 이번 Git 문맥(같은 변경이면 같음) |
| Q5 | API 응답에서 Python은 필요한 내용을 어떻게 가져오는가? | Lab 08 · S3-2 | 응답 JSON → Python 데이터 → `choices[0].message.content` / 없거나 비면 오류 |
| Q6 | 왜 같은 변경 정보에서 서로 다른 초안이 만들어지는가? | Lab 08 · S4-1 | 다른 `system` 규칙 / 프로그램의 형식 검사·재조립 / AI 결과 자체도 실행마다 달라질 수 있음 |
| Q7 | stdout과 stderr는 무엇인가? | Lab 02 · Lab 04 · Lab 09 · S2-2 | 화면·파일이 아니라 **출력 통로** / 어디에 연결하느냐(터미널·Python·파일)에 따라 도착지가 바뀜 / B3-2는 초안=stdout, 요청 횟수·오류=stderr |
| Q8 | HTTP 오류가 발생하면 어느 부분부터 확인할 수 있는가? | Lab 07 · S3-2 | 프로그램 오류인지 응답 오류인지 구분 / 상태 코드와 본문 / 범위 줄이기(프로그램 → 직접 호출 → 최소 요청 → 설정 값) / 같은 요청 무의미하게 반복하지 않기 |
| Q9 | AI가 하는 일과 사람이 하는 일은 무엇이 다른가? | Lab 08 · Lab 09 · S4-2 | AI = 초안 작성 / 프로그램 = 수집·검사·형식 확인 / 사람 = diff와 비교, 의도 확인, 실제 커밋·PR |

### 판단 수준

| 수준 | 모습 | 예 (Q1) |
| --- | --- | --- |
| 0 | 명령 이름이나 용어만 말한다 | “`git diff`랑 `git diff --cached`를 해서요.” |
| 1 | 차이는 말하지만 이유나 근거가 없다 | “하나는 add 전, 하나는 add 후 변경을 보여 줘요.” |
| 2 | 이유를 말하고 **자기 결과를 근거로** 든다 | “add 전엔 `git diff`에만 메모 줄이 나왔고 add 후엔 `--cached`에만 나왔어요. 프로그램은 제가 add했는지 모르니까 둘 다 봐야 빠짐없이 모아요.” |

### 확인 방법 (시범 수업에서)

1. **강의 전후 설명** — 같은 질문(Q1–Q9 중 3개)을 강의 전과 실습 후에 묻고 수준 변화를 본다.
2. **결과를 가리키며 설명하기** — “내 화면의 어느 줄을 보고 그렇게 말하나요?”를 함께 묻는다(수준 2의 핵심).
3. **새 상황 적용** — 실습에 없던 상황을 준다. 예: `git status --short`에 `MM`이 보이면 Git 문맥에는 무엇이 들어갈까? / `AI API 요청 횟수: 1`인데 오류가 났다면 무슨 뜻일까?
4. **되돌아가는 행동 관찰** — 막혔을 때 학습자가 스스로 관련 화면·Lab·용어를 찾아가는지 본다(순환 구조가 실제로 쓰이는지).
5. **지연 확인** — 일정 기간 뒤 S4-2 마무리 빈칸을 다시 채우게 한다.

이 기준은 설계 목표입니다. 순환형 구조의 학습 효과는 아직 검증되지 않았으며([정책 §8](../../../docs/mission-guides/learning-operation-policy.md)), 검증 결과가 나오기 전까지 효과를 주장하지 않습니다.
