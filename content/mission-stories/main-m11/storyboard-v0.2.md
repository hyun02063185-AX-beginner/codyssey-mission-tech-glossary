## 화면 구성 공통

- **위에서 아래로:** Scene 질문(작게) → 핵심 메시지(크게, 한 문장) → 한 문장 설명 → 그림. 화면당 메시지는 하나다.
- **기준 ERD 하나**(`erd-story`)를 Scene 01·03·04에서 다시 쓴다. 상자 위치·크기는 모든 상태에서 같고, 강조만 바뀐다.
- **강조 약속:** 주황 굵은 테두리·선 + 글자 이름표. 관련 없는 요소는 흐리게(투명도 0.3). 색만으로 구분하지 않는다.
- **선의 종류:** 실선 + 끝 모양 = ERD 관계(막대 두 개 = 반드시 하나, 동그라미 + 세 갈래 = 0개 이상 여러 개). 점선 화살표 = FK가 PK를 **가리킴**(실행 순서가 아님). 두 선을 같은 그림에서 섞지 않는다.
- **전환:** 같은 그림 안의 상태 변화는 0.3초 페이드만 쓴다. 상자를 움직이는 애니메이션은 Scene 02의 "나누기" 한 번뿐이다.
- 그림 파일과 상태 이름은 아래 [그림과 상태](#그림과-상태) 표를 따른다.

## Scene 01 — 데이터베이스의 설계도

**질문: ERD는 무엇을 보여주는 그림일까?** · 출처 `[노트 1장]` "우리가 만든 데이터베이스는 어떤 모양이고, ERD는 무엇인가?"

### S01-1 · ERD 등장
- **메시지:** ERD는 데이터베이스의 설계도다.
- **설명:** 어떤 표가 있고, 표끼리 어떻게 이어지는지를 한 장에 그린다.
- **그림:** `erd-story` `overview` — 6개 표 이름과 5개 관계선만. 열은 숨긴다. `[B6-1 사례]`
- **동작:** 상자가 한꺼번에 나타나고 선이 이어서 그려진다(0.6초).

### S01-2 · 읽는 법
- **메시지:** 상자는 테이블, 선은 관계다.
- **설명:** 선 끝의 막대 두 개는 '반드시 하나', 동그라미와 세 갈래 끝은 '0개 이상 여러 개'.
- **그림:** `erd-story` `read` — student 상자와 student─enrollment 선만 강조, 이름표 "상자 하나 = 테이블(표)" "선 = 관계". `[개념]`
- **동작:** 나머지가 흐려지며 두 이름표가 차례로 뜬다.

### S01-3 · 주제는 달라도
- **메시지:** 주제는 달라도, 나누고 잇는 설계는 같다.
- **설명:** 내 ERD에서도 표와 선을 찾고, 연결 표가 있다면 왜 있는지 말해 보자.
- **그림:** `same-structure` — B6-1 실제 사례(학생·수업은 다대다 → 연결 표 수강) + `[보충]` 예시 하나(블로그: 회원 1 : N 게시글, 연결 표 없이 바로 연결) + 이름표 "공통점: 표로 나누고 선으로 잇는다 · 다대다(N) 관계는 연결 테이블로 표현할 수 있다.".
- **동작:** 없음(정지 화면).

> 강사 포인트: 학생 관리 DB는 **하나의 사례**다. 모든 DB에 연결 표가 있는 것은 아니다. 표 이름이 아니라 "표 + 선"을 읽는 법을 가져간다.

## Scene 02 — 왜 나누고 연결할까?

**질문: 하나의 표에 전부 넣으면 안 될까?** · 출처 `[노트 5장]` "PK와 FK는 무엇이고 왜 쓰는가? 엑셀과는 무엇이 다른가?"

### S02-1 · 한 장의 표
- **메시지:** 한 표에 모두 넣으면 같은 정보가 반복된다.
- **설명:** 강사 이름 하나가 바뀌어도 여러 줄을 찾아 고쳐야 하고, 하나라도 놓치면 어긋난다.
- **그림:** `split-story` `one` — 학생·학교·수업·강사·점수 3행(김민준 88·72, 이서연 95). 반복 칸에 점선 테두리 + "같은 값의 반복". 모바일은 학교·점수 열을 뺀 3열. `[B6-1 사례]` 데이터를 한 장으로 합친 `[보충]` 표
- **동작:** 반복 칸 점선이 하나씩 켜진다.

### S02-2 · 나누기
- **메시지:** 정보는 주제별 표에 한 번만 적는다.
- **설명:** 학생은 학생 표에, 수업은 수업 표에. 수강 기록에는 누가 무엇을 듣는지만 남긴다.
- **그림:** `split-story` `split` — 원래 표(작게, 흐림) → 학생 · 수업 · 수강 기록 3개 표. 수업 표에 강사 이름을 둔 것과 점수를 뺀 것은 `[보충]` 단순화이며 이름표로 밝힌다(B6-1은 teacher·score를 별도 표로 둔다).
- **동작:** **이 스토리의 유일한 이동 애니메이션.** 한 장의 표의 열이 세 표로 흩어진다(0.8초).

### S02-3 · 키로 잇기
- **메시지:** PK로 행을 구분하고, FK로 다른 표를 가리킨다.
- **설명:** B6-1에서는 ERD의 선 5개가 FOREIGN KEY 선언 5개와 같다.
- **그림:** `split-story` `keys` — 수강 기록 첫 행의 student_id 1 → 학생 id 1(김민준), course_id 1 → 수업 id 1(중등 수학 기초)을 점선 화살표 ①②로 표시. 모바일도 같은 그림의 세로판(학습가이드 V03 내용을 슬라이드 색으로 재구성, V03 원본은 그대로). `[B6-1 사례]` `[개념]`
- **동작:** ① → ② 순서로 점선이 그려진다.

> 강사 포인트: B6-1의 관계선 5개는 `01_schema.sql`의 FOREIGN KEY 선언 5개와 1:1이다. 무결성·제약조건(150점 거절 등)은 학습가이드 4장으로 넘긴다.

## Scene 03 — 나눈 데이터를 어떻게 사용할까?

**질문: 서로 다른 테이블에서 원하는 정보를 어떻게 찾을까?** · 출처 `[노트 2장]` "SQL이 무엇이고, 왜 쓰는가?" · `[노트 4장]` "JOIN은 왜 필요하고, INNER JOIN과 LEFT JOIN은 무엇이 다른가?"

### S03-1 · 요청하기
- **메시지:** SQL로 원하는 결과를 요청하면, DBMS가 찾아서 표로 돌려준다.
- **설명:** 어떻게 찾을지가 아니라 무엇이 필요한지를 적는다.
- **그림:** HTML 단계 카드 4개(새 SVG 없음) — 질문 "김민준은 어떤 수업을 들을까?" → SQL(필요한 열·표·조건) → DBMS(B6-1은 SQLite: 문법 확인 → 실행 → 규칙 검사) → 결과 표(중등 수학 기초 · 중등 영어 독해). SQL 문장은 보여 주지 않는다. 자세한 처리 흐름은 가이드 V05.
- **동작:** 카드가 왼쪽부터 차례로 켜진다.

### S03-2 · JOIN = 키를 따라가기
- **메시지:** JOIN은 키를 따라 나뉜 표를 다시 잇는다.
- **설명:** JOIN은 ON 조건의 값이 같은 행끼리 잇는다. B6-1은 FK = PK를 조건으로 썼다.
- **그림:** `erd-story` `join` — student·enrollment·course 강조, 이 세 표만 PK/FK 열 공개, 연결 조건 ① `student.id = enrollment.student_id` ② `enrollment.course_id = course.id`. 결과표(Q05 첫 두 행: 김민준 · 중등 수학 기초 · 월 / 김민준 · 중등 영어 독해 · 화, 전체 26행)가 나타난다. PC는 그림 안 왼쪽 위, 모바일은 그림 아래 HTML 표. `[B6-1 사례]`
- **동작:** ① 선 → ② 선 순서로 강조가 옮겨 간 뒤 결과표가 뜬다.

### S03-3 · INNER와 LEFT
- **메시지:** INNER는 짝이 있는 행만, LEFT는 왼쪽 표를 모두 남긴다.
- **설명:** 짝이 없는 행이 사라지는지 남는지에 따라 답이 달라진다.
- **그림:** PC `join-compare` — student 13~15번(문태양 수강 0건) → INNER 2행(문태양 ✕ 사라짐) / LEFT 3행(문태양 · NULL ✓). 전체 학생 기준 INNER 26행 · LEFT 27행. 모바일은 같은 내용의 세로판(학습가이드 V06 내용을 슬라이드 색으로 재구성, V06 원본은 그대로). `[B6-1 사례]`
- **동작:** INNER 결과 → LEFT 결과 순서로 켠다.

> 강사 포인트: S01-2의 **동그라미(0개 가능)** 가 바로 문태양이다. ERD 기호와 JOIN 결과를 한 번 이어 준다.

## Scene 04 — 그래서 데이터베이스를 배우는 이유

**질문: AI가 SQL을 만들어 주는데 왜 구조를 알아야 할까?** · 출처 `[노트 2장]` SQL과 DBMS의 구분 · `[노트 3장]` "쿼리가 무엇이고, 미션의 쿼리는 각각 어떤 일을 하는가?" · `[노트 7장]` "ORM도 결국 SQL을 만든다" — AI·ORM이 SQL을 대신 써도 구조 이해가 필요하다는 같은 맥락

### S04-1 · SQL과 DBMS
- **메시지:** SQL은 요청하는 언어, DBMS는 실행하고 지키는 프로그램이다.
- **설명:** 같은 SQL로 조회·연결·집계·수정을 모두 요청한다.
- **그림:** HTML — 카드 2개(SQL · 요청하는 언어 / DBMS · 실행하는 프로그램, B6-1은 SQLite이며 PK·FK·CHECK로 잘못된 입력을 막음) + 하는 일 칩 4개: 조회 Q01–Q04 · 연결 JOIN Q05–Q09 · 집계 Q10–Q13 · 수정·삭제 Q16–Q17 (서브쿼리 Q14·인덱스 Q15 포함 17개). `[B6-1 사례]`
- **동작:** 칩이 차례로 뜬다.

### S04-2 · AI가 써 준 SQL 확인하기
- **메시지:** AI가 SQL을 써 줘도, 맞는 답인지는 구조로 판단한다.
- **설명:** 구조를 알면 결과에서 사라진 한 명을 알아챌 수 있다.
- **그림:** HTML 단계 카드 4개 — 요청 "모든 학생의 수강 수업 목록" → AI 초안 INNER JOIN: 26행 · 학생 14명, ✕ 문태양이 없다 → 구조로 확인: ERD의 동그라미 = 수강 0건인 학생도 있다 → LEFT JOIN: 27행 · 학생 15명 ✓. **`[보충]` 교육용 예시**(B6-1 진행 중 실제로 일어난 일이 아님). 숫자는 B6-1 데이터로 실행한 결과다. ✕·✓는 글자와 함께 그린 아이콘으로 표시한다.
- **동작:** 카드가 차례로 켜지고 마지막 카드만 강조 테두리.

### S04-3 · 처음의 ERD로
- **메시지:** 데이터베이스는 정보를 나누어 정리하고, 관계로 연결해, 필요한 답을 찾아내는 구조다.
- **설명:** 내 ERD에서 표 · PK · FK · JOIN 경로를 찾아 설명해 보자.
- **그림:** `erd-story` `return` — S01-1과 같은 ERD. 6개 표 모두 PK/FK 공개, JOIN 경로 선 강조, 이름표 "표 = 나누어 정리한 정보" "선 = FK가 PK를 가리키는 관계" "강조 선 = JOIN 경로". `[B6-1 사례]` `[개념]`
- **동작:** S01-1에서 이름표 3개가 차례로 겹쳐진다.

> 강사 포인트(이해 확인): 학습자가 **자기 ERD**를 열고 표 하나·선 하나·JOIN 경로 하나를 짚어 말하게 한다. 이후 독립 실습으로 넘어간다.
