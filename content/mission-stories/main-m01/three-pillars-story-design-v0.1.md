## 0. 결론 요약

- **핵심 질문** `[Owner]` 웹페이지는 문서일까, 디자인일까, 프로그램일까?
- **핵심 메시지** `[Owner]` 하나의 웹페이지는 문서·표현·기능이라는 서로 다른 역할이 협력해서 만들어진다.
- **형식** `[제안]` B6-1처럼 **4 Scene × 화면 3개 = 12화면의 압축 슬라이드 Story**로 만든다. 장면마다 핵심 개념은 3개 이하로 둔다. `PresentationSurface`(Dark 기본) 안에서 큰 구조도 한 장씩 설명한다.
- **공통 사례** `[제안]` 기존 가이드 그림의 일반화 인물 **"김코디"의 자기소개 페이지 하나**만 쓴다. 이 페이지는 *HTML만 → +CSS → +JS → 브라우저 안의 완성본*으로 네 번 바뀐다. 화면은 실제로 동작하는 작은 교육용 샘플 파일 하나에서 캡처한다. 그래야 "같은 HTML"이라는 말이 사실이 된다.
- **기존 가이드와의 분담** 기존 학습가이드 Chapter 1~9와 V01~V09는 고치지 않고 다시 쓰지도 않는다. Story는 **"무엇이 왜 일어나는가"의 큰 흐름**을 맡고, 코드 위치 찾기·검증·동료평가는 가이드 장으로 보낸다. 기존 SVG는 Story 화면에 그대로 넣지 않는다. 세로형 360px 설계이고 가이드 깊이로 그려졌기 때문이다. 대신 각 장면 끝의 "더 알아보기" 링크로 연결한다(§C.2).
- **개념지도** 핵심 노드 13 · 보충 노드 4 · 관계 20(핵심 15 · 보충 5) · 선 없는 비교 카드 5. 세 축은 모두 **DOM**에서 만나고, 이것이 지도의 중심 설명이다. 확장 개념(시맨틱 웹, JSON·YAML, Python, API·서버)은 선으로 잇지 않고 비교 카드와 상세 패널로만 보여 준다.

## A. 기존 자료 분석

### A.1 B1-1 원천 미션 요구사항 — 근거와 교육 권장 분리

`m01-terminology-raw.md`는 Notion 미션 정보에서 뽑은 **pilot·raw 추출본**이다. 아래 "확실한 근거"는 raw의 `direct` 용어와 openbook `requirements`에 함께 나오는 것만 적었다. 미션 원문 자체는 이번에 다시 열어 보지 않았다 `[원천 한계]`.

| 영역 | 확실한 근거 `[공식]` | 이번 Story와의 관계 |

| 반응형 | Mobile First, 768px·1024px 전환, nav Flexbox, 프로젝트 카드 Grid | Scene 2-3에서 "조건에 따라 규칙이 바뀐다"는 원리만. 숫자·Flex·Grid는 Ch3 |

### A.2 기존 학습가이드와의 중복·재사용 판단

기존 가이드는 "AI가 만든 **내 프로젝트**에서 코드 위치를 찾아 설명하기"가 목적이다. 장마다 💻 직접 확인, 일반화 예제 코드, AI 질문법, 동료평가 절이 있다. 새 Story는 **내 프로젝트를 열기 전에** 듣는 대면 강의 자료다. 같은 주제라도 맡는 깊이가 다르다.

| 기존 자료 | 이미 설명하는 것 | 새 Story가 맡는 것 | 판단 |
| --- | --- | --- | --- |
| Ch1 + V01 | 세 역할, `index.html`이 파일을 불러옴, `defer`, 순수 HTML/CSS/JS 확인 목록, 집 비유와 한계, Network 탭 | 세 역할을 **같은 페이지가 변하는 모습**으로 *보여 주기*. 파일 연결은 Scene 4에서 한 장으로만 | **겹침 허용.** 문장·비유·그림을 복사하지 않는다. Ch1의 집 비유는 쓰지 않는다(§E.1-12) |
| Ch2 + V02 | 구역↔태그 대응, `div class` vs 태그, h1~h6 차례, `id`↔`href`, DOM 트리 | Scene 1: "HTML = 내용 + 그 내용이 **무엇인지** 표시". 태그 이름표만 보여 준다 | 대응표·`id` 연결은 Ch2로. `div` 비교는 Ch2 고유 소재로 남긴다 |
| Ch3 + V03 | Media Query, Mobile First, 768/1024 누적, Flexbox/Grid, CSS 변수, overflow | Scene 2: "HTML 0줄 변경으로 다른 모습", "규칙 = 누구를·어떻게", "조건에 따라 다른 규칙" | 수치·누적 원리·레이아웃 도구는 Ch3로 |
| Ch4 + V04 | ⓪ 등록 + ①~⑥ 실행, 상태, class 토글, DOM ≠ 파일, Event Listeners 탭, 위임, `onclick` | Scene 3: **4단계 단순화**(클릭 → JS 처리 → DOM 변경 → 다시 그림)와 "프로그램 = 판단하고 동작" | V04의 6단계를 줄인 새 그림. 용어와 단계 이름은 V04와 어긋나지 않게 맞춘다(§C.3) |
| Ch8 + V08 | 로컬 → Git → GitHub → Pages → URL, 경로 문제 | Scene 4-3: "공개는 Pages, 결합은 **방문자의 브라우저**" | 명령·설정은 Ch8로 |
| Ch9 + V09 | HTML·CSS·JS·브라우저 기능·GitHub API·Pages 전체 협력, 방문 시간 순서 | Scene 4는 세 축과 브라우저까지만. API·저장소는 넣지 않는다 | V09는 Story를 마친 뒤 넘어갈 "다음 지도"로 링크한다 |
| instructor-notes | 장별 시연·강조·질문·조심할 설명 | Scene별 강사 흐름(§B.3)은 새로 쓴다. 장별 노트의 "조심할 설명"은 §E.1의 오해 목록에 출처로 반영 | 노트 본문은 고치지 않는다 |

**가이드에서 가져와 그대로 지킬 약속** (새 원고를 쓰더라도 어긋나면 안 되는 것)

- 일반화 예제 표시와 "특정 교육생 프로젝트가 아님"
- 선 종류 구분: 불러옴(점선) · 실행 순서(번호 실선) · 대응(짧은 선)
- H·C·J를 색만이 아니라 **모양(네모·동그라미·마름모)과 글자**로도 구분하는 V01 규칙
- "즉시 바뀐다" 대신 "브라우저가 바뀐 DOM과 CSS로 **다시 그린다**"
- "HTML 파일은 그대로, DOM이 바뀐다"
- 브라우저 처리 순서는 **단순화 모델**이라고 밝힌다

### A.3 L0 입문자에게 필요한 최소 선수개념

강의 시작 2~3분 안에 말로 짚는 것만 둔다. 화면에서는 인트로 아래 접힘 카드 하나로 둔다 `[제안]`.

| 선수개념 | 이 정도만 | 왜 필요한가 |
| --- | --- | --- |
| 파일과 폴더 | 웹페이지도 **글자로 된 파일** 몇 개다. 메모장으로도 열린다 | "파일 ≠ 화면" 구분의 출발점 |
| 브라우저 | 파일을 읽어 **화면으로 바꿔 보여 주는 프로그램**(Chrome, Edge, Safari) | Scene 4의 주인공. 지금은 "읽고 보여 준다"까지만 |
| "언어" | 컴퓨터가 읽을 수 있게 **약속한 표기법**. 모든 언어가 "프로그램"을 만드는 것은 아니다 | HTML·CSS·JS가 모두 "언어"인데 하는 일이 다르다는 Scene 1~3의 복선 |

다음은 **선수개념으로 요구하지 않는다**: 변수, 조건문 문법, 함수 문법, HTTP, Git. Scene 3의 "조건에 따라 판단한다"는 한국어 문장으로만 보여 준다.

## B. 스토리 설계

### B.1 전체 핵심 질문과 교육 목표

**Story 인트로 입력값** (`MissionStoryOverview` 재사용)

| 항목 | 값 `[제안]` |
| --- | --- |
| 미션 코드·강의 제목 | B1-1 · 문서·표현·기능, 세 가지 축으로 이해하는 웹페이지 |
| 핵심 질문 | 웹페이지는 문서일까, 디자인일까, 프로그램일까? `[Owner]` |
| 학습 목표 | ① HTML이 내용과 그 의미를 적는다는 것을 말한다 ② 같은 HTML에 CSS 규칙만 바꿔 다른 모습을 만들 수 있음을 설명한다 ③ 버튼 클릭이 JavaScript 처리와 DOM 변경을 거쳐 화면 변화가 되는 흐름을 말한다 ④ 화면의 어떤 변화를 원할 때 어느 파일을 열지 고를 수 있다 |
| 장면 흐름 | 문서에서 시작한다 → 다르게 표현한다 → 행동에 반응한다 → 하나의 웹페이지가 된다 |

**질문에 대한 마지막 답** (Scene 4-3 끝에서 다시 묻는다)

> 셋 중 하나가 아니다. 웹페이지는 **문서(HTML)를 바탕으로, 표현 규칙(CSS)과 동작 프로그램(JavaScript)이 더해져 브라우저 안에서 하나로 보이는 결과**다.

"웹페이지 = 프로그램"이라고 단정하지 않는다. HTML만으로도 웹페이지이고, 프로그램 역할은 JavaScript가 맡는다.

### B.2 공통 사례 — "김코디의 자기소개" 한 장이 네 번 바뀐다

**사례 정의** `[제안]` 교육용 일반화 사례. 화면 구석에 늘 *"교육용 예시 페이지 · 실제 교육생 프로젝트 아님"*을 표시한다.

| 구성 | HTML 요소(이름만) | 비고 |
| --- | --- | --- |
| 머리말 + 메뉴 버튼 ☰ + 메뉴(소개·프로젝트·연락) | `header`, `button`, `nav`, `a` | 메뉴는 Scene 2·3의 연결 고리 |
| 자기소개 제목 | `h1` | "안녕하세요, 김코디입니다" |
| 프로필 그림 | `img` + `alt` | **실제 인물 사진을 쓰지 않는다.** 단순 일러스트 |
| 소개 문단 | `p` | 두세 줄 |
| 프로젝트 목록 | `section`, `h2`, `ul`/`li`, `a` | 3개 |
| 바닥글 | `footer`, `a` | 연락 링크 |

미션 필수 섹션(Hero·About·Skills·Projects·Contact·Footer)을 **일부러 다 넣지 않는다**. 화면에 "미션은 더 많은 구역을 요구합니다 → Ch2"를 한 줄 둔다.

**제작 방법** `[제안]` 콘텐츠 상세 제작 단계에서 실제 동작하는 샘플 파일 세 개(`index.html`, `css/style.css`, `js/menu.js`)를 만든다. 그리고 같은 파일에서 연결만 바꿔 네 상태를 캡처한다. 네 상태가 **정말 같은 HTML**이어야 Scene 2의 "HTML 0줄 변경"이 거짓이 되지 않는다.

| 상태 | 만드는 법 | 보이는 모습 | 대응 역할 |
| --- | --- | --- | --- |
| **① HTML만** | `link`·`script` 연결 없음 | 흰 바탕, 위에서 아래로 흐르는 글. 큰 굵은 제목, 파란 밑줄 링크, 점 목록, 메뉴 글씨가 그대로 보임. ☰는 기본 회색 버튼 | 문서·의미 |
| **② +CSS** | `link`만 연결 | 색·글꼴·여백·카드. **PC 폭**: 메뉴 가로 펼침, ☰ 숨김. **모바일 폭**: 메뉴 숨김, ☰ 보임 | 표현·규칙 |
| **③ +JS** | `script defer`까지 연결 | 모바일 폭에서 ☰를 누르면 메뉴가 열리고, 다시 누르면 닫힘 | 기능·동작 |
| **④ 완성** | ③과 같음 | 브라우저 창 안의 최종 화면 + 세 파일이 결합되는 구조도 | 통합·실행 환경 |

> **주의** 상태 ①은 "스타일이 없는" 화면이 아니다. **작성자가 쓴 CSS가 없을 뿐, 브라우저 기본 스타일**(제목 굵게·크게, 링크 파랑)이 적용된 화면이다. 화면 이름표를 *"내가 쓴 CSS 없음"*으로 붙이고, 강사 노트에 이 점을 적는다(§E.1-6).

### B.3 Scene 1~4

각 Scene은 화면 3개다. 화면마다 **메시지 한 문장 + 큰 그림 하나 + 캡션 1~2줄**만 둔다. "강사 설명 흐름"은 강의 화면에 나오지 않는 강사 노트다. "학습자용 핵심 설명"은 강의 후 혼자 볼 때 펼치는 짧은 글이다.

---

#### Scene 1 — 웹페이지는 문서에서 시작한다 (HTML = 문서와 의미)

- **학습 질문** 디자인도 동작도 없는 웹페이지에는 무엇이 남을까?
- **핵심 메시지** HTML은 내용을 적고, 그 내용이 **무엇인지**(제목·문단·그림·목록·링크·버튼)를 표시한다.
- **핵심 개념(3)** 콘텐츠 · 태그(요소) · 시맨틱 HTML

| 화면 | 메시지 | 그림 | 강사 설명 흐름 |
| --- | --- | --- | --- |
| **S1-1 · 꾸밈없는 첫 화면** | 웹페이지는 먼저 **내용**이다 | 상태 ① 브라우저 캡처(창 틀 포함) | ① 핵심 질문을 던지고 답을 받지 않은 채 넘어간다. ② "이 화면에 무엇이 있나요?" 제목, 그림, 글, 목록, 링크를 손으로 짚는다. ③ **링크를 실제로 눌러 이동해 보인다.** "아직 JavaScript가 없는데도 링크는 동작한다. HTML에도 기본 기능이 있다"(Scene 3 복선). |
| **S1-2 · 내용에 이름표 붙이기** | 태그는 "이것은 제목", "이것은 목록"이라는 **이름표**다 | 같은 캡처 위에 태그 이름표(`h1` `p` `img` `ul·li` `a` `button` `nav`)를 붙인 그림. 오른쪽에 아주 짧은 HTML 조각 하나(`<h1>안녕하세요, 김코디입니다</h1>`)만 | ① 문법은 읽지 않는다. "꺾쇠 안의 이름 = 이 내용의 역할" 한 문장만. ② "`h1`은 글씨를 크게 하는 태그일까?" → 아니다. **가장 큰 제목이라는 뜻**이고, 크기는 다음 장면의 CSS가 정한다. ③ 그림의 `alt`: 그림을 못 보는 사람과 도구를 위한 **그림의 뜻**도 내용이다. |
| **S1-3 · 의미가 드러나는 구조** | 의미 있는 태그로 구역을 나누면 **사람과 도구가 구조를 읽는다** | 페이지를 `header`·`main`·`section`·`footer` 상자로 감싼 구조도. 옆에 이 구조를 읽는 쪽 아이콘: 사람(개발자), 브라우저, 화면 낭독기, 검색 도구 | ① 시맨틱 HTML = "의미를 드러내는 태그로 구조를 적는 방식". ② 미션이 시맨틱 태그를 요구한다 `[공식]`. 구역 대응과 `div` 비교는 **Ch2에서** 한다고 예고. ③ 오른쪽 아래 작은 카드 *"시맨틱 HTML ≠ 시맨틱 웹"*: 학습자가 물을 때만 펼친다(지도 C01). |

- **학습자용 핵심 설명** HTML은 웹페이지에 무엇이 있는지 적는 문서 언어입니다. 태그는 그 내용이 제목인지, 문단인지, 링크인지 알려 주는 이름표입니다. 의미에 맞는 태그를 쓰면 사람·브라우저·보조기술이 페이지 구조를 이해할 수 있습니다.
- **이해 확인 질문** "자기소개 제목을 크게 보이게 하려고 `h1`을 쓰는 걸까요?" → *아니요. 가장 중요한 제목이라는 뜻을 표시합니다. 크기와 색은 CSS가 정합니다.*
- **더 알아보기** 지도: HTML · 시맨틱 HTML · 비교 C01 / 용어: `html`, `semantic-html`, `accessibility-a11y` / 가이드: Ch2

---

#### Scene 2 — 같은 문서를 다르게 표현한다 (CSS = 표현과 규칙)

- **학습 질문** HTML을 한 글자도 바꾸지 않고 화면을 바꿀 수 있을까?
- **핵심 메시지** CSS는 "**어떤 요소를, 어떻게 보이게**"라는 규칙의 모음이다. 브라우저가 조건에 맞는 규칙을 골라 적용한다.
- **핵심 개념(3)** 스타일 규칙(선택자·선언) · 같은 HTML, 다른 표현 · 조건부 규칙(반응형)

| 화면 | 메시지 | 그림 | 강사 설명 흐름 |
| --- | --- | --- | --- |
| **S2-1 · 같은 HTML, 다른 모습** | HTML은 그대로, **CSS 파일 하나**를 연결했을 뿐이다 | 상태 ① ↔ 상태 ② PC 나란히(모바일에서는 위아래). 가운데에 "HTML 변경 0줄 · CSS 파일 연결 1줄" 배지 | ① 상태 ①에서 ②로 **전환 애니메이션 없이 한 번에** 바꿔 보여 준다. ② "글자, 그림, 목록 순서가 바뀌었나요?" → 내용과 순서는 같다. 바뀐 것은 색·글꼴·여백·배치다. |
| **S2-2 · 규칙 한 줄 읽기** | 규칙은 **누구를**(선택자) · **무엇을**(속성) · **어떻게**(값)로 적는다 | 규칙 하나(`h1 { color: …; font-size: …; }`)를 세 칸으로 나누고, 화살표로 화면 속 제목을 가리킴 | ① 이 장면에서 읽는 코드는 **이 한 줄뿐**이다. ② "CSS는 그리는 순서를 적지 않는다. **원하는 모습**을 적으면 브라우저가 그린다." 선언형이라는 단어는 소개만 한다. ③ 규칙이 많으면 서로 겹칠 수 있고, 어느 규칙이 이기는지 정하는 원리(cascade)가 있다는 것까지만 말한다. |
| **S2-3 · 조건에 따라 다른 규칙** | 화면 폭이라는 **조건**에 따라 같은 문서가 다른 배치로 보인다 | 상태 ② PC ↔ 상태 ② 모바일. 가운데에 "조건: 화면 폭 768px 이상이면" 이름표. 모바일에서 메뉴가 ☰ 뒤로 숨는 모습을 강조 | ① HTML은 한 벌, **조건에 따라 켜지는 규칙**이 있다. "모바일용 HTML이 따로 있다"는 말을 쓰지 않는다. ② 미션은 Mobile First와 768·1024px 전환을 요구한다 `[공식]`. 원리와 Flexbox·Grid는 **Ch3**. ③ 마지막에 ☰를 눌러 보인다. **아무 일도 일어나지 않는다.** "보이게 하는 것까지가 CSS. 누르면 열리게 하려면?" → Scene 3. |

- **학습자용 핵심 설명** CSS는 HTML 요소가 어떻게 보일지 정하는 스타일 언어입니다. 규칙은 "어떤 요소에, 어떤 속성을, 어떤 값으로"를 적고, 브라우저가 이 규칙을 적용해 화면을 그립니다. 화면 폭 같은 조건에 따라 다른 규칙이 적용되므로, 같은 HTML도 PC와 모바일에서 다르게 보입니다.
- **이해 확인 질문** "모바일에서 메뉴를 접고 싶습니다. 모바일용 HTML 파일을 하나 더 만들까요?" → *아니요. 같은 HTML에 화면 폭 조건이 붙은 CSS 규칙을 더합니다.*
- **더 알아보기 (선 없는 비교 카드)** *"CSS와 설정 파일(JSON·YAML)은 닮았을까?"*(지도 C02). 공통점은 원하는 상태를 이름과 값으로 적고, 실제로 처리하는 일은 다른 프로그램이 한다는 것이다. 차이점은 CSS가 **브라우저가 해석하는 스타일 언어**(선택자·조건·cascade가 있음)라는 것이다. JSON·YAML은 **여러 목적에 쓰는 데이터 표현 형식**이고, 그 값이 무슨 뜻인지는 읽는 프로그램이 정한다. 강의에서 펼치지 않고 자율 탐색용으로 둔다.
- **더 알아보기** 지도: CSS · 스타일 규칙 · 반응형 웹 · C02 / 용어: `css`, `css-cascade`, `responsive-web-design`, `css-media-query`, `mobile-first`, `breakpoint`, `json` / 가이드: Ch3

#### Scene 3 — 문서가 사용자 행동에 반응한다 (JavaScript = 기능과 프로그래밍)

- **학습 질문** 버튼을 눌렀을 때 메뉴가 열리려면 무엇이 더 필요할까?
- **핵심 메시지** JavaScript는 **프로그래밍 언어**다. 사용자의 행동(이벤트)을 받아 조건을 판단하고, **DOM**을 바꿔 화면을 바꾼다.
- **핵심 개념(3)** 프로그램(판단과 동작) · 이벤트 · DOM. 이벤트 핸들러(함수)는 "미리 맡겨 둔 할 일" 한 줄로만 보조 설명한다.

| 화면 | 메시지 | 그림 | 강사 설명 흐름 |
| --- | --- | --- | --- |
| **S3-1 · 이미 되는 것, 아직 안 되는 것** | 링크 이동은 HTML이 이미 한다. **"누르면 열고, 다시 누르면 닫기"는 판단이 필요하다** | 상태 ② 모바일 두 칸 비교: 왼쪽 "링크 클릭 → 이동 ✔ (HTML 기본 기능)", 오른쪽 "☰ 클릭 → 변화 없음 ✖" | ① JavaScript만 상호작용을 만든다는 오해를 먼저 막는다. 링크·폼 제출은 HTML의 기본 기능이다. ② ☰는 **지금 열려 있는지 보고 다르게 행동**해야 한다. 이것이 프로그램이 하는 일이다. ③ "JavaScript는 HTML·CSS와 달리 **판단하고 계산하고 순서대로 실행하는** 프로그래밍 언어다." |
| **S3-2 · 클릭에서 화면 변화까지** | 클릭 → JavaScript 처리 → DOM 변경 → 브라우저가 다시 그림 | 4단계 가로 흐름도(신규, §C.1 F5). 가운데 "JavaScript 처리" 상자 안에 한국어 문장: *"메뉴가 닫혀 있으면 → 연다 / 열려 있으면 → 닫는다"* | ① **입력 → 처리 → 결과**로 읽는다. 클릭(입력), 판단(처리), 화면 변화(결과). ② 처리는 페이지가 열릴 때 **미리 맡겨 둔 함수**(이벤트 핸들러)가 한다. 미션은 이 연결을 `addEventListener`로 하라고 요구한다 `[공식]`. 실제 코드는 "코드 보기"로 접어 두고 줄 단위로 읽지 않는다. ③ 등록 단계(⓪), 상태, 이벤트 위임은 **Ch4·V04**로 보낸다. |
| **S3-3 · 바뀌는 것은 파일이 아니라 DOM** | 브라우저는 HTML을 읽어 **DOM**(브라우저 안의 문서 모델)을 만들고, JavaScript는 그 DOM을 바꾼다 | 왼쪽 `index.html` 파일 아이콘("그대로"), 오른쪽 DOM 작은 나무(`nav`에 `is-open` 이름표가 붙었다 떨어짐), 아래에 상태 ③ 열림/닫힘 화면 | ① "메뉴를 열었다 닫았다 하면 `index.html` 파일이 바뀔까?" → 아니다. ② 바뀐 DOM에 맞는 **CSS 규칙**이 적용되어 보인다. 모양은 여전히 CSS가 정한다(Scene 2와 연결). ③ 시연할 수 있으면 개발자 도구 Elements에서 이름표가 바뀌는 모습만 보여 준다(자세한 방법은 Ch4 💻 절). |

- **학습자용 핵심 설명** JavaScript는 조건에 따라 판단하고 정해진 동작을 수행하는 프로그래밍 언어입니다. 사용자가 버튼을 누르면 브라우저가 그 사실(이벤트)을 알려 주고, 미리 맡겨 둔 JavaScript 함수가 실행됩니다. 함수는 DOM을 바꾸고, 브라우저는 바뀐 DOM과 CSS로 화면을 다시 그립니다. HTML 파일 자체는 바뀌지 않습니다.
- **이해 확인 질문** "메뉴를 열었다 닫았다 했을 때 `index.html` 파일이 바뀌었을까요?" → *아니요. 브라우저 안의 DOM이 바뀌고 화면이 다시 그려졌습니다.*
- **더 알아보기 (선 없는 비교 카드)** *"JavaScript와 Python은 무엇이 같고 다를까?"*(지도 C03). 같은 점: 둘 다 프로그래밍 언어로, 값을 기억하고(변수) 조건으로 판단하고 반복하고 함수로 일을 나눈다. 다른 점: **실행 환경**이 다르다. 브라우저가 기본으로 실행하는 언어는 JavaScript다. Python은 보통 컴퓨터·서버의 Python 인터프리터가 실행한다. JavaScript도 Node.js로 브라우저 밖에서 실행된다. 한 줄 대조 예시(같은 판단을 두 언어로)는 콘텐츠 제작 단계에서 검토한다 `[제안]`.
- **더 알아보기** 지도: JavaScript · 사용자 이벤트 · 이벤트 핸들러 · DOM · C03·C04 / 용어: `javascript`, `user-event`, `event-handler`, `add-event-listener`, `function`, `dom`, `python`, `node-js` / 가이드: Ch4

#### Scene 4 — 세 가지가 하나의 웹페이지가 된다 (브라우저 = 세 역할이 결합되는 곳)

- **학습 질문** 세 파일은 어디에서 만나 하나의 웹페이지가 될까?
- **핵심 메시지** 브라우저가 HTML로 DOM을 만들고, CSS 규칙을 적용해 그리고, JavaScript를 실행해 행동에 반응한다. 사용자는 그 결과를 **한 장의 웹페이지**로 보고 조작한다.
- **핵심 개념(3)** 브라우저(실행 환경) · 결합(DOM이 만나는 곳) · 고친 파일 ↔ 바뀌는 화면

| 화면 | 메시지 | 그림 | 강사 설명 흐름 |
| --- | --- | --- | --- |
| **S4-1 · 브라우저 안에서 만나는 세 파일** | 세 파일은 **브라우저 안의 DOM**에서 만난다 | 통합도(신규, §C.1 F6). 왼쪽에 `index.html` · `style.css` · `menu.js`(점선 "불러옴": `link`, `script defer`). 가운데 브라우저 창 안에 DOM. HTML은 "DOM을 만든다", CSS는 "DOM 요소에 규칙 적용", JS는 "DOM을 읽고 바꾼다". 오른쪽에 최종 화면과 사용자 | ① 지금까지의 세 장면을 한 장에 모은다. ② 선은 두 종류다. **점선 = 불러옴**, **번호 실선 = 읽고 실행하는 순서(단순화)**. ③ "실제 브라우저는 여러 일을 동시에 하지만, 역할을 구분하는 모델"이라고 한 번 말한다. `defer`는 이름만 짚고 이유는 Ch1. |
| **S4-2 · 무엇을 고치면 무엇이 바뀔까** | 바꾸고 싶은 것이 **내용**이면 HTML, **모습**이면 CSS, **동작**이면 JavaScript | 3행 대응 카드: "제목 문구 바꾸기 → `index.html`", "제목 색 바꾸기 → `style.css`", "메뉴가 열리는 방식 바꾸기 → `menu.js`". 각 카드에 상태 ④ 화면의 해당 위치 표시 | ① 학습자에게 **먼저 고르게 한다**(손들기·말하기). ② 파일을 고친 뒤에는 **새로고침**해야 브라우저가 다시 읽는다. ③ 섞인 경우도 있다: "메뉴가 열렸을 때의 모양"은 CSS가 정하고, "열리게 하는 것"은 JS가 한다. 기능 하나에 세 파일이 함께 일할 수 있다. |
| **S4-3 · 내 컴퓨터에서 세상으로** | GitHub Pages는 파일을 **공개**하고, 결합은 **방문자의 브라우저**에서 다시 일어난다 | 아주 짧은 흐름: 내 폴더 → GitHub 저장소 → GitHub Pages → 공개 URL → 방문자 브라우저(안에 S4-1 축소본) | ① B1-1의 결과물은 공개 URL이다 `[공식]`. ② Pages가 세 파일을 합쳐 주는 것이 아니다. 방문자의 브라우저가 파일을 받아 S4-1과 같은 일을 한다. ③ 명령과 설정은 **Ch8**. ④ **핵심 질문으로 돌아가** 답을 함께 말한다(§B.1). 마지막 표로 미션의 나머지 기능(다크모드·폼·GitHub API)도 같은 세 축으로 설명할 수 있다고 예고하고 가이드로 보낸다. |

- **학습자용 핵심 설명** 브라우저는 HTML을 읽어 DOM을 만들고, CSS 규칙을 적용해 화면을 그리고, JavaScript를 실행해 사용자 행동에 반응합니다. 그래서 내용을 바꾸려면 HTML을, 모습을 바꾸려면 CSS를, 동작을 바꾸려면 JavaScript를 엽니다. GitHub Pages로 공개하면 방문자의 브라우저가 같은 파일을 받아 같은 과정을 거칩니다.
- **이해 확인 질문** "프로젝트 목록 글씨 색만 바꾸고 싶습니다. 어떤 파일을 열까요? 메뉴가 열리지 않는다면요?" → *색은 CSS 파일, 열리지 않는 동작은 JavaScript 파일(과 연결 줄)을 먼저 봅니다.*
- **마무리 표 (미션 요구 → 세 축)** `[공식]` 요구를 세 축으로 다시 묶은 표. 시맨틱 구역(HTML) · Mobile First 768/1024, Flex/Grid(CSS) · 이벤트 → 상태 → 화면 3개 이상, `addEventListener`, `defer`(JS) · 다크모드/폼/API(세 축이 함께 일함 → Ch5~7) · Pages 공개(Ch8)
- **더 알아보기** 지도: 브라우저 · DOM · 화면 표시 · GitHub Pages / 용어: `browser-rendering`, `dom`, `index-html`, `defer`, `github-pages`, `deployment` / 가이드: Ch1, Ch8, 전체 통합(V09)

### C.3 큰 화면·모바일 표현

- **기준 화면** 1280×720 강의 화면에서 그림 하나가 본문 영역의 60~70%를 차지한다. 그림 안 글자는 투영 기준 최소 18px 상당 `[제안]`.

- **모바일(≤700px)** 나란히 비교(S2-1, S2-3, S3-1)는 위아래로 쌓고 "위: 전 / 아래: 후" 이름표를 단다. F6 결합도는 세로형 변형을 따로 만든다(파일 → 브라우저 → 화면을 위에서 아래로). 그림 안에서 가로 스크롤을 만들지 않는다. 360·390px에서 그림 안 글자가 12px 아래로 내려가면 세로형을 쓴다.
- **강의 → 복습** 강의 화면은 메시지 + 그림 + 캡션만 둔다. "학습자용 핵심 설명"·"이해 확인 질문 정답"·"코드 보기"는 접힘으로 두어 복습할 때 연다.
