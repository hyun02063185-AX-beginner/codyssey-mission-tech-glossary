**F1 대체텍스트** 웹페이지 한 장을 세 가지 역할로 나눈 구조도. HTML(네모 H)은 무엇이 있고 그것이 무엇인지 적는 문서·의미, CSS(동그라미 C)는 어떻게 보일지 조건에 따라 정하는 표현·규칙, JavaScript(마름모 J)는 행동에 어떻게 반응할지 판단하고 실행하는 기능·동작이다. 세 역할 아래의 브라우저가 세 파일을 읽고 합쳐 하나의 화면으로 보여 준다.

**강사 스크립트 — 시작 (3분)**
1. 핵심 질문을 읽고 손을 들게 한다. "문서다 / 디자인이다 / 프로그램이다." 답을 정리하지 않고 넘어간다. 마지막 화면(S4-3)에서 다시 묻는다.
2. F1을 펼쳐 세 역할 이름만 짚는다. "오늘은 한 페이지가 네 번 바뀌는 것을 봅니다. 바뀔 때마다 누가 일했는지만 기억하세요."
3. **선수개념 세 가지**를 말로만 짚는다.
   - 웹페이지도 **글자로 된 파일** 몇 개다. 메모장으로도 열린다.
   - **브라우저**(Chrome·Edge·Safari)는 파일을 읽어 **화면으로 바꿔 보여 주는 프로그램**이다.
   - **언어**는 컴퓨터가 읽도록 약속한 표기법이다. 모든 언어가 "프로그램"을 만드는 것은 아니다.

- **접힘**: "학습자 접힘 설명"·"이해 확인 답"·"연결"은 강의 화면에서 접어 두고, 강의 뒤 자율 탐색에서 펼친다.

## Scene 1 — 웹페이지는 문서에서 시작한다

중심: **HTML = 문서와 의미** · 핵심 개념: 콘텐츠 · 태그 · 시맨틱 HTML

### S1-1 · 꾸밈없는 첫 화면

| 화면 | |
| --- | --- |
| 학습 질문 | 디자인도 동작도 없는 웹페이지에는 무엇이 남을까? |
| 핵심 메시지 | 웹페이지는 먼저 내용이다. |
| 캡션 | 작성자 CSS·JavaScript 없이 HTML만 연결한 화면이다. 브라우저 기본 스타일만 보이고, 링크는 이미 눌린다. |
| 핵심 시각 자료 | F2 캡처 `assets/captures/f2-state1-desktop.png` · 이름표 "① HTML만 · 브라우저 기본 스타일" |
| 대체텍스트 | 꾸밈없는 김코디 자기소개 페이지. 흰 바탕에 파란 밑줄 링크 "김코디", 회색 기본 버튼 "☰ 메뉴", 점 목록으로 된 메뉴(소개·프로젝트·연락), 프로필 그림, 굵은 큰 제목 "안녕하세요, 김코디입니다", 소개 문단, 프로젝트 목록이 위에서 아래로 이어진다. |
| 핵심 개념 | 콘텐츠 (1) |

**강사 스크립트**
1. 실제 샘플 `sample/state-1-html.html`을 브라우저로 연다(캡처와 같은 화면).
2. "이 화면에 무엇이 있나요?" 제목, 그림, 글, 목록, 링크를 손으로 짚는다. **색과 배치는 없지만 내용은 다 있다.**
3. 메뉴의 **"프로젝트" 링크를 눌러** 그 구역으로 이동하는 것을 보여 준다. "아직 JavaScript가 없는데도 링크는 동작합니다. HTML에도 기본 기능이 있어요." (Scene 3의 복선)
4. ☰ 버튼도 눌러 본다. 아무 일도 없다. "이건 나중에."
5. **주의해서 말할 것**: 이 화면은 "스타일이 전혀 없는" 화면이 아니다. 제목이 굵고 크고 링크가 파란 것은 **브라우저 기본 스타일**이다. 우리가 쓴 CSS가 없을 뿐이다.

**학습자 접힘 설명** 웹페이지는 먼저 내용입니다. 제목·그림·글·목록·링크가 HTML 파일에 적혀 있고, 브라우저는 우리가 CSS를 쓰지 않아도 기본 스타일(굵은 제목, 파란 링크)로 보여 줍니다. 링크를 누르면 이동하는 것도 HTML과 브라우저가 하는 일입니다.

**이해 확인** "이 화면에서 제목이 크고 굵은 것은 누가 정했을까요?" → *우리가 쓴 CSS가 아니라 브라우저 기본 스타일입니다.*

**연결** 지도 N02 HTML · (보충) N15 링크·폼 · C04 HTML 기본 기능 ≠ JavaScript 동작 / 용어 `html`, `html-form` / 가이드 Ch1

### S1-2 · 내용에 이름표 붙이기

| 화면 | |
| --- | --- |
| 학습 질문 | 꺾쇠 안의 이름은 무엇을 알려 줄까? |
| 핵심 메시지 | 태그는 ‘이것은 제목’, ‘이것은 목록’이라는 이름표다. |
| 캡션 | h1은 큰 글씨가 아니라 가장 큰 제목이라는 뜻이다. 크기는 다음 장면의 CSS가 정한다. |
| 핵심 시각 자료 | F3 `assets/f3-html-desktop.svg` 상태 `tags` (모바일 `f3-html-mobile.svg`, 번호 1~7 범례) |
| 대체텍스트 | 상태 ① 화면을 다시 그린 그림에 태그 이름표 일곱 개가 가는 선으로 이어져 있다. 이름 링크는 a(누르면 이동), 메뉴 버튼은 button, 메뉴 묶음은 nav와 ul·li, 프로필 그림은 img와 그림의 뜻 alt, 가장 큰 제목은 h1(뜻이지 크기가 아님), 소개 글은 p, 프로젝트 목록은 ul·li. |
| 핵심 개념 | 태그(요소) (1) |

**강사 스크립트**
1. 문법은 읽지 않는다. "꺾쇠 `< >` 안의 이름이 **이 내용의 역할**입니다." 한 문장이면 된다.
2. 이름표를 위에서 아래로 짚는다. `a`는 누르면 이동하는 링크, `button`은 누르는 단추, `nav`는 메뉴 묶음, `img`는 그림.
3. `h1`에서 멈춘다. "h1은 글씨를 크게 하는 태그일까요?" 답을 받는다. → "아니요, **가장 큰 제목**이라는 뜻입니다. 크게 보인 건 브라우저 기본 스타일이고, 크기와 색은 다음 장면의 CSS가 정합니다."
4. `img alt`: 그림을 못 보는 사람과 도구를 위해 **그림의 뜻도 내용**으로 적는다.
5. (선택) 샘플에서 `Ctrl+U`(소스 보기)로 `index.html`을 잠깐 보여 준다. 줄 단위로 읽지 않는다. 태그를 찾아 보는 실습은 가이드 Ch2.

**학습자 접힘 설명** HTML은 내용을 적고, 태그로 그 내용이 무엇인지 표시합니다. `h1`은 "가장 큰 제목", `p`는 "문단", `ul·li`는 "목록", `a`는 "링크", `button`은 "버튼"이라는 뜻입니다. 태그는 모양을 정하지 않습니다. 모양은 CSS가 정합니다.

**이해 확인** "자기소개 제목을 크게 보이게 하려고 `h1`을 쓰는 걸까요?" → *아니요. 가장 중요한 제목이라는 뜻을 표시합니다. 크기와 색은 CSS가 정합니다.*

**연결** 지도 N02 HTML · C02 의미(시맨틱 HTML) ≠ 모양(스타일 규칙) / 용어 `html` / 가이드 Ch2

### S1-3 · 의미가 드러나는 구조

| 화면 | |
| --- | --- |
| 학습 질문 | 의미 있는 태그로 구역을 나누면 무엇이 좋을까? |
| 핵심 메시지 | 의미 있는 태그로 구역을 나누면 사람과 도구가 구조를 읽는다. |
| 캡션 | header·main·section·footer는 모양이 아니라 역할을 알린다. 이것이 시맨틱 HTML이다. |
| 핵심 시각 자료 | F3 `assets/f3-html-desktop.svg` 상태 `structure` (모바일 A~E 범례) |
| 대체텍스트 | 같은 상태 ① 화면을 점선 상자 다섯 개로 나눈 그림. header(머리말: 이름·메뉴), main 안의 section 세 개(소개·프로젝트·연락), footer(바닥글). 오른쪽 아래에 이 구조를 읽는 쪽으로 사람(개발자·동료), 브라우저(문서 구조), 화면 낭독기(구역 이동), 검색 도구(내용 파악)가 있다. |
| 핵심 개념 | 시맨틱 HTML (1) · 구역(header·main·section·footer) |

**강사 스크립트**
1. "같은 화면을 구역으로 나눠 보겠습니다." 점선 상자를 위에서 아래로 짚는다.
2. **시맨틱 HTML** = 의미를 드러내는 태그로 구조를 적는 방식. `main`은 소개·프로젝트·연락을 담는 부모다.
3. "이 구조는 누가 읽을까요?" 네 칸을 짚는다. 사람(나중에 고칠 나와 동료), 브라우저, 화면 낭독기(구역 사이를 건너뛰며 이동), 검색 도구. 효과를 과장하지 않는다("검색 순위가 오른다"처럼 단정하지 않음).
4. 미션은 Hero·About·Skills·Projects·Contact·Footer 구역과 시맨틱 태그를 요구한다 `[공식]`. 이 예시는 **축소판**이라 구역이 적다. 구역↔태그 대응과 `<div class="header">` 비교는 **가이드 Ch2**.
5. 시맨틱 웹은 강의에서 말하지 않는다. 학습자가 물으면 "이름은 비슷하지만 다른 분야입니다. 개념지도 '시맨틱 HTML' 노드의 '더 넓게 알아보기'에 있어요."(E01)

**학습자 접힘 설명** 시맨틱 HTML은 `header`(머리말), `main`(본문), `section`(주제 구역), `footer`(바닥글)처럼 의미를 드러내는 태그로 문서 구조를 적는 방식입니다. 겉모양이 같아도 의미 있는 태그를 쓰면 사람·브라우저·화면 낭독기·검색 도구가 페이지 구조를 이해할 수 있습니다. 미션의 필수 구역은 이 예시보다 많습니다(가이드 Ch2).

**이해 확인** "`<div class="header">`로 감싸고 머리말처럼 꾸미면 시맨틱 HTML일까요?" → *아니요. 이름표(class)만 header이고 태그의 뜻은 없습니다. `<header>`를 써야 합니다.*

**연결** 지도 N03 시맨틱 HTML · R05 HTML → 시맨틱 HTML · C02 · (보충) N14 접근성 · R17 · 확장 E01 시맨틱 웹 / 용어 `semantic-html`, `accessibility-a11y` / 가이드 Ch2

## Scene 2 — 같은 문서를 다르게 표현한다

중심: **CSS = 표현과 규칙** · 핵심 개념: 같은 내용 다른 표현 · 스타일 규칙 · 조건부 규칙

### S2-1 · 같은 내용, 다른 모습

| 화면 | |
| --- | --- |
| 학습 질문 | HTML 본문을 다시 쓰지 않고 화면을 바꿀 수 있을까? |
| 핵심 메시지 | 본문 내용과 구조는 그대로 두고, CSS 연결만 추가했다. |
| 캡션 | 글자·그림·목록의 순서는 같다. 바뀐 것은 색·글꼴·여백·배치다. |
| 핵심 시각 자료 | F2 캡처 둘 나란히: `f2-state1-desktop.png` 이름표 "① HTML만" · `f2-state2-desktop.png` 이름표 "② + CSS 연결" · 칩 "본문 내용과 구조는 그대로 · CSS 연결만 추가" (모바일은 위아래) |
| 대체텍스트 | 왼쪽은 꾸밈없는 상태 ① 화면, 오른쪽은 같은 내용에 CSS를 연결한 상태 ② 화면. 오른쪽은 초록 머리말 띠에 메뉴가 가로로 놓이고, 둥근 프로필 그림 옆에 큰 제목과 소개가 있으며, 프로젝트 세 개가 흰 카드 세 칸으로 나란히 있다. 두 화면의 글과 순서는 같다. |
| 핵심 개념 | 같은 내용, 다른 표현 (1) |

**강사 스크립트**
1. 샘플에서 `state-1-html.html` → `state-2-css.html`로 **탭을 바꿔** 한 번에 보여 준다(전환 효과 없이).
2. "글자, 그림, 목록 순서가 바뀌었나요?" → 같다. 바뀐 것은 색·글꼴·여백·배치다.
3. "HTML에서 바뀐 것은 무엇일까요?" → **`<head>`에 CSS 파일을 연결하는 줄 하나가 더해졌을 뿐**이다. 그 줄도 HTML이므로 "HTML은 한 글자도 안 바뀌었다"고 말하지 않는다. **본문(`<body>`)은 글자 단위로 같다.**
4. 연결 줄을 화면에 띄울 필요는 없다. 궁금해하면 소스 보기로 `<link rel="stylesheet" href="css/style.css">` 한 줄만 보여 준다.

**학습자 접힘 설명** CSS는 HTML 요소가 어떻게 보일지 정하는 스타일 언어입니다. 이 예시에서는 HTML 본문을 한 글자도 고치지 않고, `<head>`에 CSS 파일을 연결하는 줄 하나만 더했습니다. 그런데 색·글꼴·여백·배치가 모두 달라졌습니다. 내용과 구조는 HTML이, 모습은 CSS가 맡기 때문입니다.

**이해 확인** "두 화면에서 같은 것과 다른 것을 하나씩 말해 보세요." → *같은 것: 글·그림·목록과 그 순서. 다른 것: 색·글꼴·여백·배치.*

**연결** 지도 N04 CSS · R02 웹페이지 → CSS / 용어 `css` / 가이드 Ch1

### S2-2 · 규칙 한 줄 읽기

| 화면 | |
| --- | --- |
| 학습 질문 | CSS 규칙 한 줄은 어떻게 읽을까? |
| 핵심 메시지 | 규칙은 누구를(선택자)·무엇을(속성)·어떻게(값)로 적는다. |
| 캡션 | 그리는 순서가 아니라 원하는 모습을 적는다. 브라우저가 요소마다 계산해 그린다. |
| 핵심 시각 자료 | F4 `assets/f4-css-rule-desktop.svg` (모바일 `-mobile.svg`) |
| 대체텍스트 | css/style.css의 실제 규칙 중 한 줄 `h1 { font-size: 1.75rem; }`을 세 부분으로 나눈 그림. h1은 선택자(누구를), font-size는 속성(무엇을), 1.75rem은 값(어떻게). 오른쪽에 화면 속 h1 제목. 아래 세 칸: 선택자는 DOM의 h1 요소를 고르기만 하고 DOM은 바꾸지 않는다, 그리는 순서가 아니라 모습을 값으로 적는다, 브라우저가 요소마다 값을 계산해 화면에 반영한다. |
| 핵심 개념 | 스타일 규칙(선택자·속성·값) (1) |

**강사 스크립트**
1. 이 장면에서 읽는 코드는 **이 한 줄뿐**이다. "누구를 / 무엇을 / 어떻게"를 손으로 짚는다.
2. "CSS는 '먼저 이걸 하고 그다음 이걸 해라'를 적지 않습니다. **원하는 모습**을 적으면 브라우저가 계산해서 그립니다." '선언형'이라는 용어는 쓰지 않는다(지도 E04).
3. **선택자는 고르기만 한다.** "CSS가 h1을 고른다고 해서 h1의 내용이나 문서 구조가 바뀌지는 않습니다." (S4-1의 복선)
4. 규칙이 여러 개 겹치면 어느 쪽이 이기는지 정하는 원리(cascade)가 있다는 것까지만 말한다.
5. **사실 확인용 메모(말하지 않아도 됨)**: 샘플의 `h1 { font-size: 1.75rem; }`은 작은 화면용 기본 규칙이다. 768px 이상에서는 `@media` 안의 `h1 { font-size: 2.25rem; }`이 덮는다. 다음 화면(S2-3)이 이 "조건" 이야기다.

**학습자 접힘 설명** CSS 규칙은 "어떤 요소에(선택자), 어떤 속성을(속성), 어떤 값으로(값)"를 적습니다. 그리는 순서를 적는 대신 원하는 모습을 적고, 브라우저가 각 요소에 맞는 규칙을 골라 계산해 화면에 반영합니다. 선택자는 요소를 고르기만 하므로 CSS가 문서의 내용이나 구조(DOM)를 바꾸지는 않습니다.

**이해 확인** "`h1 { font-size: 1.75rem; }`에서 '누구를'은 어디인가요?" → *`h1`, 선택자입니다.*

**연결** 지도 N05 스타일 규칙 · R06 CSS → 스타일 규칙 · R10 스타일 규칙 → 화면 표시 · 확장 E04 "선언형"이라는 말 / 용어 `css`, `css-cascade` / 가이드 Ch3

**이해 확인** "모바일에서 메뉴를 접고 싶습니다. 모바일용 HTML 파일을 하나 더 만들까요?" → *아니요. 같은 HTML에 화면 폭 조건이 붙은 CSS 규칙을 더합니다.*

## Scene 3 — 문서가 사용자 행동에 반응한다

중심: **JavaScript = 기능과 프로그래밍** · 핵심 개념: 프로그램(판단과 동작) · 이벤트 · DOM

### S3-1 · 이미 되는 것, 아직 안 되는 것

| 화면 | |
| --- | --- |
| 학습 질문 | ☰를 눌렀을 때 메뉴가 열리려면 무엇이 더 필요할까? |
| 핵심 메시지 | 링크 이동은 HTML이 이미 한다. 열고 닫기에는 판단이 필요하다. |
| 캡션 | 상태 ②에서 메뉴 링크는 누르면 이동하지만, ☰는 눌러도 아무 일이 없다. |
| 핵심 시각 자료 | F2 캡처 둘: `f2-state2-desktop.png` 이름표 "메뉴 링크 → 이동 ✔ (HTML 기본 기능)" · `f2-state2-mobile.png` 이름표 "☰ → 변화 없음 ✖ (판단할 프로그램 없음)" |
| 대체텍스트 | 상태 ② 페이지 두 장. 왼쪽 PC 화면의 메뉴 링크는 누르면 해당 구역으로 이동한다(HTML 기본 기능). 오른쪽 모바일 화면의 ☰ 메뉴 버튼은 눌러도 메뉴가 열리지 않는다(판단할 프로그램 없음). |
| 핵심 개념 | 프로그램(판단과 동작) (1) |

**강사 스크립트**
1. **오해부터 막는다.** "웹페이지에서 눌러서 반응하는 건 전부 JavaScript일까요?" → 아니다. 링크 이동, 폼 제출은 HTML과 브라우저의 기본 기능이다. 샘플 PC 화면에서 "연락" 링크를 눌러 이동을 보여 준다.
2. ☰는 다르다. "누를 때마다 **지금 열려 있는지 보고** 열거나 닫아야 합니다." 상황을 보고 다르게 행동하는 것, 그것이 **프로그램**이 하는 일이다.
3. "JavaScript는 HTML·CSS와 달리 **판단하고, 계산하고, 순서대로 실행하는 프로그래밍 언어**입니다."
4. Python 같은 다른 언어 이야기는 꺼내지 않는다. 학습자가 물으면 "같은 '프로그래밍 언어' 가족이고, 실행되는 곳이 다릅니다. 개념지도 JavaScript 노드의 '더 넓게 알아보기'에 있어요."(E03)

**학습자 접힘 설명** 링크 이동과 폼 제출은 JavaScript 없이도 HTML과 브라우저가 처리합니다. 하지만 "누를 때마다 지금 상태를 보고 열거나 닫기"처럼 판단이 필요한 동작은 프로그램이 해야 합니다. JavaScript는 조건에 따라 판단하고 정해진 동작을 수행하는 프로그래밍 언어입니다.

**이해 확인** "상태 ②에서 링크는 되는데 ☰는 왜 안 될까요?" → *링크 이동은 HTML 기본 기능이지만, 열고 닫기는 판단할 프로그램(JavaScript)이 아직 없기 때문입니다.*

### S3-2 · 클릭에서 화면 변화까지

| 화면 | |
| --- | --- |
| 학습 질문 | 클릭 한 번은 어떻게 화면 변화가 될까? |
| 핵심 메시지 | 클릭 → JavaScript 처리 → DOM 변경 → 브라우저가 다시 그림. |
| 캡션 | 입력(클릭)을 받아 판단(처리)하고 결과(화면 변화)를 만든다. 이것이 프로그램이 하는 일이다. |
| 핵심 시각 자료 | F5 `assets/f5-event-desktop.svg` (모바일 `-mobile.svg` 세로 4단) |
| 대체텍스트 | 네 칸 흐름도. 1 사용자가 ☰ 버튼을 누르면 click 이벤트가 생긴다. 2 JavaScript 처리(마름모 J): 미리 등록한 함수(이벤트 핸들러)가 닫혀 있으면 열고, 열려 있으면 닫는다. 3 DOM이 바뀐다: nav에 is-open, aria-expanded=true, HTML 파일은 그대로. 4 브라우저가 바뀐 DOM에 맞는 CSS 규칙으로 다시 그려 메뉴가 보인다. 아래 점선: 다시 누르면 같은 과정으로 닫힌다. |
| 핵심 개념 | 이벤트 (1) · 프로그램의 입력→처리→결과 (2) · (보조) 이벤트 핸들러 |

**강사 스크립트**
1. 샘플 `index.html`(상태 ③)을 좁은 폭으로 열고 ☰를 눌러 열고, 다시 눌러 닫는다.
2. 그림을 번호 순서대로 짚는다. **입력 → 처리 → 결과**.
   - ① 클릭은 브라우저가 알려 주는 **이벤트**다.
   - ② 페이지가 열릴 때 "이 버튼이 눌리면 이 함수를 실행해 달라"고 **미리 맡겨 둔 함수**(이벤트 핸들러)가 실행된다. 미션은 이 연결을 `addEventListener`로 하라고 요구한다 `[공식]`.
   - ③ 함수가 **DOM**을 바꾼다(다음 화면에서 자세히).
   - ④ 브라우저가 바뀐 DOM에 맞는 CSS 규칙으로 **다시 그린다**. "즉시 바뀐다"고 말하지 않는다.
3. 판단 부분은 한국어 문장으로 읽는다. "닫혀 있으면 → 연다 / 열려 있으면 → 닫는다." 실제 코드(`js/menu.js`, `if … else`)는 궁금한 사람에게만 보여 주고 줄 단위로 읽지 않는다.
4. 등록 단계(⓪), 상태, 이벤트 위임, 다른 기능(스크롤·섹션 등장)은 **가이드 Ch4의 V04 6단계**로 보낸다.

**학습자 접힘 설명** 사용자가 버튼을 누르면 브라우저가 그 사실(click 이벤트)을 알려 주고, 미리 등록해 둔 JavaScript 함수(이벤트 핸들러)가 실행됩니다. 이 함수는 메뉴가 닫혀 있으면 열고 열려 있으면 닫기로 판단해 DOM을 바꿉니다. 브라우저는 바뀐 DOM에 맞는 CSS 규칙으로 화면을 다시 그립니다. 입력(클릭) → 처리(판단) → 결과(화면 변화), 이것이 프로그램이 하는 일입니다.

**이해 확인** "② 칸의 '미리 등록한 함수'는 언제 등록될까요?" → *페이지가 열리고 JavaScript 파일이 실행될 때 등록됩니다. 클릭할 때마다 그 함수가 불립니다.*

**연결** 지도 N08 사용자 이벤트 · N09 이벤트 핸들러 · R08 JavaScript → 이벤트 핸들러 · R14 · R15 / 용어 `user-event`, `event-handler`, `add-event-listener`, `function` / 가이드 Ch4

### S3-3 · 바뀌는 것은 파일이 아니라 DOM

| 화면 | |
| --- | --- |
| 학습 질문 | 메뉴를 열면 index.html 파일이 바뀔까? |
| 핵심 메시지 | 바뀌는 것은 파일이 아니라 브라우저 안의 DOM이다. |
| 캡션 | JavaScript가 DOM을 바꾸면, 바뀐 DOM에 맞는 CSS 규칙으로 열린 메뉴가 보인다. |
| 핵심 시각 자료 | 왼쪽 F2 캡처 둘: `f2-state3-mobile-closed.png` 이름표 "③ 처음 · 닫힘" · `f2-state3-mobile-open.png` 이름표 "③ ☰ 클릭 뒤 · 열림". 오른쪽 F5 `assets/f5-dom-desktop.svg` (모바일 `-mobile.svg`) |
| 대체텍스트 | 왼쪽: 상태 ③ 모바일 화면 두 장. 처음에는 메뉴가 닫혀 있고, ☰를 누른 뒤에는 초록 띠 아래로 소개·프로젝트·연락 메뉴가 열려 있다. 오른쪽: index.html 파일에는 nav class="site-nav", button aria-expanded="false"가 적혀 있고 그대로다. 브라우저가 해석한 DOM도 처음에는 같지만, ☰ 클릭 뒤 JavaScript가 바꾼 DOM에서는 nav.site-nav.is-open, aria-expanded="true"가 된다. 새로고침하면 파일에서 DOM을 다시 만들어 메뉴는 닫힌 채 시작한다. |
| 핵심 개념 | DOM (1) · 파일 ≠ DOM |

**강사 스크립트**
1. "메뉴를 열었다 닫았다 하면 `index.html` 파일이 바뀔까요?" 손을 들게 한다.
2. 오른쪽 그림을 위에서 아래로 짚는다. **파일**(디스크에 저장된 글자) → 브라우저가 해석 → **DOM**(브라우저 안의 문서 구조) → ☰ 클릭 → **JavaScript가 DOM을 바꿈**.
3. 시연(가능하면): 개발자 도구 Elements 탭에서 ☰를 누를 때 `nav`에 `is-open`이 붙었다 떨어지는 것만 보여 준다. 소스 보기(`Ctrl+U`)에는 변화가 없다. 자세한 방법은 가이드 Ch4 💻 절.
4. "열린 메뉴의 **모양**은 여전히 CSS가 정합니다." `is-open`이 붙은 `nav`에 맞는 CSS 규칙이 메뉴를 보이게 한다(Scene 2와 연결).
5. 새로고침하면 브라우저가 파일에서 DOM을 다시 만들기 때문에 메뉴는 닫힌 채로 시작한다.

**학습자 접힘 설명** 브라우저는 HTML 파일을 해석해 DOM이라는 문서 구조를 만듭니다. JavaScript는 이 DOM을 읽고 바꿀 수 있습니다. 메뉴를 열면 DOM에서 `nav`에 `is-open`이 붙고 버튼의 `aria-expanded`가 `true`가 되며, 브라우저는 바뀐 DOM에 맞는 CSS 규칙으로 화면을 다시 그립니다. 디스크의 `index.html` 파일은 그대로입니다. 개발자 도구 Elements 탭에 보이는 것은 파일이 아니라 지금의 DOM입니다.

**이해 확인** "메뉴를 열었다 닫았다 했을 때 `index.html` 파일이 바뀌었을까요?" → *아니요. 브라우저 안의 DOM이 바뀌고 화면이 다시 그려졌습니다.*

**연결** 지도 N11 DOM · N16 index.html · R11 JavaScript → DOM · R12 DOM → 화면 표시 · C01 index.html 파일 ≠ DOM / 용어 `dom`, `index-html`, `browser-rendering` / 가이드 Ch4

## Scene 4 — 세 가지가 하나의 웹페이지가 된다

중심: **브라우저 = 세 역할이 결합되는 곳** · 핵심 개념: 브라우저(실행 환경) · 결합 · 고친 파일 ↔ 바뀌는 화면

### S4-1 · 브라우저 안에서 하나가 되는 세 파일

| 화면 | |
| --- | --- |
| 학습 질문 | 세 파일은 어디에서 하나의 화면이 될까? |
| 핵심 메시지 | 세 파일은 브라우저 안에서 하나의 화면이 된다. |
| 캡션 | HTML은 DOM이 되고, JavaScript는 DOM을 읽고 바꾸고, CSS 규칙은 요소에 맞게 계산된다. DOM 자체를 바꾸는 것은 CSS가 아니다. |
| 핵심 시각 자료 | F6 `assets/f6-browser-desktop.svg` (모바일 `-mobile.svg` 세로형) |
| 대체텍스트 | 브라우저 통합 구조도(교육용 단순화). 왼쪽 파일 세 개: js/menu.js(J), index.html(H), css/style.css(C). index.html이 link와 script defer로 나머지 둘을 불러온다(점선). 브라우저 안에서 index.html은 해석되어 DOM이 되고, menu.js는 JavaScript 실행 단계에서 DOM을 읽고 바꾸며(양쪽 화살표), style.css 규칙은 스타일 계산 단계에서 DOM 요소를 고르기만 하고(점선, 읽기만) 요소마다 값을 계산한다. 화면 표시 단계는 DOM과 계산된 스타일로 화면을 그린다. 사용자는 화면을 보고, 누르면 이벤트가 JavaScript 실행으로 전달된다. CSS에서 나온 화살표는 DOM에 닿지 않는다. |
| 핵심 개념 | 브라우저(실행 환경) (1) · 결합(DOM + 계산된 스타일 → 화면) (2) |

**강사 스크립트**
1. "지금까지 세 장면을 한 장에 모았습니다." 파일에서 시작해 화살표를 따라간다.
   - `index.html` → **해석** → DOM
   - `style.css` → **규칙** → 스타일 계산 → (점선) DOM 요소를 **고르기만** → 계산된 모습 → 화면 표시
   - `menu.js` → **실행** → JavaScript ↔ DOM **읽고 바꾼다**
   - DOM → 화면 표시 ← 계산된 모습 → 사용자가 **본다**, 누르면 → 이벤트 → JavaScript
2. **반드시 짚을 것**: "CSS 화살표 끝을 보세요. DOM에 닿지 않고 화면 표시로 갑니다. CSS는 DOM을 바꾸지 않아요. DOM을 바꾸는 것은 JavaScript입니다."
3. 선 두 종류: **점선 = 불러옴·참고**, **실선 = 만든다·바꾼다·그린다**.
4. "실제 브라우저는 파일을 동시에 받고 여러 일을 겹쳐 합니다. 이 그림은 **역할을 구분하는 모델**입니다." `defer`는 이름만 짚는다("HTML을 다 읽은 뒤 실행"). 이유와 오류는 가이드 Ch1·Ch4.

**학습자 접힘 설명** 브라우저는 HTML을 해석해 DOM을 만들고, 각 요소에 맞는 CSS 규칙으로 모습을 계산해 화면을 그리고, JavaScript를 실행해 사용자 행동에 반응합니다. JavaScript는 DOM을 바꿀 수 있지만, CSS는 DOM을 바꾸지 않고 보이는 모습만 정합니다. 이 그림은 역할을 구분하기 위한 단순화이며, 실제 브라우저는 여러 일을 동시에 처리합니다.

**이해 확인** "세 파일 중 DOM을 바꿀 수 있는 것은 무엇인가요?" → *JavaScript입니다. HTML은 해석되어 DOM이 되고, CSS는 DOM을 바꾸지 않고 모습만 정합니다.*

**연결** 지도 N10 브라우저 · N11 DOM · N12 화면 표시 · R09~R13 · N16 index.html · R16 · (보충) R19·R20 · 확장 E05 브라우저 밖과의 통신 / 용어 `dom`, `browser-rendering`, `index-html`, `defer` / 가이드 Ch1

| 화면 | |

1. 그림의 오른쪽 열(파일)을 가리고 **학습자에게 먼저 고르게 한다.** "제목 문구를 바꾸려면 어느 파일?" 손들기 → 공개. 세 번 반복.
2. 고친 뒤에는 **새로고침**해야 브라우저가 파일을 다시 읽는다.
3. **섞인 경우**: "메뉴가 열렸을 때 글자 색을 바꾸고 싶다면?" → CSS(`.site-nav.is-open` 관련 규칙이나 메뉴 링크 규칙). "열리게 하는 것"은 JS, "열린 모양"은 CSS. 기능 하나에 세 파일이 함께 일하기도 한다.
4. 자기 프로젝트에서 실제 위치를 찾는 실습은 가이드 Ch1~Ch4의 💻 절이 출발점이다.

**학습자 접힘 설명** 바꾸고 싶은 것이 내용이면 HTML, 모습(색·크기·배치)이면 CSS, 동작(언제·어떻게 반응할지)이면 JavaScript 파일을 엽니다. 파일을 고친 뒤에는 새로고침해야 브라우저가 파일을 다시 읽어 화면에 반영합니다. 메뉴처럼 기능 하나에 세 파일이 함께 일하는 경우도 많습니다.

**이해 확인** "프로젝트 목록 글씨 색만 바꾸고 싶습니다. 어떤 파일을 열까요? 메뉴가 열리지 않는다면요?" → *색은 CSS 파일, 열리지 않는 동작은 JavaScript 파일(과 HTML의 연결 줄)을 먼저 봅니다.*

## 부록 A. 확장 설명 카드 원고 (지도 상세 패널 "더 넓게 알아보기" · 강의에서 펼치지 않음)

**E01 · 시맨틱 HTML과 시맨틱 웹은 다르다** (노드 N03) — 이름이 비슷하지만 다른 이야기입니다. 시맨틱 HTML은 `header`·`main`·`section`처럼 의미를 드러내는 태그로 **문서의 구조**를 적는 방식입니다. 시맨틱 웹은 컴퓨터가 **데이터의 의미**를 해석하고 서로 연결할 수 있게 하려는 별도의 표준과 기술 체계(RDF 등)입니다. 둘은 "의미"라는 생각을 공유할 뿐, 하나가 다른 하나의 다음 단계는 아닙니다. (용어사전에 시맨틱 웹 항목은 아직 없습니다.)

**E02 · CSS와 설정 형식(JSON·YAML)은 닮았을까?** (노드 N04, 용어 `json`) — 닮은 점: 셋 다 원하는 상태를 이름과 값으로 적고, 실제로 그 일을 처리하는 것은 다른 프로그램입니다. 다른 점: CSS는 **브라우저가 해석하는 스타일 언어**라서 선택자로 요소를 고르고, 조건(`@media`)을 두고, 겹친 규칙의 우선순위(cascade)를 정합니다. JSON과 YAML은 여러 목적에 쓰는 **데이터 표현 형식**이라 그 자체로 스타일이나 동작의 뜻이 없고, 값의 뜻은 그것을 읽는 프로그램이 정합니다. CSS가 설정 파일의 한 종류인 것도, JSON이 CSS의 한 종류인 것도 아닙니다.

**E03 · JavaScript와 Python** (노드 N07, 용어 `python`, `node-js`) — 둘 다 **프로그래밍 언어**입니다. 값을 기억하고(변수), 조건으로 판단하고, 반복하고, 함수로 일을 나눌 수 있습니다. 다른 점은 주로 **실행되는 곳**입니다. 웹 브라우저가 기본으로 실행하는 언어는 JavaScript입니다. Python은 보통 컴퓨터나 서버의 Python 인터프리터가 실행합니다. JavaScript도 Node.js 같은 실행 환경을 쓰면 브라우저 밖에서 실행됩니다.

**E04 · "선언형"이라는 말** (노드 N05) — CSS처럼 "어떻게 보이면 좋겠다"는 **원하는 결과**를 적고, 실제 처리 순서는 프로그램(브라우저)에 맡기는 방식을 선언형이라고 부르기도 합니다. "언제, 어떤 조건에서, 무엇을 할지" 순서대로 적는 방식과 비교하는 말입니다. 입문용 구분일 뿐 엄밀한 분류는 아니며, JavaScript도 선언형 스타일로 쓸 수 있습니다. (용어사전 항목은 아직 없습니다.)

**E05 · 브라우저 밖과의 통신 (API·서버)** (노드 N10, 용어 `fetch-api`, `http-request-response`, `rest-api`) — 브라우저는 다른 서버에 데이터를 요청하고 응답을 받아 화면에 쓸 수도 있습니다. B1-1의 GitHub 프로젝트 카드가 그 예입니다. 이 Story는 세 파일과 브라우저까지만 다룹니다. 요청과 응답은 가이드 Ch7과 Frontend 분야 기술지도에서 이어집니다.
