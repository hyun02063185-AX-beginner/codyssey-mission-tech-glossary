**지도의 중심 설명** `[제안]`: 세 축(HTML·CSS·JavaScript)은 서로 직접 잇지 않는다. 셋 다 **DOM**에 작용하는 관계로 만난다. HTML은 DOM이 되고, CSS는 DOM 요소에 규칙을 적용하고, JavaScript는 DOM을 읽고 바꾼다. 서로 역할을 나누되 같은 대상 위에서 일한다는 것을 선 세 개로 보여 준다.

## D.1 지도 질문·범위·밀도

- **지도 질문** 웹페이지를 이루는 세 역할은 서로 어떤 관계이고, 어디에서 만날까?
- **Story와의 경계** Story는 *시간 흐름*(클릭 → 처리 → DOM → 다시 그림, 로컬 → 공개)을 맡는다. 지도는 *의미 관계*(역할 분담, 포함·구체화, 작용 대상)만 그린다. **지도에는 실행 순서 선(`흐름`)을 두지 않는다.** 이벤트 처리 순서는 Story S3-2와 가이드 V04가 맡는다(정책 §5-2).
- **밀도** B3-1 지도(44노드·67관계, 일반망·AWS 두 체계)를 복제하지 않는다. Frontend 분야 기술지도의 M01 overlay(23노드)는 미션 기술 *전체*를 넓게 강조하므로, 그것과도 겹치지 않게 **세 축 + 브라우저**로 좁힌다. 크기는 B6-1(11노드·12관계)보다 조금 큰 수준이다. 다크모드·폼·GitHub API·localStorage·Intersection Observer 노드는 **넣지 않는다**. 이 개념들은 분야 기술지도 링크로 넘긴다.

## D.2 관계 유형 (B1-1 전용 정의)

B3-1의 `포함`은 "영역·배치·실행 위치", `대응`은 "일반망 ↔ AWS"라는 뜻이라 B1-1에 그대로 쓰면 의미가 섞인다. B1-1은 아래 네 유형만 쓴다 `[제안]`.

| 유형 | 뜻 | 쓰는 곳 | 선 모양 `[제안]` |
| --- | --- | --- | --- |
| **역할** | A가 B라는 역할을 맡는다 / A의 한 축이 B다 | 웹페이지 ↔ 세 축·브라우저 | 굵은 실선 |
| **포함** | B는 A의 한 부분이거나, A를 구체화한 방식이다(**개념 포함·구체화**. 공간 배치가 아님) | HTML → 시맨틱 HTML, CSS → 반응형 웹 등 | 가는 실선 + 열린 삼각 |
| **작용** | A가 B를 만들거나, B에 적용되거나, B를 바꾼다 | 세 축 → DOM, DOM → 화면 표시 | 점선 + 화살촉 |
| **연관** | 위 셋이 아닌 관계. 구체적인 뜻은 이름표에 적는다 | 사용자 → 이벤트, index.html → CSS 등 | 가는 점선 |

- `선행`(학습 순서)은 관계선이 아니라 `learningOrder`로 둔다(B3-1 원칙과 같음).
- **비교**는 선을 긋지 않는 카드다(§D.4.3). JavaScript–Python, CSS–JSON·YAML처럼 **분류가 같거나 관점이 닮은 것**은 관계선으로 표현하면 포함·상속처럼 읽히므로 카드로만 둔다.
- 엔진 확인 필요: B6-1 지도 데이터는 `역할`·`포함`만 쓴다. `작용`·`연관`을 받으려면 어댑터·범례·검증 규칙을 바꿔야 할 수 있다(Codex 검토 항목).

### D.4.2 세 축 간 연결 — 일부러 그리지 않은 선

| 그리지 않은 선 | 이유 |
| --- | --- |
| HTML ↔ CSS, CSS ↔ JS, HTML ↔ JS 직접 선 | 세 축은 서로를 바꾸지 않고 **DOM 위에서** 만난다. 직접 선을 그리면 "CSS가 HTML을 바꾼다" 같은 오해가 생긴다. 역할 분담은 R01~R03이 맡는다 |
| JavaScript → 스타일 규칙 | JS가 class를 바꾸면 다른 CSS 규칙이 적용되지만, 그것은 DOM을 거친 결과다(R11 → R10). 패널 설명으로 둔다 |
| 이벤트 핸들러 → DOM | R11(JavaScript → DOM)과 겹친다. 선이 많아지면 중심 설명이 흐려진다 |
| index.html → HTML | 같은 것을 둘로 나눈 선이 된다. N16은 "파일", N02는 "언어·역할"이라는 차이를 패널에 적는다 |
| 브라우저 → DOM / 브라우저 → JavaScript | 브라우저는 모든 것과 연결되어 허브가 되어 버린다. R04·R13 두 개만 둔다 |

| ID | 제목 | 노드 | 선을 긋지 않는 이유 | 카드 본문 요지 |
| --- | --- | --- | --- | --- |
| C01 | 시맨틱 HTML ≠ 시맨틱 웹 | N03 (+ 확장: 시맨틱 웹) | 선을 그리면 시맨틱 웹이 HTML의 다음 단계처럼 읽힌다 | 시맨틱 HTML은 **문서 구조**의 의미를 태그로 표시한다. 시맨틱 웹은 **데이터**의 의미를 기계가 해석·연결하게 하는 별도 표준 체계(RDF 등)다. 이름이 비슷하고 "의미"라는 생각을 공유할 뿐이다 |
| C02 | CSS와 설정 파일(JSON·YAML) | N04, N05 (+ 확장: JSON·YAML) | 포함·상속 관계가 아니라 **비교 관점**이다 | 공통: 원하는 상태를 이름·값으로 적고, 처리는 다른 프로그램이 한다. 차이: CSS는 브라우저 전용 스타일 언어(선택자·조건·cascade). JSON·YAML은 범용 데이터 형식이고, 뜻은 읽는 프로그램이 정한다 |
| C03 | JavaScript와 Python | N07 (+ 확장: Python, Node.js) | "같은 분류(프로그래밍 언어)"는 관계선이 아니다. 선을 그으면 둘이 연결된 기술처럼 읽힌다 | 공통: 변수·조건·반복·함수. 차이: 실행 환경. 브라우저가 기본으로 실행하는 언어는 JS다. Python은 보통 인터프리터로 실행한다. JS도 Node.js로 브라우저 밖에서 실행된다 |
| C04 | HTML 파일 ≠ DOM | N02, N16, N11 | R09가 이미 "HTML → DOM"을 그린다. 같다는 선을 더하면 혼동이 커진다 | 파일은 디스크의 글자이고, DOM은 브라우저 메모리의 문서 모델이다. JS가 바꾸는 것은 DOM이고, 새로고침하면 파일에서 다시 만든다 |
| C05 | 원하는 모습을 적기 vs 언제·어떻게 할지 적기 | N04, N07 | 언어 사이의 우열이나 분류 체계처럼 보이면 안 된다 | 입문용 비교: CSS는 **원하는 모습**(선언), JS는 **조건과 순서**(판단·실행)를 적는다. 엄밀한 패러다임 분류가 아니다. JS도 선언형 스타일로 쓸 수 있다 |

```
  [N15 링크·폼]······  [N03 시맨틱]  [N05 스타일 규칙] [N09 이벤트 핸들러]
                          ⋮          [N06 반응형 웹]     ↑
                     [N14 접근성]                    [N08 사용자 이벤트]
                                                         ↑
 ─────────────────────── 브라우저 영역 ─────────────────────────────
                    [N11 DOM]  ───────→  [N12 화면 표시]     [N13 사용자]
          (N02·N05·N07에서 작용선 세 개가 위에서 모임)
```

- 세 축은 **같은 높이의 세 열**로 둔다. 열 순서(HTML·CSS·JS)는 Story 순서와 같다.
- DOM은 세 열 아래 **가운데**에 둔다. 작용선 세 개(R09·R10·R11)가 위에서 모이는 모양이 이 지도의 대표 장면이다.
- 사용자는 오른쪽 아래에 두고 R14로 JS 열에 올라간다. 화면 표시와는 선을 긋지 않는다(사용자는 화면을 "보는" 쪽. 그림이 아닌 패널 설명).
- 보충 노드(점선 테두리)는 각 열 바깥쪽에 둔다. 켜고 꺼도 핵심 노드 좌표는 움직이지 않는다(정책 §5-4).
- 모바일(≤700px): 세 열을 유지하되 지도 확대·이동으로 본다. 하단 시트 43dvh(UI 기준 v1.2). 처음에는 "전체 맞춤"으로 핵심 13노드가 다 보이게 한다.

### D.5.2 강의 시연 순서 (5단계)

| 단계 | 강조 | 말할 것 | 연결 Story |
| --- | --- | --- | --- |
| 1 | R01~R04 | 웹페이지 하나에 세 역할과 실행 환경 | 인트로 |
| 2 | R09·R10·R11 (+R06) | **세 축은 DOM에서 만난다.** 직접 선이 없는 이유 | S3-3, S4-1 |
| 3 | R05·R07·R08 | 축마다 하나씩 구체화: 시맨틱 HTML, 반응형, 이벤트 핸들러 | S1-3, S2-3, S3-2 |
| 4 | R14 → R15 + C04 | 사용자 행동이 이벤트가 되고 함수가 불린다. 파일이 아니라 DOM이 바뀐다 | S3-2, S3-3 |
