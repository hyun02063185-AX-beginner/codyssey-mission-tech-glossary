**지도의 중심 설명** `[제안]` 교육용 단순화이며, 패널에 이 점을 밝힌다.

> HTML은 브라우저가 해석해 **DOM**이 되고, JavaScript는 그 **DOM을 읽고 바꾸며**, CSS는 **DOM 요소에 맞는 규칙**으로 모습을 정한다. 브라우저는 **DOM과 계산된 스타일을 합쳐 화면을 그린다.**

지도에서 세 축(HTML·CSS·JavaScript)끼리는 직접 잇지 않는다. 세 축의 선은 모두 브라우저 영역(DOM·화면 표시)으로 내려가 **화면 표시**에서 모인다. HTML과 JS는 DOM을 거쳐서, CSS는 바로 모인다.

## D.1 지도 질문·범위·밀도

- **지도 질문** 웹페이지를 이루는 세 역할은 서로 어떤 관계이고, 브라우저 안에서 어떻게 하나의 화면이 될까?
- **Story와의 경계** Story는 *시간 흐름*(클릭 → 처리 → DOM → 다시 그림, 로컬 → 공개)을 맡는다. 지도는 *의미 관계*(역할 분담, 개념 포함, 구현·연결)만 그린다. **지도에는 실행 순서 선(`흐름`)을 두지 않는다.** 이벤트 처리 순서는 Story S3-2와 가이드 V04가 맡는다(정책 §5-2).
- **밀도** B3-1 지도(44노드·67관계)를 복제하지 않는다. Frontend 분야 기술지도의 M01 overlay(23노드)와도 겹치지 않게 **세 축 + 브라우저**로 좁힌다. 다크모드·폼 검증·GitHub API·localStorage·Intersection Observer 노드는 넣지 않고 분야 기술지도 링크로 넘긴다.
- **학습 범위** 시맨틱 웹, JSON·YAML, Python, 선언형, API·서버는 **강의 필수 내용이 아니다.** 노드로 만들지 않고 확장 설명 카드(§D.4.4)로만 둔다. 강의에서는 펼치지 않는다.

## D.2 관계 유형 — 최종 후보와 선택 이유

### D.2.1 유형 집합

기존 공유 타입 `RelationType`(`src/missionConceptMap/conceptMapTypes.ts`)은 `포함`·`역할`·`흐름`·`대응`·`연관`·`선행` 여섯 가지다. 공유 검증기(`scripts/validate_mission_concept_map.py`)도 이 여섯 가지만 허용한다. B1-1은 **새 유형을 만들지 않고 셋만 쓴다.**

| 유형 | B1-1에서의 뜻 (지도 데이터 `relationTypes`에 미션별로 적음) | 쓰는 관계 | 쓰지 않는 이유(쓰지 않는 유형) |
| --- | --- | --- | --- |
| **역할** | A가 B라는 역할을 맡는다 | 웹페이지 → 세 축, 브라우저 → 웹페이지·화면 표시 | — |
| **포함** | B는 A의 한 부분이거나 A를 구체화한 방식이다. **개념 포함이며 공간 배치가 아니다** | HTML → 시맨틱 HTML, CSS → 스타일 규칙, HTML → 링크·폼 | — |
| **연관** | 위 둘이 아닌 관계. 뜻(구성·구현 수단·바탕·계기·불러옴·공개)은 **이름표와 설명**에 적는다 | 나머지 13개 | — |
| `흐름` | — | — | B3-1에서는 통신 경로(`path`) 전용이다. B1-1 지도는 실행 순서를 그리지 않는다 |
| `대응` | — | — | 공유 검증기에서 일반망 → AWS 교차 관계 전용이다 |
| `선행` | — | — | 관계선이 아니라 `learningOrder`로 둔다(공유 규칙) |

- **`작용`을 추가하지 않는 이유** `연관`의 공유 정의가 이미 "구체적인 뜻(연결·**적용**·할당·…)은 label과 description에 적는다"이다. `작용`을 추가하면 `RelationType` 유니언, 검증기 `TYPES`, 상세 패널의 유형별 묶음(`ConceptMapDetailPanel`의 `['포함','역할','흐름','연관','대응']`), 캔버스 선 모양 분기가 모두 바뀌어 B3-1 코드에 영향을 준다.
- **`포함`의 뜻이 B3-1과 다른 문제** B3-1 데이터는 `포함`을 "A 안에 B가 놓인다(영역·배치·실행 위치)"로 정의한다. 유형의 뜻은 코드에 박혀 있지 않고 지도 데이터의 `relationTypes`에 있다(코드 검색으로 확인). 그래서 B1-1 데이터에 B1-1의 뜻을 따로 적는다. 화면 범례에 이 뜻이 실제로 나오는지는 **미검증**이다(§D.8).

- R10: "선택자가 DOM 요소를 고르고, 브라우저가 요소마다 적용할 값을 계산한다. CSS는 DOM의 구조나 내용을 바꾸지 않는다. JavaScript가 class를 바꾸면 그 요소에 맞는 규칙이 달라질 뿐이다."
- R12: "지도는 순서를 그리지 않는다. 클릭에서 다시 그리기까지의 순서는 Story S3-2에서."
- R14 → R15 → (핸들러) → R11 → R12를 이어 읽으면 Story S3-2의 순서와 같아 보인다. 패널에 **"순서는 Story S3-2에서. 지도는 누가 누구와 어떤 관계인지만 보여 줍니다"**라고 적는다.

### D.4.2 일부러 그리지 않은 선

| 그리지 않은 선 | 이유 |
| --- | --- |
| HTML ↔ CSS, CSS ↔ JS, HTML ↔ JS 직접 선 | 세 축은 서로를 바꾸지 않고 브라우저 안에서 만난다. 직접 선을 그리면 "CSS가 HTML을 바꾼다" 같은 오해가 생긴다. 역할 분담은 R01~R03이 맡는다 |
| 스타일 규칙 → DOM / CSS → DOM | CSS가 DOM을 바꾸는 것처럼 읽힌다(r1에서 삭제). 선택자가 요소를 고른다는 사실은 R10 설명에 둔다 |
| JavaScript → 스타일 규칙 | JS가 class를 바꾸면 적용 규칙이 달라지지만, DOM을 거친 결과다(R11 → R12, R10). 패널 설명으로 둔다 |
| 이벤트 핸들러 → DOM | R11(JavaScript → DOM)과 겹친다 |
| index.html → DOM | 비교 카드 C01과 충돌한다. 파일 → 언어(R16) → DOM(R09)으로 간접 연결된다 |
| 브라우저 → DOM / 브라우저 → JavaScript | 브라우저가 모든 것과 이어진 허브가 된다. R04·R13 두 개만 둔다 |

### D.5.1 배치 초안 (PC, 위 → 아래 · 왼쪽 → 오른쪽)

```
                               [N17 GitHub Pages]··
                                                  ⋮
                         ┌──── [N01 웹페이지] ────┐ ←── [N10 브라우저]
```

- 세 축은 **같은 높이의 세 열**로 둔다. 열 순서(HTML·CSS·JS)는 Story 순서와 같다.
- 브라우저 영역의 **DOM과 화면 표시**를 가운데 아래에 나란히 둔다. HTML·JS 선은 DOM으로, 스타일 규칙 선은 화면 표시로 내려온다. 세 선이 **화면 표시**에서 모이는 모양이 이 지도의 대표 장면이다.
- 사용자는 오른쪽 아래에 두고 R14로 JS 열에 올라간다.
- 보충 노드(점선 테두리)는 각 열 바깥쪽에 둔다. 켜고 꺼도 핵심 노드 좌표는 움직이지 않는다(정책 §5-4).
- 모바일(≤700px): 세 열을 유지하고 확대·이동으로 본다. 하단 시트는 43dvh(UI 기준 v1.2). 처음에는 "전체 맞춤"으로 핵심 14노드가 다 보이게 한다.
- 위 그림은 **설계 스케치**다. 실제 좌표·선 겹침은 미검증이다(§D.10).
