# B1-1 학습 시나리오 v1.0

## 1. 프로젝트 목적

제목: **AI가 만든 웹사이트, 이제 내가 이해하고 설명하기**

대상: IT와 프로그래밍 지식이 거의 없고, AI를 활용해 B1-1 미션을 수행하는 코디세이 교육생

목표: 코드를 직접 작성하는 방법을 가르치는 것이 아니라, AI가 생성한 웹사이트의 구조와 동작을 이해하고 실제 코드에서 근거를 확인해 설명하도록 돕는다.

사용자가 직접 교육생을 대상으로 강의할 예정이므로 학습자용 원고와 강사용 핵심 설명을 함께 준비한다.

## 2. 공통 학습 구조

**관찰 → 점 → 선 → 면 → 코드 확인 → 자기 설명**

- 관찰: 웹사이트에서 실제 동작을 확인한다.
- 점: 모르는 기술과 궁금한 질문을 발견한다.
- 선: 여러 개념의 역할과 연결 관계를 이해한다.
- 면: 기술들이 협력해 하나의 기능을 완성하는 전체 구조를 이해한다.
- 코드 확인: AI가 작성한 실제 프로젝트에서 관련 파일·함수·스타일을 찾는다.
- 자기 설명: 배운 내용을 자신의 말로 설명한다.

문법 암기나 직접 코딩이 아니라 **기능 시연 → 원리 이해 → 코드 위치 확인 → 설명**을 중심에 둔다.

## 3. Chapter 구성

### Chapter 1 — 웹사이트는 어떤 파일들로 만들어질까?

미션 요구: 순수 HTML·CSS·JavaScript, `index.html`·`css/`·`js/`·`images/`, `defer`, 외부 라이브러리 제한

점: HTML 파일만으로도 화면이 나타나는데 CSS와 JavaScript는 왜 필요할까?

선: 파일과 폴더 → HTML 구조 → CSS 표현 → JavaScript 동작 → 브라우저 화면

면: 서로 다른 파일이 협력하여 하나의 웹사이트가 되는 구조

**V01:** 실제 웹페이지를 HTML·CSS·JavaScript의 역할로 분해한 구조도

코드 분석: 각 파일의 위치와 역할을 찾아 화면 요소와 연결한다.

### Chapter 2 — 웹페이지의 구역은 코드에서 어떻게 구분될까?

미션 요구: Hero·About·Skills·Projects·Contact·Footer, 시맨틱 HTML

점: 화면의 구역은 어떤 기준으로 구분할까?

선: 화면 구역 → HTML 요소 → 태그 의미 → 문서 구조

면: 의미 있는 태그와 콘텐츠가 페이지 구조를 형성하는 과정

**V02:** 실제 웹 화면의 구역과 HTML 구조를 연결한 대응도

코드 분석: 사이트의 각 섹션과 HTML 태그의 대응 관계를 찾는다.

### Chapter 3 — 화면 크기에 따라 디자인이 달라지는 이유

미션 요구: 모바일 퍼스트, 768px/1024px 브레이크포인트, Flexbox, Grid, CSS 변수

점: 동일한 웹사이트가 PC와 모바일에서 다르게 보이는 이유는?

선: 화면 크기 → Media Query → CSS 배치 규칙 → Flexbox·Grid → 레이아웃

면: HTML 구조를 유지하면서 CSS가 다양한 화면에 대응하는 구조

**V03:** PC·태블릿·모바일 배치 변화 비교도

코드 분석: 실제 Media Query와 레이아웃 관련 CSS를 확인한다.

### Chapter 4 — 버튼을 누르면 화면은 어떻게 바뀔까?

미션 요구: 햄버거 메뉴, 스크롤 기능, Intersection Observer, `addEventListener`, 이벤트 → 상태 → 화면 업데이트 3개 이상

점: 사용자가 버튼을 클릭했다는 사실을 JavaScript는 어떻게 알고 반응할까?

선: 사용자 행동 → Event → Handler → 상태 또는 DOM 변경 → 화면 업데이트

면: HTML·JavaScript·DOM이 협력해 인터랙션을 완성하는 구조

**V04:** 이벤트 발생부터 DOM과 화면 변화까지의 단계별 작동 흐름도

코드 분석: 실제 기능 세 가지의 이벤트 처리 코드와 화면 변화 위치를 추적한다.

### Chapter 5 — 다크모드는 왜 새로고침 후에도 유지될까?

미션 요구: 테마 전환, localStorage 저장 및 복원

점: 페이지를 다시 열어도 다크모드를 기억하는 이유는?

선: 클릭 → 테마 상태 변경 → CSS 적용 → localStorage 저장 → 다시 읽기

면: 화면 변경과 설정 유지라는 서로 다른 책임의 결합

**V05:** 테마 전환 흐름과 새로고침 후 복원 흐름을 구분한 구조도

코드 분석: 상태 변경, 스타일 적용, 저장·복원 코드를 각각 찾는다.

### Chapter 6 — 입력한 정보가 올바른지 어떻게 확인할까?

미션 요구: Contact 폼, 필수값·이메일 검증, 오류 메시지

점: 사용자가 잘못 입력한 정보는 어떻게 확인할까?

선: 입력 → 값 읽기 → 검증 → 성공·실패 분기 → 결과 표시

면: 사용자 입력과 JavaScript 검증, 화면 피드백이 연결되는 구조

**V06:** 정상 입력과 오류 입력의 분기 흐름도

코드 분석: 입력 검증과 오류 표시 코드를 찾는다. 검증 성공과 실제 전송 성공은 구분한다.

### Chapter 7 — 외부 서버 정보가 웹사이트에 나타나는 과정

미션 요구: GitHub API, `fetch`, `async/await`, `try/catch`, `map`·`filter`, 로딩·성공·오류·빈 상태

점: GitHub에 있는 데이터가 내 웹사이트에 어떻게 나타날까?

선: 브라우저 → HTTP 요청 → GitHub API → 응답 → 데이터 처리 → 화면 표시

면: 브라우저와 외부 서버가 요청과 응답으로 연결되는 구조

**V07:** 브라우저와 GitHub API 사이의 요청·응답 구조도

**V07 보조 자료:** 로딩·성공·오류·빈 결과의 네 가지 화면 상태 비교

코드 분석: API 호출부터 데이터 가공과 카드 렌더링까지 코드 흐름을 추적한다.

### Chapter 8 — 웹사이트가 인터넷에 공개되는 과정

미션 요구: GitHub 저장소, GitHub Pages 배포, README, 제출용 스크린샷, 공개 사이트 점검

점: 내 컴퓨터에서 만든 사이트를 다른 사람은 어떻게 볼까?

선: 로컬 프로젝트 → Git → GitHub → GitHub Pages → 공개 URL

면: 개발 결과물의 저장과 공개 배포가 연결되는 구조

**V08:** 로컬 프로젝트부터 GitHub Pages 공개까지의 흐름도

코드 분석: 실제 GitHub 저장소·배포 사이트·README·제출물을 비교한다.

## 5. 시각 자료 제작 원칙

시각화는 보조 장식이 아니라 학습의 핵심 자료다.

- SVG 구조도와 흐름도를 적극적으로 활용한다.
- 연결선에는 역할·인과·데이터 흐름 중 어떤 관계인지 명확히 표현한다.
- 구조 관계와 실행 순서를 혼동하지 않는다.
- 학습자가 그림만 보아도 핵심 작동 구조를 이해할 수 있도록 한다.
- 초심자가 이해하기 어려운 용어에는 간단한 설명을 넣는다.
- 반응형 웹에서도 읽을 수 있도록 제작한다.
- 기존 기술용어사전의 정의와 시각 자료를 가능한 범위에서 재사용한다.
- 일반화한 개념 모델과 실제 구현 코드는 반드시 구분한다.
