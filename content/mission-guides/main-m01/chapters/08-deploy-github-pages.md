# Chapter 8 — 웹사이트가 인터넷에 공개되는 과정

> 지금까지 만든 사이트는 **내 컴퓨터 안**에서만 열립니다. 동료평가자는 내 컴퓨터를 열어 볼 수 없습니다. **내 컴퓨터에서 만든 사이트를 다른 사람은 어떻게 볼 수 있을까요?**

**이 장에서 알게 되는 것**

- 로컬 프로젝트가 **Git → GitHub → GitHub Pages → 공개 URL**로 이어지는 과정
- **Git, GitHub, GitHub Pages**가 각각 무엇을 하는지
- 제출물(저장소 URL, 배포 URL, README, 스크린샷)과 **공개한 사이트를 점검하는 법**

📱 모바일에서는 **핵심 그림과 핵심 개념 설명**(아래 "미션이 요구하는 제출물" 앞까지)만 읽어도 충분합니다. 💻 그 뒤의 직접 확인과 코드 분석은 컴퓨터 앞에서 내 프로젝트를 열고 읽으면 좋습니다.

> 표기 규칙(`[공식]` `[시나리오]` `[사전]` `[권장]` `[AI 보충]`)은 [README](../README.md#표기-규칙)를 참고하세요.

## 내 컴퓨터의 사이트를 다른 사람이 보려면?

> **내 컴퓨터에서 만든 사이트를 다른 사람은 어떻게 볼까?** `[시나리오]`

내 컴퓨터의 `index.html`을 열면 브라우저에 사이트가 보이지만, 그 파일은 **내 컴퓨터에만** 있습니다. 다른 사람이 보려면 두 가지가 필요합니다.

1. 파일을 **인터넷 어딘가에 올려 두는 일** — 저장과 공유
2. 그 파일을 **웹 주소(URL)로 열 수 있게 하는 일** — 공개

이 장은 이 두 가지가 어떤 순서로 이어지는지 다룹니다.

## 저장에서 공개까지

![V08: 5단계 세로 흐름도. 1 내 컴퓨터의 프로젝트 폴더, 2 내 컴퓨터의 Git 저장소(git add와 commit으로 기록), 3 GitHub의 원격 저장소(git push로 올림, 저장소 URL과 README가 제출물), 4 GitHub Pages(Settings에서 Pages를 설정하면 정적 파일을 웹사이트로 공개), 5 공개 URL의 사이트(배포 URL과 스크린샷이 제출물). 아래 상자는 로컬에서는 되는데 배포하면 달라질 수 있는 네 가지를 정리합니다.](../assets/v08-deploy-flow.svg)

*교육용 단순화 모델입니다. 점선 표식은 제출물을 뜻합니다.*

### 그림 읽는 법

1. **①②는 내 컴퓨터 안**입니다. 프로젝트 폴더의 변화를 **기록**(commit)해 Git 저장소에 쌓습니다. 아직 아무도 볼 수 없습니다.
2. **③은 GitHub**입니다. `git push`로 기록을 올리면 인터넷의 **원격 저장소**에 사본이 생깁니다. 하지만 이 단계의 GitHub는 **코드 보관소**일 뿐 웹사이트가 아닙니다.
3. **④⑤에서 공개**가 일어납니다. 저장소 설정에서 GitHub Pages를 켜면 파일이 **웹사이트로 제공**되고, 방문자의 브라우저가 URL로 요청해 사이트를 봅니다.
4. 화살표 옆 글은 **그 단계에서 하는 일**(명령 또는 설정)입니다. 점선 표식은 **제출물**이 만들어지는 자리입니다.

> **개발 결과물은 먼저 저장·공유되고(Git → GitHub), 그다음에 따로 공개됩니다(GitHub Pages).** 저장과 공개는 서로 다른 단계입니다.

---

## Git, GitHub, GitHub Pages는 서로 다릅니다

- [**Git**](../../../terms/git.md) — 내 컴퓨터에서 **파일의 변경 기록**을 남기는 도구입니다. 기록 하나가 [커밋](../../../terms/commit.md)이고, 기록이 담긴 폴더가 [저장소](../../../terms/repository.md)입니다. 인터넷 없이도 씁니다. `[사전]`
- [**GitHub**](../../../terms/github.md) — Git 저장소를 **온라인에 보관하고 공유**하는 서비스입니다. 내 기록을 [push](../../../terms/push.md)로 올려 두면 다른 사람과 나눌 수 있습니다. `[사전]`
- [**GitHub Pages**](../../../terms/github-pages.md) — 저장소의 정적 파일을 **웹사이트로 공개**하는 GitHub의 기능입니다. `[사전]`

> **GitHub에 올렸다고 자동으로 공개되는 것은 아닙니다.** Git과 GitHub도 같은 제품이 아닙니다. Pages 같은 배포 설정이 필요합니다. `[사전]`

---

## GitHub Pages는 무엇을 해 줄까?

GitHub Pages는 저장소에 있는 HTML·CSS·JavaScript·이미지 같은 **파일을 그대로** 웹 주소로 내보냅니다. `[사전]`

- **정적 파일**을 제공하는 것이라 **서버에서 코드를 실행하지 않습니다.** 파일의 JavaScript는 방문자의 **브라우저**에서 실행됩니다. 이 가이드의 사이트가 순수 HTML·CSS·JS로 동작하는 이유입니다. `[사전]`
- 서버 데이터베이스나 **비밀값을 안전하게 숨기는 곳이 아닙니다.** 올린 파일은 누구나 볼 수 있습니다. `[사전]`
- 주소는 보통 `https://사용자이름.github.io/저장소이름/` 모양입니다. 저장소 이름이 **주소의 일부**가 됩니다. `[AI 보충]`
- 설정은 저장소의 **Settings → Pages**에서 합니다. **어느 branch의 어느 폴더**를 공개할지 고릅니다. 화면 이름은 GitHub 업데이트로 바뀔 수 있으니 공식 문서를 함께 확인하세요. `[AI 보충]`
- 공개 직후에는 사이트가 **조금 늦게** 반영될 수 있습니다. `[AI 보충]`
- 무료 계정은 **공개(public) 저장소**에서 쓰는 경우가 일반적입니다. 요금제 정책은 바뀔 수 있으니 확인하세요. `[AI 보충]`

## 배포하면 달라질 수 있는 것

[배포](../../../terms/deployment.md)는 내 컴퓨터의 파일을 누구나 열 수 있는 주소로 바꾸는 일입니다. `[사전]` **내 컴퓨터에서는 잘 되던 것이 배포 뒤 깨지는** 대표 원인이 있습니다. `[사전]` `[AI 보충]`

### 1. 경로

1장에서 본 경로 차이가 여기서 문제가 됩니다. [절대·상대 경로](../../../terms/absolute-relative-path.md)

- `css/style.css` — 지금 파일 **기준**의 경로입니다. 대체로 안전합니다.
- `/css/style.css` — 사이트의 **맨 위(루트)** 에서 시작합니다. 프로젝트 주소(`사용자.github.io/저장소/`)에서는 저장소 이름이 빠져 **깨질 수 있습니다.**

### 2. 대소문자

Windows나 Mac에서는 `Images/`와 `images/`를 같은 폴더로 취급하기도 하지만, 배포 환경은 **구분**하는 경우가 많습니다. 폴더·파일 이름의 대소문자가 코드의 경로와 **정확히 같은지** 확인하세요. `[사전]`

### 3. localStorage는 주소별로 다릅니다

5장에서 본 대로 저장소는 **주소(origin)별**입니다. 내 컴퓨터에서 켜 둔 다크모드는 배포한 주소에서는 보이지 않습니다. 배포 사이트에서 처음에 기본 테마로 보이는 것은 정상입니다. `[사전]`

### 4. 반영 지연과 저장된 옛 버전

방금 고쳐서 올렸는데 사이트가 그대로라면, 배포가 **아직 반영되지 않았거나** 브라우저가 **옛 파일을 보여 주는** 중일 수 있습니다. 잠시 기다린 뒤 **강력 새로고침**(`Ctrl + Shift + R`)을 해 보세요. `[AI 보충]`

### 참고: https 주소에서의 요청

배포된 사이트는 `https://`로 열립니다. 사이트가 불러오는 이미지나 데이터 주소도 `https://`여야 합니다. `http://`로 불러오는 자원은 브라우저가 막을 수 있습니다. GitHub API 주소는 이미 `https://`입니다. `[AI 보충]`

## 미션이 요구하는 제출물

**제출물** `[공식]`

- **GitHub 저장소 URL** — 내 코드가 있는 저장소 주소
- **배포 URL** — GitHub Pages로 공개한 사이트 주소
- **README** — 제출물에 포함되는 필수 문서
- **스크린샷** — 데스크톱, 모바일, 다크모드 화면 (제출 증거)

**배포 요구** `[공식]`

- GitHub Pages 배포 URL에서 **반응형·상호작용·API·폼 검증이 동작**해야 합니다.
- 로컬이 아니라 **배포 URL을 새 탭에서** 열어 확인합니다.

**동료평가에서 확인하는 점** `[공식]`

- 배포 URL에서 요구 기능이 **실제로** 보이는가
- 상대 경로와 배포 설정이 맞는가
- **로컬 화면만이 아니라** 배포 URL에서 새로고침과 기능을 점검했는가

### README에는 무엇을 쓸까 `[권장]`

미션은 README가 **필수 문서**라고 합니다. 무엇을 써야 하는지는 이 저장소 자료에 자세히 나와 있지 않아서, 일반적으로 읽는 사람에게 도움이 되는 내용을 소개합니다.

- 프로젝트가 무엇인지 (한두 문장)
- **배포 URL** 링크
- 주요 기능 (다크모드, 폼 검증, GitHub 데이터 등)
- 사용한 기술 (순수 HTML·CSS·JavaScript)
- 폴더 구조와 실행 방법
- 스크린샷

## 💻 공개한 사이트를 직접 점검하기

배포했다면 **내 컴퓨터의 파일이 아니라 공개 URL**을 열고 아래 순서로 확인합니다.

1. **새 탭(또는 시크릿 창)에서 배포 URL**을 엽니다. 처음 방문한 사람이 보는 화면입니다. (다크모드가 기본 테마로 시작하는 것이 정상입니다.)
2. **새로고침**해도 화면과 기능이 정상인지 봅니다.
3. **화면 폭을 바꿔** 반응형을 확인합니다. (3장의 방법) 메뉴와 카드가 폭에 맞게 바뀌는지 봅니다.
4. **메뉴·스크롤·등장 효과**를 눌러 봅니다. (4장)
5. **다크모드를 켜고 새로고침**해 선택이 유지되는지 봅니다. (5장)
6. **Contact 폼**에 잘못된 값과 정상 값을 넣어 봅니다. (6장)
7. **GitHub 데이터**가 보이는지, 안 보인다면 오류 안내가 나오는지 봅니다. (7장)
8. **F12**를 열고 **Console의 빨간 오류**와 **Network의 빨간 줄**(404 등)이 없는지 봅니다. 파일을 못 찾는다는 오류가 보이면 경로나 대소문자를 의심합니다.
9. 가능하면 **스마트폰으로도** 같은 주소를 열어 봅니다.

이 확인 결과가 **스크린샷**(데스크톱·모바일·다크모드)의 재료가 됩니다.

## 내 프로젝트의 저장소와 배포 사이트 비교하기

### 찾는 방법

- **GitHub 저장소 첫 화면**: `index.html`이 맨 위에 있는지, `css/`·`js/`·`images/` 폴더 이름의 **대소문자**가 코드와 같은지, README가 아래에 표시되는지 봅니다.
- **Settings → Pages**: 어느 branch와 폴더로 공개되는지, 공개된 주소가 무엇인지 확인합니다.
- **편집기 검색**: `href="/`, `src="/`처럼 `/`로 시작하는 경로를 찾습니다. 프로젝트 주소에서 깨질 수 있습니다. 또 `http://`로 시작하는 자원도 찾아봅니다.
- **저장소와 배포 사이트를 나란히** 열어, 저장소의 파일 이름이 배포 사이트의 Network 요청과 같은지 비교합니다.

## AI에게 이렇게 물어보세요

> 1장의 네 가지 규칙(**수정하지 말고 설명만 / 파일·줄 번호 / 내 화면과 연결 / 답은 가설**)을 그대로 적용합니다.

> **배포 전 경로 점검**
> 이 프로젝트의 HTML·CSS·JavaScript에서 `/`로 시작하는 절대 경로(`href="/…"`, `src="/…"`, CSS의 `url(/…)`)와 `http://`로 시작하는 자원을 모두 찾아 파일 이름과 줄 번호로 알려 줘. GitHub Pages 프로젝트 주소(`사용자.github.io/저장소/`)에서 깨질 수 있는 곳은 후보로만 알려 주고 수정은 하지 마.

> **대소문자 점검**
> 코드에서 참조하는 파일·폴더 경로와 실제 저장소의 파일·폴더 이름이 **대소문자까지 정확히 같은지** 비교해서 다른 곳이 있으면 알려 줘. 수정은 하지 마.

> **배포 설정 이해**
> GitHub Pages로 이 프로젝트를 공개하려면 어떤 설정(branch, 폴더)이 필요한지, 그리고 `index.html`이 어디에 있어야 하는지 이 저장소 구조를 기준으로 설명해 줘. 설정은 내가 직접 할 테니 단계만 알려 줘.

> **README 점검**
> 이 프로젝트의 README에 배포 URL, 주요 기능, 사용 기술, 스크린샷이 있는지 확인하고, 실제 프로젝트와 맞지 않는 내용(없는 기능을 말하는 문장 등)이 있는지 알려 줘. 고치지는 마.

> README 초안을 AI에게 맡길 수도 있지만, **내 사이트에 실제로 있는 기능만 적혀 있는지** 반드시 직접 확인하세요.

### AI의 답을 확인하는 법

| AI가 말한 것 | 내가 확인할 것 |
| --- | --- |
| "절대 경로가 깨질 수 있습니다" | 배포 URL에서 Network 탭의 빨간 줄(404)로 실제로 깨졌는지 |
| "대소문자가 다릅니다" | 저장소 화면의 폴더 이름과 코드의 글자를 하나씩 비교 |
| "Pages가 이 폴더를 공개합니다" | Settings → Pages에 표시된 branch·폴더와 같은지 |

## 동료평가에서는 이런 질문이 나옵니다

**동료평가에서 받을 수 있는 질문** `[공식]`

- 로컬에서 정상인 페이지가 GitHub Pages 배포 뒤 깨질 수 있는 이유는 무엇인가요?
- 로컬에서는 되는데 배포에서 API나 자원이 깨질 수 있는 이유는 무엇인가요?

**이렇게 설명할 수 있습니다** (예시이며, 내 사이트의 실제 주소와 이름으로 바꿔 말하면 됩니다)

> 먼저 `git commit`으로 내 컴퓨터의 Git 저장소에 변경을 기록하고, `git push`로 GitHub 저장소에 올립니다. 그다음 저장소 설정의 Pages에서 공개할 branch와 폴더를 골라 GitHub Pages로 공개했고, 방문자는 `https://사용자.github.io/저장소/` 주소로 접속합니다. 로컬에서는 되던 것이 배포 뒤 깨질 수 있는 이유는 절대 경로, 파일 이름의 대소문자, 주소별로 나뉘는 localStorage, 반영 지연 때문입니다. 그래서 로컬이 아니라 배포 URL을 새 탭에서 열어 반응형, 메뉴, 다크모드, 폼, GitHub 데이터를 모두 확인했습니다.

**자주 하는 실수** `[공식]`

- 로컬 캡처만 있고 배포 URL을 확인하지 않음 → 배포 URL을 새 탭에서 열어 점검
- 로컬 화면만 확인하고 상대 경로와 새로고침 동작을 점검하지 않음 → Network 탭의 404 확인

## 핵심 내용 정리

- 사이트는 **commit(기록) → push(올림) → Pages(공개) → 공개 URL(접속)** 순서로 세상에 나갑니다.
- **Git은 기록 도구, GitHub는 저장·공유 서비스, GitHub Pages는 공개 기능**입니다. 올렸다고 자동으로 공개되지 않습니다.
- 제출물은 **저장소 URL, 배포 URL, README, 스크린샷**입니다.
- 배포 후에는 **경로, 대소문자, 주소별 저장소, 반영 지연**을 의심하며 **공개 URL에서** 직접 점검합니다.
