# Chapter 7 — 외부 서버 정보가 웹사이트에 나타나는 과정

> 내 포트폴리오에 GitHub 저장소 목록이 카드로 나타납니다. 그런데 이 정보는 내 파일 안에 적혀 있지 않습니다. **내 웹사이트는 GitHub에 있는 데이터를 어떻게 가져올까요?**

**이 장에서 알게 되는 것**

- 브라우저와 GitHub 서버가 **요청과 응답**으로 연결되는 과정

## 요청에서 화면까지

![V07: 내 JavaScript, 브라우저(fetch), GitHub API 세 참여자의 흐름도. 1 로딩 상태를 보여 주고, 2 fetch를 호출하고, 3 브라우저가 HTTP GET 요청을 GitHub API에 보내고, 4 GitHub API가 상태 코드와 JSON으로 응답하고, 5 응답이 JavaScript에 전달되고, 6 확인하고 데이터를 가공하고, 7 상태에 맞는 화면을 그립니다. 아래 상자는 놓치기 쉬운 점 네 가지를 정리합니다.](../assets/v07-github-api-flow.svg)

*교육용 단순화 모델입니다. 실제로는 네트워크 안에서 더 많은 일이 일어납니다.*

### 그림 읽는 법

1. 세 참여자는 **내 코드(JavaScript)**, **요청을 보내는 브라우저(fetch)**, **데이터를 가진 외부 서비스(GitHub API)** 입니다.
2. **①~②**: 요청을 보내기 전에 먼저 **로딩 상태**를 화면에 보여 주고, `fetch`를 호출합니다.
3. **③~④**: 요청은 오른쪽(GitHub)으로, **응답은 다시 왼쪽으로** 돌아옵니다. 응답에는 **상태 코드**와 **JSON 본문**이 담깁니다.
4. **⑤~⑦**: 응답을 받은 JavaScript가 **확인하고, 가공하고, 화면을 그립니다.** ⑦의 결과는 다음 그림(네 가지 상태)에서 이어집니다.
5. 아래 상자는 이 흐름에서 놓치기 쉬운 점입니다. 특히 **응답이 도착했다고 성공은 아닙니다.**

> **브라우저와 외부 서버가 요청과 응답으로 연결되고, 받은 데이터를 JavaScript가 가공해 화면으로 바꿉니다.**

## 요청과 응답이란

[HTTP 요청과 응답](../../../terms/http-request-response.md)은 브라우저(클라이언트)가 요청을 보내고 서버가 결과로 답하는 **웹 통신의 기본 단위**입니다. `[사전]`

- **요청**에는 보통 **방법(method)** 과 **주소**가 들어 있습니다. 데이터를 읽을 때는 `GET`을 씁니다. ([HTTP GET](../../../terms/http-get.md))
- **응답**에는 **상태 코드**와 **본문**이 들어 있습니다. 상태 코드는 처리 결과를 숫자로 알립니다. (200 성공, 404 없음, 403 허용되지 않음 등. [HTTP 상태 코드](../../../terms/http-status-code.md))
- 본문은 보통 [JSON](../../../terms/json.md)이라는 **텍스트 형식**입니다. JavaScript가 객체와 배열로 바꿔 쓸 수 있습니다.

GitHub 저장소 목록을 요청하는 주소는 이런 모양입니다. `[AI 보충]`

```
https://api.github.com/users/사용자이름/repos
```

그러면 이런 모양의 JSON이 돌아옵니다. (일부 항목만 보인 예)

```json
[
  {
    "name": "my-portfolio",
    "description": "자기소개 사이트",
    "html_url": "https://github.com/…",
    "language": "JavaScript",
    "fork": false
  }
]
```

대괄호 `[ ]`는 **여러 개**(배열)를, 중괄호 `{ }`는 **저장소 하나**를 뜻합니다. `description`이나 `language`는 비어 있는 저장소에서 `null`이 올 수 있어서 화면에 쓰기 전에 확인이 필요합니다.

### GitHub API와 fetch는 같은 것이 아닙니다

- **GitHub API** — 데이터를 제공하는 **서비스**입니다.
- **fetch** — 브라우저에서 그 서비스에 **요청을 보내는 도구**입니다.

미션 동료평가에도 "GitHub API와 fetch는 각각 어떤 역할을 하나요?"가 나옵니다. `[공식]`

## 기다림을 다루는 문법: Promise와 async/await

네트워크 요청은 **시간이 걸립니다.** 응답이 오기 전에 다음 줄을 실행해 버리면 아직 없는 데이터를 화면에 쓰게 됩니다. 그래서 JavaScript는 이런 작업을 **나중에 끝나는 일**로 다룹니다.

- [**Promise**](../../../terms/promise.md) — "나중에 결과가 오면 알려 주겠다"는 약속표입니다. `fetch`는 Promise를 돌려줍니다. `[사전]`
- [**async/await**](../../../terms/async-await.md) — 이 약속을 **순서대로 읽히게** 쓰는 문법입니다. `await`는 결과가 올 때까지 **그 함수의 진행**을 잠시 멈춥니다. 브라우저 전체가 멈추는 것이 아니라 다른 일은 계속됩니다. `[사전]`
- **try/catch** — 실패할 때를 대비한 구조입니다. `try` 안에서 문제가 생기면 `catch`로 넘어갑니다. `await`는 실패 처리를 자동으로 해 주지 않습니다. `[사전]` `[공식]`

([비동기 프로그래밍](../../../terms/asynchronous-programming.md)에서 더 깊이 살펴볼 수 있습니다.)

### fetch의 함정: 404·403도 "성공"으로 돌아옵니다

가장 중요한 점입니다. [fetch](../../../terms/fetch-api.md)는 **서버가 응답하기만 하면** 상태가 403이든 404든 **정상적으로 끝난 것처럼** 돌려줍니다. `catch`로 가는 경우는 **응답 자체가 없을 때**(네트워크 끊김 등)입니다. `[사전]`

- **응답이 도착했다 ≠ 요청이 성공했다**입니다.
- 그래서 `response.ok`(또는 `response.status`)를 **직접 확인**해야 합니다.
- 확인하지 않으면 실패 응답의 본문을 성공 데이터처럼 처리해 화면이 이상해집니다.

## 받은 JSON을 카드로: filter와 map

받은 JSON은 **저장소 여러 개의 목록(배열)** 입니다. 화면에 쓰려면 두 가지 일을 합니다. `[시나리오]` (`map`·`filter` 사용은 시나리오 v1.0의 미션 요구 항목입니다.)

- **filter** — **조건에 맞는 것만 남깁니다.** 예: 다른 사람 저장소를 복사해 온 것(`fork`)은 빼기.
- **map** — **하나하나를 다른 모양으로 바꿉니다.** 예: 저장소 데이터 하나를 **카드 하나**로 만들기.

```js
// filter: fork가 아닌 저장소만 남김
const mine = repos.filter((repo) => !repo.fork);

// map: 저장소 하나를 카드(<li>) 하나로 바꿈
const cards = mine.map((repo) => {
  const li = document.createElement('li');
  li.textContent = repo.name;
  return li;
});
```

> **API가 준 글자는 `textContent`로 넣습니다.** `innerHTML`에 문자열로 조합해 넣으면, 그 안의 태그가 **코드로 실행될 수 있습니다.** 이것이 [XSS](../../../terms/xss.md)입니다. 저장소 설명처럼 내가 쓰지 않은 글자는 항상 조심합니다. `[사전]`

## 네 가지 화면 상태

![V07 보조: 로딩, 성공, 오류, 빈 결과 네 가지 화면 상태를 위에서 아래로 비교한 그림. 각 상태마다 아이콘, 언제 나타나는지, 화면 모습, 코드에서의 의미가 있습니다.](../assets/v07-ui-states.svg)

*일반화한 예입니다. 상태 이름과 문구는 프로젝트마다 다를 수 있습니다.*

### 그림 읽는 법

1. 맨 위 상자는 **어떤 상태가 되는지** 정하는 규칙입니다. 요청을 시작하면 로딩, 응답이 정상이면 데이터 개수에 따라 성공 또는 빈 결과, 실패하면 오류입니다.
2. 아래 네 칸은 각 상태를 **아이콘 모양과 테두리 모양**으로 구분합니다. (색만이 아닙니다.)
3. 같은 영역이 **한 번에 하나의 상태만** 보입니다.

### 네 상태의 의미

[UI 상태](../../../terms/ui-state.md)는 **현재 상황에 따라 같은 화면이 다르게 보이는 경우**입니다. `[사전]`

- **로딩** — 요청을 보내고 응답을 기다리는 동안 "불러오는 중"을 보여 줍니다.
- **성공** — 응답이 정상이고 데이터가 1개 이상입니다. `map`으로 카드를 만들어 보여 줍니다.
- **오류** — HTTP 오류(403·404 등)나 네트워크 실패입니다. **무엇이 문제인지와 다음 행동**을 사용자 화면에 알립니다. 콘솔에만 남기면 안 됩니다. `[사전]` `[공식]`
- **빈 결과** — 응답은 정상인데 보여 줄 데이터가 **0개**입니다. 오류와 **다른 문구**로 안내합니다.

### 왜 네 가지를 구분할까?

성공 화면만 만들고 나머지를 같은 빈 화면으로 두면, 사용자는 **고장**과 **데이터 없음**을 구분할 수 없습니다. 또 실패한 뒤에 **이전 성공 카드가 그대로** 남아 있으면 지금 데이터가 정상이라고 **오해**합니다. 그래서 오류나 로딩으로 바뀔 때는 이전 카드를 지웁니다. `[사전]` `[공식]`

## 요청 한도와 403

비로그인(비인증) 상태로 GitHub API를 부르면 **시간당 60회**라는 요청 한도가 있습니다. `[공식]` 이 한도를 넘으면 응답이 `403` 같은 오류로 올 수 있습니다.

- [Rate Limiting](../../../terms/rate-limiting.md)(요청 한도)과 [HTTP 403](../../../terms/http-status-code-403.md)은 **같은 개념이 아닙니다.** 한도가 **원인**이고 403은 **그것이 나타나는 한 방식**일 수 있습니다. `[사전]`
- **403이 곧 권한 문제**인 것도 아닙니다. 상태 코드만 보고 원인을 단정하지 않고, 사용자에게 **이해할 수 있는 안내**("요청 한도에 도달했을 수 있어요. 잠시 후 다시 시도해 주세요")를 보여 주는 것이 좋습니다. `[사전]` `[공식]`
- 한도를 아끼려면 같은 요청을 **자동으로 반복하지 않아야** 합니다. `[공식]`
- GitHub는 응답 머리글(`x-ratelimit-remaining` 등)로 남은 횟수를 알려 줍니다. `[AI 보충]`

> 로그인 정보(토큰)를 쓰면 한도가 늘지만, 그 값을 **프론트 코드에 적어 두면 누구나 볼 수 있습니다.** 이 미션은 비인증 요청을 전제로 합니다. `[AI 보충]`

## 미션이 요구하는 것

- `fetch`와 `async/await`로 GitHub API를 호출하고, **loading·success·error·empty** 상태를 구분한다 `[공식]`
- 응답 확인과 `try/catch`로 실패를 처리하고 상태를 화면에 반영한다 `[공식]`
- 비인증 요청의 시간당 60회 한도와 403을 고려해 실패 시 **오류 상태 UI**를 제공한다 `[공식]`
- `map`·`filter`로 데이터를 가공해 카드로 보여 준다 `[시나리오]`

**동료평가에서 확인하는 점** `[공식]`

- 데이터·로딩·실패·빈 결과가 **서로 구분**되어 보이는가
- 요청 URL, 응답 상태 확인, 데이터 변환, 화면 상태 갱신이 **분리**되어 있는가
- 오류를 콘솔에만 남기지 않고 **화면에** 알리는가

## 💻 요청과 응답을 개발자 도구로 직접 보기

### 응답을 눈으로 확인하기

1. 내 사이트를 연 상태에서 **F12 → Network** 탭을 열고 **새로고침**합니다.
2. 목록 맨 위의 **필터**에서 `Fetch/XHR`을 고르면 `api.github.com` 요청만 보입니다. 하나를 클릭합니다.
3. 오른쪽에서 확인하세요.
   - **Headers**: 요청 주소(`Request URL`), 방법(`GET`), **상태 코드**(`Status Code`)
   - **Preview 또는 Response**: 돌아온 **JSON 본문**
   - **Response Headers**의 `x-ratelimit-remaining`: 남은 요청 횟수

V07의 ③(요청)과 ④(응답)이 눈에 보이는 순간입니다. 그림 속 "상태 코드와 JSON"이 실제로 어떻게 생겼는지 확인하세요.

### 네 가지 상태를 직접 만나 보기

- **로딩**: Network 탭 위쪽의 **Throttling**(속도 제한)을 느린 네트워크(예: Slow 3G 또는 Slow 4G)로 바꾸고 새로고침하면 "불러오는 중" 화면이 오래 보입니다.
- **오류**: Throttling을 **Offline**으로 바꾸고 새로고침하면 요청이 실패해 오류 화면이 나타납니다. 이때 이전 성공 카드가 **남아 있지 않은지**도 보세요.
- **성공**: 원래대로 돌려놓고 새로고침합니다.
- **빈 결과**: 보여 줄 데이터가 없는 상황은 코드를 바꿔야 만들 수 있어서, **복사본에서** 다른 사용자 이름이나 조건으로 시도해 보세요. (원본은 건드리지 않습니다.)

> ⚠️ **요청 한도를 아껴 주세요.** 비인증 요청은 시간당 60회입니다. 새로고침을 반복하면 한도를 쓰게 되니 필요한 만큼만 시도하세요.

- **화면 → 코드**: 카드나 안내 문구를 요소 선택 도구로 클릭하고, 그 요소의 `id`·`class`로 JavaScript를 검색합니다.

### 일반화 예제 — 호출부터 화면까지

> 🔷 **일반화 예제** 구조를 보여 주려고 새로 쓴 코드입니다. 이름은 **가정**이며 **내 프로젝트의 코드가 아닙니다.**

```js
const username = 'octocat';
const url =
  `https://api.github.com/users/${username}/repos`;

const statusBox =
  document.querySelector('#repo-status');
const list =
  document.querySelector('#repo-list');

// 한 번에 하나의 상태만 보여 줌
function setStatus(state, message) {
  statusBox.dataset.state = state;
  statusBox.textContent = message;
  if (state !== 'success') {
    // 이전 카드 지우기
    list.replaceChildren();
  }
```

```js
async function loadRepos() {
  // ① 로딩 상태 먼저
  setStatus('loading', '불러오는 중…');

  try {
    // ② 요청을 보내고 응답을 기다림
    const response = await fetch(url);

    // 403·404도 '도착한 응답'이라
    // 직접 확인해야 함
    if (!response.ok) {
      throw new Error(String(response.status));
    }

    // ⑥ JSON을 풀고 가공
    const repos = await response.json();
    const mine = repos.filter(
      (repo) => !repo.fork);

    // 데이터가 0개면 '빈 결과'
    if (mine.length === 0) {
      setStatus('empty',
        '표시할 저장소가 없습니다.');
      return;
    }

    // map: 데이터 하나를 카드 하나로
    const cards = mine.map((repo) => {
      const li = document.createElement('li');
      li.textContent = repo.name;
      return li;
    });

    // ⑦ 카드를 그리고 '성공' 상태로
    list.replaceChildren(...cards);
    setStatus('success', '');
  } catch (error) {
    // 403이면 요청 한도를 안내
    const limited = error.message === '403';
    setStatus('error', limited
      ? '요청 한도에 도달했을 수 있어요.'
      : '불러오지 못했어요.');
  }
}

loadRepos();
```

이 코드는 이렇게 읽습니다.

- `setStatus` — **상태 하나를 정하고 화면에 반영**합니다. 로딩·오류·빈 결과일 때는 이전 카드를 지웁니다.
- `await fetch(url)` — V07의 ②~⑤입니다. 응답이 올 때까지 이 함수가 기다립니다.
- `if (!response.ok) { throw … }` — **응답 확인**입니다. 실패 응답을 `catch`로 보내 오류 상태로 만듭니다.
- `await response.json()` — 본문을 읽어 풀어내는 것도 **기다려야 하는 일**입니다.
- `filter` → 길이 확인 → `map` — **가공**입니다. 빈 결과는 여기서 갈립니다.
- `catch` — 네트워크 실패와 위에서 던진 오류를 **한곳에서** 받습니다. 403이면 한도 안내 문구를 씁니다.
- `textContent`로 글자를 넣어 API가 준 문자열이 코드로 실행되지 않게 합니다.

### 구현 상태 점검 `[공식]`

- `fetch`와 `async/await`를 쓴다
- 응답 상태(`response.ok` 또는 `status`)를 확인한다
- `try/catch`로 실패를 처리한다
- 로딩·성공·오류·빈 결과가 **서로 다른 화면**으로 나타난다
- 오류를 **사용자 화면**에 보여 준다 (콘솔에만 남기지 않음)
- 실패 뒤에 이전 성공 카드가 남아 있지 않다
- 같은 요청을 자동으로 반복하지 않는다

## 동료평가에서는 이런 질문이 나옵니다

**동료평가에서 받을 수 있는 질문** `[공식]`

- GitHub API와 `fetch`는 M01에서 각각 어떤 역할을 하나요?
- `fetch`가 네트워크 요청 자체라면 `async/await`는 이 요청의 무엇을 읽기 쉽게 하나요?
- API가 실패했는데 이전 결과가 그대로 보이면 사용자는 무엇을 오해할 수 있나요?
- 403을 받았을 때 권한 부족 외에 API 요청 한도도 점검해야 하는 이유는 무엇인가요?
- Rate Limit과 HTTP 403은 왜 같은 개념이 아니면서 함께 나타날 수 있나요?

**이렇게 설명할 수 있습니다** (예시이며, 내 사이트의 실제 이름으로 바꿔 말하면 됩니다)

> `fetch`가 브라우저에서 GitHub API에 GET 요청을 보내고, GitHub API는 상태 코드와 JSON으로 응답합니다. `await`로 응답을 기다린 뒤 `response.ok`로 성공 여부를 확인합니다. 403·404도 도착한 응답이라 `fetch`가 실패로 처리하지 않기 때문입니다. 실패하면 `catch`에서 오류 상태로 바꿔 화면에 안내하고, 성공하면 JSON을 `filter`와 `map`으로 가공해 카드로 그립니다. 데이터가 0개면 빈 결과로, 요청 중에는 로딩으로 구분해 보여 줍니다. 비인증 요청은 시간당 60회 한도가 있어 403이 올 수 있으므로 그 경우 한도 안내 문구를 보여 줍니다.

**자주 하는 실수** `[공식]`

- 성공 화면만 만들고 오류·빈 상태가 없음 → Offline 실험, 데이터 없음 상황 확인
- 응답이 성공했다고 가정하고 HTTP 오류나 빈 배열을 처리하지 않음 → `response.ok`와 길이 확인 코드 찾기
- 403을 무조건 권한 오류로만 표시하거나 요청을 자동 반복함 → 403 처리 문구, 반복 호출 여부 확인
- 오류를 콘솔에만 남김 → 오류 상황에서 화면에 안내가 보이는지

## 핵심 내용 정리

- 브라우저의 `fetch`가 GitHub API에 **요청**을 보내고, GitHub는 **상태 코드와 JSON**으로 **응답**합니다.
- **응답이 도착했다고 성공은 아닙니다.** `response.ok`를 확인하고, 네트워크 실패는 `catch`로 받습니다.
- 데이터는 `filter`·`map`으로 가공하고, 화면은 **로딩·성공·오류·빈 결과** 중 하나로 보여 줍니다.
- 비인증 요청은 **시간당 60회** 한도가 있고, 한도 초과가 403으로 나타날 수 있습니다.
