# Chapter 4 — 버튼을 누르면 화면은 어떻게 바뀔까?

> 모바일에서 ☰ 버튼을 누르면 메뉴가 열립니다. 페이지가 새로 로드되는 것도 아닌데 화면이 바뀌죠. **버튼을 눌렀다는 사실을 JavaScript는 어떻게 알고 반응할까요?**

**이 장에서 알게 되는 것**

- 클릭에서 화면 변경까지의 **흐름**(이벤트 → handler → 변경 → 화면)
- 바뀌는 것은 HTML 파일이 아니라 **DOM**이라는 점
- 내 프로젝트의 기능 하나를 **코드까지 추적하는 방법**

📱 앞부분(그림까지)만 읽어도 핵심을 알 수 있습니다. 💻 뒤쪽은 컴퓨터 앞에서 내 프로젝트를 열고 읽으면 좋습니다.

> **V04는 햄버거 메뉴(class를 붙이고 떼는 방식)의 대표 실행 흐름**입니다. 다른 기능은 같은 원리를 따르지만 차이가 있고, 그 차이도 함께 설명합니다. 내 프로젝트의 구현 방식은 그림과 다를 수 있습니다.
>
> 표기 규칙(`[공식]` `[시나리오]` `[사전]` `[권장]` `[AI 보충]`)은 [README](../README.md#표기-규칙)를 참고하세요.

## 클릭했다는 걸 JavaScript는 어떻게 알까?

> **사용자가 버튼을 클릭했다는 사실을 JavaScript는 어떻게 알고 반응할까?** `[시나리오]`

"JavaScript가 계속 화면을 지켜보고 있다가 눌리면 반응하겠지"라고 생각하기 쉽습니다. 실제로는 다릅니다. **페이지가 열릴 때 "이 버튼에서 click이 오면 이 함수를 불러 주세요"라고 브라우저에 미리 등록**해 두고, 눌리는 순간에는 **브라우저가 그 함수를 불러 줍니다.**

이 "미리 등록"과 "누를 때마다 실행"을 나눠 보는 것이 이 장의 핵심입니다.

## 클릭에서 화면 변경까지

![V04(햄버거 메뉴의 대표 흐름): 사용자, 브라우저, 내 JavaScript, DOM 네 참여자가 세로선으로 있고, 준비 단계(점선 화살표로 이벤트 등록)와 번호 순서의 실행 단계(1 클릭, 2 이벤트로 핸들러 호출, 3 상태 결정, 4 DOM 변경, 5 브라우저가 화면 다시 그림, 6 사용자가 결과를 봄)를 보여 주는 흐름도. 아래 상자는 이 그림이 햄버거 메뉴의 대표 흐름임을 밝히고, 맨 위로(스크롤 위치 변경)·섹션 등장(화면에 들어옴)·브라우저 기본 동작·이벤트 위임과의 차이를 요약합니다.](../assets/v04-event-dom-flow.svg)

*교육용 단순화 모델입니다. 실제 브라우저 내부에는 이벤트 큐 등 더 많은 단계가 있습니다. 예시는 모바일 햄버거 메뉴입니다.*

### 그림 읽는 법

1. 위쪽 네 칸은 **누가 일하는지**입니다. 사용자 / 브라우저 / 내 JavaScript / DOM.
2. **⓪ 점선 화살표**(준비): 페이지가 열릴 때 **한 번** 일어납니다. "이 버튼에서 click이 오면 이 함수를 불러 달라"고 등록합니다.
3. **① → ⑥ 실선 화살표**(실행): 번호 순서대로 **누를 때마다** 일어납니다.
4. 화살표의 **방향**을 따라가 보세요. ⑤는 DOM에서 브라우저로, ⑥은 브라우저에서 사용자 쪽으로 돌아옵니다. **결과가 눈으로 돌아오는 것**입니다.
5. 아래 상자는 다른 기능과 이 틀이 **어디서 달라지는지** 알려 줍니다.

점선(준비·연결)과 실선(순서)을 다른 선으로 그린 이유는 구조와 순서를 섞지 않기 위해서입니다. 점선은 "미리 연결해 둠", 실선은 "그 연결 덕분에 시간이 흐르며 일어나는 일"입니다.

> **HTML이 요소를 준비하고, JavaScript가 이벤트를 받아 DOM을 바꾸고, CSS와 브라우저가 그 결과를 화면으로 보여 주며, 이 셋이 이벤트 하나를 중심으로 협력합니다.**

## 준비와 실행: 이벤트, 핸들러, addEventListener

- [**사용자 이벤트**](../../../terms/user-event.md) — 사람이 클릭·입력·스크롤할 때 브라우저가 만드는 **신호**입니다. (`click`, `scroll`)
- [**이벤트 핸들러**](../../../terms/event-handler.md) — 그 신호가 왔을 때 실행하려고 **등록해 둔 함수**입니다. ("메뉴를 열어라")
- [**addEventListener**](../../../terms/add-event-listener.md) — "이 요소에서 이 신호가 오면 이 함수를 불러 달라"고 **등록**하는 방법입니다. 페이지가 열릴 때 한 번 실행됩니다.

`[사전]` 사전 정의를 줄인 것입니다.

이 흐름은 **실행 순서**입니다. 화살표 방향대로 시간이 흐릅니다. (2장의 "대응 선", 1장의 "불러옴 선"과 종류가 다릅니다.) `[AI 보충]`

- 사용자 행동 → **Event**: 사람의 클릭을 브라우저가 "click 사건"이라는 **신호**로 만듭니다.
- Event → **Handler**: 그 신호를 기다리던 **함수**가 불려 나옵니다. (미리 등록되어 있어야 함)
- Handler → **상태·DOM**: 함수가 "지금 상황"과 "문서 구조"를 바꿉니다.
- DOM → **화면**: 브라우저가 바뀐 구조와 CSS로 화면을 다시 그립니다.

> **defer와의 연결 (1장)** 등록하려면 버튼이 **이미 있어야** 합니다. JavaScript를 `defer`로 연결하면 HTML을 다 읽은 뒤에 실행되어, 코드가 버튼을 **찾을 수 있습니다.**

## 바뀌는 것은 HTML 파일이 아니라 DOM

[DOM](../../../terms/dom.md)은 브라우저가 HTML을 읽어 메모리에 만든 **문서의 객체 구조**이고, JavaScript가 문서를 읽고 바꾸는 통로입니다. `[사전]`

- **HTML 소스 파일** — 내가 쓴(또는 AI가 쓴) 텍스트 파일. 버튼을 눌러도 **그대로**입니다.
- **DOM** — 브라우저가 메모리에 만든 문서 구조. 버튼을 누르면 **바뀝니다.** (클래스 추가, 글자 변경 등)

코드에서 요소를 찾을 때는 `document.querySelector('.menu-toggle')`처럼 **CSS 선택자**와 같은 규칙으로 이름을 지정합니다. `[사전]` `[AI 보충]`

그래서 "HTML 파일을 다시 열지 않았는데 화면이 바뀌는 이유"는 **DOM이 바뀌었기 때문**입니다. (아래 "클릭하는 순간의 변화 직접 보기"에서 눈으로 볼 수 있습니다.)

## "상태"는 어디에 있을까?

[상태 변경](../../../terms/state-change.md)은 **프로그램이 기억하는 값이 바뀌는 일**입니다. `[사전]` 메뉴라면 "지금 **열려 있다 / 닫혀 있다**"가 상태입니다.

**상태가 꼭 JavaScript 변수 안에 있는 것은 아닙니다.** 이 미션 수준의 코드에서는 **HTML 요소의 class나 속성이 곧 상태**인 경우가 많습니다.

- 요소의 **class** — 메뉴에 `is-open`이 있으면 열림
- 요소의 **속성** — 버튼의 `aria-expanded="true"`, 메뉴의 `hidden` 속성 있음/없음
- JavaScript **변수** — `let isLoading = true` (7장에서 자주 만남)

메뉴 상태를 표현하는 방식은 **프로젝트마다 다릅니다.** `is-open` 같은 class, `hidden` 속성, `aria-expanded` 등을 단독으로 또는 함께 씁니다. 이 장의 예시는 class 방식입니다. `[AI 보충]`

그래서 V04의 ③ "새 상태를 정한다"와 ④ "DOM을 바꾼다"는 코드 한 줄에 **함께** 일어나기도 합니다. (`classList.toggle`이 그 예입니다.) 그림에서는 이해를 돕기 위해 **나눠 그렸습니다.**

### 모양은 누가 바꿀까: JavaScript는 스위치, CSS는 모양

JavaScript가 메뉴에 `is-open` 클래스를 붙이면(이 장의 예시 방식), **CSS에 미리 써 둔 `.is-open` 규칙이** 메뉴를 보이게 합니다. (`hidden` 속성을 켜고 끄는 방식이면 브라우저 기본 규칙이나 CSS가 그 속성을 읽어 숨깁니다.)

- **JavaScript** — **언제** 바꿀지 판단하고 **스위치(클래스)** 를 켭니다.
- **CSS** — 스위치가 켜졌을 때 **어떻게 보일지** 정합니다.
- **브라우저** — DOM과 CSS를 합쳐 화면을 다시 그립니다. ([브라우저 렌더링](../../../terms/browser-rendering.md))

"모양을 고치고 싶다 → CSS", "언제 열릴지 고치고 싶다 → JavaScript"라는 기능 찾기의 규칙이 여기서 나옵니다. 1장의 역할 구분이 그대로 이어집니다. `[AI 보충]`

## 기능마다 같은 원리, 다른 변화

미션은 사용자 행동이 화면 변화로 이어지는 기능을 **최소 세 가지** 요구합니다. `[공식]` 대표적인 세 가지를 V04의 번호에 맞춰 봅니다. (일반화한 예입니다. `[AI 보충]`)

**☰ 햄버거 메뉴**

- ① ☰ 버튼을 **클릭** → ② click handler 호출
- ③ 메뉴가 지금 열려 있나? → 반대로
- ④ (이 예시) 메뉴 요소의 `is-open` 클래스, 버튼의 `aria-expanded`. 방식은 프로젝트마다 다릅니다.
- ⑤ CSS의 `.is-open` 규칙이 메뉴를 보이게 함

**↑ 맨 위로 버튼**

- ① ↑ 버튼을 **클릭** → ② click handler 호출
- ③ 판단은 거의 없음
- ④ **스크롤 위치**를 맨 위로 (`window.scrollTo`) — DOM 구조는 그대로입니다.
- ⑤ 브라우저가 맨 위로 이동시킴

**섹션 등장 애니메이션**

- ① 섹션이 **화면에 들어옴** → ② Intersection Observer의 콜백 호출
- ③ 화면에 들어왔나? (`isIntersecting`)
- ④ 섹션에 `is-revealed` 클래스 추가
- ⑤ CSS의 투명도·이동 전환(transition)으로 서서히 나타남

### 변화의 종류를 구분하기

세 기능은 "이벤트 → handler → 변화 → 화면"이라는 **공통 원리**를 따르지만, ④에서 일어나는 **변화의 종류**가 다릅니다.

- **DOM이 바뀜**(class·속성·글자) — 메뉴 열기(`is-open`), 섹션 등장(`is-revealed`), 스크롤에 따라 버튼 보이기(`is-visible`). Elements 패널에서 속성이 바뀌는 모습으로 확인합니다.
- **스크롤 위치가 바뀜**(DOM은 그대로) — 맨 위로(`window.scrollTo`), 메뉴 링크의 부드러운 이동. 페이지가 움직일 뿐 Elements의 요소는 그대로입니다.
- **브라우저 기본 동작·CSS가 처리** — `<a href="#…">` 이동, `<details>`, `scroll-behavior: smooth`. JavaScript에서 해당 handler를 찾기 어렵습니다.

> 정직하게 짚어 둘 점: **V04의 ④ "DOM을 바꾼다"는 햄버거 메뉴 기준입니다.** "맨 위로"는 문서 구조가 아니라 스크롤 위치를 바꿉니다. 그래도 사용자가 한 행동이 handler를 거쳐 화면 변화로 이어진다는 큰 흐름은 같습니다.

### 클릭이 아닌 계기: 스크롤과 Intersection Observer

- **클릭** — `click` 이벤트. ☰ 메뉴, 맨 위로 버튼
- **스크롤** — `scroll` 이벤트. 맨 위로 버튼 보이기/숨기기, 메뉴 줄 모양 변화
- **요소가 화면에 들어옴** — [Intersection Observer](../../../terms/intersection-observer-api.md). 섹션이 보일 때 나타나는 애니메이션

Intersection Observer는 "요소가 화면에 들어오거나 나가는 시점"을 브라우저가 **알려 주는** 기능입니다. 코드가 스크롤 위치를 매번 계산하지 않아도 됩니다. `[사전]` 클릭 이벤트는 아니지만 **"브라우저가 알려 주면 함수가 실행된다"는 흐름은 같습니다.** V04에서 ①이 "클릭" 대신 "화면에 들어옴"으로 바뀐다고 생각하면 됩니다.

## 버튼에 직접 연결되지 않은 경우 `[AI 보충]`

V04는 "버튼에 직접 등록한 handler"를 그린 **대표 흐름**입니다. 실제 프로젝트에는 이런 경우도 있습니다.

- **이벤트 위임** — 버튼이 아니라 **부모 요소**(`nav`, `body`, `document`)에 리스너 하나를 달고, "클릭된 곳이 어디인가(`event.target`)"를 보고 처리합니다. ⓪의 등록 위치와 ②에서 불리는 곳이 부모일 뿐 ③~⑥은 같습니다.
- **브라우저 기본 동작** — `<a href="#projects">` 클릭 시 해당 위치로 이동, `<details>`·`<summary>`는 JavaScript 없이 열고 닫힘, 폼 제출. ⓪~③이 없거나 줄어듭니다.
- **CSS가 맡는 변화** — `scroll-behavior: smooth`로 부드러운 이동. JavaScript 이벤트 없이 CSS 규칙이 영향을 줍니다. [부드러운 스크롤](../../../terms/smooth-scroll.md) `[사전]`

이벤트 위임이 가능한 것은 자식의 클릭이 부모에게도 전달되는 **이벤트 전파** 덕분입니다. ([이벤트 전파](../../../terms/event-propagation.md)) `[사전]`

> 그래서 **버튼 줄에 `addEventListener`가 안 보이면 "기능이 없다"가 아니라 "다른 곳에서 처리하고 있다"** 일 수 있습니다. 부모 요소와 `document`, 그리고 JavaScript 밖(HTML 속성·CSS)까지 살펴보세요.

### `onclick`이 아니라 `addEventListener`인 이유

- `<button onclick="…">`(inline)는 동작을 **HTML 안**에 적습니다. 파일 역할이 섞이고, 한 버튼에 동작을 여러 개 붙이기 어렵습니다. 이 미션에서는 쓰지 않습니다. `[공식]`
- `addEventListener`는 동작을 **JavaScript 파일**에 적습니다. 파일 역할 분리가 유지되고 한 버튼에 동작을 여러 개 붙이기 쉽습니다. 이 미션에서 쓰는 방식입니다. `[공식]`

`[사전]` 구조(HTML)와 동작(JavaScript)을 분리하기 위한 것입니다.

> 더 알아보기: [이벤트 전파](../../../terms/event-propagation.md)(자식의 클릭이 부모에게도 전달되는 흐름), [preventDefault](../../../terms/prevent-default.md)(링크 이동·폼 제출 같은 기본 동작을 막기. 6장에서 만납니다.)

- 햄버거 메뉴, 부드러운 스크롤, 스크롤 탑(맨 위로), 스크롤에 따른 내비게이션 변화, Intersection Observer 애니메이션을 제공한다 `[공식]`

- `var` 대신 `const`/`let`, inline style 없이 구현한다 `[공식]`

## 💻 클릭하는 순간의 변화 직접 보기

### 화면은 바뀌는데 파일은 그대로다

1. 내 사이트에서 ☰ 버튼을 **누르기 전에** **F12**로 개발자 도구를 열고, 왼쪽 위 화살표 버튼(`Ctrl+Shift+C`)으로 **메뉴 목록**을 클릭해 선택합니다. **Elements** 패널에서 그 줄의 **태그 안 속성 전체**(`class="…"`, `hidden`, `aria-expanded="…"` 등)를 봐 둡니다.
2. ☰ 버튼을 **누르고** 같은 줄을 다시 보면 속성이 바뀌어 있습니다. (브라우저에 따라 바뀐 줄이 잠깐 강조됩니다.)
3. 이번에는 **`Ctrl + U`**(페이지 소스 보기)로 원본 HTML을 열어 같은 메뉴를 찾아봅니다. 거기에는 **누른 뒤의 변화가 없습니다.**

Elements에서는 바뀌었는데 원본 HTML은 그대로입니다. 바뀐 것은 파일이 아니라 **브라우저가 메모리에 만든 문서 구조(DOM)** 라는 것이 눈에 보입니다. `[사전]`

> 💡 **class가 안 바뀌어도 이상한 것이 아닙니다.** 프로젝트에 따라 `hidden` 속성이 사라지거나, 버튼의 `aria-expanded`가 바뀌거나, 부모 요소의 class가 바뀔 수 있습니다. 메뉴 요소에서 변화가 안 보이면 **버튼·부모(`header`, `body`)** 도 눌러 보며 찾아보세요.

### 이 버튼에는 어떤 코드가 연결되어 있을까 (Chrome 기준)

1. Elements 패널에서 ☰ 버튼 줄을 선택합니다.
2. 오른쪽 아래 패널 탭에서 **Event Listeners**를 고릅니다. (안 보이면 `»`를 눌러 펼칩니다.)
3. 목록에서 **`click`**을 펼치면 오른쪽에 `main.js:12` 같은 **파일과 줄 번호**가 나옵니다. 클릭하면 그 코드로 이동합니다.

이것이 이번 장 전체의 **핵심 기술**입니다. 화면의 버튼에서 출발해 그 버튼에 연결된 코드를 **직접** 찾는 방법입니다.

> **목록에 `click`이 안 보이면** 이상한 것이 아닙니다.
> 1. 오른쪽 패널의 **Ancestors**(조상) 체크 표시를 켜 보세요. 버튼의 **부모 요소**에 `click` 리스너가 달려 있으면(이벤트 위임) 이때 보입니다.
> 2. 그래도 없으면 JavaScript 없이 **브라우저의 기본 동작**이나 CSS가 하는 기능일 수 있습니다.

## 내 프로젝트에서 기능 하나를 코드까지 추적하기

> 코드를 **한 줄씩 이해하려 하지 마세요.** 목표는 "이 기능의 ⓪ 등록 줄, ③④ 핸들러, ⑤ CSS 규칙이 **어디 있는지**" 찾는 것입니다.

### 가장 중요한 방법: "이름의 고리"를 따라가기

한 기능은 보통 **같은 이름**이 세 파일에 나옵니다. 그 이름을 검색으로 따라갑니다. `[AI 보충]`

```
HTML  <button class="menu-toggle">
        ↑ 화면의 버튼을 만듦
JS    document.querySelector(
        '.menu-toggle')
        ↑ 그 버튼을 찾아 이벤트 등록
CSS   .menu-toggle { … }
        ↑ 그 버튼의 모양
```

따라가는 순서는 이렇습니다.

1. **화면의 버튼 → HTML**: 요소 선택 도구로 버튼을 클릭하고 Elements에서 `class`·`id`를 확인합니다.
2. **그 이름 → JavaScript**: 편집기에서 그 이름을 검색(`Ctrl+Shift+F`)합니다. `querySelector(…)`가 나오는 줄이 목표입니다.
3. **거기서 `addEventListener` 찾기**: 같은 줄 근처이거나, 위의 Event Listeners 탭이 알려 주는 줄입니다. **버튼에 없으면** 부모 요소·`document`에 달린 리스너(`event.target`·`closest(`가 보이면 이벤트 위임)나 브라우저 기본 동작을 의심합니다.
4. **핸들러 안의 `classList`·`setAttribute`·`scrollTo`…**: **무엇을 바꾸는지** 확인합니다.
5. **바뀌는 class·속성 → CSS**: 검색해서 `.is-open { … }` 같은 규칙, 또는 `[hidden]`·`[aria-expanded]` 같은 속성 규칙을 찾습니다.

### 일반화 예제 — 기능 3개의 코드 모양

> 🔷 **일반화 예제** 개념을 보여 주려고 새로 쓴 코드입니다. 클래스 이름은 **가정**이며 **내 프로젝트의 코드가 아닙니다.** 모양이 비슷한 부분을 내 코드에서 찾아 비교하세요.
>
> **읽는 요령** — `const 이름 = …`: 이름에 값을 붙임(바꾸지 않을 값). `() => { … }`: "함수 만들기"이며 `{ }` 안이 **일어날 일**. `//`로 시작하는 줄은 설명(주석)입니다.

**① 햄버거 메뉴**

```html
<button class="menu-toggle"
        aria-expanded="false"
        aria-controls="site-menu">
  메뉴
</button>
<nav id="site-menu" class="site-menu">
  …
</nav>
```

```js
// 버튼과 메뉴 찾기
const menuToggle =
  document.querySelector('.menu-toggle');
const siteMenu =
  document.querySelector('#site-menu');

// ⓪ click이 오면 아래 함수를 불러 달라고 등록
menuToggle.addEventListener('click', () => {
  // ③④ is-open 클래스를 넣었다 뺐다
  // 결과(지금 열림?)는 true/false
  const isOpen =
    siteMenu.classList.toggle('is-open');
  // 버튼의 '열림' 상태도 함께 알림
  menuToggle.setAttribute(
    'aria-expanded', String(isOpen));
});
```

```css
.site-menu { display: none; }

/* ⑤ 이 규칙이 켜지면 메뉴가 보임 */
.site-menu.is-open { display: block; }
```

> **같은 기능의 다른 구현 (참고)** 내 프로젝트가 아래처럼 만들어졌다면 `is-open`이 **없습니다.** 그래도 V04의 틀은 같습니다.
>
> ```js
> // 방식 B: hidden 속성을 켜고 끔
> menuToggle.addEventListener('click', () => {
>   siteMenu.hidden = !siteMenu.hidden;
>   menuToggle.setAttribute(
>     'aria-expanded', String(!siteMenu.hidden));
> });
>
> // 방식 C: 이벤트 위임
> // (버튼이 아니라 document에 등록)
> document.addEventListener('click', (event) => {
>   // 클릭된 곳이 메뉴 버튼(또는 그 안쪽)인가?
>   const button =
>     event.target.closest('.menu-toggle');
>   if (button) {
>     // 여기서 메뉴를 열고 닫음
>   }
> });
> ```

> **3장 "메뉴를 연 채 넓혀 보기"의 힌트** 위처럼 `.site-menu.is-open`(클래스 두 개)이 3장의 `@media` 안 `.site-menu`(클래스 한 개)보다 **더 구체적인 규칙**이면 이길 수 있어, 넓은 폭에서도 세로 메뉴가 남을 수 있습니다. 내 프로젝트가 그런지는 **직접 확인**해 보세요. 그렇지 않은 구조일 수도 있습니다.

**② 맨 위로 버튼**

```js
const toTopButton =
  document.querySelector('.to-top');

// ⓪ 등록
toTopButton.addEventListener('click', () => {
  // ④ 스크롤 위치를 맨 위로, 부드럽게
  window.scrollTo({
    top: 0,
    behavior: 'smooth'
  });
});

// 스크롤할 때마다 호출되는 또 하나의 이벤트
window.addEventListener('scroll', () => {
  // 400px 넘게 내려오면 버튼 보이기
  toTopButton.classList.toggle(
    'is-visible', window.scrollY > 400);
});
```

**③ 섹션 등장 애니메이션 (Intersection Observer)**

```js
// 요소가 화면에 들어오거나 나갈 때
// 불리는 함수를 만듦
const observer = new IntersectionObserver(
  (entries) => {
    entries.forEach((entry) => {
      // 화면에 들어왔다면
      if (entry.isIntersecting) {
        // ④ 클래스를 붙이고
        entry.target.classList
          .add('is-revealed');
        // 한 번만 보이면 되니 관찰을 멈춤
        observer.unobserve(entry.target);
      }
    });
  },
  // 요소의 20%가 보이면
  { threshold: 0.2 }
);

// ⓪ 이 요소들을 관찰 대상으로 등록
document.querySelectorAll('.reveal')
  .forEach((section) => {
    observer.observe(section);
  });
```

```css
.reveal {
  opacity: 0;
  transform: translateY(16px);
  transition: opacity .4s, transform .4s;
}

/* ⑤ 이 규칙이 켜지면 서서히 나타남 */
.reveal.is-revealed {
  opacity: 1;
  transform: none;
}
```

### 내 프로젝트의 기능 세 가지를 추적해 보기

위의 틀로 내 프로젝트의 기능 세 가지를 같은 순서로 따라가 보세요. 기능마다 이 다섯 가지를 찾으면 됩니다.

- ① 계기 — 어떤 요소에서 어떤 이벤트가 오는가
- ⓪ 등록하는 줄 — `addEventListener` / `observe`가 있는 파일과 줄, 그리고 **등록된 요소**(버튼? 부모? 없음?)
- ③④ 핸들러가 바꾸는 것 — class? 속성? 스크롤? 기본 동작?
- ⑤ 화면을 바꾸는 CSS 규칙 — 파일과 줄

### 구현 상태 점검 `[공식]`

- 사용자 행동이 화면 변화로 이어지는 기능이 **3개 이상**이다
- 이벤트는 `addEventListener`로 연결했다 (`addEventListener` 검색)
- inline `onclick`을 쓰지 않았다 (HTML에서 `onclick=` 검색)
- `var`를 쓰지 않고 `const`/`let`을 썼다 (`var ` 검색)
- Intersection Observer를 쓴다 (`IntersectionObserver` 검색)
- JavaScript를 `defer`로 연결했다 (`index.html`의 `<script` 확인)
- JavaScript가 `.style.…`로 스타일을 직접 건드리는 곳이 있는지 확인한다 (`.style.` 검색)

> ⚠️ **검토 필요** 미션의 "inline style 없이" 요구가 **JavaScript가 `.style`로 값을 넣는 것까지** 포함하는지는 이 저장소의 자료만으로 단정할 수 없습니다. 클래스를 붙이고 떼는 방식은 이 문제를 피합니다. 원문 또는 운영진에게 확인하세요.

### 오류를 만났을 때: 가장 흔한 것 하나

개발자 도구의 **Console** 탭에 빨간 글씨로 이런 오류가 나올 수 있습니다.

```
Uncaught TypeError:
Cannot read properties of null
(reading 'addEventListener')
```

번역하면 **"찾으려던 요소가 없다(null)"** 입니다. 의심할 곳은 세 가지입니다. `[사전]`

- **이름 오타** (`.menu-toggle` ↔ `.menu-togle`) → HTML의 class와 JS의 이름을 **글자 단위로** 비교
- **`defer` 누락** (HTML을 다 읽기 전에 실행) → `index.html`의 `<script` 줄
- **그 페이지에 요소가 아예 없음** → Elements에서 검색

반대로 "한 번 눌렀는데 두 번 동작한다(열렸다 바로 닫힘)"면 **같은 리스너가 두 번 등록**되었을 수 있습니다. `[사전]`

## AI와 함께 기능을 추적하는 법

> 1장의 네 가지 규칙(**수정하지 말고 설명만 / 파일·줄 번호 / 내 화면과 연결 / 답은 가설**)을 그대로 적용합니다.

> **기능 하나를 끝까지 추적**
> 화면의 **[☰ 메뉴 버튼]**을 누르면 일어나는 일을 코드 기준으로 단계별로 추적해 줘. ① 버튼이 있는 HTML 줄, ② `addEventListener`로 등록하는 줄(**버튼에 직접인지, 부모에 달린 이벤트 위임인지, 아니면 브라우저 기본 동작인지도 구분해서**), ③ 핸들러가 하는 일, ④ DOM에서 바뀌는 것(class·속성), ⑤ 그 변화로 화면을 바꾸는 CSS 규칙 — 각각 **파일 이름과 줄 번호**와 함께 알려 줘. 초보자가 이해할 수 있게 쓰고, **코드는 수정하지 마.**

> **이벤트 지도**
> 이 프로젝트의 모든 `addEventListener`와 `IntersectionObserver` 사용 위치를 표로 정리해 줘. 열은 **대상 요소 / 이벤트 종류 / 하는 일 / 파일:줄**. 사용자 행동이 화면 변화로 이어지는 기능이 몇 개인지도 세어 줘. 수정은 하지 마.

> **상태 찾기**
> 이 프로젝트의 JavaScript에서 "상태"라고 부를 수 있는 것(변수 값, class, 속성)을 찾아서, 각각 **어떤 기능의 상태**이고 **어느 코드가 바꾸는지** 설명해 줘. 변수에만 있는 상태와 HTML 요소의 class/속성에 있는 상태를 구분해 줘.

> **미션 제약 점검**
> 이 프로젝트에 inline `onclick`, `var`, JavaScript의 `.style` 직접 사용이 있는지 검색해서 **검색한 패턴과 결과(파일:줄)** 를 알려 줘. 없으면 "없다"고 근거와 함께 말해 줘. 수정하지 마.

> **오류 원인 후보**
> 개발자 도구 Console에 이 오류가 나와: `(오류 메시지를 그대로 붙여넣기)`. 이 프로젝트 코드 기준으로 **원인 후보**를 가능성이 높은 순서로 알려 줘. 고치지는 말고, 내가 직접 확인할 방법을 알려 줘.

| AI가 말한 것 | 내가 확인할 것 |

## 핵심 내용 정리

- JavaScript는 지켜보는 것이 아니라, **미리 등록해 둔 함수가 이벤트가 올 때 호출**됩니다. (⓪ 준비 → ①~⑥ 실행)
- 클릭하면 바뀌는 것은 HTML 파일이 아니라 **DOM**이고, 모양은 **CSS 규칙**이 정합니다.
- 기능마다 변화의 종류가 다릅니다. DOM이 바뀌기도 하고, 스크롤 위치가 바뀌기도 하고, 브라우저 기본 동작이 맡기도 합니다.
- 기능을 찾을 때는 **화면 → 요소의 class/id → JavaScript 검색 → CSS 검색** 순서로 이름의 고리를 따라갑니다.
