## 3. 선 — 개념의 역할과 연결 관계

```
사용자 행동 → Event → Handler → 상태 또는 DOM 변경 → 화면 업데이트
```

### 3-1. 이 선은 무슨 뜻일까?

이번 선은 **실행 순서**입니다. 화살표 방향대로 시간이 흐릅니다. (2장의 "대응 선", 1장의 "불러옴 선"과 종류가 다릅니다.) `[AI 보충]`

| 연결 | 관계의 종류 | 쉬운 말 |
| --- | --- | --- |
| 사용자 행동 → Event | **신호화** | 사람의 클릭을 브라우저가 "click 사건"이라는 **신호**로 만듭니다 |
| Event → Handler | **호출** | 그 신호를 기다리던 **함수**가 불려 나옵니다 (미리 등록되어 있어야 함) |
| Handler → 상태·DOM | **변경** | 함수가 "지금 상황"과 "문서 구조"를 바꿉니다 |
| DOM → 화면 | **반영** | 브라우저가 바뀐 구조와 CSS로 화면을 다시 그립니다 |

### 3-2. 이벤트와 핸들러 — "준비"와 "실행"을 나눠 보기

| 용어 | 한 문장 | 이 장에서는 |
| --- | --- | --- |
| [사용자 이벤트](../../../terms/user-event.md) | 사람이 클릭·입력·스크롤할 때 브라우저가 만드는 **신호** | `click`, `scroll` |
| [이벤트 핸들러](../../../terms/event-handler.md) | 그 신호가 왔을 때 실행하려고 **등록해 둔 함수** | "메뉴를 열어라" |
| [addEventListener](../../../terms/add-event-listener.md) | "이 요소에서 이 신호가 오면 이 함수를 불러 달라"고 **등록**하는 방법 | 페이지가 열릴 때 한 번 실행 |

`[사전]` 위 한 문장은 사전 정의를 줄인 것입니다.

JavaScript는 누르지 않을 때 **계속 지켜보며 돌고 있는 것이 아닙니다.** 페이지가 열릴 때 **"이 버튼에서 click이 오면 이 함수를 불러 주세요"** 라고 브라우저에 **한 번 등록**해 두고, 이후는 브라우저가 신호가 올 때 함수를 부릅니다. 그래서 V04에는 **⓪ 준비**(한 번)와 **①~⑥ 실행**(누를 때마다)이 따로 있습니다. `[AI 보충]`

> **defer와의 연결 (1장)** 등록하려면 버튼이 **이미 있어야** 합니다. JavaScript를 `defer`로 연결하면 HTML을 다 읽은 뒤에 실행되어, 코드가 버튼을 **찾을 수 있습니다.**

### 3-3. DOM — 바뀌는 것은 "파일"이 아니라 "구조"

[DOM](../../../terms/dom.md)은 브라우저가 HTML을 읽어 메모리에 만든 **문서의 객체 구조**이고, JavaScript가 문서를 읽고 바꾸는 통로입니다. `[사전]`

| | 무엇인가 | 클릭하면? |
| --- | --- | --- |
| **HTML 소스 파일** | 내가 쓴(또는 AI가 쓴) 텍스트 파일 | **그대로** |
| **DOM** | 브라우저가 메모리에 만든 문서 구조 | **바뀜** (클래스 추가, 글자 변경 등) |

관찰 ②에서 본 것이 바로 이 차이입니다. 코드에서 요소를 찾을 때는 `document.querySelector('.menu-toggle')`처럼 **CSS 선택자**와 같은 규칙으로 이름을 지정합니다. `[사전]` `[AI 보충]`

### 3-4. 상태 — "지금 어떤 상황인가"를 기억하는 값

[상태 변경](../../../terms/state-change.md)은 **프로그램이 기억하는 값이 바뀌는 일**입니다. `[사전]` 메뉴라면 "지금 **열려 있다 / 닫혀 있다**"가 상태입니다.

메뉴 상태를 표현하는 방식은 **프로젝트마다 다릅니다.** `is-open` 같은 class, `hidden` 속성, `aria-expanded` 등을 단독으로 또는 함께 씁니다. 이 장의 예시는 class 방식입니다. `[AI 보충]`

초보자가 헷갈리는 점: **상태가 꼭 JavaScript 변수 안에 있는 것은 아닙니다.** 이 미션 수준의 코드에서는 **HTML 요소의 class나 속성이 곧 상태**인 경우가 많습니다.

| 상태를 어디에 두나 | 예 | 읽는 법 |
| --- | --- | --- |
| 요소의 **class** | 메뉴에 `is-open`이 있으면 열림 | "클래스가 있나?" |
| 요소의 **속성** | 버튼의 `aria-expanded="true"`, 메뉴의 `hidden` 속성 있음/없음 | "속성 값이 무엇인가?" |
| JavaScript **변수** | `let isLoading = true` (7장에서 자주 만남) | "변수 값이 무엇인가?" |

그래서 V04의 ③ "새 상태를 정한다"와 ④ "DOM을 바꾼다"는 코드 한 줄에 **함께** 일어나기도 합니다. (`classList.toggle`이 그 예입니다.) 그림에서는 이해를 돕기 위해 **나눠 그렸습니다.** `[AI 보충]`

### 3-5. 모양은 누가 바꿀까 — JavaScript는 "스위치", CSS는 "모양"

JavaScript가 메뉴에 `is-open` 클래스를 붙이면(이 장의 예시 방식), **CSS에 미리 써 둔 `.is-open` 규칙이** 메뉴를 보이게 합니다. 역할이 나뉩니다. (`hidden` 속성을 켜고 끄는 방식이면 브라우저 기본 규칙이나 CSS가 그 속성을 읽어 숨깁니다.)

| | 하는 일 |
| --- | --- |
| JavaScript | **언제** 바꿀지 판단하고 **스위치(클래스)** 를 켬 |
| CSS | 스위치가 켜졌을 때 **어떻게 보일지** 정함 |
| 브라우저 | DOM과 CSS를 합쳐 화면을 다시 그림 ([브라우저 렌더링](../../../terms/browser-rendering.md)) |

이렇게 나누면 코드를 찾기 쉽습니다. "모양을 고치고 싶다 → CSS", "언제 열릴지 고치고 싶다 → JavaScript". 1장에서 본 역할 구분이 그대로 이어집니다. `[AI 보충]`

### 3-6. 클릭이 아닌 계기 — 스크롤과 Intersection Observer

| 계기 | 방식 | 이 미션에서 |
| --- | --- | --- |
| 클릭 | `click` 이벤트 | ☰ 메뉴, 맨 위로 버튼 |
| 스크롤 | `scroll` 이벤트 | 맨 위로 버튼 보이기/숨기기, 메뉴 줄 모양 변화 |
| 요소가 **화면에 들어옴** | [Intersection Observer](../../../terms/intersection-observer-api.md) | 섹션이 보일 때 나타나는 애니메이션 |

Intersection Observer는 "요소가 화면에 들어오거나 나가는 시점"을 브라우저가 **알려 주는** 기능입니다. 코드가 스크롤 위치를 매번 계산하지 않아도 됩니다. `[사전]` 클릭 이벤트는 아니지만, **"브라우저가 알려 주면 함수가 실행된다"는 흐름은 같습니다.** V04에서 ①이 "클릭" 대신 "화면에 들어옴"으로 바뀐다고 생각하면 됩니다.

> **모든 인터랙션이 JavaScript는 아닙니다.** 메뉴 링크를 눌렀을 때 부드럽게 이동하는 것은 CSS 한 줄(`scroll-behavior: smooth`)로도 가능합니다. [부드러운 스크롤](../../../terms/smooth-scroll.md)은 내 프로젝트가 CSS로 하는지 JavaScript로 하는지 **직접 확인**해 보세요. `[사전]` `[AI 보충]`

### 3-7. `onclick`이 아니라 `addEventListener`인 이유

| | `<button onclick="…">` (inline) | `addEventListener` |
| --- | --- | --- |
| 동작을 적는 곳 | **HTML 안** | **JavaScript 파일** |
| 파일 역할 분리 | 섞임 | 유지됨 |
| 한 버튼에 동작 여러 개 | 어려움 | 쉬움 |
| 이 미션 | 쓰지 않음 `[공식]` | 쓰는 방식 `[공식]` |

`[사전]` 구조(HTML)와 동작(JavaScript)을 분리하기 위한 것입니다.

> 더 알아보기: [이벤트 전파](../../../terms/event-propagation.md) (자식의 클릭이 부모에게도 전달되는 흐름), [preventDefault](../../../terms/prevent-default.md) (링크 이동·폼 제출 같은 기본 동작을 막기. 6장에서 만납니다.)

### 3-8. 버튼에 직접 연결되지 않은 경우 `[AI 보충]`

V04는 "버튼에 직접 등록한 handler"를 그린 **대표 흐름**입니다. 실제 프로젝트에는 이런 경우도 있습니다.

| 경우 | 어떻게 동작하나 | V04와의 차이 |
| --- | --- | --- |
| **이벤트 위임** | 버튼이 아니라 **부모 요소**(`nav`, `body`, `document`)에 리스너 하나를 달고, "클릭된 곳이 어디인가(`event.target`)"를 보고 처리 | ⓪의 등록 위치와 ②에서 불리는 곳이 **부모**임. ③~⑥은 같음 |
| **브라우저 기본 동작** | `<a href="#projects">` 클릭 시 해당 위치로 이동, `<details>`·`<summary>`는 JS 없이 열고 닫힘, 폼 제출 | ⓪~③이 없거나 줄어듦. 브라우저가 대신 처리 |
| **CSS가 맡는 변화** | `scroll-behavior: smooth` 로 부드러운 이동 | JS 이벤트 없이 CSS 규칙이 영향 |

이벤트 위임이 가능한 것은 자식의 클릭이 부모에게도 전달되는 **이벤트 전파** 덕분입니다. `[사전]` ([이벤트 전파](../../../terms/event-propagation.md))

> 그래서 **버튼 줄에 `addEventListener`가 안 보이면 "기능이 없다"가 아니라 "다른 곳에서 처리하고 있다"** 일 수 있습니다. 부모 요소와 `document`, 그리고 JavaScript 밖(HTML 속성·CSS)까지 살펴보세요.

## 4. 면 — V04: 이벤트에서 DOM과 화면까지

![V04(햄버거 메뉴의 대표 흐름): 사용자, 브라우저, 내 JavaScript, DOM 네 참여자가 세로선으로 있고, 준비 단계(점선 화살표로 이벤트 등록)와 번호 순서의 실행 단계(1 클릭, 2 이벤트로 핸들러 호출, 3 상태 결정, 4 DOM 변경, 5 브라우저가 화면 다시 그림, 6 사용자가 결과를 봄)를 보여 주는 흐름도. 아래 상자는 이 그림이 햄버거 메뉴의 대표 흐름임을 밝히고, 맨 위로(스크롤 위치 변경)·섹션 등장(화면에 들어옴)·브라우저 기본 동작·이벤트 위임과의 차이를 요약합니다.](../assets/v04-event-dom-flow.svg)

**교육용 단순화 모델**입니다. 실제 브라우저 내부에는 이벤트 큐 등 더 많은 단계가 있습니다. 예시는 **모바일 햄버거 메뉴**입니다.

### 그림 읽는 순서

1. 위쪽 네 칸은 **누가 일하는지**입니다. 사용자 / 브라우저 / 내 JavaScript / DOM.
2. **⓪ 점선 화살표**(준비): 페이지가 열릴 때 **한 번** 일어납니다. "이 버튼에서 click이 오면 이 함수를 불러 달라"고 등록합니다.
3. **① → ⑥ 실선 화살표**(실행): 번호 순서대로 **누를 때마다** 일어납니다.
4. 화살표의 **방향**을 따라가 보세요. ⑤는 DOM에서 브라우저로, ⑥은 브라우저에서 사용자 쪽으로 돌아옵니다. **결과가 눈으로 돌아오는 것**입니다.
5. 아래 상자에서 다른 기능·경우가 이 틀과 **어디서 달라지는지** 확인합니다. (뒤의 "공통 원리와 차이" 표와 이어집니다.)

실선(순서)과 점선(준비·연결)을 **다른 선으로 그린 이유**: 점선은 "미리 연결해 둠", 실선은 "그 연결 덕분에 시간이 흐르며 일어나는 일"입니다. 구조와 순서를 섞지 않기 위함입니다.

### 같은 흐름, 세 기능

일반화한 예입니다. 번호는 V04의 번호입니다. `[AI 보충]`

| | ☰ 햄버거 메뉴 | ↑ 맨 위로 | 섹션 등장 애니메이션 |
| --- | --- | --- | --- |
| ① 계기 | ☰ 버튼을 **클릭** | ↑ 버튼을 **클릭** | 섹션이 **화면에 들어옴** |
| ② 호출되는 것 | click handler | click handler | Intersection Observer의 콜백 |
| ③ 상태 판단 | 메뉴가 지금 열려 있나? → 반대로 | (판단 거의 없음) | 화면에 들어왔나? (`isIntersecting`) |
| ④ 바뀌는 것 | (이 예시) 메뉴 요소의 `is-open` 클래스, 버튼의 `aria-expanded`. 방식은 프로젝트마다 다름(`hidden` 속성 등) | **스크롤 위치**를 맨 위로 (`window.scrollTo`) | 섹션에 `is-revealed` 클래스 추가 |
| ⑤ 화면을 바꾸는 것 | CSS의 `.is-open` 규칙 | 브라우저가 맨 위로 이동시킴 | CSS의 투명도·이동 전환(transition) |

### 공통 원리와 차이 — 변화의 종류를 구분하기

세 기능은 "이벤트 → handler → 변화 → 화면"이라는 **공통 원리**를 따르지만, ④에서 일어나는 **변화의 종류**가 다릅니다.

| 변화의 종류 | 예 | 확인하는 곳 |
| --- | --- | --- |
| **DOM이 바뀜** (class·속성·글자) | 메뉴 열기(`is-open`), 섹션 등장(`is-revealed`), 스크롤에 따라 버튼 보이기(`is-visible`) | Elements 패널에서 속성이 바뀌는 모습 |
| **스크롤 위치가 바뀜** (DOM은 그대로) | 맨 위로(`window.scrollTo`), 메뉴 링크의 부드러운 이동 | 페이지가 움직일 뿐 Elements의 요소는 그대로 |
| **브라우저 기본 동작·CSS가 처리** | `<a href="#…">` 이동, `<details>`, `scroll-behavior: smooth` | JavaScript에서 해당 handler를 찾기 어려움 |

> 정직하게 짚어 둘 점: **V04의 ④ "DOM을 바꾼다"는 햄버거 메뉴 기준입니다.** "맨 위로"는 문서 구조가 아니라 **스크롤 위치**를 바꿉니다. 그래도 사용자가 한 행동이 handler를 거쳐 화면 변화로 이어진다는 큰 흐름은 같습니다.

### 면 — 한 문장

> **HTML이 요소를 준비하고, JavaScript가 이벤트를 받아 DOM을 바꾸고, CSS와 브라우저가 그 결과를 화면으로 보여 주며, 이 세 가지가 이벤트 하나를 중심으로 협력합니다.**

## 5. 코드 확인 — 내 프로젝트에서 찾기

> 🎯 코드를 읽을 때 **한 줄씩 이해하려 하지 마세요.** 목표는 "이 기능의 ⓪ 등록 줄, ③④ 핸들러, ⑤ CSS 규칙이 **어디 있는지** 찾는 것"입니다.

### 5-1. 가장 중요한 방법 — "이름의 고리"를 따라가기

한 기능은 보통 **같은 이름**이 세 파일에 나옵니다. 그 이름을 검색으로 따라갑니다. `[AI 보충]`

```
HTML  <button class="menu-toggle">     ← 화면의 버튼을 만듦
JS    document.querySelector('.menu-toggle')   ← 그 버튼을 찾아 이벤트 등록
CSS   .menu-toggle { … }                ← 그 버튼의 모양
```

| 추적 순서 | 어떻게 |
| --- | --- |
| ① 화면의 버튼 → HTML | 요소 선택 도구로 버튼 클릭 → Elements에서 `class`·`id` 메모 |
| ② 그 이름 → JavaScript | 편집기에서 그 이름 검색(`Ctrl+Shift+F`). `querySelector(…)`가 나오는 줄이 목표 |
| ③ 거기서 `addEventListener` 찾기 | 같은 줄 근처. 바로 관찰 ③의 Event Listeners 탭이 알려 주는 줄. **버튼에 없으면** 부모 요소·`document`에 달린 리스너(`event.target`·`closest(` 가 보이면 이벤트 위임)나 브라우저 기본 동작을 의심 |
| ④ 핸들러 안의 `classList`·`setAttribute`·`scrollTo`… | **무엇을 바꾸는지** 확인 |
| ⑤ 바뀌는 class·속성 → CSS | 검색해서 `.is-open { … }` 같은 규칙, 또는 `[hidden]`·`[aria-expanded]` 같은 속성 규칙 찾기 |

### 5-2. 일반화 예제 — 기능 3개의 코드 모양

> 🔷 **일반화 예제** 개념을 보여 주려고 새로 쓴 코드입니다. 클래스 이름은 **가정**이며 **내 프로젝트의 코드가 아닙니다.** 모양이 비슷한 부분을 내 코드에서 찾아 비교하세요.
>
> **읽는 요령** — `const 이름 = …`: 이름에 값을 붙임(바꾸지 않을 값). `() => { … }`: "함수 만들기"이며 `{ }` 안이 **일어날 일**. `//`로 시작하는 줄은 설명(주석)입니다.

**① 햄버거 메뉴**

```html
<button class="menu-toggle" aria-expanded="false" aria-controls="site-menu">메뉴</button>
<nav id="site-menu" class="site-menu">…</nav>
```

```js
const menuToggle = document.querySelector('.menu-toggle');   // 버튼 찾기
const siteMenu = document.querySelector('#site-menu');       // 메뉴 찾기

menuToggle.addEventListener('click', () => {                 // ⓪ click이 오면 아래 함수를 불러 달라고 등록
  const isOpen = siteMenu.classList.toggle('is-open');       // ③④ is-open 클래스를 넣었다 뺐다. 결과는 true/false
  menuToggle.setAttribute('aria-expanded', String(isOpen));  // 버튼의 '열림' 상태도 함께 알림
});
```

```css
.site-menu { display: none; }
.site-menu.is-open { display: block; }   /* ⑤ 이 규칙이 켜지면 메뉴가 보임 */
```

> **같은 기능의 다른 구현 (참고)** 내 프로젝트가 아래처럼 만들어졌다면 `is-open`이 **없습니다.** 그래도 V04의 틀은 같습니다.
>
> ```js
> // 방식 B: hidden 속성을 켜고 끔 (class는 쓰지 않음)
> menuToggle.addEventListener('click', () => {
>   siteMenu.hidden = !siteMenu.hidden;
>   menuToggle.setAttribute('aria-expanded', String(!siteMenu.hidden));
> });
>
> // 방식 C: 이벤트 위임 (버튼이 아니라 document에 등록)
> document.addEventListener('click', (event) => {
>   const button = event.target.closest('.menu-toggle');   // 클릭된 곳이 메뉴 버튼(또는 그 안쪽)인가?
>   if (button) { /* 여기서 메뉴를 열고 닫음 */ }
> });
> ```

> **3장 관찰 ③(메뉴를 연 채 넓히기)의 힌트** 위처럼 `.site-menu.is-open`(클래스 두 개)이 3장의 `@media` 안 `.site-menu`(클래스 한 개)보다 **더 구체적인 규칙**이면 이길 수 있어, 넓은 폭에서도 세로 메뉴가 남을 수 있습니다. 내 프로젝트가 그런지는 **직접 확인**해 보세요. 그렇지 않은 구조일 수도 있습니다.

**② 맨 위로 버튼**

```js
const toTopButton = document.querySelector('.to-top');

toTopButton.addEventListener('click', () => {                 // ⓪ 등록
  window.scrollTo({ top: 0, behavior: 'smooth' });            // ④ 스크롤 위치를 맨 위로, 부드럽게
});

window.addEventListener('scroll', () => {                     // 스크롤할 때마다 호출되는 또 하나의 이벤트
  toTopButton.classList.toggle('is-visible', window.scrollY > 400);  // 400px 넘게 내려오면 버튼 보이기
});
```

**③ 섹션 등장 애니메이션 (Intersection Observer)**

```js
const observer = new IntersectionObserver((entries) => {      // 요소가 화면에 들어오거나 나갈 때 불리는 함수
  entries.forEach((entry) => {
    if (entry.isIntersecting) {                               // 화면에 들어왔다면
      entry.target.classList.add('is-revealed');              // ④ 클래스를 붙이고
      observer.unobserve(entry.target);                       // 한 번만 보이면 되니 관찰을 멈춤
    }
  });
}, { threshold: 0.2 });                                       // 요소의 20%가 보이면

document.querySelectorAll('.reveal').forEach((section) => {
  observer.observe(section);                                  // ⓪ 이 요소들을 관찰 대상으로 등록
});
```

```css
.reveal { opacity: 0; transform: translateY(16px); transition: opacity .4s, transform .4s; }
.reveal.is-revealed { opacity: 1; transform: none; }          /* ⑤ 이 규칙이 켜지면 서서히 나타남 */
```

| 점검 | 검색어 | 결과 |
| --- | --- | --- |

### 5-5. 오류를 만났을 때 — 가장 흔한 것 하나

개발자 도구의 **Console** 탭에 빨간 글씨로 이런 오류가 나올 수 있습니다.

```
Uncaught TypeError: Cannot read properties of null (reading 'addEventListener')
```

번역하면 **"찾으려던 요소가 없다(null)"** 입니다. 의심할 곳은 세 가지입니다. `[사전]`

| 의심 | 확인 |
| --- | --- |
| 이름 오타 (`.menu-toggle` ↔ `.menu-togle`) | HTML의 class와 JS의 이름을 **글자 단위로** 비교 |
| `defer` 누락 (HTML을 다 읽기 전에 실행) | `index.html`의 `<script` 줄 |
| 그 페이지에 요소가 아예 없음 | Elements에서 검색 |

반대로 "한 번 눌렀는데 두 번 동작한다(열렸다 바로 닫힘)"면 **같은 리스너가 두 번 등록**되었을 수 있습니다. `[사전]`

## 6. AI에게 물어보기

> 1장의 네 가지 규칙(**수정하지 말고 설명만 / 파일·줄 번호 / 내 화면과 연결 / 답은 가설**)을 그대로 적용합니다.

> **① 기능 하나를 끝까지 추적**
> 화면의 **[☰ 메뉴 버튼]**을 누르면 일어나는 일을 코드 기준으로 단계별로 추적해 줘. ① 버튼이 있는 HTML 줄, ② `addEventListener`로 등록하는 줄(**버튼에 직접인지, 부모에 달린 이벤트 위임인지, 아니면 브라우저 기본 동작인지도 구분해서**), ③ 핸들러가 하는 일, ④ DOM에서 바뀌는 것(class·속성), ⑤ 그 변화로 화면을 바꾸는 CSS 규칙 — 각각 **파일 이름과 줄 번호**와 함께 알려 줘. 초보자가 이해할 수 있게 쓰고, **코드는 수정하지 마.**

> **② 이벤트 지도**
> 이 프로젝트의 모든 `addEventListener`와 `IntersectionObserver` 사용 위치를 표로 정리해 줘. 열은 **대상 요소 / 이벤트 종류 / 하는 일 / 파일:줄**. 사용자 행동이 화면 변화로 이어지는 기능이 몇 개인지도 세어 줘. 수정은 하지 마.

> **③ 상태 찾기**
> 이 프로젝트의 JavaScript에서 "상태"라고 부를 수 있는 것(변수 값, class, 속성)을 찾아서, 각각 **어떤 기능의 상태**이고 **어느 코드가 바꾸는지** 설명해 줘. 변수에만 있는 상태와 HTML 요소의 class/속성에 있는 상태를 구분해 줘.

> **④ 미션 제약 점검**
> 이 프로젝트에 inline `onclick`, `var`, JavaScript의 `.style` 직접 사용이 있는지 검색해서 **검색한 패턴과 결과(파일:줄)** 를 알려 줘. 없으면 "없다"고 근거와 함께 말해 줘. 수정하지 마.

> **⑤ 오류 원인 후보**
> 개발자 도구 Console에 이 오류가 나와: `(오류 메시지를 그대로 붙여넣기)`. 이 프로젝트 코드 기준으로 **원인 후보**를 가능성이 높은 순서로 알려 줘. 고치지는 말고, 내가 직접 확인할 방법을 알려 줘.

> 사용자가 `________`를 `________`하면, 브라우저가 `________` 이벤트를 만듭니다.

> (이 함수는 버튼에 직접 연결되어 있기도 하고, `________`처럼 부모에 연결된 위임이기도 합니다.)
> 이 함수는 `________`(상태)를 확인해 `________`(DOM: class·속성 등)를 바꿉니다.
> 그러면 CSS의 `________` 규칙이 적용되어 화면이 `________`.
> 이때 `index.html` 파일 자체는 **바뀌지 않고**, 바뀌는 것은 `________`입니다.

**같은 틀로 기능 세 가지를 30초씩** 말해 보세요. 세 번째 기능이 클릭이 아니라면 ①번 문장만 바꾸면 됩니다.

### 좋은 설명의 기준

- ☐ **준비(등록)** 와 **실행(누를 때)** 을 구분해 말했다.
- ☐ "HTML이 바뀐다"고 말하지 않고 **"DOM이 바뀐다"** 고 말했다.
- ☐ JavaScript가 **스위치(class)** 를 켜고 CSS가 **모양**을 정한다는 것을 말했다.
- ☐ 내 프로젝트의 **실제 파일명과 줄 번호**를 하나 이상 말했다.

## 정리

- JavaScript는 지켜보는 것이 아니라, **미리 등록해 둔 함수가 이벤트가 올 때 호출**됩니다. (⓪ 준비 → ①~⑥ 실행)
- 클릭하면 바뀌는 것은 HTML 파일이 아니라 **DOM**이고, 모양은 **CSS 규칙**이 정합니다.
- 기능을 찾을 때는 **화면 → 요소의 class/id → JavaScript 검색 → CSS 검색** 순서로 이름의 고리를 따라갑니다.
