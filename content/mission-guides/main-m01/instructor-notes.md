## 0. 한 장 요약 — 이 수업에서 반드시 남겨야 할 세 가지

1. **"코드를 외우지 않는다. 위치를 찾는다."** 학습자의 최종 능력은 *기능 → 요소 이름(class/id) → 코드 위치*를 따라가는 것입니다.
2. **"선의 종류를 구분한다."** 불러옴(구조) · 대응 · 실행 순서는 다른 이야기입니다. 그림을 읽을 때 매번 *"이 선은 무슨 관계인가?"* 를 묻습니다.
3. **"AI의 답은 가설이다."** 줄 번호와 근거를 요구하고, 학습자가 개발자 도구로 직접 확인합니다.

### 공통 진행 틀 (제안)

내부 설계 흐름(관찰 → 점 → 선 → 면 → 코드 확인 → 자기 설명)은 **제작자와 강사를 위한 기준**이며, **학습자에게는 이 용어를 쓰지 않습니다.** 원고에서는 아래처럼 자연스러운 제목으로 나타납니다.

| 내부 설계 단계 | 강사가 하는 일 | 원고에서의 모습 |
| --- | --- | --- |
| 관찰 | 직접 시연하고, 학습자가 자기 사이트로 따라 해 보게 함. 기록을 강요하지 않음 | 장마다 💻 표시가 붙은 직접 확인 절 |
| 점 | 장의 질문을 던져 호기심을 만든 뒤 바로 설명으로 이어 감. 답을 쓰게 하지 않음 | 장 첫머리의 질문, "왜 …일까?" 제목 |
| 선 | 개념 사이의 관계를 하나씩 짚음. "이 화살표는 무슨 관계?"를 묻되 답은 설명으로 줌 | "…를 이루는 …", "준비와 실행" 같은 개념 설명 절 |
| 면 | SVG를 화면에 크게 띄우고 원고의 "그림 읽는 법" 순서대로 가리키며 설명. 그림 한 장이 장 전체의 요약이 되게 함 | 장 앞쪽의 핵심 그림 절 |
| 코드 확인 | 시연은 짧게, 학습자가 **자기 프로젝트에서 직접 찾게 함.** 막힌 사람을 순회하며 도움 | "내 프로젝트에서 … 찾아보기" 류의 절 |
| 자기 설명 | 마무리에서 원고의 동료평가 질문과 "이렇게 설명할 수 있습니다" 예시를 보여 주며 **말하는 방식**을 안내. 예시는 정답이 아니라 내 사이트의 이름으로 바꿔 쓰는 틀 | 동료평가 절과 정리 절 |

**모바일/PC 활용 (제안)**: 이동 중에는 각 장의 앞부분(질문·그림·핵심 개념)만 읽으면 되고, 컴퓨터에서는 뒷부분의 직접 확인과 코드 분석으로 이어집니다. 강의에서는 앞부분을 먼저 다루고, 직접 확인과 코드 찾기를 실습 시간에 배치하면 자연스럽습니다.

### 수업 전 준비

- 시연용 **예시 프로젝트 한 개**(강사 본인 것 또는 동의받은 것). 이 가이드는 특정 교육생의 코드를 싣지 않았으므로 시연 코드는 강사가 준비합니다.
- 개발자 도구를 화면에 크게 띄우는 설정(글자 확대). 단축키는 Chrome 기준이며 Edge도 대체로 같습니다.
- SVG는 **라이트·다크 모두** 읽히지만, 강의실 프로젝터에서는 밝은 화면을 권장합니다.

## 1. Chapter 1 — 웹사이트는 어떤 파일들로 만들어질까?

**핵심 메시지 한 문장** "웹사이트는 내용(HTML)·모양(CSS)·동작(JavaScript) 파일이 협력한 결과다."

### 시연 순서 (제안)
1. 학습자 사이트를 열고 **화면에서 내용·모양·반응을 하나씩 짚어 줍니다.** ("이 글씨는 내용, 이 색은 모양, 이 버튼의 반응은 동작")
2. F12 → Network → 새로고침. 파일 목록을 보며 **"브라우저가 이 파일들을 받아 왔습니다."**
3. 복사본에서 CSS 연결만 끈 모습 → JS 연결만 끈 모습을 보여 줌. **CSS가 없으면 내용은 남고 모양이 사라지고, JS가 없으면 모양은 남고 반응이 사라진다**는 대비가 핵심입니다.

### 강조 포인트
- **"불러옴"과 "읽는 순서"는 다르다.** V01 ①의 점선은 *구조 관계*(index.html이 가리킴), ②의 번호는 *순서*입니다. 처음부터 이 구분을 심어 두면 이후 장의 그림이 쉬워집니다.
- `defer`는 *"HTML을 다 읽은 뒤 실행"* 이라는 한 문장만. 4장에서 오류 화면으로 다시 만납니다.
- 경로(`css/…` vs `/css/…`)는 *8장 배포*의 복선입니다. 지금은 "로컬에서 되는데 배포하면 깨질 수 있다" 정도만.

### 자주 나오는 질문
| 질문 | 답 |
| --- | --- |
| HTML만 있어도 사이트 아닌가요? | 가능합니다. 하지만 모양과 반응이 없습니다. 1장의 "파일이 없으면 어떻게 보일까" 실험이 대답입니다. |
| 그냥 한 파일에 다 넣으면 안 되나요? | 화면은 나옵니다. 다만 *"모양을 고치려면 어디를 열지"* 가 정해지지 않습니다. 파일 분리는 **위치 찾기**를 위한 것입니다. |
| `defer`를 안 붙여도 되던데요? | 스크립트가 HTML 아래쪽에 있거나 우연히 요소가 먼저 만들어진 경우엔 됩니다. 이 미션은 `defer` 연결을 요구하므로 `[공식]` 이유를 설명할 수 있어야 합니다. |
| 라이브러리를 안 썼는지 `https://`만 검색하면 되나요? | 충분하지 않습니다. `https://`가 있어도 단순 링크일 수 있고, 없어도 내려받은 파일이나 `package.json`·`import`로 쓰고 있을 수 있습니다. 원고 "순수 HTML·CSS·JavaScript는 무엇을 뜻할까?"의 확인 목록(HTML `script`·`link`, JS `import`, 의존성 파일, 내려받은 `.min.js`)를 함께 보게 하세요. |
| CDN으로 폰트나 아이콘 쓰면 안 되나요? | 저장소 자료로는 확정할 수 없습니다. **미션 원문/운영진 확인**이라고 답하세요. (README의 검토 필요 항목) |
| `index.html`은 왜 이름이 정해져 있나요? | 폴더 주소로 접속하면 서버가 기본으로 내주는 파일 이름이 관례로 `index.html`이기 때문입니다. GitHub Pages도 같습니다. |

### 조심할 설명
- "HTML은 프로그래밍 언어가 아니다"는 맞지만 학습자에게 **"그래서 하찮다"** 로 들리지 않게 하세요. 구조를 맡는다는 점을 강조합니다.
- 집 비유(뼈대·인테리어·전기)는 원고에 *한계까지* 적어 두었습니다. 비유만 남기지 말고 **"CSS와 JS는 HTML 요소를 찾아서 일한다"** 로 돌아오세요.

### V01 해설 포인트
- ① 파일 → ② 순서 → ③ 화면 분해 순으로 위에서 아래로 읽습니다.
- ③에서 햄버거 메뉴를 **세 역할로 쪼개서** 설명합니다. ("보이게 하는 건 CSS, 열고 닫는 건 JavaScript")
- ②의 순서는 **단순화**라고 한 번은 말해 주세요. 학습자가 "브라우저가 정말 이 순서로만 일하나요?"라고 물으면, "실제론 동시에 받는 등 더 복잡하지만, 지금은 역할을 구분하는 모델"이라고 답합니다.

### 강의에서 짚을 설명 포인트
- 세 파일의 역할을 **같은 사이트의 실제 예**(메뉴, 색, 제목)로 설명합니다.
- `index.html`의 `link`·`script` 줄을 열어 "여기서 나머지 파일을 불러온다"를 보여 줍니다.
- `defer`는 "HTML을 다 읽은 뒤 실행"이고, 없을 때는 요소를 못 찾는 오류가 날 수 있다고 정리합니다.

## 2. Chapter 2 — 웹페이지의 구역은 코드에서 어떻게 구분될까?

**핵심 메시지 한 문장** "눈에 보이는 구역은 CSS가 칠하고, 코드의 구역은 **의미를 가진 태그**가 만든다."

### 시연 순서 (제안)
1. 사이트를 스크롤하며 구역 이름을 함께 짚음.
2. **요소 선택 도구**(`Ctrl+Shift+C`)로 구역에 마우스를 올려 *"색칠된 것이 코드에서는 이름 있는 요소"* 임을 보여 줌.
3. 메뉴 클릭 → 주소의 `#projects` → Elements에서 `id="projects"` 를 찾아 **같은 이름으로 이어짐**을 확인.

### 강조 포인트
- **`class`와 태그의 차이**가 이 장의 가장 큰 오개념 교정입니다. `<div class="header">`는 이름표만 header입니다.
- 제목 태그는 **크기가 아니라 차례**입니다. "글자를 크게 하려고 `h1`을 쓴다"는 오해를 정면으로 다룹니다.
- `id`↔`href="#…"` 연결은 **한 글자라도 다르면 끊깁니다.** 오타 체크 습관을 심기에 좋습니다.

### 자주 나오는 질문
| 질문 | 답 |
| --- | --- |
| `div`로 만들어도 똑같이 보이는데요? | 화면은 같지만 브라우저·검색 도구·화면 낭독기·AI가 읽는 구조가 다릅니다. 원고 "태그에 의미가 있다는 것" 절. |
| `h1`을 여러 개 써도 되나요? | 문법 오류는 아니지만 보통 **하나**를 권합니다. 동료평가에서 제목 흐름을 보므로 이유를 설명할 수 있으면 됩니다. |
| `id`와 `class`는 뭐가 다른가요? | `id`는 **페이지에서 하나뿐인** 이름표(링크가 가리키는 대상), `class`는 **여러 곳이 공유**하는 이름표(CSS가 모양을 줄 때). |
| 내 사이트는 Hero가 `header` 안에 있는데요? | 괜찮습니다. 가이드 그림은 일반화한 예입니다. **"내 사이트는 이렇게 대응된다"** 를 말할 수 있으면 됩니다. |
| 화면 구역마다 태그가 딱 하나씩 대응하나요? | 아닙니다. 구역이 여러 겹의 요소로 만들어지거나, 요소 하나가 여러 구역을 감싸거나(`main`·`header`), 두 구역이 한 `section`에 합쳐질 수 있습니다. "구역을 **감싸는 가장 바깥 요소**가 무엇인지"를 개발자 도구로 확인하게 하세요. |
| `section`과 `article`은 어떻게 고르나요? | `section`은 주제 구역, `article`은 따로 떼어도 이해되는 독립 덩어리(프로젝트 카드 등)입니다. 초보 단계에서는 "카드 하나 = article" 정도로 충분합니다. |

### 조심할 설명
- 시맨틱 태그가 **"SEO에 좋다"** 는 식의 단정은 피하세요. 원고는 *구조 이해에 도움*(사람·도구·AI)으로 한정했습니다.
- 접근성(화면 낭독기)을 언급할 때는 "이동 지점으로 쓰일 수 있다" 수준으로. 세부 규칙은 이 장의 범위가 아닙니다.

### V02 해설 포인트
- **대응은 1:1이 아닐 수 있습니다.** 그림 맨 아래 상자("대응이 항상 1:1은 아닙니다")를 꼭 짚어 주세요. 학습자의 사이트가 그림과 다르면 그 차이 자체가 좋은 설명 소재입니다.
- **선은 대응 관계**입니다. "이 선을 따라가면 실행되나요?"라는 질문이 나오면 *아니요, 대응일 뿐*이라고 답하고 4장의 번호 화살표와 구분합니다.
- 점선 테두리 `<main>`은 **포함 관계** 설명에 씁니다. "다섯 구역이 main 안에 들어 있다."
- 아래 비교 상자(`div class="header"` vs `<header>`)를 *마지막에 한 번* 크게 보여 주세요. 이 장의 요약입니다.

### 강의에서 짚을 설명 포인트
- 메뉴가 구역으로 가는 이유를 `id`와 `href="#…"`가 **같은 이름**이기 때문이라고 설명합니다.
- `<div class="footer">`와 `<footer>`의 차이는 "이름표 vs 역할을 가진 태그"로 정리합니다.
- 제목 태그의 숫자는 글자 크기가 아니라 **차례**라고 짚습니다.

## 3. Chapter 3 — 화면 크기에 따라 디자인이 달라지는 이유

**핵심 메시지 한 문장** "HTML은 그대로, **조건에 따라 CSS 규칙만 켜지고 꺼진다.**"

### 시연 순서 (제안)
1. 장치 모드(`Ctrl+Shift+M`)로 폭을 360 → 767 → 768 → 1023 → 1024로 **천천히** 바꿔 보이며, 바뀌는 순간을 짚습니다.
2. 같은 요소를 선택해 **Styles 패널**에서 `@media (min-width: 768px)` 규칙이 켜지고 꺼지는 것을 보여 줌. (이 시연이 가장 강력합니다.)
3. 확대(`Ctrl +`)가 폭을 줄이는 효과도 있음을 보여 줌. 장치 모드를 못 쓰는 환경의 대안입니다.

### 강조 포인트
- **규칙이 쌓인다** (V03 위 막대). 1100px에서는 기본·768·1024가 *모두* 적용됩니다. "768 규칙은 768~1023에서만 켜진다"는 오해가 흔합니다. `min-width`는 *이상*이므로 위로 계속 누적됩니다.
- **Mobile First = 작은 화면이 기본값.** `@media` 바깥의 규칙이 모바일 기준이라는 것을 코드에서 직접 확인하게 하세요.
- **HTML은 두 벌이 아니다.** V03의 초록 상자 문장을 한 번 소리 내어 읽어 줍니다.
- Flexbox/Grid는 문법이 아니라 **"한 방향 vs 행과 열"** 의 구분만. `repeat(3, 1fr)`은 "같은 폭 열 3개"까지만 읽게 합니다.

### 자주 나오는 질문
| 질문 | 답 |
| --- | --- |
| 768 말고 다른 숫자를 써도 되나요? | 원칙은 콘텐츠가 어색해지는 지점이지만, 이 미션은 **768·1024 전환을 확인**합니다 `[공식]`. 사전도 "모든 사이트의 정답이 아니다"라고 합니다. |
| `max-width`로 줄이는 방식도 있던데요? | 가능하지만 미션은 Mobile First(`min-width`)를 요구합니다. 방식 차이를 아는 것은 좋습니다. |
| `px`와 `rem`은 뭐가 다른가요? | `px`는 고정, `rem`은 기본 글자 크기에 비례. 고정 폭이 좁은 화면에서 옆으로 밀림을 만든다는 것까지만 다룹니다. |
| CSS 변수는 꼭 써야 하나요? | 두 가지를 구분해 답하세요. ① **동료평가 문항**: B1-1 Notion 동료평가에 CSS 변수(`:root`) 사용 이유를 묻는 문항이 있습니다 `[공식]`. ② **필수 구현 조건**인지는 저장소 자료로 확정하지 못했습니다. 그래서 "쓰라고 정해졌는지는 원문 확인, 하지만 쓴 이유(또는 안 쓴 이유)는 반드시 설명할 수 있어야 한다"가 안전한 답입니다. |
| 메뉴를 열어 둔 채 넓히면 이상해요 | 3장 "메뉴를 연 채 넓혀 보기" 도전 과제입니다. 4장 예제 아래의 힌트(규칙의 구체성)와 연결하되, **내 프로젝트가 실제로 그런지 직접 확인**하게 하세요. 구조에 따라 안 그럴 수도 있습니다. |

### 조심할 설명
- **필수 조건과 권고를 섞어 말하지 마세요.** 미션 요구는 Mobile First·768/1024 전환·메뉴 Flexbox·카드 Grid입니다. `viewport` 줄, 고정 `px` 폭 피하기, `gap` 사용, `@media`를 기본 규칙 아래에 두기는 **`[권장]`** 입니다. 원고 "구현 상태 점검" 절이 이 둘을 나눠 적었습니다. 다만 "좁은 화면에서 가로 overflow가 없는지"는 동료평가 확인 포인트입니다.
- "모바일용 코드와 PC용 코드가 따로 있다"는 표현을 쓰지 마세요. **한 CSS 안에 조건부 규칙**입니다.
- 1100px에서 "768 규칙이 꺼졌다"고 말하지 마세요. 덧붙은 규칙은 *계속 켜져 있고*, 같은 속성은 뒤의 규칙이 덮을 뿐입니다.

### V03 해설 포인트
- 위 막대 → 가운데 세 화면 → 초록 상자 → 아래 설명 순.
- 카드 `1·2·3`이 *같은 번호가 같은 카드*임을 짚어, **HTML은 같고 배치만 다르다**는 시각적 증거로 씁니다.
- 이 그림은 **모바일 화면(360~390px)에서 읽히도록 세로로 쌓았습니다.** 수업에서는 세 화면을 한눈에 비교하려면 SVG 파일을 브라우저에서 직접 열어 창에 맞춰 크게 보여 주세요.
- 열 개수(1·2·3)와 메뉴 방식은 **일반화 예**입니다. 학습자 사이트가 실제로 어느 폭에서 바뀌는지 직접 폭을 바꿔 보며 비교하게 하세요.

### 강의에서 짚을 설명 포인트
- 같은 사이트가 폭에 따라 달라지는 이유를 `@media`가 **조건에 따라 규칙을 켜기 때문**이라고 설명합니다.
- 1100px에서는 기본·768·1024 규칙이 **모두** 적용된다는 점을 한 번 더 짚습니다.
- 메뉴는 한 방향(Flexbox), 카드는 행과 열(Grid)이라는 구분으로 정리합니다.

## 4. Chapter 4 — 버튼을 누르면 화면은 어떻게 바뀔까?

**핵심 메시지 한 문장** "JavaScript는 지켜보는 게 아니라, **미리 등록해 둔 함수가 이벤트가 올 때 호출**된다. 바뀌는 건 HTML 파일이 아니라 DOM이다."

### 시연 순서 (제안) — 이 장은 순서가 중요합니다
1. **"화면은 바뀌는데 파일은 그대로다"를 먼저.** 메뉴를 누르기 전후에 Elements 패널의 class 변화를 보이고, `Ctrl+U`(소스 보기)에는 **변화가 없음**을 보입니다. 이 대비가 *"DOM ≠ HTML 파일"* 을 한 번에 이해시킵니다.
2. **"이 버튼에는 어떤 코드가 연결되어 있을까" — Event Listeners 탭.** 버튼 → click → `파일:줄` 점프. 학습자가 "코드 위치 찾기"를 체감하는 순간입니다.
3. 그 다음에 V04를 띄워 **⓪ 준비 → ①~⑥ 실행**을 설명합니다. 그림을 먼저 보여 주면 추상적으로 들립니다.
4. 같은 흐름을 **맨 위로 버튼 → 섹션 등장**에 적용해 "계기만 바뀐다"를 확인.

### 강조 포인트
- **⓪와 ①~⑥을 구분.** 점선(준비 1회)과 실선(매번)이 다른 선인 이유입니다.
- **상태는 변수만이 아니다.** 이 수준의 코드에서는 class/속성이 곧 상태입니다. 학습자가 "상태가 어디 있죠? 변수가 안 보여요"라고 막히는 지점입니다.
- **JS는 스위치, CSS는 모양.** `is-open` 클래스를 붙이면 CSS가 모양을 정합니다. "모양을 고치려면 CSS, 언제 열릴지를 고치려면 JS"를 기능 찾기의 규칙으로 줍니다.
- **이름의 고리**: HTML `class` ↔ JS `querySelector` ↔ CSS `.class`. 검색 한 번으로 세 파일을 오가는 것이 이 장의 실전 기술입니다.
- **V04는 대표 흐름일 뿐입니다.** 햄버거 메뉴(class 방식)를 기준으로 그렸습니다. 학습자가 "제 건 class가 없는데요"라고 하면 틀린 것이 아니라 **방식이 다른 것**입니다. 그림 아래 상자와 원고 4절의 "변화의 종류" 표로 공통 원리와 차이를 설명하세요.
- **`defer` 회수.** `null` 오류 화면("오류를 만났을 때" 절)을 보여 주고 1장의 `defer` 설명으로 돌아갑니다.

### 자주 나오는 질문
| 질문 | 답 |
| --- | --- |
| 버튼을 눌렀는데 `class`가 안 바뀌어요 | 정상일 수 있습니다. 구현 방식이 `hidden` 속성, `aria-expanded`, 부모 요소의 class 등일 수 있습니다. 메뉴·버튼·부모를 모두 눌러 보며 **Elements에서 변하는 것**을 찾게 하세요. |
| 버튼에 `addEventListener`가 안 보여요 | ① 부모/`document`에 달린 **이벤트 위임**일 수 있습니다(Event Listeners 탭의 Ancestors 체크, 코드의 `event.target`·`closest(`). ② `<a href="#…">`·`<details>` 같은 **브라우저 기본 동작**이나 CSS(`scroll-behavior`)가 처리할 수 있습니다. 원고 "버튼에 직접 연결되지 않은 경우" 절. |
| JavaScript는 계속 돌면서 클릭을 기다리나요? | 아닙니다. 페이지가 열릴 때 **등록**해 두고, 이벤트가 오면 브라우저가 함수를 부릅니다. (V04 ⓪) |
| 버튼을 누르면 HTML이 바뀌나요? | 파일은 그대로, **DOM**이 바뀝니다. 위의 `Ctrl+U` 비교. |
| 상태가 뭔가요? 변수에 있어야 하죠? | "지금 열려 있나?" 같은 지금 상황입니다. 변수일 수도 있고 class/속성일 수도 있습니다. |
| `=>` 이게 뭐죠? | "함수를 만드는 문법"이라고만 하세요. 읽는 법은 `{ }` 안이 *일어날 일*. (원고 "일반화 예제"의 읽는 요령) |
| `onclick`을 쓰면 왜 안 되죠? | 미션 제약입니다 `[공식]`. 이유는 HTML과 동작이 섞여 위치 찾기·관리가 어렵기 때문. |
| Intersection Observer는 click이 아닌데 같은 흐름인가요? | 네. ①이 "클릭" 대신 "화면에 들어옴"으로 바뀔 뿐, ②~⑥ 구조는 같습니다. |
| `.style`로 직접 바꾸면 inline style 위반인가요? | 저장소 자료로는 확정할 수 없습니다 `[검토 필요]`. class 토글은 문제를 피하는 방식이라고만 안내하고 원문 확인을 권합니다. |

### 조심할 설명
- **직접 확인 단계에서 class만 찾게 하지 마세요.** 속성 전체(`class`·`hidden`·`aria-expanded`)를 보게 해야 합니다.
- **"맨 위로"는 DOM을 바꾸지 않습니다.** 스크롤 위치를 바꿉니다. 원고가 정직하게 적었으니 *"그래도 흐름은 같다"* 로 이어 가세요. 모든 기능이 DOM 변경이라고 단정하지 마세요.
- ③(상태 결정)과 ④(DOM 변경)은 `classList.toggle` 한 줄에서 **한 번에** 일어납니다. V04는 이해를 위해 나눠 그린 모델임을 말해 주세요.
- 화면이 "즉시" 바뀐다는 표현은 피하고, **"브라우저가 바뀐 DOM과 CSS로 다시 그린다"** 로 말하세요. (사전: 렌더링은 DOM 이후의 별도 단계)
- 이벤트 위임·브라우저 기본 동작은 원고 "버튼에 직접 연결되지 않은 경우" 절에서 **"V04와 다른 경우"** 로만 다룹니다. 이벤트 전파 자체는 "더 알아보기" 링크로 두었으니, 질문이 나오면 짧게 답하되 본 흐름을 흐리지 않게 하세요. `preventDefault`는 6장에서 만납니다.


### V04 해설 포인트 (이 장의 핵심 그림)
- 읽는 순서: **네 참여자 → ⓪(점선) → ①②③④⑤⑥(실선).**
- 화살표의 *방향*을 짚습니다. ⑤는 DOM에서 브라우저로, ⑥은 사용자 쪽으로 돌아옵니다. 결과가 *눈으로 돌아오는* 그림입니다.
- 아래 상자의 다른 기능·경우(맨 위로, 섹션 등장, 기본 동작, 이벤트 위임)를 **①~⑥의 어느 자리가 달라지는지** 짚어 설명합니다. "맨 위로"는 ④가 스크롤 위치, "섹션 등장"은 ①이 화면 진입입니다.
- 이 그림은 **교육용 단순화 모델**입니다. 이벤트 큐 등 내부 단계는 생략되었습니다.

### 강의에서 짚을 설명 포인트
- ☰ 버튼 하나를 ⓪(준비)와 ①~⑥(실행)로 나눠 설명합니다.
- 바뀐 것은 HTML 파일이 아니라 DOM이라는 점을 `Ctrl+U` 비교로 보여 줍니다.
- 내 프로젝트의 기능 세 가지를 같은 틀(계기 → handler → 변화 → CSS)로 훑어 줍니다. 파일명·줄 번호를 짚어 주면 좋습니다.

## 5. Chapter 5 — 다크모드는 왜 새로고침 후에도 유지될까?

**핵심 메시지 한 문장** "테마를 **바꾸는 일**(화면)과 선택을 **기억하는 일**(localStorage)은 서로 다른 책임이고, 페이지를 열 때 **읽고 → 같은 방법으로 적용**한다."

### 시연 순서 (제안)
1. 다크모드를 켜고 새로고침해 **그대로인 것**을 먼저 보여 줍니다. 그다음 "왜 그대로일까?"를 던지고 V05로 갑니다.
2. F12 → **Application → Local Storage**에서 `theme` 값이 `dark`·`light`로 바뀌는 것을 보여 줍니다. **저장소가 눈에 보이는** 순간입니다.
3. 값을 **지우고 새로고침**하면 기본 테마로 돌아가는 것을 보여 줍니다. "저장된 값이 곧 선택"이 체감됩니다.
4. Elements에서 `<html>`의 `data-theme`(또는 class)가 붙었다 떨어지는 것을 보여 줍니다. **화면 담당**이 하는 일입니다.

### 강조 포인트
- **두 책임**: V05에서 ③(화면)과 ④(기억)이 **갈라지는 부분**이 핵심입니다. 동료평가 질문("왜 다른 책임인가요")에 대한 답이기도 합니다.
- **변수에만 저장하면 안 되는 이유**: 새로고침은 페이지를 새로 만드는 일이라 변수도 처음 값으로 돌아갑니다.
- **②에서 ③을 다시 쓴다**: 두 흐름이 같은 `applyTheme`을 공유한다는 점을 짚으면 코드 구조가 쉬워집니다.
- **주소(origin)별 저장소**: 로컬과 배포 주소의 저장값이 다릅니다. 8장 점검에서 다시 만나는 복선입니다.
- **CSS 변수와의 연결**: 3장에서 "값에 이름 붙이기"를 배운 이유가 여기서 드러납니다. 다크모드는 **변수 값만 바꿔치기**합니다.

### 자주 나오는 질문
| 질문 | 답 |
| --- | --- |
| localStorage와 쿠키는 뭐가 다른가요? | 쿠키는 요청마다 서버로 전송되고 작은 값에 쓰입니다. localStorage는 서버로 가지 않고 브라우저에만 남습니다. 사전 `client-side-storage`의 비교를 보여 주세요. |
| 시크릿 창에서는 왜 저장이 안 되나요? | 브라우저 설정에 따라 저장이 막히거나 창을 닫으면 지워질 수 있습니다. 그래서 접근을 `try/catch`로 감싸는 것이 안전합니다. |
| 새로고침 때 잠깐 밝았다가 어두워져요 | 깜빡임입니다. `defer` 스크립트는 HTML을 다 읽은 뒤 실행되기 때문입니다. 일찍 적용하는 방법이 있지만 미션의 `defer` 요구와의 양립은 **원문 확인**이 필요합니다. |
| 다른 컴퓨터에서도 기억하나요? | 아니요. localStorage는 **그 브라우저, 그 주소**에만 있습니다. 서버에 저장하는 것이 아닙니다. |
| 비밀번호를 저장해도 되나요? | 안 됩니다. 페이지의 모든 스크립트가 읽을 수 있고 사용자가 직접 고칠 수도 있습니다. |

### 조심할 설명
- "localStorage가 서버에 저장한다"는 표현은 쓰지 마세요. **사용자의 브라우저 안**입니다.
- 다크모드를 "배경색을 검게 바꾸는 기능"으로 단순화하지 마세요. 글자·테두리·포커스의 대비까지 포함한다는 점을 한 번은 말해 주세요.
- 깜빡임 해결책을 단정적으로 권하지 마세요. 미션 제약과의 관계를 먼저 확인해야 합니다.

### V05 해설 포인트
- **위쪽 ①**(바꿀 때) → **가운데**(저장소) → **아래쪽 ②**(다시 열 때) 순으로 읽습니다.
- ③과 ④가 **같은 시점에 갈라지지만 다른 일**이라는 점, 그리고 ②의 ③이 위의 ③과 **같은 동작**이라는 점을 짚습니다.
- 점선은 **저장소와 주고받는 값**(쓰기·읽기), 실선은 **실행 순서**입니다.

### 강의에서 짚을 설명 포인트
- 테마를 바꾸는 코드와 저장하는 코드를 **따로** 찾아 설명합니다.
- 페이지를 열 때 `getItem`으로 읽고, 값이 없으면 기본 테마를 쓴다는 순서를 설명합니다.

## 6. Chapter 6 — 입력한 정보가 올바른지 어떻게 확인할까?

**핵심 메시지 한 문장** "`submit`에서 **기본 동작을 막고** 값을 검사해, 오류는 **잘못된 칸 옆에**, 정상이면 **오류를 지운다.** 검증 통과는 전송 성공이 아니다."

### 시연 순서 (제안)
1. 빈 값 → `name@` → 정상 값 순서로 제출하며 **칸 옆 문구의 변화**를 보여 줍니다.
2. 제출 직후 **주소창이 그대로**인 것을 짚어 `preventDefault`가 동작한다는 증거로 씁니다. (막히지 않았다면 주소 끝에 `?email=…`이 붙습니다.)
3. 입력칸에서 **Enter 키**를 눌러 같은 검증이 일어나는 것을 보여 줍니다. `submit` 이벤트를 쓰는 이유입니다.
4. V06을 띄워 ①~④와 **두 갈래**를 설명합니다.

### 강조 포인트
- **갈라지는 지점은 ④ 검증 하나**입니다. ①~③은 정상이든 오류든 같습니다.
- **오류 문구는 "무엇이 문제이고 어떻게 고치는지"** 를 담습니다. "오류가 발생했습니다"는 나쁜 예입니다.
- **정상이 되면 이전 오류를 지웁니다.** 가장 흔한 실수입니다.
- **검증 통과 ≠ 전송 성공.** V06 맨 아래 상자를 꼭 짚어 주세요. 화면 문구가 "보냈습니다"처럼 전송을 약속하면 오해를 만듭니다.
- 이메일 **형식** 검사는 주소가 **실제로 있다는 뜻이 아닙니다.**

### 자주 나오는 질문
| 질문 | 답 |
| --- | --- |
| `required`를 쓰면 되는데 왜 JS로 또 검사하나요? | 브라우저 기본 말풍선은 모양과 위치를 제어하기 어렵습니다. 미션은 **칸 근처의 구체적인 안내**를 요구합니다 `[공식]`. 두 방식을 함께 쓰는 구성도 있습니다. |
| `novalidate`는 뭔가요? | 브라우저의 기본 검증을 꺼서 직접 만든 검증과 겹치지 않게 하는 속성입니다. 내 프로젝트가 쓰는지 확인하면 됩니다. |
| 정규식을 외워야 하나요? | 아니요. 이 가이드는 "느슨한 형식 검사"의 의미만 다룹니다. 엄격한 정규식은 정상 주소를 거절할 수 있습니다. |
| 서버에도 검증이 필요한가요? | 브라우저 검증은 사용자 경험을 위한 것이고 서버 검증을 대신하지 못합니다. 이 미션의 범위는 화면 쪽 검증입니다. |
| 폼이 실제로 메시지를 보내야 하나요? | 저장소 자료로는 **확정할 수 없습니다**(README의 검토 필요 항목). 원문 확인을 안내하세요. |

### 조심할 설명
- **"성공"이라는 단어**를 조심하세요. "검증에 성공했다"와 "전송에 성공했다"는 다릅니다.
- `alert()`를 무조건 나쁘다고 말하기보다 **"칸별 안내를 대신하지 못한다"** 로 설명합니다.
- `aria-*`는 심화입니다. 나오면 "화면 낭독기가 오류를 칸과 함께 읽게 하는 연결"이라고만 짧게 답하세요.

### V06 해설 포인트
- 위에서 아래로 ①~④를 읽고, **④에서 두 갈래**로 나뉜다는 것을 짚습니다.
- 왼쪽(오류)은 점선 테두리와 ✕, 오른쪽(정상)은 실선 테두리와 ✓로 **색 외에도 구분**된다는 점을 알려 줍니다.
- 맨 아래 상자는 반드시 읽어 줍니다. "이 그림에는 서버로 보내는 단계가 없습니다."

### 강의에서 짚을 설명 포인트

- 오류가 **칸 옆에** 있어야 하는 이유(어느 칸을 고칠지 바로 알 수 있음)를 말합니다.
- 정상 입력 때 오류가 지워지는 코드의 위치를 짚습니다.

## 7. Chapter 7 — 외부 서버 정보가 웹사이트에 나타나는 과정

**핵심 메시지 한 문장** "`fetch`가 GitHub API에 **요청**하고 **응답**이 오면, **응답이 성공인지 확인**한 뒤 가공해 **네 가지 상태** 중 하나로 보여 준다."

### 시연 순서 (제안)
1. F12 → Network → `Fetch/XHR`에서 `api.github.com` 요청을 열고 **Headers(상태 코드)** 와 **Preview(JSON)** 를 보여 줍니다. V07의 ③④가 실물이 되는 순간입니다.
2. **Throttling을 Offline**으로 바꿔 새로고침해 **오류 상태**를 보여 줍니다. 이전 카드가 남지 않는지도 짚습니다.
3. **느린 네트워크**로 바꿔 **로딩 상태**가 오래 보이게 합니다.
4. 응답 헤더의 `x-ratelimit-remaining`으로 **남은 한도**를 보여 줍니다.
5. V07과 V07 보조(네 가지 상태)를 순서대로 설명합니다.

### 강조 포인트
- **GitHub API ≠ fetch.** 서비스와 요청 도구입니다. 동료평가 질문에 그대로 나옵니다.
- **응답이 도착했다고 성공이 아닙니다.** `fetch`는 403·404에서도 정상 종료하므로 `response.ok`를 직접 확인합니다. 이 장에서 **가장 중요한 한 문장**입니다.
- **`catch`로 가는 경우**는 네트워크 실패처럼 **응답 자체가 없을 때**와, 코드가 직접 던진 오류입니다.
- **네 상태는 한 번에 하나**이고, 상태가 바뀌면 **이전 카드를 지웁니다.**
- **403은 권한 문제만이 아닙니다.** 비인증 한도(시간당 60회) 초과도 403으로 올 수 있습니다. 상태 코드만 보고 원인을 단정하지 않습니다.
- **`textContent`로 넣는 이유**: API가 준 글자를 `innerHTML`에 조합하면 코드로 실행될 수 있습니다(XSS).

### 자주 나오는 질문
| 질문 | 답 |
| --- | --- |
| Promise와 async/await는 뭐가 다른가요? | Promise는 "나중에 올 결과"를 나타내는 약속이고, async/await는 그 약속을 **순서대로 읽히게** 쓰는 문법입니다. |
| `await`를 쓰면 화면이 멈추나요? | 아니요. 그 함수의 진행만 잠시 멈추고 브라우저의 다른 일은 계속됩니다. |
| `map`과 `filter`는 뭐가 다른가요? | `filter`는 **조건에 맞는 것만 남기고**, `map`은 하나하나를 **다른 모양으로 바꿉니다.** 카드 만들기가 `map`입니다. |
| 토큰을 쓰면 한도가 늘지 않나요? | 늘지만, 토큰을 프론트 코드에 적으면 누구나 볼 수 있습니다. 이 미션은 비인증 요청을 전제로 합니다. |
| 한도에 걸리면 어떻게 하나요? | 사용자에게 한도 안내를 보여 주고, 같은 요청을 **자동으로 반복하지 않습니다.** 테스트로 새로고침을 반복하면 한도를 쓰니 주의시키세요. |
| 빈 결과와 오류는 뭐가 다른가요? | 빈 결과는 **응답은 정상인데 데이터가 0개**, 오류는 **요청이 실패**입니다. 문구도 달라야 합니다. |

### 조심할 설명
- "API가 실패하면 `catch`로 간다"고 **단순화하지 마세요.** HTTP 오류는 `catch`로 가지 않고 `response.ok`로 걸러야 합니다.
- "JSON이 JavaScript 객체다"라고 말하지 마세요. JSON은 **텍스트 형식**이고, 읽어서 객체로 바꿉니다.
- 한도 숫자는 **미션 조건**(시간당 60회)으로 말하고, GitHub 정책이 바뀔 수 있다는 점을 덧붙입니다.

### V07 해설 포인트
- **세 참여자**(내 코드 / 브라우저 / GitHub API)를 먼저 짚고, ③④에서 **요청은 오른쪽, 응답은 왼쪽**으로 가는 방향을 보여 줍니다.
- ①에서 **로딩을 먼저** 보여 주는 이유(응답을 기다리는 동안 사용자가 모르면 고장으로 오해)를 말합니다.
- 아래 상자 네 줄은 모두 동료평가 질문과 연결됩니다.

### V07 보조(네 가지 상태) 해설 포인트
- 맨 위 상자의 **분기 규칙**("무엇이 어떤 상태가 되나")을 먼저 읽어 줍니다.
- 네 카드를 **아이콘과 테두리 모양**으로 구분하는 것을 보여 주고, 색에만 의존하지 않는다는 점을 말합니다.
- 오류 카드의 "이전 성공 카드는 지웁니다"와 빈 결과 카드의 "오류와 다른 문구"를 특히 강조합니다.

### 강의에서 짚을 설명 포인트
- 요청 → 응답 → `response.ok` 확인 → JSON → `filter`/`map` → 화면의 **네 덩어리**가 코드에서 나뉘어 있는지 보여 줍니다.
- `fetch`가 도구이고 GitHub API가 서비스라는 점을 한 번 정리합니다.
- 403에서 요청 한도를 함께 의심해야 하는 이유를 설명합니다.

## 8. Chapter 8 — 웹사이트가 인터넷에 공개되는 과정

**핵심 메시지 한 문장** "**commit → push → Pages → 공개 URL.** 저장·공유(Git·GitHub)와 공개(Pages)는 다른 단계이고, 배포 뒤에는 **공개 URL에서** 다시 점검한다."

### 시연 순서 (제안)
1. 내 컴퓨터의 `index.html`을 연 모습과 **배포 URL**을 나란히 보여 주며 "왜 다른 사람은 앞의 것을 못 볼까?"를 던지고 시작합니다.
2. GitHub 저장소 화면(파일 목록, README)과 **Settings → Pages**의 공개 설정을 보여 줍니다.
3. 배포 URL을 **새 탭(시크릿 창)** 에서 열어 원고의 **9단계 점검**을 빠르게 훑습니다.
4. 대소문자가 다른 경로나 `/`로 시작하는 경로가 깨지는 사례가 있다면 Network 탭의 빨간 줄로 보여 줍니다.
5. V08을 띄워 단계별로 정리합니다.

### 강조 포인트
- **Git ≠ GitHub ≠ GitHub Pages.** 기록 도구 / 저장·공유 서비스 / 공개 기능입니다. 올렸다고 자동 공개가 아닙니다.
- **GitHub Pages는 정적 파일을 그대로 제공**합니다. 서버 코드를 실행하지 않고, 비밀값을 숨기는 곳이 아닙니다.
- **로컬에서 되는데 배포하면 깨지는 네 가지**: 경로, 대소문자, 주소별 localStorage, 반영 지연·캐시. 1·5장의 복선이 여기서 회수됩니다.
- **제출물은 네 가지**: 저장소 URL, 배포 URL, README, 스크린샷(데스크톱·모바일·다크모드).
- **점검은 로컬이 아니라 배포 URL에서.** 동료평가 질문 그대로입니다.

### 자주 나오는 질문
| 질문 | 답 |
| --- | --- |
| push했는데 사이트가 안 보여요 | push는 **GitHub에 올리는 일**일 뿐입니다. Settings → Pages 설정과 반영 시간을 확인합니다. |
| 배포한 사이트가 예전 모습이에요 | 반영 지연이거나 브라우저가 옛 파일을 보여 주는 중일 수 있습니다. 잠시 기다린 뒤 강력 새로고침(`Ctrl+Shift+R`)을 해 봅니다. |
| 로컬에서는 이미지가 보이는데 배포하면 안 보여요 | 경로와 **대소문자**를 먼저 확인합니다. 배포 환경은 구분하는 경우가 많습니다. |
| 다크모드가 처음엔 꺼져 있어요 | 정상입니다. 저장소는 **주소별**이라 배포 주소에는 아직 저장된 값이 없습니다. |
| 비공개 저장소로도 Pages를 쓸 수 있나요? | 요금제 정책에 따라 다릅니다. 무료 계정은 공개 저장소에서 쓰는 경우가 일반적이니 공식 문서를 확인하게 하세요. |
| README에는 무엇을 써야 하나요? | 미션은 README를 필수 문서로 요구하지만 세부 항목은 저장소 자료에 없습니다. 원고의 항목은 **권장**임을 밝히고 안내하세요. |

### 조심할 설명
- Git 명령 사용법을 깊이 다루지 마세요. 이 장은 **commit·push가 각각 어떤 일인지**까지입니다.
- "GitHub에 올리면 사이트가 된다"고 단정하지 마세요.
- Pages 설정 화면의 문구는 **바뀔 수 있다**고 먼저 말해 두세요.

### V08 해설 포인트
- **① ②는 내 컴퓨터, ③ 이후는 GitHub·인터넷**이라는 위치 구분을 먼저 짚습니다.
- 화살표 옆 글은 **그 단계에서 하는 일**(명령·설정)이고, 점선 표식은 **제출물**이 생기는 자리입니다.
- 아래 상자는 "배포하면 달라지는 네 가지"입니다. 각 항목이 어느 장의 복선인지 연결해 줍니다. (경로 → 1장, localStorage → 5장)

### 강의에서 짚을 설명 포인트
- commit은 내 컴퓨터 안의 기록, push는 GitHub로 올리기, Pages는 공개라는 세 단계를 구분해 설명합니다.
- 제출물 네 가지가 V08의 어느 자리에서 만들어지는지 가리킵니다.
- 배포 점검에서 Console의 빨간 오류와 Network의 404를 보는 습관을 안내합니다.

## 9. 전체 통합 — 하나의 웹사이트를 한눈에 보기 (V09)

**핵심 메시지 한 문장** "모든 기술은 **사용자가 보는 화면 하나**를 만들고, 움직이고, 공개하기 위해 일한다. 기능마다 **누가 일하는지**를 물으면 설명할 수 있다."

### 진행 제안
1. 먼저 V09의 **위에서 아래 구조**를 보여 줍니다. 용어를 외우게 하기보다 **"누가 무엇을 맡는가"** 로 읽습니다.
2. 아래 **기능별 카드**에서 채워진 칸과 점선 칸을 비교합니다. 예를 들어 "다크모드 카드에서 HTML이 점선인 이유"처럼 **직접 일하지 않는 쪽**을 짚으면 이해가 깊어집니다.
3. **"방문자가 주소를 열면"** 타임라인을 따라가며 1~8장의 개념이 순서대로 등장하는 것을 보여 줍니다.
4. PC 화면이라면 **전체 관계도**를 띄워 한 번에 관계를 보여 줍니다. 모바일용 세로 그림과 같은 내용입니다.

### 강조 포인트
- **용어 나열이 아니라 협력**입니다. HTML·CSS·JS는 화면을 만들고, 브라우저 기능은 JS를 돕고, GitHub API는 데이터를, GitHub Pages는 공개를 맡습니다.
- **선의 종류**가 의미를 가집니다. 불러옴·연결(점선) / 대응 / 실행 순서(번호 실선) / 요청 ↔ 응답(양쪽 화살표) / 저장(점선 상자). 지금까지의 그림이 같은 규칙입니다.
- **브라우저 기능**(DOM·이벤트, Intersection Observer, localStorage, fetch)은 JavaScript 자체가 아니라 **브라우저가 JavaScript에 제공하는 도구**입니다. 이 구분이 선명하면 7장의 `fetch` vs GitHub API도 쉬워집니다.
- **직접 일하지 않는 쪽까지 구분**하면 설명이 정확해집니다. 예: 반응형은 CSS가, 공개는 GitHub Pages가 일합니다.

### 조심할 설명
- V09는 **교육용 단순화**입니다. 실제로는 브라우저·네트워크 안에서 더 많은 일이 동시에 일어납니다.

## 11. 제작 메모 (강사가 알아 둘 것)

- 가이드의 코드는 모두 **일반화 예제**입니다. 특정 교육생의 실제 프로젝트 코드를 싣지 않았고, 실제 학습자 질문 기록도 저장소에 없어서 각 장 첫머리의 질문은 시나리오 v1.0과 미션 요구에서 구성했습니다. 강의 후 실제 질문이 모이면 질문 문구를 실제 질문으로 교체하면 좋습니다. `[AI 보충]`
- 아직 확정되지 않은 것(**CSS 변수가 필수 구현 조건인지**, 외부 폰트·아이콘, `.style` 직접 사용)은 원고에 *검토 필요*로 표시했습니다. CSS 변수는 B1-1 Notion **동료평가 문항**으로는 확인된 항목(`[공식]`)이므로, 강의에서는 "설명할 수 있어야 하는 항목"으로 다루고 필수 여부만 미션 원문으로 확인하세요.
- 시각 자료 V01~V09는 **모바일(360~390px)에서 글자가 읽히도록** 폭 360 기준 세로형으로 설계했습니다. (V09 PC용 관계도만 가로형입니다.) 강의실의 큰 화면에서는 SVG 파일을 브라우저에서 직접 열어 창에 맞춰 키워 보여 주세요.
- 개발자 도구 단축키·탭 이름은 **Chrome 기준**입니다.
- 이 폴더의 SVG는 서비스 화면에는 아직 연결되지 않았습니다. 강의에서는 마크다운 미리보기나 브라우저에서 SVG 파일을 직접 열어 쓰세요.
- 폼의 **실제 전송 여부**, 테마 **깜빡임 해결 방식**과 미션 제약의 관계, README 세부 항목은 저장소 자료로 확정하지 못했습니다. 강의 전에 미션 원문으로 확인하면 Q&A가 깔끔해집니다. (README의 검토 필요 항목)
