# B6-1 강사용 노트 — 설명 깊이 조절과 정확성 메모

> 학습자에게 의무적으로 가르칠 강의 대본이 아닙니다. 전공과 경험이 서로 다른 성인 초심자의 질문에 따라 설명의 깊이를 바꾸고, **강사가 틀리게 말하기 쉬운 지점**을 미리 확인하기 위한 참고자료입니다.

## 전체 운영 원칙

- 먼저 **그림과 한 가지 사례(문태양)** 를 보여 주고, 용어의 이름은 뒤에서 붙입니다.
- 각 장의 **"한 문장 정리"를 자기 말로 설명할 수 있으면** 기본 학습 목표는 도달한 것으로 봅니다. SQL 문법을 쓰지 못해도 목표 미달이 아닙니다.
- **B6-1의 6개 표, `enrollment`, 17개 쿼리는 하나의 구현 사례**입니다. 다른 교육생의 도메인(예: 도서관, 가계부)과 표 이름이 달라도 같은 개념으로 설명하게 합니다.
- **요구와 구현 선택을 구분**해서 말합니다. "연결 표를 써야 한다", "Python 스크립트가 필요하다"는 요구가 아닙니다.
- 원고의 `[요구 정리]`는 Notion 정리본에 근거합니다. **원본 미션 문서를 대조하기 전에는** "공식이 반드시 이렇게 명시했다"고 단정하지 않습니다.
- 학습자의 **실제 발언이나 시행착오를 대신 만들어 말하지 않습니다.** 학습 노트에 남은 질문만 "노트에 있는 질문"이라고 소개합니다.

## 안전 수칙 (시연·실습 전에 꼭 확인)

| 위험 | 이유 | 안내 |
| --- | --- | --- |
| `01_schema.sql` 실행 | 첫머리에서 `DROP TABLE IF EXISTS`로 **6개 표를 모두 삭제**하고 다시 만듦 | **새로 만든 연습용 DB**에서만. 데이터가 든 DB 옆에서 실행하지 않음 |

| `03_queries.sql` 실행 | Q16·Q17이 DB를 **실제로 바꿈**. 같은 DB에서 다시 실행하면 결과가 달라짐 | 새 DB에서 `01 → 02 → 03` 순서로 시작 |

## 장별 포인트

### 01 데이터베이스 기초
**오해:** 엑셀은 DB가 아니라서 규칙을 못 지킨다. / DB는 대용량 전용이다. **정리:** 엑셀에도 유효성 검사와 조회 함수가 있습니다. 차이는 규칙과 관계를 **저장소의 기본 설계로** 지키느냐입니다. 학습 노트도 "데이터가 많으냐가 아니라 관계를 표현하고 규칙으로 지킬 수 있느냐"로 정리했습니다. **DB, DBMS, SQL, SQLite**를 "파일 / 프로그램 / 언어 / 그 프로그램의 이름"으로 구분하게 하세요.
**시연:** 박서준 이름이 8행 반복되는 시트를 먼저 보여 주고 `teacher` 한 줄로 줄이기.
**macOS 경험:** 노트의 "사실/해석 구분"을 그대로 활용합니다. Apple이 왜 넣었는지는 **공식 설명을 찾지 못했다**는 부분을 지우지 마세요. 다른 OS에서는 `sqlite3` 명령이 없을 수 있습니다. (Windows 11 제작 PC는 없었고 Python의 `sqlite3` 모듈은 있었음)

### 02 데이터 모델링
**오해:** ERD는 설계 후 문서용 그림이다. / 표 개수와 구조에 정답이 있다. **정리:** ERD는 **요약**이고 규칙의 전부는 `01_schema.sql`에 있습니다. (`erd.mmd`에는 복합 `UNIQUE`와 `CHECK`가 없음) 설계는 선택이고 대안이 있습니다.
**질문:** "서랍장 칸을 정하기 전에 무엇을 먼저 적었나요?"
**정확성 메모:** `schema`는 PostgreSQL 등에서 "이름 공간"의 뜻으로도 쓰입니다. SQLite에서 `DATE`로 선언한 열도 값은 **글자(text)** 로 저장됩니다. (`typeof` 확인)

### 03 키와 관계
**오해:** FK는 "다른 표의 번호가 들어 있는 열"일 뿐이다. / 연결 표는 N:M에서 필수 조건이다. **정리:** FK는 **선언**이고, 켜져 있어야 검사됩니다. 연결 표는 N:M을 풀기 위한 **한 가지 표준적 방법**이며 요구가 아닙니다.
**정확성 메모:**
- "PK는 비어 있을 수 없다"는 일반 규칙입니다. SQLite에서 `INTEGER PRIMARY KEY`가 아닌 PK는 `NOT NULL`을 따로 쓰지 않으면 `NULL`을 허용하는 역사적 예외가 있습니다. B6-1은 모든 PK가 `INTEGER PRIMARY KEY`라 해당하지 않습니다.
- `INTEGER PRIMARY KEY`는 SQLite에서 rowid의 별칭이라 번호가 자동으로 붙습니다. `AUTOINCREMENT`가 없으면 마지막 행을 지운 뒤 **번호가 재사용될 수 있습니다.** (실행 확인) 스키마 주석의 "자동 증가 키로 동작"은 이 점에서 느슨한 표현입니다.
- `UNIQUE (student_id, course_id)`는 재수강을 기록하지 못합니다. 설계 한계로 설명하세요.
**시연:** 문태양과 영어 회화가 **왜 일부러 들어 있는지**를 먼저 질문으로 던진 뒤 6장에서 답을 줍니다.

### 04 제약조건과 무결성
**오해:** `FOREIGN KEY`를 적으면 항상 검사된다. / PRAGMA는 DB 파일에 한 번 저장하면 된다. **정리:** SQLite는 **연결마다** 켜야 합니다. (실행 확인: 새 연결 기본값 0, 같은 파일의 다른 연결도 0, 트랜잭션 안에서는 무시) 켜기 전에 들어간 잘못된 행은 남고 `PRAGMA foreign_key_check`로 찾습니다.
**정확성 메모:** 무결성 세 종류(개체·참조·도메인)의 분류는 교재마다 다릅니다. 노트는 `UNIQUE`를 도메인 무결성으로 묶었습니다. 제약조건은 **의미의 정확성**(점수를 85 대신 58로 입력)을 막지 못합니다.
**주의:** FK 검사를 끄는 실험은 학습자가 실수로 원본에 하지 않도록 **복사본 DB**를 강조하세요.

### 05 SQL과 쿼리
**오해:** `sqlite3 student_mgmt.db < 파일`은 SQL이다. / Python이 SQLite를 대신 처리한다. **정리:** 터미널 명령 / SQL 문 / 점 명령 / Python 스크립트 **네 층**을 표로 나눕니다. Python의 `sqlite3` 모듈은 SQLite 라이브러리를 **직접 호출**하며, `sqlite3` 명령을 실행하는 것이 아닙니다. 방법 A만으로도 과제는 완성됩니다.
**정확성 메모:** `ORDER BY` 없이 `LIMIT`을 쓰면 어떤 행이 나올지 정해지지 않습니다. Windows PowerShell은 `<` 리다이렉션을 지원하지 않습니다. (오류 확인) 대안(`.read` 등)은 설치된 `sqlite3`에서 직접 확인한 뒤 안내하세요.

### 06 JOIN
**오해:** JOIN은 FK가 있어야 한다. / LEFT JOIN은 "더 많은 결과를 내는 JOIN"이다. **정리:** JOIN은 `ON` 조건만 있으면 FK 없이도 됩니다. FK는 "번호가 유효하다"를 지키는 규칙입니다. FK가 꺼진 상태에서 생긴 고아 행은 INNER JOIN에서 **조용히 사라집니다.** (26행 vs 수강 행 27개)
**정확성 메모:** LEFT JOIN 뒤 `WHERE`에서 오른쪽 열 조건을 걸면 INNER처럼 동작합니다. B6-1 README는 "INNER 3 / LEFT 2", 쿼리 파일 머리말은 "INNER 4 / LEFT 2"라 **세는 기준을 먼저 합의**하세요.
**시연:** 학생 13~15번을 INNER/LEFT로 바꿔 가며 보여 주기. Q08을 INNER로 바꾸면 0행.

### 07 집계
**오해:** `HAVING`은 `WHERE`의 다른 이름이다. / `COUNT(*)`와 `COUNT(열)`은 같다. **정리:** 시점이 다릅니다. 임건우(93·66, 평균 79.5)가 좋은 예입니다. `WHERE point >= 80`이면 평균이 93.0이 됩니다. LEFT JOIN과 함께 쓰면 `COUNT(*)`는 1, `COUNT(e.id)`는 0입니다.
**정확성 메모:** SQLite는 `GROUP BY`에 없는 열을 선택해도 비교적 허용하지만 다른 DBMS는 오류입니다. 평균의 평균과 건당 평균은 다릅니다. 표시용 `ROUND`와 `HAVING`의 판정값은 다릅니다. (정도윤 80.3)

### 08 서브쿼리와 인덱스
**오해:** 서브쿼리와 인덱스는 둘 다 "빠르게 하는 기능"이다. / 인덱스를 만들면 항상 빠르다. **정리:** 서브쿼리는 **질문의 논리**(값을 먼저 구함), 인덱스는 **찾는 방법**(결과는 그대로). 인덱스는 저장 공간과 쓰기 비용이 듭니다.
**가장 중요한 정확성 메모:** B6-1의 `UNIQUE (student_id, course_id)`가 **자동 색인** `sqlite_autoindex_enrollment_1`을 만들고, 그 색인은 `student_id`가 첫 열이라 Q15의 `CREATE INDEX` **이전에도** `SEARCH ... USING INDEX`입니다. 즉 이 스키마에서 Q15의 색인은 **중복에 가깝습니다.**
- B6-1을 비난하지 않습니다. 요구(INDEX 1개 + 적용 이유)는 충족했고, **이것이 "인덱스가 항상 이득은 아니다"의 실제 사례**입니다.
- 색인이 정말 필요한 후보는 아직 `SCAN`인 `enrollment.course_id`, `score.enrollment_id`입니다. 다만 표가 26·30행이라 속도 차이는 측정할 수 없습니다.
- `EXPLAIN QUERY PLAN`의 `notused` 열은 버전별 내부 값이라 읽지 않고 `detail`만 읽습니다.
- `NOT IN`과 `NULL`: 서브쿼리 결과에 `NULL`이 있으면 `NOT IN`이 아무 행도 고르지 못합니다. Q17은 `enrollment.student_id`가 `NOT NULL`이라 안전합니다.

### 09 수정과 삭제
**오해:** 외래키가 있으니 삭제는 안전하다. / `DELETE`는 언제든 되돌릴 수 있다. **정리:** FK는 **자식이 있는 부모의 삭제**만 막습니다. `score`는 마지막 자식이라 `WHERE` 없는 `DELETE`를 막지 못합니다. (30행 전부 삭제 확인) 확정 전에는 트랜잭션을 취소할 수 있지만, B6-1 스크립트는 `commit()`으로 결과를 확정합니다. 변경 전후 확인을 명시적 트랜잭션으로 묶어 취소하는 실습은 하지 않았습니다.
**강조:** 영향 행 수 확인, 전·후 `SELECT`, **연습용 복사본**. `01_schema.sql`과 `run_queries.py`의 삭제 동작을 반드시 언급합니다.
**정확성 메모:** 03 파일은 한 번 실행하면 DB 상태가 바뀝니다. 같은 DB에서 두 번 실행하면 Q17은 영향 행 0, Q08은 0행입니다.

### 10 전체 통합
**오해:** 모든 개념이 SQL을 한 번 실행할 때 순서대로 한 번씩 일어난다. / 모든 교육생이 Python으로 SQL을 실행해야 한다. **정리:** 설계·규칙·조회·변경·실행 방법은 **서로 다른 층**입니다. V10은 교육장 Mac의 `sqlite3` 명령을 활용하고 Python으로 반복 실행·결과 정리를 추가한 B6-1 사례입니다. 공통 학습 목표는 SQL·DBMS·표·결과의 연결이며 실행 도구는 교육생마다 달라도 됩니다. V10의 선 종류(전달 / 읽고 쓰기 / 1→N)를 해설하세요.
**JPA/ORM:** 이번 미션에서 **쓰지 않았음**을 분명히 하고 후속 학습 연결로만 말합니다. JPA는 Java 규격이고, 후속 미션(B6-2·B6-3)의 ORM은 정리본에 따르면 SQLAlchemy(Python)입니다. 정리본은 B6-1을 그 미션의 필수 선행으로 직접 지정하지 않는다고 적고 있습니다.
**주의:** 10장의 "스스로 점검해 보기"는 **공식 동료평가 문항이 아닙니다.** B6-1의 동료평가 문항은 확인하지 못했으므로 공식 문항처럼 소개하지 마세요.

## 자료 수정 전에 확인할 사항

- 원본 미션 문서에서 요구 수치와 제출물 형식을 **독립적으로 확인했는지**
- B6-1 저장소가 `8b99440` 이후 바뀌었는지(쿼리 개수·문서 문구·파일 구조)
- 다른 교육생의 DBMS(MySQL·PostgreSQL·H2)에서도 공통 설명이 통하는지. 특히 `PRAGMA`, `EXPLAIN QUERY PLAN`, `GROUP BY`의 너그러움은 SQLite 특성입니다
- macOS `sqlite3` CLI에서 `[실행 확인]` 항목(실행 계획 출력 형식 포함)이 같은지
- SVG의 선이 실행 순서인지, 가리킴(FK)인지, 읽고 쓰기인지를 해설할 수 있는지
