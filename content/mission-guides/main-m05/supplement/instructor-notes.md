# B3-1 보강 자료 — 강사 노트

> 대상 원고: [기업 홈페이지 구성도로 읽는 네트워크](README.md). 상태: 콘텐츠 초안(독립 검토 전).

## 수업 목표

교육생이 **기업 홈페이지 예시**의 구성도를 보고 (1) 구역·요소의 위치와 역할, (2) 허용되는 연결, (3) 요청·응답의 실제 이동 순서, (4) 직원의 게시·저장 흐름을 말로 설명하고, (5) B3-1 AWS 구성과 비교해 **무엇이 대응하고 무엇이 없는지** 구분하게 합니다. 용어 암기가 아니라 “이 상자는 어디에 있고, 무슨 일을 하고, 누가 먼저 연결을 시작할 수 있고, 데이터는 어느 방향으로 가는가”를 그림에서 읽는 연습입니다.

## 권장 진행 순서

| 단계 | 하는 일 | 쓰는 그림 |
| --- | --- | --- |
| 0 | **그림을 먼저** 1~2분 보게 합니다(설명을 읽기 전). 원고의 세 질문(방문자가 있는 면, A·B·C의 출발점, 모두 거치는 장비)에 말로 답하게 한 뒤, 아래의 읽는 법으로 확인합니다. 색 면(구역)·회색 선(연결)·실선 화살표와 번호(요청의 이동)의 약속을 말하게 하고, 용어 설명은 하지 않고 “자세한 것은 다음 그림에서 본다”고 말합니다. | 그림 0 |
| 1 | 질문으로 시작: “회사 홈페이지는 누구나 보는데, 직원용 시스템은 왜 밖에서 안 열릴까?” 답을 먼저 말로 받습니다. | 없음 |
| 2 | 그림 1에서 **위치→역할→허용/차단** 순서로 읽습니다. 이동 방향은 아직 다루지 않습니다. | 그림 1 |
| 3 | 방문자 요청 한 번을 번호대로 따라갑니다. 방화벽·NAT·경로표를 **세 가지 질문**으로 구분합니다. | 그림 2 |
| 4 | 직원의 게시 흐름을 따라갑니다. 같은 서브넷(스위치)과 다른 서브넷(게이트웨이→경로표→방화벽)을 대비합니다. | 그림 3 |
| 5 | B3-1과 비교합니다. **빈 칸(없는 것)을 먼저** 찾게 한 뒤 대응되는 칸을 봅니다. “게시·저장” 줄은 없는 것(게시 화면·DB·별도 파일 저장소)과 있는 것(서버 디스크의 `dist`)을 나누어 말하게 합니다. | 그림 4, 4 보충 |
| 6 | 자기 배포의 대응표를 채웁니다(다른 호스팅 방식 포함). | 원고 장면 4의 확인 활동 |

그림 0은 전체 연결을 보는 **지도**이고, 용어와 순서의 설명은 그림 1~4를 장면별로 나눕니다. 용어를 한 그림에 모아 설명하려 하지 않은 것이 설계 의도입니다. 그림 0 앞에서 방화벽·NAT·경로표의 차이를 가르치려 하지 않습니다.

## 혼동하기 쉬운 것과 확인 질문

| 혼동 | 구분하는 질문 | 바로잡는 말 |
| --- | --- | --- |
| 방화벽 = NAT = 라우터 | “통과시킬까? / 어느 주소로 바꿀까? / 다음 길은?” | 세 장치는 서로 다른 질문에 답합니다. 한 장비에 합쳐져 있어도 일은 다릅니다. |
| NAT가 있으면 안전하다 | “주소를 바꾸는 것과 허용을 판단하는 것은 같은가?” | NAT는 주소 대응입니다. 허용 판단은 방화벽 규칙입니다. |
| DMZ = 내부망의 일부 | “DMZ는 무엇과 무엇 사이에 있나?” | 공개 서비스와 내부망 사이를 **분리**하는 구역입니다. |
| 이 그림이 모든 회사의 표준이다 | “방화벽·라우터는 항상 한 장비인가?” | 배치와 장비 수는 기업마다 다릅니다. NIST 용어집도 DMZ를 여러 방식으로 정의합니다. |
| 저장하면 인터넷에 공개된다 | “저장 구역에 인터넷이 직접 닿나?” | 공개 웹 서버가 공개 상태 자료를 조회해 응답해야 보입니다. |
| 응답에도 별도 허용 규칙이 항상 필요하다 | “연결 상태를 기억하는 장치는 응답을 어떻게 처리하나?” | 허용된 연결의 응답은 그 연결에 속한 응답으로 보고 요청의 반대 방향으로 통과시킵니다. 응답이 지나는 실제 경로와 장비 순서는 기업망과 장비 설정에 따라 다를 수 있습니다. |
| `0.0.0.0/0 → IGW`는 장비다 | “이 줄은 무엇 안에 적힌 것인가?” | Route Table의 규칙 한 줄입니다. 요청이 통과하는 지점이 아닙니다. |
| Security Group = 경계 방화벽 | “어디에 적용되는가?” | EC2의 네트워크 인터페이스에 적용됩니다. |
| Public Subnet = DMZ | “각각을 누가 어떻게 정의하는가?” | Public Subnet은 AWS의 경로 정의, DMZ는 분리 설계 개념입니다. 동일시하지 않습니다. |
| 방문자도 기업망 안에 있다 | “방문자 상자는 어느 면 안에 있나요?” | 방문자는 “인터넷(기업망 밖)” 면에 있습니다. 라우터와 방화벽·NAT가 안과 밖의 경계입니다. 웹 서버(DMZ)와 직원 PC(내부 업무망)는 기업망 안입니다. |
| 그림 0에 응답이 없으니 응답은 가지 않는다 | “응답은 어느 그림에서 봤나요? 그림 0의 화살표는 요청인가요, 응답인가요?” | 그림 0의 A·B·C는 모두 연결을 먼저 시작하는 **요청**이라 실선입니다. 허용된 연결의 응답은 반대 방향으로 가며, 점선(응답)은 그림 2·3에서 봅니다. 선 모양의 뜻(실선=요청, 점선=응답)은 모든 그림에서 같습니다. |
| 그림 0의 모든 상자가 B3-1에 있다 | “B3-1 기록에서 이 상자를 가리켜 보세요.” | 방문자 접속(A)에 해당하는 일부뿐입니다. B(직원 게시)·C(자료 조회)와 저장 구역·내부 업무망은 B3-1 기록에 없습니다. |
| B3-1에 직원망·게시 시스템·DB가 있다 | “B3-1 기록에서 이 상자를 가리켜 보세요.” | 직원용 게시 화면·DB·별도 파일 저장소는 고정된 기록에 없습니다. 다만 빌드된 `dist` 정적 파일은 EC2 서버 디스크에 저장되어 Nginx가 제공합니다. |

## 말할 때 조심할 것

- “회사는 보통 이렇게 한다”는 말을 쓰지 않습니다. “설명을 위한 한 가지 예시”라고 말합니다.
- 그림 4의 “B3-1 AWS” 칸을 **교육생이 따라 만들어야 할 정답**으로 제시하지 않습니다. B3-1의 IP·리소스 값은 당시 기록이며 복사하는 실습이 아닙니다.
- 정적 호스팅이나 다른 클라우드를 쓴 교육생에게 VPC·EC2를 강요하지 않습니다. “내 배포에서 이 역할을 누가 맡았나”만 묻습니다.
- AWS가 모든 역할을 물리 장비와 1:1로 대신한다고 말하지 않습니다. 비슷한 역할이 **다른 위치에 다른 방식으로** 놓일 수 있습니다.
- 인바운드 요청이 Route Table을 “지나간다”고 말하지 않습니다. 경로표는 규칙이며, `0.0.0.0/0 → IGW`는 Subnet 밖으로 나가는 패킷의 다음 대상을 정하는 줄입니다.

## 확인하는 방법

교육생이 직접 그림 한 장을 **빈 칸 채우기**로 설명하게 합니다. 정답 용어보다 근거를 듣습니다.

0. 그림 0에서 방문자 상자가 어느 면 안에 있는지 가리키게 하고(기업망 밖), B와 C가 저장 구역으로 들어가는 길을 가리키며 저장 구역에 **먼저 연결을 시작하는 쪽**이 각각 누구인지(B는 관리 화면 서버, C는 공개 웹 서버) 말하게 합니다.
1. 그림 2의 ②③④를 가리키고 각각이 답하는 질문을 말해 보게 합니다.
2. 그림 3에서 “저장됨”이 보이는데 방문자가 못 본다면 확인할 것 세 가지를 순서대로 말하게 합니다.
3. 그림 4에서 B3-1에 없는 상자를 모두 찾고, 그것을 없는 이유(정적 파일 배포이므로)와 연결해 설명하게 합니다.
4. 그림 4 보충에서 `0.0.0.0/0 → IGW`와 Security Group이 각각 **어디에 속하는지** 말하게 합니다.

평가는 교육생의 실제 구현과 자기 설명을 기준으로 합니다. 용어를 틀리게 말해도 위치·역할·방향의 구분을 맞게 설명하면 부분 통과로 봅니다.

## 접근성·화면 안내

- 각 그림은 대체 설명을 본문에 글로 제공합니다. 그림이 안 보이거나 읽기 어려운 교육생은 대체 설명과 요소별 표만으로 같은 내용을 읽을 수 있습니다.
- 허용/차단은 색만이 아니라 **체크·엑스 모양, 점선 테두리, 글자**로 구분합니다. 요청(실선)과 응답(점선)도 선 모양으로 구분합니다(그림 2·3). 선 모양의 뜻은 모든 그림에서 같습니다(실선=요청, 점선=응답). 그림 0은 세 경로가 모두 요청이라 실선만 쓰고 응답은 그리지 않으며, 경로는 선 색, 구간마다 반복되는 문자·번호(A1·B1·C1…), 번호 모양(동그라미·네모·육각형)으로 구분합니다.
- 그림 1~4는 가로 360 단위의 세로형입니다. 그림 0은 가로 1144 단위의 가로형이라 PC에서 크게 보여 주고, 휴대전화에서는 줄이지 않고 확대해서 읽게 합니다. 크게 열기 링크로 파일을 따로 열어 브라우저 확대를 쓸 수 있습니다.

## 근거와 한계

- 일반 개념은 NIST·CISA 자료로, AWS 설명은 AWS 공식 VPC 문서로, B3-1 사례는 `Codyssey_B3-1` 고정 커밋 `c68929943f1904a5c7c8033d2d49a30ace56e3d1`로 대조했습니다. 세부는 [QA 기록](qa.md)에 있습니다.
- 현재 AWS 계정·서버 상태와 B3-1 원본 미션의 전체 요구사항은 확인하지 못했습니다.

## 패킷의 여행을 이용한 대면 강의

[기업망 보강 자료의 체험](README.md#packet-journey)을 그림 1과 그림 2 사이에서 엽니다. 자동 재생보다 **한 단계 진행**으로 멈추고 설명하는 것을 기본으로 합니다. 이전 단계·처음부터 재시작으로 같은 장면을 다시 보여 줄 수 있습니다.

1. 그림 0·1과 전체 연결망을 보여 주며 “선이 연결되었다는 건 무슨 뜻일까?”를 묻습니다. 회색 선과 이번에 전달된 경로, 움직이는 패킷을 구별합니다.
2. DNS 조회 1~5단계를 진행합니다. DNS는 도메인 주소를 확인하며 웹 요청을 대신 전달하지 않는다고 설명합니다.
3. R1(3단계)·R2(4단계)에서 목적지 IP → 경로표의 일치 줄 → 다음 방향을 함께 짚습니다. 전체 인터넷 길을 한 번에 정하지 않는다는 점과 간소화한 표임을 알립니다.
4. 공유기 NAT(2단계, 웹 요청은 12단계)에서 변환 전·후 주소를 비교합니다. 이전 단계로 돌아가 PC가 만든 값도 확인합니다.
5. DNS 응답이 PC에 도착한 10단계에서 멈추고, 11단계의 별도 HTTP 요청과 비교합니다.
6. 회사 방화벽/NAT(17단계)의 허용 규칙과 목적지 주소 변환을 따로 설명합니다. 길이 있다는 사실과 허용된다는 사실은 다릅니다.
7. 웹 응답 19~26단계를 진행하고 R4(22단계)가 R3를 고르는 경로표를 보여 줍니다. 인터넷 경로는 달라도 같은 NAT·방화벽의 매핑·연결 상태를 유지하는 조건을 짚습니다.
8. 그림 4와 가이드 3장으로 돌아가 Route Table(다음 길 규칙), IGW(공인·사설 IPv4 대응), ENI의 SG(허용), Nginx(HTTP 응답)에 기능적 역할을 연결합니다. Route Table을 통과 장비처럼 말하지 않습니다.

학습자가 자기 말로 답하도록 묻습니다.

- 라우터는 패킷을 다음 어디로 보낼지 어떻게 알까요?
- 경로표는 장비인가요, 정보인가요?
- NAT를 통과한 뒤 IP:포트는 무엇이 달라졌나요?
- 패킷을 보내는 것과 방화벽이 허용하는 것은 같은 일인가요?
- DNS 응답을 받았다고 웹페이지가 이미 도착한 것일까요?

PC에서는 전체도를 함께 보고, 모바일에서는 필요한 경우 그림 확대와 좌우 이동을 안내합니다. 키보드로 버튼과 그림에 초점을 옮길 수 있습니다. 동작 줄이기 설정에서는 위치 전환을 즉시 표시하므로 움직임 대신 단계·주소·선택 줄을 짚습니다. 관계·용어 링크는 새 탭으로 열어 현재 단계를 남기고 돌아올 수 있습니다.

이 자료는 실제 패킷 캡처·현재 AWS 설정 확인이 아닙니다. DNS 캐시 응답, UDP DNS·TCP HTTP, 일부 연결 과정 생략 조건을 설명하고, 그림 0의 B·C 경로는 기존 자료로 이어갑니다. 이 질문에 답해 본 결과를 바탕으로 실습에 진입하며 자료를 봤다는 사실만으로 이해 완료라고 판정하지 않습니다.
