#### C2PA metadata 처리 (범위와 이유)

두 가이드 복사본 SVG에는 `<metadata><c2pa:manifest>...</c2pa:manifest></metadata>` 형태의 C2PA 콘텐츠 자격 증명(서명 포함 manifest)이 들어 있었다. 이 manifest는 특정 바이트 내용에 대한 서명이므로, 위 본문 수정으로 파일 바이트가 바뀌면 그 서명은 더 이상 수정된 내용과 일치하지 않는다. 수정된 파일에 무효가 된 서명을 그대로 남기면 "이 내용이 서명된 원본과 같다"는 거짓 신호를 주므로, **가이드 복사본 2개에서만** `<metadata>`...`</metadata>` 엘리먼트 전체를 제거했다. `src/assets/b3-1/`의 원본 SVG는 수정하지 않았으므로 그쪽의 C2PA manifest는 변경 없이 그대로 보존되어 있다. 다만 이 manifest의 서명을 실제로 검증하지는 않았으므로, 암호학적으로 유효한지는 **미검증**이다.

제거 방법과 확인: 매우 긴 `<metadata>` 한 줄을 콘솔에 출력하거나 모델이 읽지 않도록, `grep -b`로 `<metadata`/`</metadata>` 태그의 바이트 오프셋만 먼저 확인한 뒤 `head -c`/`tail -c`로 그 바이트 구간만 잘라 제거했다(파일 내용을 출력하지 않음). 자르기 전후로 경계 바이트 몇 글자만 확인해 `<svg ...>` 여는 태그가 `...xmlns:c2pa="http://c2pa.org/manifest">`로 정상 종료되고, 그 직후 `<title>` 엘리먼트가 바로 이어지는 것을 확인했다. 제거 후 두 파일 모두 `<svg>/<title>/<desc>/<defs>/<style>` open/close 태그 개수가 1:1로 일치함을 `grep`으로 재확인했다(**정적 태그 검사**일 뿐 XML 파싱이 아니다). 이 환경에서는 스크립트 인터프리터(node/python) 실행과 일부 셸 명령이 승인 절차에 막혀 정식 XML 파서(`xml.dom.minidom`, `xmllint` 등)를 직접 돌리지는 못했다 — 이 Claude 자체 QA에서 정식 파서 검증은 **미실시**로 남긴다. (이후 GPT가 Python ElementTree로 수정 SVG 2개의 전체 XML 파싱 PASS와 `<metadata>` 0개를 독립 확인했다. 이는 GPT의 검증이며 Claude가 수행한 것으로 소급하지 않는다.)

화면 텍스트 배치는 실제 렌더링으로 확인하지 못했다(이 환경에 브라우저 도구가 없음). 대신 교체한 문구가 기존 문구와 비슷하거나 더 짧은 길이인지 확인했다: `서버의 호스트 공개키`는 `서버의 호스트 공개키와 지문`보다 짧고, `지문 계산 후 비교`는 `known_hosts와 비교`와 비슷한 길이이며 같은 상자(`width="190"`) 안의 다른 줄(`처음: 공개키를 확인 후 저장`)보다 짧다. `0.0.0.0/0 · 전체 IPv4 공간`은 `0.0.0.0/0 · 인터넷 전체`보다 길지만, 같은 그림의 더 긴 줄(`203.0.113.7/32 · 내 공인 IP 하나(예시)`)이 같은 폭에서 이미 문제없이 쓰이고 있어 폭을 넘기지 않을 것으로 판단했다. 이 판단은 실제 렌더링 확인의 대체가 아니며, 공개 연결 이후 시각 QA에서 재확인이 필요하다.

## 구조 판단: 7장이 핵심 목표를 전달하는가

사용자가 밝힌 핵심 목표는 "일반 네트워크 구성의 역할·용어와 AWS 서비스·자원의 대응"이다. 독립적으로 판단한 결과, 현재 7장 구조는 이 목표에 적합하다고 본다.

- 2장이 역할 대응표를 **전체 매핑의 중심**으로 명시하고, 이미 승인·공개된 `network-aws-role-comparison`(`data/curated/concept-connections-v1.json`, status `PUBLISHED`)과 같은 축을 재사용한다. 새 대응 원칙을 만들지 않고 검토된 자료를 그대로 따른 점이 적절하다.
- 1장(배포 개념)과 7장(검증·운영)은 2장의 매핑을 쓰기 전/후의 맥락으로 기능하며 중복되지 않는다.
- 3~6장은 2장 표의 각 행(경로/접근 통제/인증/응답 서비스)을 한 장씩 깊게 다루는 구조로, 단순 반복이 아니라 "이름만으로 결론 내리지 말라"는 공통 교육 포인트(Public Subnet 이름, SG와 SSH 키 구분, `curl` 200과 브라우저 성공 구분)를 각 장의 고유 질문으로 분리해 전달한다.
- 3장과 2장이 같은 SVG·같은 IGW/Route Table 사실을 다시 언급하지만, 3장의 질문("Public Subnet이면 바로 접속될까?")은 2장과 다른 오해를 겨냥하므로 유지할 가치가 있다고 판단했다. 삭제·병합을 제안하지 않는다.

구조를 바꾸지 않기로 한 판단이며, 이는 수정이 필요하다는 뜻은 아니다.
