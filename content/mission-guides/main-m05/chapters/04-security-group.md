# 4. 웹 방문과 서버 관리는 어떻게 구분할까?

> 같은 EC2에 들어오더라도, 웹페이지 보기와 서버에 로그인하기는 왜 다른 규칙을 쓸까요?

## 목적지 포트와 출발지

`[개념]` 보안 그룹(Security Group)은 EC2 네트워크 인터페이스에 적용하는 **허용 규칙**입니다. 인바운드 규칙은 어떤 출발지가 어떤 프로토콜·포트로 들어올 수 있는지를 정합니다. 규칙에 없는 접속은 허용되지 않습니다. 보안 그룹은 **상태 저장형**이므로 허용된 요청에 대한 응답 트래픽은 반대 방향 규칙을 따로 열지 않아도 돌아갑니다. [AWS 보안 그룹 설명](https://docs.aws.amazon.com/us_en/AWSEC2/latest/UserGuide/ec2-security-groups.html).

| 목적 | 흔히 쓰는 프로토콜·포트 | B3-1 사례의 허용 출발지 |
| --- | --- | --- |
| 공개 웹페이지 | HTTP, TCP 80 | `0.0.0.0/0` (모든 IPv4) |
| 서버 관리 | SSH, TCP 22 | 작업자의 당시 공인 IPv4 한 개(`/32`) |

`[B3-1 사례]` 이 규칙은 [2026-10-14 배포 기록](https://github.com/hyun02063185-AX-beginner/Codyssey_B3-1/blob/c68929943f1904a5c7c8033d2d49a30ace56e3d1/docs/deployment-log-2026-10-14.md)에 남아 있습니다. 당시의 작업자 IP는 현재의 허용 주소라는 뜻이 아니므로 여기서는 적지 않습니다.

`0.0.0.0/0`은 “언제나 위험해서 금지”도, “항상 괜찮다”도 아닙니다. 누구나 보아야 하는 공개 HTTP 서비스에서는 목적에 맞을 수 있습니다. 관리용 SSH에는 훨씬 좁은 출발지를 쓰는 것이 적절합니다. 또한 보안 그룹이 80번을 허용해도 Nginx가 실행되지 않거나 해당 포트에서 듣지 않으면 웹페이지는 열리지 않습니다.

![AWS 네트워크 역할과 HTTP·SSH 경로 비교](../assets/aws-network-roles.svg)

[그림 크게 열기](../assets/aws-network-roles.svg)

그림의 HTTP와 SSH 선은 **서로 다른 접속 목적**을 나타냅니다. HTTP를 열었다고 SSH 로그인이 허용되는 것이 아니고, SSH용 키를 가졌다고 보안 그룹의 출발지 제한을 통과하는 것도 아닙니다.

## 내 프로젝트에 연결하기

`[확인 활동]` 내 서비스에서 방문자가 쓰는 포트와 관리자가 쓰는 포트, 각 규칙의 출발지, 그 포트에 응답하는 프로그램을 나란히 적으세요. 관리형 플랫폼을 썼다면 포트와 접근 제어를 플랫폼이 대신 관리하는지 확인하세요.

**한 문장 정리:** 보안 그룹은 “어디에서 어느 포트로 들어올 수 있는가”를 정하고, 웹 방문과 서버 관리에는 서로 다른 규칙을 적용합니다.
